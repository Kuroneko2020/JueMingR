# 最小工程治理试运行计划

## 一、文档性质

本文件是最小工程治理在活动期内使用的试运行计划，对应 [Phase 0-K Issue](https://github.com/Kuroneko2020/JueMingR/issues/9)。它不是永久工程规范，不是项目架构，也不是 CI、性能、测试或版本规范；它只提供三个真实任务共同试用的最小方法，不把 Phase 0-I 的完整研究报告直接升级为规则。

试运行结束后，应把真实任务证明有效的结论提炼到合适的正式载体，并按[文档治理规则](../规范/文档治理规则.md)删除本计划或使它退出当前路由。

当前阶段、任务、阻塞和下一步等动态状态仍只记录在 GitHub Issue，不写入本文件。

## 二、试运行目标

本轮通过真实任务验证：

- 风险分级能否减少 AI 的范围膨胀和技术债；
- 规则是否会增加项目所有者的负担；
- 一屏任务契约是否足以约束一次任务；
- 硬停止与软警戒是否合理；
- 独立审查是否真正发现问题；
- 治理成本是否低于它所防止的问题。

试运行只验证这些候选方法，不预先认定它们都应长期保留。

## 三、角色分工

### 项目所有者

项目所有者只负责：

- 判断产品应给用户什么结果；
- 判断用户体验和与 Legacy 的差异是否可以接受；
- 决定高风险的成本与后果是否值得；
- 作出最终批准。

项目所有者不需要决定内部代码、测试、缓存、分析器、CI、分支或审查流程如何实现。

### 执行 Agent

执行 Agent 负责：

- 理解任务目标、非目标和现有事实；
- 完成必要调查、技术方案和获准实现；
- 在明确授权内操作 Git 和 GitHub；
- 提供与结论相匹配的证据；
- 一旦越界、冲突或缺少可靠依据就停止。

### 独立审查 Agent

独立审查 Agent 负责：

- 从新对话按项目入口冷启动；
- 对照任务契约检查实际改动；
- 检查范围、重复实现、状态所有权、证据边界和旧路径残留；
- 报告技术问题，但不代替项目所有者作产品验收。

## 四、风险分级

| 等级 | 普通语言定义 | 默认处理 |
| --- | --- | --- |
| 简单 | 容易撤销，不改变用户功能，不触碰外部数据，改动范围小而明确 | 使用最短任务契约和快速验证 |
| 标准 | 修改普通用户行为或多个相关文件，但影响可控且能够回滚 | 使用完整核心契约，并安排独立审查 |
| 高风险 | 涉及加载、安装、用户数据、多人、安全、许可证、依赖、核心运行时、性能敏感路径或难以回滚 | 单独授权，先说明回滚，安排独立审查和与风险相应的验证 |

执行 Agent 可以根据新证据把任务升级为更高风险，但不得为了减少流程自行降级。项目所有者不需要理解风险术语；Agent 必须用普通语言说明最坏后果和需要作出的产品判断。

## 五、一屏任务契约

每个任务开始前，必须能在一屏内说明以下核心内容：

```text
任务：
用户或项目会得到什么结果：
本轮不做什么：
允许修改什么：
永久只读或禁止修改什么：
风险和最坏后果：
怎样证明完成：
什么情况必须停止：
本轮允许哪些 Git/GitHub 动作：
最终需要项目所有者判断什么：
```

简单任务可以省略不适用的风险扩展，但不能省略目标、范围、完成依据、停止条件和授权边界。若无法在一屏内说清，应拆分任务或重新澄清。

一个 Issue 对应一个能够独立验收、延期、取消和回滚的结果。同一结果内部的起草、复核、修订和收尾留在同一个 Issue，不为每个内部步骤机械新建 Issue。

## 六、默认授权边界

- 调查和纯文档任务只有在具体任务 Issue 明确授权时，才可直接提交到 `main`、推送 `origin/main` 或关闭任务 Issue。
- 当前仍未授权任何生产代码。
- 未来生产代码获准后，默认使用短生命周期任务分支和 PR。
- 具体任务 Issue 可以授权 Agent 创建任务分支、提交、推送任务分支、创建或更新 PR，以及更新 Issue 和 PR 评论。
- 合并 PR、关闭 Issue、直接推送 `main`、创建 Release 或 Tag，仍需要项目所有者明确批准。
- Agent 不得 force push、改写共享历史或自行删除远程分支。
- 自动验证通过不能自动扩大上述权限。

只有出现新的用户结果、独立风险验证、架构决定或范围外缺陷时，才另立 Issue。

## 七、硬停止条件

出现以下任一情况，必须停止：

- 需要越过允许写入路径白名单；
- 需要新增第三方依赖；
- 需要改变已批准架构；
- 任务增加第二个独立用户结果；
- 风险升级为高风险但尚未取得相应授权；
- 无法建立可靠的验收依据；
- 工作区出现无法解释的改动；
- 需要修改 Legacy 或游戏安装目录；
- 连续两轮修复仍没有明确根因，准备进入第三轮试错；
- 仓库、路线图、总跟踪 Issue 和任务 Issue 互相冲突。

停止后不得继续写入。执行 Agent 应更新任务 Issue，用普通语言说明停止原因和缺少的决定，并等待新的授权。

## 八、软警戒而非机械配额

前 20 至 30 个真实任务中，文件数量、diff 大小、持续时间、修订轮数和检查耗时只用于观察，不是成功目标或立即失败条件。

出现明显扩张时，Agent 应停下来判断：是否出现第二个独立目标、是否需要拆分任务、是否触及共享基础设施、是否需要升级风险、是否需要重新取得授权。

本计划不写死具体文件数、行数或分钟阈值。在积累真实任务数据后，再决定是否形成稳定范围。

不得为了看起来符合数字而拆碎文件、少写测试、制造无意义提交、隐藏生成文件或制造第二个假消费者。

## 九、验证和证据分开

以下状态彼此独立：

- 代码已经写完；
- 自动检查已经通过；
- 已在游戏实机验证；
- 已完成多人验证；
- 已完成性能测量；
- 项目所有者已验收；
- 已正式发布。

一个状态完成不能冒充另一个状态。未做或未授权的验证必须明确写为未做或未知。

具体证据分轴继续遵循[Legacy 平替与行为契约规则](../规范/Legacy平替与行为契约规则.md)。

## 十、独立审查的使用边界

- 标准与高风险生产任务在最终合并前默认需要独立审查。
- 简单调查和纯文档任务不默认增加一次完整的第二审查。
- 审查 Agent 必须在新对话中冷启动，不沿用实现者的判断。
- 审查只对照任务契约和实际 diff，不无目的重审全项目。
- AI 审查不能替代项目所有者的产品验收。
- 审查发现问题时，默认修正具体问题，不通过增加更多永久规则来收口。

## 十一、三个真实试运行任务

以下任务按顺序试运行，每项仍需独立 Issue 和明确授权；本计划不创建这些任务 Issue。

### 试运行任务 1：性能治理基线

验证热路径识别、功能关闭成本、何时需要测量，以及如何避免性能检查拖慢所有普通任务。

### 试运行任务 2：测试与审计基线

验证自动测试、实机、多人和项目所有者验收能否分开记录，验收依据是否独立，快检查和慢检查能否分层，以及如何防止十五小时审计。

### 试运行任务 3：版本、配置与发布基线

验证 Git、Issue、ADR、配置 schema、兼容记录和 Release 的职责，升级与回滚边界，以及如何避免用版本号推进冒充产品进展。

## 十二、最小试运行记录

每个试运行任务只在对应 Issue 的收尾评论记录：

- 实际持续时间；
- 发生了几轮修订；
- 向项目所有者提出了几个问题；
- 是否发生范围扩大；
- 独立审查是否发现真实问题；
- 哪些规则有用；
- 哪些规则无用或昂贵；
- 建议保留、修改还是删除哪些规则。

不得为每次试运行新建更新记录 Markdown、Excel 台账或数据库。

## 十三、试运行结束门

三个试运行任务完成后，应建立独立复盘 Issue。复盘结果只能是：

- 正式化最小工程治理；
- 修改后继续试运行；
- 放弃部分或全部候选规则。

若决定正式化，只提炼被真实任务证明有效的最小规则，另行决定是否需要 ADR，并删除本计划或使它退出当前路由。不得复制 Phase 0-I 完整报告，也不得保留没有实际价值的检查。

## 十四、防止治理自身膨胀

- 一次低风险事故不自动产生永久规则。
- 一个故障尽量只有一个最接近事实的主门。
- 每条规则都必须能用普通语言说明它防止什么问题。
- 没有真实捕获、成本过高或与其他门重复的规则应删除。
- 不使用自然语言精确字符串证明工程治理合规。
- 不建立治理规则的逐次更新历史。
- 项目所有者花费的时间和理解负担本身就是治理成本。
