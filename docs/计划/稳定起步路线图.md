# JueMingR 稳定起步路线图

## 一、文档性质

本文件是 JueMingR 在“稳定起步”完成前的高层路线图，记录候选阶段要解决的问题、阶段间的大致依赖、退出条件和稳定起步的定义。

本文件不是当前任务状态账本。当前进展以 [“JueMingR：稳定起步总跟踪”Issue](https://github.com/Kuroneko2020/JueMingR/issues/7) 为准，具体任务状态和授权以总跟踪 Issue 指向的当前任务 Issue 为准。路线图可以通过受控决策调整；一次任务完成不在正文追加更新流水。

本路线图与稳定起步总跟踪 Issue 对应，只在“稳定起步”活动期内进入当前路由。达到稳定起步后，应先提炼仍然有效的长期结论，再按 [文档治理规则](../规范/文档治理规则.md) 使本路线图退出当前路由；具体删除或替代方式由届时的收口任务决定。

## 二、为什么需要该路线图

Codex 和网页 ChatGPT 对话都有有限上下文，聊天可能被压缩、截断或丢失。项目连续性不能依赖某次对话仍然存在，也不能要求项目所有者在多个 Agent 之间人工转述工程上下文。

仓库和 GitHub Issues 必须足以恢复当前方向、有效决定、动态状态和授权边界。为避免重新形成 Legacy 中大型 `AI_HANDOFF`、`CURRENT_STATUS`、更新记录和多事实源并存的问题，长期事实、阶段方向、当前状态、任务授权和实际文件变化分别由不同载体承担。

以下只记录已经形成稳定规则、决定或可追溯结论的基础，不表示生产功能已经实现，也不记录实时百分比：

- **独立重写与 Legacy 永久只读**：仓库边界见 [`AGENTS.md`](../../AGENTS.md)；JueMingR 不在编译期或运行时引用 Legacy。
- **正式文档进入 Git 与受控演进**：以 [文档治理规则](../规范/文档治理规则.md) 和 [ADR-0001](../决策/ADR-0001-文档体系与受控演进.md) 约束文档职责、权威和生命周期。
- **Legacy 行为恢复与差异验收方法**：以 [Legacy 平替与行为契约规则](../规范/Legacy平替与行为契约规则.md) 和 [ADR-0002](../决策/ADR-0002-Legacy平替策略与行为契约方法.md) 约束证据、临时基线、风险深度和用户验收。
- **原版 Terraria 同进程技术路线和兼容策略**：以 [技术平台与兼容规则](../规范/技术平台与兼容规则.md) 和 [ADR-0003](../决策/ADR-0003-原版同进程加载路线与兼容策略.md) 记录产品平台、clean-room、兼容与恢复边界。
- **AI 编码失控模式调查**：[Phase 0-I Issue](https://github.com/Kuroneko2020/JueMingR/issues/6) 已完成；调查结果作为后续最小工程治理的证据输入，不直接升级为完整规则。
- **跨会话连续性系统**：本路线图、稳定起步总跟踪 Issue、当前任务 Issue 和 [ADR-0004](../决策/ADR-0004-跨会话连续性与稳定起步路线图.md) 分别承担稳定方向、动态状态、任务授权和决策理由。

## 五、稳定起步前的候选阶段

以下阶段名称和顺序是当前框架，不是永久编号、精确排期或实施授权。每个阶段都需要独立 Issue 和明确授权；发现更合适的依赖或拆分方式时，应按本路线图的维护规则调整。

### 阶段 A：最小工程治理与试运行

**主要依赖**：AI 编码失控模式调查已经完成，跨会话连续性系统已经建立。

**目标**：

- 把 Phase 0-I 的研究结论压缩为普通人可理解的最小日常规则；
- 明确 Agent 可以自动做什么，以及哪些事项必须等待项目所有者批准；
- 用少量真实任务试运行；
- 删除无用、昂贵或增加项目所有者负担的规则。

**退出条件**：

- 新任务可以使用一页以内的任务契约；
- 项目所有者只需查看产品结果和高风险差异；
- Agent 不再把工程术语问题转交给项目所有者；
- 治理尚未膨胀成大型审计体系。

### 阶段 B：性能治理基线

**主要依赖**：阶段 A 已形成可试运行的最小任务边界和授权方式。

**目标**：

- 定义热路径，以及 Tick、帧、Hook、扫描、分配、缓存、日志和关闭成本；
- 定义何时必须测量；
- 区分静态形态、微基准和实机帧时。

**退出条件**：

- “注意性能”被替换为可执行规则；
- 性能检查有场景、预算和退出条件；
- 测量工具不进入正式产品路径；
- 不要求所有普通任务运行昂贵性能审计。

### 阶段 C：测试与审计基线

**主要依赖**：阶段 A 的最小治理可以承载分层检查，阶段 B 已明确性能证据不能被普通测试替代。

**目标**：

- 区分结构测试、行为测试、集成、实机、多人和用户验收；
- 建立独立 oracle；
- 防止字符串审计和测试投机；
- 按快速、PR、夜间、发布和实机分层。

**退出条件**：

- 普通提交不会触发十五小时审计；
- 每项检查能说明防止什么故障；
- 慢检查不默认阻塞无关任务；
- 检查有 owner、成本和退休条件。

### 阶段 D：版本、配置与发布基线

**主要依赖**：阶段 A 至 C 已能区分任务授权、验证层级和检查成本。

**目标**：

- 分离产品版本、配置 schema、兼容记录、Git 和 Release；
- 定义构建与发布记录；
- 定义升级、回滚和发布证据。

**退出条件**：

- 不再为每个内部步骤推进产品版本；
- Git、Issue、ADR、Release 各自职责明确；
- 用户发布变化和内部工程历史分开。

### 阶段 E：Legacy 数据迁移策略

**主要依赖**：[Legacy 平替与行为契约规则](../规范/Legacy平替与行为契约规则.md) 已明确数据自然归属和证据边界，阶段 D 已明确版本与回滚职责。

**目标**：

- 清点配置、快捷键、笔记、蓝图和角色/世界事实数据；
- 定义复制、转换、冲突、幂等和回滚；
- 保持 Legacy 永久只读。

**退出条件**：

- 每类数据都有明确归属和迁移决定；
- 不扫描或删除未经用户授权的数据；
- 迁移失败不会损坏 Legacy。

### 阶段 F：总体架构与状态所有权

**主要依赖**：行为、平台、治理、性能、测试和数据边界已经形成足以约束架构的输入。

**目标**：

- 定义项目和模块边界；
- 定义依赖方向；
- 定义唯一状态 owner；
- 定义唯一游戏操作出口；
- 定义 UI、Runtime、Diagnostics 和功能之间的边界。

**退出条件**：

- 架构由 ADR 和图明确；
- 关键边界可由编译器、类型或架构测试执行；
- 不直接复制 Legacy 的 Service、Manager 和调用链。

### 阶段 G：可重复构建与项目骨架

**主要依赖**：阶段 F 的总体边界已经批准，工具链和合法游戏引用输入已有明确决定。

**目标**：

- 建立最小解决方案和项目；
- 锁定工具链；
- 建立合法游戏引用输入；
- 使干净克隆可以按文档恢复构建条件。

**退出条件**：

- 项目骨架不包含业务功能；
- 不依赖私人绝对路径；
- Legacy 零编译和运行依赖；
- 构建步骤可复现。

### 阶段 H：最小原版加载链验证

**主要依赖**：阶段 G 的可重复骨架，以及 [ADR-0003](../决策/ADR-0003-原版同进程加载路线与兼容策略.md) 规定的平台和 clean-room 边界。

**目标**：

- 实现最小 clean-room 加载验证；
- 验证 config、AppDomainManager、Harmony 单一上下文和一次性 Runtime 交接；
- 验证失败恢复。

**退出条件**：

- 当前目标 Terraria 版本能安全加载；
- 失败后原版游戏能够恢复；
- 结果不依赖 Legacy 生产代码；
- 验证原型不自动升级为完整产品实现。

### 阶段 I：代表性纵向功能切片

**主要依赖**：阶段 F 至 H 已形成可执行架构、可重复构建和最小加载能力，前述治理与验证基线可共同使用。

至少选择三类切片：

- 简单只读或 Overlay；
- 有状态 UI 与持久化；
- 高副作用或多人敏感自动化。

**目标**：

- 验证行为合同、架构、测试、性能和验收流程能够共同工作。

**退出条件**：

- 至少一个切片完成项目所有者用户体验验收；
- 不存在第二套基础设施；
- 自动、实机、多人、性能和项目所有者证据不互相冒充。

### 阶段 J：稳定开发基线验收

**主要依赖**：前述阶段所需退出门均已满足，遗留未知和未授权事项已明确记录。

**目标**：

- 按下一节“稳定起步的定义”逐项验收整体基线；
- 明确稳定起步后长期产品路线和动态状态载体的接替方式。

**退出条件**：

- “稳定起步的定义”全部满足；
- 稳定起步总跟踪 Issue 以 `completed` 关闭；
- 后续长期产品跟踪方式已经通过独立决定建立。

## 六、稳定起步的定义

只有同时满足以下条件，才算 JueMingR 稳定起步：

- 新 Codex 或网页 ChatGPT 对话可以只依靠仓库和 Issues 恢复状态；
- 文档、行为平替、平台兼容和最小工程治理已经形成闭环；
- 性能、测试、审计、版本和发布有不过度的最低基线；
- 总体架构和状态所有权已经批准；
- 项目可以从干净克隆恢复构建条件；
- 最小加载链在当前目标 Terraria 版本上完成指定实机验证；
- 至少一个代表性纵向切片完成；
- 产品、自动、实机、多人、性能和项目所有者验收分别记录；
- 后续任务不需要依赖旧聊天才能开始；
- 项目所有者不需要理解内部代码或在 Agent 之间人工传话。

## 七、新会话冷启动协议

新 Codex 或网页 ChatGPT 对话固定按以下顺序恢复：

1. [`AGENTS.md`](../../AGENTS.md)；
2. [`docs/README.md`](../README.md)；
3. 本路线图；
4. [“JueMingR：稳定起步总跟踪”Issue](https://github.com/Kuroneko2020/JueMingR/issues/7)；
5. 总跟踪 Issue 指向的当前任务 Issue；
6. 当前任务路由要求的规范与 ADR；
7. Git 当前分支、HEAD 和工作区状态。

完成读取与核验后，先报告：

- 当前稳定提交；
- 当前阶段；
- 当前任务；
- 当前阻塞；
- 本次授权范围；
- 下一项已授权动作；
- 哪些内容仍未授权。

若仓库、路线图、总跟踪 Issue 和当前任务 Issue 互相冲突，停止写入，并列报告冲突；不得使用聊天记忆自行裁决。

## 八、网页 ChatGPT 的恢复方式

项目所有者可以复制以下启动语：

> 请读取 Kuroneko2020/JueMingR 的 AGENTS.md、docs/README.md、docs/计划/稳定起步路线图.md、“JueMingR：稳定起步总跟踪”Issue 和其中指向的当前任务 Issue。
>
> 先告诉我当前稳定提交、当前阶段、当前任务、阻塞和下一项已授权动作。不要依赖此前聊天记忆，也不要开始修改仓库。

## 九、Codex 的恢复方式

项目所有者可以复制以下启动语：

> 从当前 Git 仓库根目录冷启动。
>
> 依次读取 AGENTS.md、docs/README.md、稳定起步路线图、稳定起步总跟踪 Issue 和当前任务 Issue。
>
> 核验分支、HEAD、origin/main 和工作区后，只复述当前任务契约与写入边界，等待进一步授权。不得依赖此前会话记忆。

## 十、路线图维护规则

- 当前动态状态不写入路线图；
- 任务完成不在路线图追加状态；具体任务 Issue 按事实收口，并同步更新总跟踪 Issue 的项目级投影；
- 只有阶段目标、顺序或退出门变化时才修改路线图；
- 路线图变化必须有专门 Issue 和项目所有者批准；
- 普通功能任务不得顺手重排路线图；
- 历史依赖 Git，不在正文保留旧版计划；
- 不创建每日、每提交或每对话更新记录；
- 远期阶段只写方向，不提前生成大量空文件；
- 路线图与现实冲突时修改路线图，不为维护旧计划而扭曲实际项目。
