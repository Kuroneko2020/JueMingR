# 物品箱子与多人权威

本页包含 Legacy .6/.7 历史、目标 .8 定向静态发现及 R 首轮实现经验；没有以这些静态事实代替真实箱子/多人操作。实际合同见[三项使用与接受边界](../功能介绍/自动存放功能行为合同.md#r-使用与接受边界)，职责见[实现设计](../设计/物品自动处理实现设计.md)，验证与接受证据见 [#46](https://github.com/Kuroneko2020/JueMingR/issues/46)。历史策略不能覆盖所有者决定，实现接受不升级静态证据等级。

## R：来源成员、失效与真实操作交集

新物品不能只看背包数量增长：容器取出/购买/搬动也会增长。R 的可靠世界拾取或正常手动开启产物先形成有限取得机会，再绑定当前未保护的兼容整栈成员；20 旧量＋3 新取得可处理23，后来等值换入不能继承旧成员资格。查看 `ItemSourceHooks`、`ItemHostObservation`、`ItemAutomationFeature` 及 `ItemHostChecks.UnifiedSourceAndFocus`；实际接受来源以主合同为准，旧限定“只认地面”或名单直接清旧库存不再生效。

`ItemNearbyStorage` 的容量等待原来只在 Execute 比较位置，而 Feature 会先按相同 observation revision 早退，导致仅移动仍等剩余120 tick。现在仅在存在容量等待时由 Storage.Update 比较缓存位置并发布失效，发生于 Feature.Update 之前，不制造新来源、不逐帧扫箱。`CapacityBackoff` 必须只移动、不同时 Pickup，才能区分这个回归；短等待不等于永久停转或性能故障。

未知出售/丢弃和中断来源持有的槽也必须覆盖原版手动快速堆叠。`ItemPendingGuards.QuickStack` 保留 StoreBlocked 的共享 scratch/netInv 排他，其余只判断实际写入交集：.8 的 Pack 为10–49非空非收藏非币；Inventories 入口额外 MoveCoins，仅移除/回写原非收藏币槽，不回写任意 Air。不要借未知出售保护58槽就猜原版每条路径都写58槽。`ItemHostChecks.Transactions/Guards` 覆盖两个公开入口、异常所有权及热栏/弹药/Air/其它玩家/自动操作的正向边界。公开夹具只核验准入，真实写范围由固定 .8 原件补足，不能称多人资源守恒已实测。

## R 首轮接入中的可复用边界

指定 .8 的库存槽锁只覆盖部分入口，不是统一事务锁。主包接收、弹药接收、手柄开袋、实际用料与排序需要按真正写入范围核对；用 Air 伪装一个在途弹药槽，会让空槽分支覆盖它。选择性存放必须传自己的来源数组，不应临时改真实槽或收藏状态。FlexibleTileWand 的材料会决定放置结果，应等待原选择的受保护材料，不能过滤成另一种材料后悄悄改变放置物。

出售保护需到实际 SellItem；鼠标持物点击商店与背包 cursorOverride 是不同入口，却共享前58槽备份/收款范围。普通金币购买可能将找零写进空槽；客机某槽收到 Air 后、同批尚未完成时仍属受保护范围。自定义货币购买的 ItemCacheCreate/Restore 覆盖所有源库存，不能只保护一种奖章的扣料点。上述结论来自已核验 .8 的定向原件与隔离反例，不是三拓扑实机证明。

客机反向85不等于成功 ACK；原版 unlock 也不证明余量回复已完整应用。一个共享 netInv 批次收集其全部来源5回复后才能核对组总余量，原版源栈合并可能重排每槽数量。没有 R 请求 ID 时，不编造跨断线精确提交协议。不可判定的副作用保持未确认，不重发、不回填，也不因此暂停无关范围。

同会话旧 Receipt 与重新进入的原始报文不能混为一谈。`8a1e504` 的隔离夹具已证前者被精确批次检查拒绝；A 结束且同槽 B 开始后人工再次注入原始 A，仍会误结算 B。已读目标 .8 业务与接收链可排除单份 A 仅因自然迟到再次消费，但额外合法 A 帧的原版可达性仍有固定 Windows/.NET 发送缓冲证据缺口。所有者限定接受本阶段此项残余风险并[延期调查 #48](https://github.com/Kuroneko2020/JueMingR/issues/48)，原夹具、输出及再评估条件由该 Issue 定位；没有确认真实丢物/复制，也没有证明绝不会发生。延期不等于测试通过，不扩成其它安全问题的通用豁免。

观察版本需要分别记录不同操作的临时准入门。把虚空在途锁和物品使用等多个条件合并成一个 busy bool，会在一个门解除、另一个仍忙时吞掉必要重评。反过来，原版失败收款可能只 clone 相同的58槽，不能仅凭对象换新就制造每次轮询的重复交易。生产 Host 还须与独立编译的 ABI 夹具接通；只把适配器源码重新编译到替身中，会掩盖 field/property 差异。

三项统一来源时，只给兼容身份加时间戳不足以结束机会：一个成员处理后、下一次扫描前，玩家已可能取出同类；收藏同类也可能让旧组一直存在。R 在成功外层因果结束时共享一次58槽观察并同步绑定实际合格成员，之后普通观察只能删除关联。提交成员立即退役，结果/资源所有权另行收口；新取得才可再次捕获当前整栈。纯提示偏好应只影响显示，不能复用整个配置值不等来清来源或重置尝试。上述为本轮实现与隔离反例所得，未证明实机/多人接受。

目标 .8 的重铸浮字与 `AdvancedPopupRequest` 使用同一 `PopupText` 池，但 Item 重载会处理物品上下文/数量，不能直接拿它拼完整业务句子。Advanced 的 `freeAdvanced` 排除普通拾取合并，ResetText 清除旧槽特效；应在清源前从实际物品取 `AffixName()`，只在业务完成并释放自有状态后同步显示确认数量。提示异常不得落入业务异常分支或从 LastResult 重放；关闭时先短路取名和格式化。#46 本次核对了 .8 原始方法与 ABI，隔离失败注入只证明接线/一次性/业务隔离，原版池与字体的实际观感仍需对应实机证据，不能用替身像素代替。

原版拒售的58槽 clone 需要两个不同判断：已知同步原版恢复可在证明来源、币值、回购及全58槽语义不变后保留成员标识；普通以后出现的等值副本仍须取消关联。不能一律把所有 clone 当新物，也不能一律把等值替换当同一物。手动原物/钥匙释放同样不能看消费后的 `Main.mouseLeft/Right`；R 使用唯一输入 owner 的有效许可加 `PlayerInput.MouseInfo` 原始左右键真实释放。焦点只挡新动作，不应挡来源记录或在途回执。

目标 .8 定向补查覆盖全部 `OpenableBag` 58项（21宝藏袋、26匣子、11特殊物品），而不是按三个示例建立白名单；`TryGettingDevArmor` 的21分支最终仍走同一 QuickSpawnItem/GetItem 直接接收链。`TryOpenContainer` 最后一件调用 `SetDefaults(0)` 后 stack 为0，仍符合实际扣减判据；夹具若只写 type=0 却残留 stack，会误报来源缺口。`WorldItem.ReplaceWith` 后应读该 WorldItem 的实际余量，`newAndShiny` 不承担来源证明。原件身份沿用[目标 .8 附录](../功能介绍/自动存放功能行为合同.md#84-目标-1458-定向原版证据)，补充方法和哈希在 #46 的任务证据；静态覆盖不代表58项逐一实机通过。

## 容器字段不能替代语义分类

旧资料中 `Main.tileContainer` 含 21/467、梳妆台 88、展示类 470/475 等，不都拥有可改名的世界 Chest。普通箱 21/467 为 2×2，梳妆台 88 为 3×2；fake chest 441/468 需进一步辨明行为。世界非负 chest index 与个人银行 -2（猪猪/钱币槽/Chester）、-3（保险箱）、-4（护卫熔炉）、-5（虚空）不同。假人/帽架装备由 tile entity 承担，不是 Chest 名称数据。

原版机制笔记偏重“普通宝箱”能力分类，较晚[宝箱显名功能说明](../功能介绍/Legacy更多信息.md)却明确包含梳妆台与 fake chest 默认名解析。不能用 tileContainer 一刀切，也不能把旧笔记的窄能力建议改成 R 已接受的显示范围；该差异在未来容器功能任务核对真实代码与用户行为。

来源：`Terraria原版参考笔记/Chest_Container_notes.md`、`Inventory_Equipment_notes.md`，以及旧功能介绍 `更多信息页/宝箱显名.md`。

## 拾取来源与同类堆叠

`GetItem(WorldItem, PickupItemFromWorld)` 与共享 Item overload 的用途不同；LootAll 不一定经过 ItemSlot，cursor 从容器拿走后即使关 UI 仍保留来源。数组身份比 context 3/4/32 这类辅助数字更能证明容器归属。`newAndShiny` 会被 UI 清理、可能由非世界来源设置，也可能在钱币/合并栈时不设置，不能当可靠拾取标记。`Item.CanStack` 还检查 type、prefix 和可堆叠性，不只是名称相同。

较晚 Legacy 自动堆叠说明要求选择性 pending transaction，容器取出不得触发重新存回，入队后来源变化也须拒绝旧请求；钱币由自动存钱开启时独占。容器关闭不解除钱币取出保护，观察失败不等于离开银行范围。见[Legacy 物品](../功能介绍/Legacy物品.md)。这些历史状态规则可供行为任务分析，不要求 R 移植旧队列。

源码复核补充：普通世界拾取要求此前前 58 槽内同 type+prefix 总量为零（包括收藏旧栈）；受控开袋没有此限制。候选签名收集获准身份的所有合格整栈，不是新增数量额度，过去从容器取出的同类也可能在后来独立获准的开袋批次中入选。普通物品的全局取出 revision 会使旧请求失效，不是钱币的银行范围租约。来源、例子、测试真实覆盖见[Legacy STORE-02 至 STORE-08](../功能介绍/自动存放功能行为合同.md#store-02-来源是取得依据不是背包差值本身)及 E04–E06；这些是 Legacy `6ac6356c0c564f43284590c168855e96c50e13f7` 静态事实，R 已接受的数量目标以主合同第 1 节为准，不能据此认定旧策略获准保留。

## 选择性调用不等于最终存妥

同一 Legacy 基线的 `QuestFishStorageCompat.cs:378–434,524–606,958–998` 构造原 Item 引用与 SlotReference 的选择性 SourceInventory，没有沿用旧 mask/favorite 临时改写；前检合计世界箱及银行，实际三参 QuickStack 只进世界 Chest 路径。.7 `NearbyChests.cs:10–30` 按 8000 个世界 Chest 索引、600px 枚举，不按最近排序，也不能以“普通箱”排除有真实 Chest 的梳妆台。

兼容层以候选 type 总量或选中槽数量任一减少判成功，执行器据此成功，服务可结束整个提交批次；没有核对所有目标增加，部分完成与整批完成不能混称。原版 .7 客户端锁槽并发 5/85 后返回，Legacy 的即时数量比较没有最终服务器回执关联。`Program.InventoryAutomationActionTests.cs:280–335` 的 fake Succeeded 在背包快照仍有 3 个时也期待清 pending，只证明控制流程。原版中途异常的恢复、物品守恒、重试幂等及多人最终结果仍未证明。

600tick 年龄门只在 `AutoStackService.RegisterRetry` 检查，最多是初试后再安排 3 次，不是总共 3 次，也不是所有 UI 等待都会十秒到期。来源票据没有 120tick TTL。详细路径、版本原件哈希与限制见[合同证据附录 E07–E10](../功能介绍/自动存放功能行为合同.md#82-路径符号和证据覆盖)；本结论不授权复制旧队列或新建测量/恢复系统。

## MoveCoins 的零返回与参数签名

`NearbyChests.GetBanksInRangeOf` 的成功且无银行、成功且有银行、读取失败是三态，失败不可释放保护。旧 `ChestUI.MoveCoins` 某些路径会在修改后返回 0，不能凭 raw 0 认为无副作用并执行 fallback。空银行首币历史补救只覆盖能证明的 player.bank，不泛化到其它三银行。

反射 `SetDefaults(int, ItemVariant = ...)` 的可选参数不使它变成一参方法；需要完整签名与正确参数。应在写入前完成解析和恢复条件准备，不能先改钱币再找失败补救。

来源：`Terraria原版参考笔记/Inventory_Equipment_notes.md`、`Chest_Container_notes.md`；后续对相应版本 `Player.cs`、`UI/ChestUI.cs`、`GameContent/NearbyChests.cs` 定向查调用和原始返回路径。

## ABI 与多人证据不可泛化

1.4.5.6 `WorldItem.inner` 是 public field；1.4.5.7 是 public property、private setter。这是编译 ABI 差异，同源码分别编译不证明一个 DLL 跨两版通用。较晚 Legacy 自动堆叠文档明确其当时测试包只面向 .7；R 编译目标 .8 不受这些树替代。

旧 .7 箱内定位提交时请求当前玩家 section 的原版 159 数据同步。请求发出不证明数据已到、周边所有箱子已同步，更不证明服务器权威或多人验收。只读 `Main.chest[].item` 可以报告客户端当前已知结果，不能编造未同步容器；需要核对来源、section、响应时机与拓扑。来源：旧功能介绍 `物品页/自动堆叠.md`、`搜索查询页/箱内物品定位.md`；本地对应原件在 `references/terraria/1.4.5.7/Terraria/`，定向查 `WorldItem` 与消息处理，不执行网络行为。

## 目标 .8：参数名不是来源，输入槽不是完整冲突范围

指定 .8 EXE 的 `QuickSpawnItem` 也使用名为 `PickupItemFromWorld` 的 GetItemSettings，且下游 GetOrDropItem 不保留传入的开启 source；不能用设置名或任意 GetItem 当世界拾取凭据。原版 `TryOpenContainer` 先生成全部产物再扣原物，嵌套回调里马上卖/扔/存会抢正在操作的原料，并可能重复统计同一取得。应保留窄的上游因果，调用结束后确认实际主包接收；虚空接收和落地余量分开，后来真实拾取可成为新事件。来源：[目标 .8 附录 V8-01/02](../功能介绍/自动存放功能行为合同.md#84-目标-1458-定向原版证据)，绑定 EXE 哈希和必要方法，不是从 .7 猜等价。

出售不只写来源槽：.8 `SellItem` 可收款到 0..53 并递归合币，正常容量失败恢复前 58 槽备份；后续还有回购和清源。垃圾桶操作共享 trashItem 并替换旧内容，旅行模式可能附带研究。两个来源槽不同不能证明操作互不冲突。相反，Legacy 快速开袋仅因任一清理开关开启就在入队时让路 24 tick，卖扔在选自身名单前等全部堆叠 pending，并非真实资源比较；不能将其复制为必要同步。证据见同合同 E16–E18、V8-04/05。

## 目标 .8：按原版权威区分完成判据

本地开启直接入包、出售和垃圾桶没有各自的逐次服务器业务 ACK；库存/trash 通过普通消息 5 同步，不能发明不存在的回执作为永久等待条件。世界拾取同步 21，服务器检查世界槽/保留归属，通常不回发给原发送者；来源事实与全网资源结果应分开。

附近存箱不同：客户端对选定槽 LockNetSlot、发 5/85 后返回；服务器读取该发送者的槽组，实际 Transfer/Restore，逐源槽发 5，目标槽走 32。反向 85 只是被挡箱提示。收到一个槽回复或本地数量减少不能证明整批成功；无业务事务 ID 时须限制这条路径的未完成批次、保留会话和真实范围，不能叠发后猜归属、超时补一次或回写旧快照。未同步箱内容也不能被当成无目标。来源：[目标 .8 权威矩阵](../功能介绍/自动存放功能行为合同.md#85-按路径区分本地结果与服务器权威)；这是静态设计依据，三种拓扑仍须后续固定候选的真实运行验证。
