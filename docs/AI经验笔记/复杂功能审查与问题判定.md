# 复杂功能审查与问题判定

本文面向 JueMingR 的所有功能，提供理解真实行为、调查相互作用、判定问题和有限收口的方法。它既适用于另开会话审查已有功能，也适用于功能完成后的整批变更审查。蓝图只是一个案例；UI、快捷键、战斗、移动、钓鱼、物品、地图、笔记、存储、后台工作、联机和性能均可按实际风险选用相应部分。

这是按需经验指导，没有独立产品裁定权，不增加每任务必读、审批、角色、固定轮数、检查表、台账、CI 或全量矩阵。简单问题可以由一条确定路径和针对性证据解决；跨组件问题才需要展开相应状态、时序和恢复关系。已经适用的合同与规则由原载体负责，不在此另建一套制度。

硬边界仍查[工程独立审查边界](../规范/工程治理规则.md#八独立审查边界)、[持续实施与集中独审](../规范/工程治理规则.md#十二新会话交接与沟通)、[独立判定依据](../规范/测试与审计规则.md#五独立判定依据)、[时间和成本边界](../规范/测试与审计规则.md#十二时间和成本边界)、[停止条件](../规范/测试与审计规则.md#十七停止条件)，以及[总体架构与状态所有权](../设计/总体架构与状态所有权.md)。具体行为先由[功能索引](../功能介绍/功能索引.md)找到当前合同；本文的例子不能反向增加功能承诺、改变权限或削减已接受能力。

## 一、审查要回答什么，覆盖分母是什么

审查的目的，是判断一个明确对象是否满足已接受的用户结果和关键边界，发现并处理有依据的问题，同时说明证据可以支持多大的结论。发现数量、报告长度、文件数量和审查轮次不代表质量。

“在指定提交和范围内没有发现可确认缺陷”是有效结果。排除一个原本担心的路径、纠正错误测试期待、确认限制确实已经接受、指出一个决定性的窄证据缺口，也可能是有效产出。反过来，列出大量未经证实的可能性并不证明审查深入。

先确认本次的覆盖分母：

- **用户结果分母**：本次要判断哪些能力、场景和支持边界；来自原任务、有效合同和明确补充，而不是测试刚好覆盖了什么。
- **变更分母**：整批变更的基线到候选，包含与其语义相关的源码、测试期待、工具和说明；最后一个提交或最近验证点不自动等于整批工作。
- **因果分母**：哪些状态 owner、真实消费者、副作用、共享机制和恢复责任会改变本次判断；可以跨文件、程序集和多层消费者。
- **证据分母**：各个必要判断由什么事实支持，哪些只是记录声明，哪些本轮执行或核验复用，哪些仍未知。测试大组名和分项数量不是这个分母。

这些信息能在既有任务记录或短说明中说清即可，不需要再建分母账本、完成率或逐文件勾选表。专题本来只涉及一个入口时，不为了使用方法扩大题目；一条变化确实传播到多个消费者时，也不能以“只改了一行”省略它们。

如果所有者明确委托“全项目审查”，范围就应按实际功能域和共享机制建立覆盖：从功能索引、当前实现与状态所有权确定哪些领域已经检查、哪些仅复用有效证据、哪些尚未覆盖，并据实限制结论，不能自行缩成最近一个功能。若委托的是当前专题或某功能整工作包，则不默认扩大为全仓普查。**本指南适用于整个项目，不表示使用它的一次专题审查已经审过全项目。**

## 二、两种审查模式，与两条独立性轴

### 两种模式的范围来自不同地方

| 事项 | 单独会话的专题审查 | 功能完成后的整批变更审查 |
| --- | --- | --- |
| 典型问题 | 当前某功能或问题族在真实玩家路径上是否有成立问题？ | 这批实现/修复是否完成约定结果，处理原问题并保护实际受影响行为？ |
| 起点 | 指定版本、专题、原问题和有效合同，可以没有近期 diff。 | 原任务与补充、约定 BASE→HEAD 的完整语义变化、证据和未决点。 |
| 扩展 | 沿主题内有正向关系的机制和消费者，必要时看长期未改的接缝。 | 从整批变化及原问题沿实际传播扩展，也可能读未改但消费新语义的代码。 |
| 历史用途 | 提供版本对应的线索、已接受边界与可判别反例；历史概括不代替当前事实。 | 复用仍适用的完整审查、验证与已关闭责任；新变化仅使相关部分失效。 |
| 主要产出 | 固定范围、已审链路、问题分类、排除依据、未证部分及有限下一步。 | 当前工作包是否满足交付责任、具体受阻依赖、修订及必要传播是否关闭。 |
| 停止 | 重要切片与有据扩展已处理，实质疑问有结论或明确窄缺口，下一步无新判别价值。 | 整批必要责任有适用证据，无破坏本目标的未关闭确认缺陷，返修影响与未决点已核。 |

不是每次都要把两种模式各做一遍。功能交付中已经成立的集中独审，不因另一个名称再追加一次相同“最终深审”；另开专题审查也不自动取得修产品、运行游戏、安装或合并权限。

### 新会话和独立正确答案互不替代

**上下文独立性**关心审查者是否参与过被审实现或测试期待的起草，是否受到同一解题过程的锚定。**判定依据独立性**关心正确答案从哪里来。

| 上下文 | 判定依据 | 实际含义 |
| --- | --- | --- |
| 新会话、未参与起草 | 只照抄作者解释和从实现生成的期待 | 有上下文独立性，仍可能共同相信错误答案。 |
| 原实现上下文 | 对照原目标、目标版本事实和独立不变量 | 自查有价值，不能冒充规则要求的独立审查。 |
| 未参与起草的审查上下文 | 独立理解原结果，再核作者解释、实现和测试 | 两条轴都具备，仍需说明覆盖和证据限制。 |

一种有用的阅读顺序是先理解原问题、有效合同和关键反例，再用开发说明帮助定位实现，而非把开发说明当成唯一答案。这是减少锚定的策略，不要求盲查、不禁止共享可信资料，也不要求额外安排新会话或多轮审查。

## 三、从用户目标到真实行为链

先用玩家语言说清本次应该完成的事情，再找到实际入口和最终事实。不要从类名、测试组名或“该函数返回 true”开始定义成功。

有效期望要能回到原用户结果、明确接受的合同和真实原版支持。“普通”“常见”“同类”“符合标准”等词转成程序谓词时，要核每个新增条件来自哪里：所有者明确排除、真实消费者必需条件和实施者自行偏好不能混成不透明白名单。用户转发开发包并委托实施，不表示逐项核验了全部技术断言或有意接受未点明的范围缩减。

开发者自行缩窄的派生说明与从同一解释生成的测试，不能互相证明满足原意；矛盾成立时，明确撤销受影响条款并保留正确边界，普通技术选择与真正产品裁决分开。例如“不同尺寸不能互换”是必要几何条件，“所以所有非默认尺寸都不参加”则是另一项范围决定；应沿共同谓词核家族成员、手放、自动动作、数量、后处理与完成的传播。另一方面，“原版理论上能做到”只说明合法可达性，不会自动把所有原版能力提升成当前功能必须完整自动覆盖的承诺。已接受范围、新需求与设计偏好仍须分别判断。

通用调查链可以写成：**用户目标 → 实际入口与当前前提 → 状态/身份与决策 → 真正消费者 → 副作用 → 权威结果与下游消费 → 失败、取消、恢复和退休**。这表示需要建立的关系，不要求引擎内部严格按这条线性顺序运行，也不是每种功能都要有网络或物品消费。

| 关系 | 适合追问的问题 |
| --- | --- |
| 目标和前提 | 哪个已接受行为？哪种模式、世界、角色、拓扑或界面状态？缺料、超距、未知和不支持怎样表达？ |
| 实际入口 | 玩家从哪儿发起？Hook 是否真的执行？调用前的分支、输入仲裁和阶段是否允许它发生？ |
| 状态和身份 | 哪个 owner 拥有事实？缓存/快照属于哪个时点、generation、物品引用、对象或文件版本？谁会撤销它？ |
| 决策和消费者 | 计划被谁接受？消费者实际读取了哪个目标、来源和设置？中间是否重新选择、替换、改向或推迟？ |
| 副作用 | 世界、物品、钱币、输入、UI、文件、资源或后台工作实际改变了什么？动作失败是否仍有部分效果？ |
| 权威结果 | 成功由本地 owner、原版、文件提交还是服务器确认？请求、预测、暂存和真实成功是否分开？ |
| 下游 | 进度、数量、显示、重试和下一动作是否消费了正确含义的结果？有没有第二份过时事实？ |
| 恢复与退出 | 关闭、失焦、取消、异常、死亡、换世界或迟到回执后，哪些责任结束，哪些有限在途责任仍需收尾？ |

按[架构的状态原则](../设计/总体架构与状态所有权.md#11-状态所有权原则)区分原版事实、observation、派生判断、cache、UI projection 和诊断。显示有一行文字不证明动作完成，文件排队不证明落盘，网络发送不证明服务器接受，缓存 miss 也不等于真实空状态。

严格字段也要追到最终消费者再定罪。完整 form 含美术编码，不等于最终同类关系仍要求两端 form 全等；真实 OR／fallback 可能已经在正确责任处放宽材质，同时保各对象自身解码和完整成员。没有具体同族误排对或确定路径时，不把字段名或某个严格比较自动记成 Bug。

对原版动作还要核实际阶段与可达性。调用原版函数只证明来源；其前置状态、合法输入、release、选择、范围和时序仍需符合[原版合法操作与 TAS 可达原则](../规范/Legacy平替与行为契约规则.md#原版合法操作与tas可达原则)。不要求所有实现经 OS 模拟输入，也不能用直接写资源/结果或修改计时证明自动化可达。

涉及后台、绘制或多人时，只把真正参与该结果的部分加入链。一个纯文本设置说明修改，不因项目有 worker 就审全后台；一个后台结果会覆盖新编辑，就需要读到发布和新鲜度消费者，不能止于序列化成功。

## 四、从一个样本扩展到同因问题链

用户的例子通常是入口，不天然是范围上限。先抽出可证伪的机制：

> 在前提 P 和顺序 T 下，状态 S 被 A 产生；B 将它当成含义 Q 使用，造成已接受行为禁止的结果 R。

还不能说明这句话时，先保留候选原因。确认共同机制后，沿实际关系查清它的入口、成员、分支和消费者，不仅给点名对象加特例。

### 关联与边界

| 方向 | 有意义的扩展依据 | 不足以扩展或应分开的情况 |
| --- | --- | --- |
| 因果 | 共同错误前提、语义转换或结果分类能造成相同违约。 | 只有外观相似、同目录、同类名、以前曾出过Bug。 |
| 数据 | 共享可变对象、身份、库存来源、快照、缓存、配置或结果类型。 | 只有字段同名；数据已按独立合同接住且不再受该错误影响。 |
| 控制 | 共同门禁、跳过原方法、早退、重复提交、异常或取消清理决定实际结果。 | 另一分支使用不同的独立门与结果协议；调用图能继续展开不构成理由。 |
| 时间 | 动作前证明跨到消费后、输入脉冲后晚回调、旧 worker/回包晚到能改变结论。 | 生命周期和身份边界已切断传播；无依据任意扩大完整时域或重试次数。 |
| 权威 | 本地预测、文件提交、主机执行和远端同步之间有真实责任变化。 | 仅因同进程就合并权威；或仅因功能支持联机而要求所有内部纯逻辑都实机复现。 |

停止点是因果被切断、被独立合同和有效证据接住，或进入另一种与当前结果没有正向关系的机制。文件没改不等于没受影响；换了 owner 也不自动证明安全。需要说明为何该 owner 的门或输入事实确实使原失效机制不再传播。

### 同因范围核清，不等于逐成员全跑

可把共享成员和实际入口枚举清楚，用共享代码、版本事实及不变量证明共同部分；只有原版规则、owner、权限、消费者、时序或恢复语义不同，才选择不同代表。一个有限物品集合不要求把成员、数量、布局、拓扑与事件顺序全部相乘执行。

例如，若确认“已提交请求”被某共享结果分类误读为“已成功”，调查应跟到消费该分类的进度、重试、归还与反馈，而不是把所有请求系统都报Bug。另一个消费者若明确要求权威确认，就可能在边界之外。

### 不预设单一终极根因

复杂故障可能需要多个条件共同作用：旧快照本身无害，只有取消后新身份复用、晚回调再提交时才造成覆盖；某个输入沿只有在模态切换与延迟清理相遇时才泄漏。此时应保留必要条件及顺序，分别判断哪一个职责应防止违约。

可以修共同前提，也可以在产生错误语义的责任处设置恰当边界。根因修复不意味着一律改最底层或重写架构。多个促成原因不要求追到无限深的组织/历史根因；能够解释现象、确定合理影响、支持修复并接受相关验证即可。

## 五、什么构成 Bug，什么仍是风险或建议

| 分类 | 证据门槛 | 合理处理 |
| --- | --- | --- |
| 确认缺陷 | 有当前有效预期、合理可达触发、确定路径或可靠观察、违约结果与具体后果。 | 处理其真实影响；明确静态路径可以成立，不机械等待实机再现。 |
| 潜伏缺陷 | 还未在玩家机器报告，但触发可达、违约路径和后果已确定，满足确认缺陷同样门槛。 | 仍按真实缺陷处理，不能用“隐患”降低责任；与仅可能发生的风险分开。 |
| 有具体证据的风险 | 已有真实边界事实、合理触发和可能后果，但一个决定性前提或结果仍未知。 | 写清已知与未知、影响哪个决定、最短判别手段；是否阻塞另判。 |
| 待证假设 | 有一种可能解释，触发、传播或后果缺乏正向证据。 | 在相关且有判别力时有限调查；证实后升级，证伪后关闭。 |
| 非阻塞建议 | 未违反当前合同，只是设计、体验、维护或进一步优化取舍。 | 说明收益/代价与授权范围，不包装成修复。 |
| 已接受边界 | 有明确、当前仍适用的所有者决定或有效合同，接受指定限制。 | 核实际条件是否仍在边界内；它不等于该轴已经测试通过，也不允许扩大限制。 |

缺少一个测试、没有显式 guard、代码复杂、旧测试 FAIL 或注释措辞，本身不能单独证明产品Bug。相反，确定的违约路径也不能仅因“不常见”“历史旧债”“没实机复现”被降为建议。

分别判断以下三件事：

1. **确认度**：我们知道什么，凭什么知道，哪一环仍未证明。
2. **严重性**：一旦发生，玩家结果、数据、物品、权威、输入或运行会受多大影响。
3. **相关性与当前责任**：它怎样正向关联本次目标、变化或当前版本的实际严重故障，是否阻塞当前哪一部分。

“后果很严重”不能补足未证触发；“只读审查”也不意味着必须把所有观察都变成当前交付前置。关键证据缺口确实会改变当前安全/正确性交付判断且无可信替代证明时，可以阻塞相应依赖。普通未知、范围外测试名或“还未证明无害”不能自动阻塞全部任务。

报告阻塞意见时，自然说清：什么支持/合法前提，哪条实际路径，违反哪个已接受行为，给玩家什么后果，什么有限证据足以关闭。信息可以写在既有报告中，不需要为每个发现生成新卡片。

## 六、主动反证，防止确认性偏差与自造 oracle

审查者也会在一个可疑字段、一份用户案例或自己最初解释上锚定。新写一个会失败的测试，可能只是把同一个误解自动化；新会话也可能共享作者的错误 oracle。这里的 oracle 指判断实际结果应当如何的依据。

把将要升级为缺陷或阻塞的发现，交给一次有限的反证检查：

1. **核正确答案来源。** 来自原目标、有效合同、目标版本原版事实、独立性质/不变量或已确认观察吗？仅从新实现输出、已有测试期待或开发解释推出来时，先重建依据。
2. **尝试证明触发不可达。** 当前真实入口、上游门禁、模式、类型/对象身份、生命周期、调用阶段或拓扑是否已阻断这条路径？不要只截一个内部函数。
3. **找最强保护。** 将重新验证、cache失效、所有权转移、权威确认、finally、晚回调拒绝等放回真实先后顺序，观察原指控是否还成立。
4. **比较竞争解释。** 可能是原版本来拒绝、已接受边界、测试替身/夹具、等待前提、候选身份、环境或观察方式问题。每个解释也要有事实，不能用“也许还有保护”否认确定缺陷。
5. **选择能推翻自己的下一步。** 例如查“旧回调能否覆盖新的revision”，而不只再跑一次保存；查“服务端拒绝时进度是否仍完成”，而不只看请求发送。
6. **检查是否偷加要求。** 是否无依据要求固定消费数、固定命中率、强制重算、立即完成、所有中断自动恢复、原子整批事务、完整时域或所有路径零成本？没有当前依据时，改成建议或撤掉期待。
7. **允许撤回并停止。** 保护生效、前提不可达或接受边界适用时，明确“该担心已排除”。同机制换一个外观不重开。

反证不要求证明系统在所有可能世界里安全，只给具体指控一次公平、有限的被推翻机会。确定路径仍成立后，也不因想出无限备选解释而拒绝确认。

### 独立依据可以组合，但缺口要说清

合同说明用户应看到什么，目标版本消费者说明合法阶段和副作用，独立不变量说明物品或身份不能怎样变化，真实场景说明完整入口和表现；它们可共同支持一个结论。某一层没有完整 oracle 时，不用很多弱证据掩盖关键空白。

可使用性质和变形关系，例如“取消后旧结果不得覆盖新的编辑”“纯展示切换不应增加存储命令”“同一真实动作的合法邻接帧变化不应额外收一次本体材料”。这些性质先要有合同或机制依据，不能因为便于测试就成为新要求。输出由实现公式算出的期望值，不能独自证明该公式正确。

## 七、真实场景与时间交错怎样有限取样

先按不同语义分支取样，再决定所需证据层。相同 owner、消费者、前置和失败语义可共享证明；换了权限、身份、实际消费者、提交点或恢复方式，通常才产生新的判别分支。

有用的时间边界包括：已规划但尚未消费；解析后真正消费者前；副作用发生但原调用未返回；用户已经松键而旧清理尚未完成；世界已完成而库存/网络责任在途；旧身份退休后结果到达；关闭后再开启；文件读完但新编辑已产生。只选会改变当前判断的边界，不在每一行前后都注入异常。

| 例子 | 有判别力的不同分支 | 不需要机械补的内容 |
| --- | --- | --- |
| UI按下后布局/滚动变化 | 原命中仍同一目标，或已变为另一目标/隐藏；释放尾是否归原owner。 | 全部窗口大小×所有控件组合。 |
| 短按自动化后延迟Completed | 手动意图在真实接管时记录，或错误依赖晚回调当时按键；旧token与新token。 | 用永久长按重复代替短脉冲，也不用穷举每个等待帧数。 |
| 文件保存与新编辑交错 | 旧保存成功只确认旧revision；失败/取消/旧世界回执不会覆盖新正文。 | 所有文件内容、每种磁盘速度和无关功能测试。 |
| 物品合堆 | 整堆入已有格、部分合入后继续、空格接收、原体未写；来源身份是否真的转移。 | 所有数量排列和同型物品全组合。 |
| worker取消后晚结果 | 当前serial/generation不同、相同请求仍有效、最后引用已退出。 | 任意延时枚举或每任务新建回放框架。 |
| 联机提交后移除UI/投影 | 新动作已撤销，旧请求仍可准确收尾；成功、明确拒绝、无法关联。 | 把每种工具都套同一种ACK/超时。 |

交互因素和事件顺序是场景选择工具，不是统一组合强度门。NIST 的研究启发是：问题可能需要少数条件共同出现，也可能依赖先后而不要求紧邻；它不证明本项目每个故障最多几阶，更不意味着一定要运行2-way/3-way或全部排列。[来源与限制](#十二外部原始来源与适用边界)见文末。

真正的 Terraria 实机、完整渲染、真实物理输入、真人多人和性能测量各回答不同问题，按具体风险触发。原生CPU消费者检查可以验证所执行的阶段和断言，不能冒充完整Main/Draw、OS输入或真实socket；对纯逻辑确定路径，也不机械把所有者再次游戏操作设为确认前提。

## 八、按功能选择真实链和语义分支

以下为选用入口。只读与本次目标和风险有关的部分；不是每个功能都照抄全套，也不是对现有实现的缺陷指控。具体合同与设计优先于条件性例子。

### 1. UI、绘制、命中与图形资源

真实链通常是：状态/命令 → Prepare得到的布局与资源 → 实际Draw的坐标/裁剪/层级 → HitTest采用的几何 → 按下/释放提交 → 命令回执与反馈。分清逻辑、UI缩放、屏幕、世界坐标，布局revision与显示资源身份，以及绘制和命中各自使用的时点。

当风险命中时，可区分正常可见、滚动/尺寸变化、隐藏/裁剪、失焦、无新输入的Draw、资源待准备/已就绪/退休。条件性例子：按钮按下后滚动，释放落在另一个条目，关键是旧armed是否仍能提交旧/新目标，不是截图里按钮看上去是否整齐。

Draw是否偷偷读盘、加载资源、推进业务、取走输入，按实际调用核；资源所有者、共享借用、替换/释放与缓存失效按真实身份查。只有纯文案修订且布局与行为无实质影响时，不因此重验世界动作、多人或完整资源生命周期。像素、遮挡和手感需要实际呈现证据，纯几何单测不替代。

入口：[F5设计](../设计/F5控制界面样板与UI基础.md)、[笔记合同](../功能介绍/笔记功能行为合同.md)、[笔记设计](../设计/笔记功能实现设计.md)、[实体显名设计](../设计/实体显名与样式配置实现设计.md)、[绘制与资源经验](绘制分层与图形资源.md)。

### 2. 快捷键、输入捕获、释放与仲裁

真实链通常是：物理样本 → 原版映射 → 主键/修饰键边沿 → 文字/模态/overlay仲裁 → 捕获owner → 动作命令 → 持续/释放尾 → 控制归还。区分物理输入、映射触发、自动注入和原版release状态；已有释放责任可能长于发起动作的界面。

相关分支包括按下/保持/松开、组合重叠、双击/拖拽、失焦/重开、录入期间、捕获后界面消失、手动接管和新选择意图。条件性例子：关闭一页不代表已捕获按键的松开可以泄给下一页；也不能为了“恢复”制造原版没有观察到的release。

文本编辑问题不自动要求战斗或库存全量验证；只有共同捕获/仲裁机制实际改变，才沿真实消费者扩展。一次新鲜样本与释放尾证据不能由持续轮询旧状态代替。

入口：[统一快捷键合同](../功能介绍/统一快捷键功能行为合同.md)、[快捷键设计](../设计/统一快捷键实现设计.md)、[输入经验](输入捕获与坐标域.md)、[架构UI与输入边界](../设计/总体架构与状态所有权.md#21-ui-与输入边界)。

### 3. 战斗、移动、钓鱼与其他原版动作自动化

真实链通常是：玩家目标/预测 → 当前对象身份与门禁 → 合法输入或临时借用 → 原版真正阶段/消费者 → 实际攻击、运动、投射物或鱼获 → 当前观察 → 归还。预测正确、预览正确和实际消费者正确是不同结论；临时朝向、装备、瞄准与工具计时也有不同owner。

按涉及机制选择按住/释放、同动画内下一合法机会/新动画、原版重用/非重用、目标丢失、投射物身份复用、碰撞/地形变化、手动接管及原生结束。移动还可能需要区分地面/空中、坐骑或抓钩等真正改变消费者的状态；钓鱼需关注浮标/产物、临时装备及原版回收时机。并非所有武器、坐骑、鱼竿都要逐个全跑，共享分支以机制和独立依据覆盖，消费者不同的代表另选。

不要从显示路径推100%命中，从理想预测推实际手感，或从调用原版API推阶段必然合法。只修改预测展示而未改变输入/消费者时，不自动追加装备搬运与安装恢复验证；实际输入owner变动则应追到真实动作和收尾。

入口：[战斗合同](../功能介绍/战斗辅助行为合同.md)、[战斗设计](../设计/战斗辅助实现设计.md)、[移动合同](../功能介绍/移动辅助行为合同.md)、[移动设计](../设计/移动辅助实现设计.md)、[钓鱼合同](../功能介绍/钓鱼与配装行为合同.md)、[钓鱼设计](../设计/钓鱼与配装实现设计.md)、[工具设计](../设计/工具与自动采集实现设计.md)、[战斗移动钓鱼经验](战斗移动与钓鱼机制.md)。

### 4. 物品、钱币、身份与实际消费

真实链通常是：允许处理的真实来源 → 资格/保护/人工意图 → 当前引用/槽/类型 → 原版选择、搬运或收费 → 实际接收者与消费 → 同步/观察 → 归还与未知保护。相同type、同数量、同slot不是同一来源；数量增长也可能是旧堆合入、自动整理或回包，不能自动当新授权。

有判别力的分支可以是整堆/部分合堆、空格/no-op、来源耗尽/替换、人工取出、满银行、原生零返回但已有写入、取消时已经消费、旧token尾返回。钱币尤其区分原面值、换算总值和实际写集；不能只看返回数量判是否没有副作用。

条件性例子：自动归包把暂存物合入另一堆，若原接收者增长而incoming数量未减，正确判断要查原版helper语义；不能由一个计数条件猜来源已消失。只改物品查询显示时，无实际搬运/消费传播就无需整套存钱或归还测试。

入口：[物品处理合同](../功能介绍/自动存放功能行为合同.md)、[处理设计](../设计/物品自动处理实现设计.md)、[存钱合同](../功能介绍/自动存钱与主动取出保护行为合同.md)、[存钱设计](../设计/自动存钱与主动取出保护实现设计.md)、[快捷物品设计](../设计/保持收藏与快捷物品使用实现设计.md)、[物品与权威经验](物品箱子与多人权威.md)。

### 5. 地图、笔记、蓝图库、配置与保存恢复

真实链通常是：自然数据归属 → 读取与schema/损坏分类 → 当前编辑/业务命令 → 固定revision快照 → 编码与机械写入 → 原子提交/失败 → 回执 → dirty/保存显示/恢复。区分请求保存、写入完成、当前最新内容已保存和玩家已看到反馈。

按风险选择首次缺文件、正常重开、损坏/未来版本/权限错误、连续编辑、旧保存晚回、取消/关闭、角色/世界/服务器切换、删除后旧结果到达。可接受的“缺失默认值”不能吞掉应保护原件的损坏或未知格式。删除/清除后旧快照是否能复活，是比多跑几个普通保存更有判别力的交错。

只改页面提示不自动触发schema迁移或跨角色存档实验。存储格式或自然scope改变时，才需要真实文件、隔离数据、恢复和权限证据；不得直接用玩家真文件试坏路径。

入口：[地图合同](../功能介绍/地图标记与揭示区域统计行为合同.md)、[地图设计](../设计/地图标记与揭示区域统计实现设计.md)、[足迹设计](../设计/足迹记录路线与回放实现设计.md)、[笔记设计](../设计/笔记功能实现设计.md)、[蓝图采集合同](../功能介绍/蓝图采集行为合同.md)、[蓝图采集设计](../设计/蓝图采集实现设计.md)、[配置与数据布局](../设计/配置持久化与用户数据布局.md)、[持久状态经验](信息地图与持久状态.md)。

### 6. worker、异步取消与旧结果

真实链通常是：owner发出准确请求 → 不可变输入/serial与generation → 有界队列或现有调度 → 计算/I/O → 发布前核身份 → 游戏线程owner接收 → 当前状态提交/释放。后台不得把live Terraria object当可变共享事实；相关界限见[游戏线程与后台工作](../设计/总体架构与状态所有权.md#15-游戏线程与后台工作边界)。

区分取消前已受理写入、尚未发布读取、同身份新revision、不同世界/Runtime、最后引用退出、排队背压、失败与真正空结果。条件性例子：按钮关闭只撤展示需求，若已受理保存仍有收尾责任，就不能把关闭一律解释成撤销字节写入；相反，旧读取不能覆盖新编辑。

若只是纯同步算法、没有异步结果传播，不需要建立取消矩阵。需要取证时优先用现有可控请求/发布接点和身份反例，不为每个worker新增平台、全局事件总线或常驻重放器。

入口：[状态矩阵](../设计/总体架构与状态所有权.md#12-完整状态所有权矩阵)、[Session生命周期](../设计/总体架构与状态所有权.md#14-session-生命周期)、[蓝图投影设计](../设计/蓝图世界投影实现设计.md)、[笔记设计](../设计/笔记功能实现设计.md)、[持久状态经验](信息地图与持久状态.md)。

### 7. 联机权威、请求与回包

真实链通常是：本地观察/请求 → 原版协议和当前连接身份 → 主机/服务器执行 → 明确回包或原版规定的同步方式 → 真实扣料/世界结果 → 远端与用户所见 → 断线/移除后的有限责任。Host&Play同进程不合并客户端和主机角色。

按具体协议区分有明确ACK与无独立ACK、本地预测/最终结果、成功/明确拒绝/无法关联、重复/迟到包、同坐标新请求、禁用功能后旧请求仍在途。没有原版ACK的分支不能被人为统一成永远pending；已有明确回执也不能仅看本地变化就宣告成功。

纯本地只读文本或纯值逻辑没有新的网络传播时，不机械要求真人多人。若交付主张就是房主/客机可用，相关真实拓扑证据仍需按合同取得；mock、发送成功或单人运行不替代它。关闭新动作也不自动解除已发请求的扣料/关联责任。

入口：[技术平台的多人拓扑](../规范/技术平台与兼容规则.md#九单人与多人拓扑)、[架构结果语义](../设计/总体架构与状态所有权.md#174-结果语义)、[物品与权威经验](物品箱子与多人权威.md)、[投影合同](../功能介绍/蓝图世界投影行为合同.md)、[工具设计](../设计/工具与自动采集实现设计.md)。

### 8. 性能、开关、事件失效与长期重复成本

真实链通常是：需求/开关与共享消费者 → 调度/cadence → 实际扫描/分配/I/O → 缓存key与freshness → 事件失效 → 重复更新成本 → 关闭、在途收尾和最后引用释放。先指出在哪个当前路径产生什么成本，再选择证明方式。

可区分关闭且无责任、关闭但有限在途责任、稳定无变化、相关dirty、无关dirty、局部变化、大量合法内容、预算暂停后续办与自然退休。调用次数、扫描步数和分配断言可证工作量；FPS、帧时或真实延迟需要相应测量，不能互相替代。

用户报告“一阵一阵”“偶尔停住”“反复回首”时，还要观察事件顺序与可执行机会。先找哪个真实消费者在什么条件下本来可以继续，再对齐后继准备、源／缓存当前性、输入门与消费回执；平均吞吐、小图最终完成不能单独证明没有反复空档。相同实际物品、增益和可达条件的原版基线可判断额外等待，不同工具切换则保各自合法时序。

必要 I/O、原版冷却或一次合理初始化不是自动缺陷；同一否定事实按候选种类重复并耗尽预算、拖晚已有合法后继，则有明确因果。结构成本、工作量、真实延迟与帧率分别下结论，证据足够就关闭对应机制；剩余用户症状沿最短判别路径调查，不让一个确定的局部修复代签其它原因，也不扩成全项目永久时序审计。

条件性例子：补料后应醒来与缺料时不反复全扫需要同时看资格wake、有效来源和候选进度；一个旧dirty标记不能单独证明无限循环，要查是否持续重新授予同一批工作。有限观察、必要收尾与已有共享Hook常数早退不等于性能Bug，也不新造所有路径零成本承诺。

只有文案或不影响成本的局部修改时，不默认重做基准/FPS。共享高频输入、布局、worker或缓存失效机制变化，按[性能规则](../规范/性能治理规则.md)及[工作量入口](../设计/高频路径工作量回归.md)选择真实受影响责任，不以同程序集指纹变化把所有证据作废。

入口：[性能规则](../规范/性能治理规则.md)、[架构观察与cadence](../设计/总体架构与状态所有权.md#16-游戏观察模型)、[绘制资源经验](绘制分层与图形资源.md)、[行为验证经验](行为验证与假绿辨别.md)。

### 9. 加载、安装与恢复仅在对应任务触发

加载/兼容机制、程序集身份、首个Hook、交接时机、安装工具或受控文件恢复发生变化时，真实链包括宿主身份 → 就绪 → Hook提交 → Runtime交接 → 失败隔离 → 受控安装/备份/恢复。要区分源码、包字节、实际安装和普通加载；源码删除不等于已安装诊断退出。

这些是相应高风险任务的责任，不是每次功能审查的额外第二安装审计。普通文档加入或仅Git身份变化，在产品和构建输入未变时不触发重复重建。业务窄修仍需取得实际影响所需的构建、验证和包资格；已有证据成立后，不因追加审查或合并重复重建，也不另加第二安装/恢复审计。实际安装与玩家数据权限仍由原授权和工具安全门决定。

入口：[技术平台规则](../规范/技术平台与兼容规则.md)、[最小原版加载链](../设计/最小原版加载链验证.md)、[构建与骨架](../设计/可重复构建与项目骨架.md)、[初始化经验](初始化与原版调用时序.md)、[测量退出与假绿经验](行为验证与假绿辨别.md)。

## 九、案例怎样使用，怎样避免倒写历史

### 固定版本案例：原版1.4.5.8平台

平台目标的坡号、玩家朝向和Smart路线二维运动不是同一事实。自然Lookup可能保留旧连续锁，两个同材料但不连续的几何段因此与同段后继不同；原版Spin还可能修改有限邻格。一个“向下三格成功”的样本不能单独证明上坡、双端缺口、暂平后继成坡或邻格权限。

可据真实机制选择代表：自然Lookup成功与原体被跳过；同段与独立新段；允许的图纸邻写与范围外/永久mask/原本要求平形；实际消费、合法FrameX连接变化、最终完整Match。这里说明如何选不同语义分支，不要求所有平台图形全排列，也不把平台坡3/4新增为普通锤击承诺。

该版本知识的当前落点是[蓝图经验](蓝图多格物体与镜像.md)、[工具经验](工具与自动采集.md)、[投影合同](../功能介绍/蓝图世界投影行为合同.md)及其设计。固定版本案例不承载当前PR、包、安装或测试流水。

### 其他类型的条件性案例

- **UI例子**：若布局在Prepare后被滚动改变，截图正常不能证明释放命中仍正确；检查几何身份与原armed责任即可，不因此查全部世界动作。
- **保存例子**：若旧保存回执到达时已有新编辑，保存成功应确认它实际写入的revision，不能清掉新编辑的dirty；旧/新revision交错比重复普通保存更有判别力。
- **物品例子**：若原版整堆合入直接增加接收者而不减少incoming计数，仅看incoming减少会错过来源转移；需核真实helper和接收端变化，不能认领所有同型堆。
- **预测例子**：若测试期待由同一预测公式生成，公式与测试可以同时错；选一个独立原版阶段或几何事实反证，而不是增加更多同公式样本。

这些条件性例子不指控对应现实现有Bug。历史案例的准确来源见相应经验正文。没有读到某次原审查全文、原任务和具体提交时，不推断审查者当时是否看过、是否受压缩/模型设置影响或为什么遗漏。后来发现可能来自旧窄覆盖、上游错误oracle、原版新证据、新功能扩大或修复引入交互；需要版本事实才能区分，不能把后来新增需求倒写成旧Bug。

## 十、有限证据、失败分类与复用

遇到红灯先确认：失败对象和候选身份是什么，实际运行了哪个入口，输入和断言是否代表目标，异常来自产品、测试设施还是环境。一个大组FAIL不是所有分项都错；某些分项成立也不能把整组改签PASS。

| 证据 | 可以支持 | 不自动支持 |
| --- | --- | --- |
| 明确静态路径/结构 | 可达因果、所有权、分支与确定违约；或明确结构事实。 | 游戏加载、真实体验、所有拓扑与性能。 |
| 纯值/单元检查 | 给定输入与断言的隔离逻辑。 | 原版Hook、真实UI、文件权限或多人权威。 |
| 原生组件/消费者检查 | 实际执行到的原版阶段、组件组合及断言。 | 完整Main/Draw、真实桌面输入、真人网络或普通安装。 |
| 文件/包/安装回执 | 相应字节、目标和工具实际完成的动作。 | 产品行为、体验及其它候选。 |
| 玩家实机反馈 | 实际报告的版本、场景和结果。 | 未说明的方向、数量、环境、多人、FPS或所有边界。 |
| 测量 | 指定方法和场景的成本/延迟等指标。 | 任意输入、所有机器或正确性不变量。 |

测试期待确实错误可以修正，不能为变绿降低当前行为；修改理由应由独立合同或事实支持。等待上限本身不是产品时限，除非合同或独立要求明确规定；有持续进展的超时不能单独证明永不完成，也不能把它改称已完成。实际失败原件保留，调查哪个原因仍未决，选择能区分它的最短手段。

复用取决于相关语义、输入、断言、运行环境/身份、owner和证明前提是否仍适用。纯导航、交付事实回写或无关字段变化，不机械作废原产品证据；共享消费者或测试期待改变，则沿真实传播补未覆盖或失效部分。保留原执行提交、dirty状态和环境，不将复用写成本轮亲自执行。

完整责任可以由有效的完整审查、增量复核和不同层证据组合。缺关键部分仍准确标未完成，不用空子集、测试名、大量弱证据或分组重命名制造完成。规则详见[原始证据与正式结论](../规范/测试与审计规则.md#十四原始证据与正式结论)和[任务验收与广泛回归](../规范/测试与审计规则.md#任务验收与广泛回归)。

## 十一、怎样写结论，何时停止与重开

### 让读者看得见判断边界

一份有用的结论通常能说明：审查模式、固定候选与整批/专题范围；使用的原目标和合同；实际查到的关键链；确认问题与具体风险/假设/建议/接受边界；排除线索的依据；执行、复用、记录声明与未知各是什么；有限关闭条件或停止理由。

无需逐命令日志，也不必把每个未涉及轴都列成待办。可以使用下面的短表达，再按任务补足必要事实：

> 在指定候选和范围内，已核用户入口、相关共享机制、实际消费者及恢复责任。未发现可确认缺陷／发现以下具体问题。该结论由哪些静态与运行证据支持；哪些现有线索已被哪些保护排除；未证部分只限制哪些主张。下一步若有，能够回答哪个尚未决的问题。

### 以证据充分结束，以新事实重开

沿[必要性、判别力、相称性与收敛性](../规范/测试与审计规则.md#十二时间和成本边界)判断下一步：

- 缺失它会改变哪个当前用户结果或交付决定？
- 它能区分哪个未决原因，或覆盖什么不同失效机制？
- 最小可靠手段是什么，成本是否与后果相称？
- 它仍服务当前目标，还是已经变成另一个设施/审计工程？

当前必要责任有足够证据、相关确认缺陷已关闭且没有决定性未证前提时，可以结束。仍有关键缺口而环境/授权不能取得时，准确结束为对应部分未知、未完成或受阻；不填PASS，也不清零其它独立成立证据。停止扩张不放行确定缺陷，停止盲试也不停止其它独立授权工作。

新可靠玩家报告、原前提被推翻、保护失效、共享机制/消费者改变、目标版本或支持边界变化、修复进入新语义分支、原证据适用性失效、所有者改变目标或接受边界，均可能重开相应责任。

仅换会话/审查者、报告没有Bug、还能想到抽象风险、同机制换一个名字、无关hash变化或“尚不能证明绝对安全”，不独立构成重开理由。返修只复核实际修订、必要传播和未决点，闭合后不重复审查无变化部分；不按固定分钟、轮数或Bug数量签通过。
