# ADR-0012：关键注释同次交付与五个底线路由

- 状态：Proposed
- 日期：2026-09-06
- 对应任务：[关键代码注释落实与开发入口一致性补全 #32](https://github.com/Kuroneko2020/JueMingR/issues/32)
- 对应条款：[工程治理规则](../规范/工程治理规则.md#关键注释与同次交付待接受补充)、[文档治理规则](../规范/文档治理规则.md#同一任务的同步责任待接受补充)

## 背景

当前已有加载链、群系显示和 F5 基础。项目所有者要求现在补齐既有关键位置的说明，并让新实施者与审查者从仓库和 Issues 恢复读取要求。Legacy 五个底线中的注释目标是说明契约、边界、原因和易误改点，不是增加注释数量；其旧类名、审计设施和历史流程不构成新版依赖。

## 候选决定

将关键注释纳入代码变更的同次交付和既有独立审查；根 AGENTS 提供性能、功能、注释、指令风险、职责边界五个短入口，细则仍由各领域现有文档承担。文档同步责任随事实变化触发，动态状态继续只由 Issues 记录。

本补充不重做性能、功能、风险和架构治理，不证明既有实现全部合规。注释规则不替代类型、测试或设计；不强制逐行注释、不设比例或关键词门、不翻译全仓，也不建立永久注释台账、专用审计器或新审批角色。网页 ChatGPT 仍为可选辅助。

## 代价与替代方案

维护者需要在同一任务维护受影响的说明，审查者需要核对准确性；局部短注释与正式设计分工可限制重复成本。拒绝仅提出未来建议、每处都写说明或复制旧版制度：前者留下现有缺口，后两者制造噪声和维护债。

## 接受与演进边界

本 ADR 保持 Proposed，新增条款保持待接受；现有工程与文档治理规则继续有效。只有经独立语义审查、项目所有者接受并授权机械最终化、最终化窄审和明确合并授权，合并进入 `main` 后新增长期要求才生效。候选完成不授权后续功能或发布。

以后可通过正常受控修改调整或撤销本补充；实质决策变化按现有 ADR 演进规则办理，不静默改写已接受历史。
