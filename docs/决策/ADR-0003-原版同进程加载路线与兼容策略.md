# ADR-0003：原版同进程加载路线与兼容策略

- 状态：Accepted
- 日期：2026-08-29

## 背景

JueMingR 是 JueMingZ 的完整重写，但产品仍服务原版 Terraria，不把玩家迁移到 tModLoader，也不建设服务器端产品组件。

TerrariaHelper 是 JueMingZ 最初效仿的原版同进程加载基线。JueMingZ 在长期演化中形成了有现实故障证据支持的必要增量，也积累了多重 fallback、宽泛程序集解析、部分状态和不安全安装恢复等加载技术债。

Phase 0-G.1 对 TerrariaHelper、早期 JueMingZ 和当前 JueMingZ 完成了 31 项差异审计。该矩阵留在研究材料中，本 ADR 不复制完整矩阵，只记录项目所有者已经接受的长期路线选择。

当前 TerrariaHelper 材料主要是二进制发行物、反编译输出和说明文本，没有发现其自身明确允许复制、修改和再分发的源码许可证。Harmony 等可识别第三方组件的许可证只覆盖各自组件，不能外推到 TerrariaHelper 整体。

研究时，Legacy 编译引用快照为 Terraria 1.4.5.7；项目所有者已在 Terraria 1.4.5.8 上确认 JueMingZ 能加载和运行。两项证据的范围不同，且当前研究只证明静态路线与版本表面，不是 JueMingR 加载器、全功能、多人、性能或发布验收。

## 决策

1. JueMingR 保持原版 Terraria 客户端辅助工具身份，不依赖 tModLoader。
2. 采用与 TerrariaHelper 同源的原版 `Terraria.exe` 同进程加载路线；“同源”只指技术路线，不表示复用其代码或实现来源。
3. 使用 clean-room 方式重新实现加载链，不复制 TerrariaHelper 反编译源码、资源或无授权实现。
4. 以受控 config、最小 AppDomainManager、最小早期初始化、明确核心门槛、单一上下文 Harmony 可达性、经验证宿主回调和一次性 Runtime 交接组成的最小职责链为基线。
5. 只吸收有现实证据证明必要的 JueMingZ 增量，不复制当前 JueMingZ 全套复杂加载链。
6. 核心与功能采用两级能力探测：核心失败时整体不激活，单项失败时安全关闭相应功能并说明原因。
7. 产品默认面向 Terraria 官方最新稳定版；验证记录绑定精确游戏版本、程序集身份、环境、渠道和场景。
8. Windows 10 和 Windows 11 是主要测试范围；旧 Windows 按 CLR、API、宿主、权限和位数能力判断，不只按版本号封锁。
9. Steam 与 GOG 默认渠道中立并共用产品实现；只有实际差异才拆分兼容记录。
10. 单人以客户端本地完整功能为目标，Steam Host & Play 和客户端连接独立专服进入验证矩阵。
11. JueMingR 只安装在客户端，不建设专用服务器组件；多人能力按功能调查权威与最终结果。
12. 安装必须具备预检、冲突保护、原子写入、精确进程外恢复和幂等卸载。
13. 第三方依赖从官方上游获取，固定身份并履行许可证、notice 和分发义务。
14. 具体约束以 [技术平台与兼容规则](../规范/技术平台与兼容规则.md) 为准。

## 被拒绝的方案

### 改为 tModLoader Mod

拒绝。该方案会改变产品身份和玩家安装前提，不能满足继续服务原版 Terraria 生态的已定目标。

### 直接复制 TerrariaHelper 反编译代码

拒绝。当前材料没有建立源码复用授权，反编译输出也不是可验证的作者源码；路线知识可以参考，具体实现必须 clean-room 重写。

### 直接复制当前 JueMingZ 复杂加载链

拒绝。该方案会同时继承必要经验和已识别技术债，无法满足最小、单一、可审计和可恢复的目标。

### 发明新的第三套注入体系

拒绝。既定同源路线已经提供可解释的必要职责；没有现实需求证明另造体系的额外复杂度和风险有收益。

### 无实际收益时引入 x64 外部控制面和 IPC

拒绝。它不会消除游戏内桥受 32 位宿主和 Terraria ABI 约束的事实，却会增加跨进程协议、部署和故障面。未来出现独立收益时必须另立决策。

### 按未知游戏版本号无条件硬封锁

拒绝。版本号不是完整能力证明；未知版本应进入核心和功能两级能力探测，同时不得被冒充为完整支持。

### 只按 Windows 版本号硬封锁

拒绝。实际约束来自 CLR、Windows API、宿主、权限和依赖位数；厂商生命周期不能替代程序能力判断。

### 预先维护 Steam/GOG 两套实现

拒绝。安装路径和渠道标签不能证明运行 ABI 不同；只有实际程序集或行为差异才能支持拆分。

## 结果

优点：

- 保留原版 Terraria 产品、启动和联机身份；
- 复用已证明的加载路线知识，同时清理长期加载债；
- 通过核心和功能能力门使版本兼容与降级更可观察；
- 安装失败具有进程外恢复路径，卸载不依赖宽泛删除；
- 多人能力按功能和权威结果验证，不在设计阶段全局猜测。

代价：

- 游戏内桥仍受 32 位 .NET Framework 宿主和 Terraria 内部 ABI 约束；
- 每次游戏更新都需要重新进行能力探测与实机验证；
- clean-room 实现增加前期分析和实现成本；
- `AppDomainManager` 与 config 仍存在 Terraria 自身逻辑开始前的启动失败风险；
- 项目必须维护进程外安装恢复工具以及第三方许可证材料；
- 多人完整度只能通过逐功能、逐拓扑证据积累。

## 后续验证门

进入正式生产加载链实施或作出发布支持声明前，至少需要在独立授权的工作中建立以下证据门：

- 精确目标游戏版本的最小 Hook 验证；
- Harmony 单一上下文装载验证；
- config 冲突、安装中断和失败恢复验证；
- Windows 10/11 最小加载验证；
- Steam 正常启动、Overlay、成就和原版身份验证；
- Steam Host & Play 与客户端连接独立专服验证；
- 未测试游戏版本的核心能力门验证。

完成这些门槛所需的最小验证原型同样必须另行授权；原型及其证据不自动授权生产实现。

本 ADR 不授权当前执行上述验证，不授权创建项目骨架、加载器、安装器、依赖或生产代码。

## 被替代方式

本 ADR 不替代 ADR-0001 或 ADR-0002；它只决定技术平台、加载路线和兼容策略。

若产品身份、同进程路线、clean-room 边界或兼容策略发生实质变化，应创建新的 Accepted ADR，明确替代范围、迁移方式和关联规则更新。本 ADR 随后标记为 `Superseded` 并链接到新 ADR，不得静默改写原决定。
