# ADR-0007：版本、配置与发布采用分层身份和显式迁移

- 状态：Proposed
- 日期：2026-08-31
- 对应任务：[Phase 0-N Issue #14](https://github.com/Kuroneko2020/JueMingR/issues/14)
- 对应规则草案：[版本、配置与发布规则](../规范/版本配置与发布规则.md)

## 背景

JueMingR 需要在进入项目骨架、Legacy 数据迁移和真实发布之前，先明确“哪个源码”“哪个构建”“用户看到哪个版本”“配置是什么格式”“在哪个 Terraria 环境验证过”和“正式发布了什么”分别由什么身份承担。

这些问题若共用一个号码，会产生无法裁定的状态：一个 commit 可能从未发布；多个 commit 可以组成一次发布；产品升级可能不改变配置；配置迁移可能独立于用户功能；同一程序集版本可能覆盖多个修复构建；编译引用版本也不能证明真实 Terraria 环境已经验证。

Legacy 的代表性样本同时展示了正面机制和缺口：

- 源码、运行时 token、程序集版本、测试包 manifest 和更新记录曾交叉核对，能够暴露版本链脱节；
- 测试包 manifest 记录了 DLL SHA-256，却没有来源 commit，因而不能从包本身证明精确源码；
- 当前 Legacy 没有 Git Tag 或 GitHub Release 作为公开发布锚点；
- 部分配置读取能区分缺文件和损坏，并在损坏时保护原件；
- 部分蓝图导入会拒绝未知未来 schema，笔记复合写入有失败回滚；
- 但未知未来 schema 的拒写、schema 校验和严格原子替换并未在所有配置合同中一致成立。

外部官方资料说明了各机制的职责边界：

- [Semantic Versioning 2.0.0](https://semver.org/) 用 `MAJOR.MINOR.PATCH` 表达已经定义的 public API 变化，并明确已发布版本内容不得修改；它不会替项目定义配置、游戏环境或用户行为兼容合同。
- [Git Tag 文档](https://git-scm.com/docs/git-tag)把 annotated tag 定位为适合发布的、带元数据的对象；Tag 锚定 Git 对象，不证明二进制如何构建。
- [GitHub Releases 文档](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)说明 Release 基于 Tag，负责发布说明和可下载资产；普通 Release 的可编辑能力不等于资产不可变。
- [Microsoft .NET 版本指南](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/versioning)区分程序集身份、Windows 文件版本和说明性版本；三者不是同一个字段。
- [C# 确定性编译文档](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-options/code-generation)与 [Source Link 文档](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/sourcelink)表明确定性和来源元数据是相关但不同的能力：相同输入可得到相同输出，不代表 commit 已自动记录。
- [JSON Schema](https://json-schema.org/understanding-json-schema/reference/schema)可以声明 schema dialect，[System.Text.Json 未映射成员文档](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/missing-members)则说明未知字段可能被默认忽略；二者都不提供适用于所有产品的迁移、备份、降级和旧程序写回政策。

配置迁移没有统一通用答案。JueMingR 必须根据自己的用户数据、失败恢复和降级风险建立项目合同，不能把序列化库的默认行为写成产品保证。

Phase 0-N 是最小工程治理试运行的第三个真实任务。本 ADR 只提出治理决策，不创建实际版本、Tag、Release、发布资产、迁移器、构建系统、CI 或生产代码。

## 决策草案

1. 分离源码、构建、产品、schema、Terraria 兼容和正式发布六种身份；任何一种身份都不能冒充另外五种。
2. 产品版本只在明确获准的真实发布准备中确定和推进；内部任务、Issue、PR、commit、文档、测试、审计、构建和打包都不自动推进产品版本。
3. JueMingR 不继承 JueMingZ 的产品版本号。
4. JueMingR 使用 `MAJOR.MINOR.PATCH` 作为自己的用户版本规则：`MAJOR` 表示需要用户明确注意和接受的不兼容产品变化，`MINOR` 表示保持既有合同和升级路径的新增用户价值，`PATCH` 表示不破坏既有用户合同的修复。当前不承诺严格 SemVer public API 模型；schema 和 Terraria 兼容变化不机械决定段位，`0.x` 仍遵守已承诺边界，同一变化按最高实际用户影响判断；难以判断时只由项目所有者裁决用户发布意义，不把内部实现判断转交给项目所有者。
5. 完整构建身份必须绑定来源 commit、clean/dirty 及 dirty 输入身份、构建类型与目标、可复核工具链、构建入口、影响输出的主要参数、编译引用与第三方依赖、外部构建记录时间、产物清单和 SHA-256。无法为 dirty 未提交输入建立不可歧义身份时，产物只用于当次探索性诊断，不能升级为 clean 候选证据或正式发布候选。记录 commit、确定性构建和哈希各有边界，均不能单独证明来源可信、正确、安全或已批准；具体工具和 manifest 形式延期决定。
6. `AssemblyVersion`、`FileVersion` 和 `InformationalVersion` 的精确映射延期到项目骨架阶段；后续必须使用一个权威版本输入，并让产物显示产品版本和 commit。
7. 需要长期维护的持久化合同使用独立 schema；不同数据合同可以独立演进，不要求所有配置、日志和临时文件共用一个机械版本。
8. schema 迁移必须显式、有序、来源只读、先验证、在隔离结果中完成、保留可恢复原件并能安全重复执行。单文件迁移与多文件一致性单元必须分开；后者要定义整体验证、明确切换点、中断状态、恢复和幂等，不能把逐文件原子替换当作整组原子。
9. 来源身份条件必须从最终复核原子地延续到事实源切换完成；紧邻切换的普通“先检查、后替换”不足以证明没有并发覆盖。无法保证条件式或排他切换时，只保留隔离候选并报告冲突，不自动覆盖当前事实源；具体锁、API 或事务延期决定。
10. 旧程序遇到未知未来 schema 时默认拒绝写回原文件；反序列化器忽略未知字段不能证明无损兼容。
11. 从 JueMingZ 导入数据与 JueMingR 自身 schema 升级分别记录；本 ADR 不设计具体 Legacy 数据映射。
12. 正式发布绑定产品版本、指向精确 commit 的版本 Tag、对应 GitHub Release、发布资产、SHA-256、验证范围和项目所有者明确批准。
13. 需要项目所有者 Terraria 实机证据的正式发布必须建立“受测资产—最终资产”字节级闭环：直接提升通过全部门的同一字节 clean 候选，或以受控的确定性/可重复构建证明重建资产字节等价；不能证明等价时必须对最终字节重新执行相应验证，不能只绑定同一 commit。
14. 已发布资产不得在同一产品版本下静默替换；已发布 Tag 不得移动。修复、撤回和替代必须保留可识别历史。
15. 发布说明只记录用户相关变化、配置影响、兼容变化、已知问题和必要操作；内部提交、审查和完整测试流水由 Git、Issue、PR 和 ADR 保存。
16. 本 ADR 不授权创建产品版本、Tag、Release、发布资产、Changelog、配置迁移器、构建、打包、CI、项目骨架或生产代码。

具体执行边界见[版本、配置与发布规则草案](../规范/版本配置与发布规则.md)。只有本 ADR 被项目所有者接受、文档入口受控更新且相关提交合并到 `main` 后，该规则才生效。

## 被拒绝的方案

### 继续使用 JueMingZ 版本号

拒绝。JueMingR 是独立重写，版本号若延续会让用户误以为实现、数据和兼容承诺连续，也会把 Legacy 内部阶段历史带入新产品。

### 每个 commit 或内部任务推进产品版本

拒绝。commit 是源码身份，任务是协作边界。二者数量与用户发布价值没有一一对应关系，会使版本号变成内部进度计数器。

### 用一个版本号同时表示产品、配置、Terraria 和构建

拒绝。这四类对象独立变化。单号会让“产品不变但 schema 迁移”“同一产品重建”“同一源码验证多个 Terraria 环境”等事实无法准确表达。

### 把项目所有者测试包称为正式发布

拒绝只改变称呼并跳过发布门。测试包用于收集指定实机证据，可能仍有未验证轴，也没有正式 Tag、Release、发布说明和发布批准；但同一字节的 clean 候选在满足全部发布门后可以提升为正式资产，不需要在实机后强制生成一份未经测试的新字节。

### 配置损坏后自动重置并覆盖

拒绝。解析失败不等于文件不存在。覆盖会销毁诊断和恢复所需的原件，并可能把短暂权限或格式问题扩大成永久数据损失。

### 让旧程序写回未知新 schema

拒绝。旧程序可能忽略新字段或改变新语义，写回会静默丢失未来数据。除非未来合同明确证明无损 round-trip，否则必须拒写。

### 所有配置文件共用一个机械版本

拒绝。不同长期数据合同具有不同 owner、风险和演进速度。全局版本会制造无关迁移和耦合；日志、缓存和临时文件也不需要机械加入长期 schema。

### 在同一版本下静默替换发布资产

拒绝。相同版本号指向不同字节会破坏复现、故障定位、哈希核验和用户信任。平台允许编辑不代表项目应该这样做。

### 现在建立完整自动发布流水线

拒绝。当前没有项目骨架、真实构建输入或首个发布候选，无法用实际风险校准流水线。提前实现会越过授权并形成维护负担。

### 每个内部变化都写入 Changelog

拒绝。Git、Issue、PR 和 ADR 已保存内部历史；把全部内部活动复制到 Changelog 会建立第二套历史，并使用户找不到真正相关的发布变化。

## 优点

- 每个测试包和正式资产都能明确回答“哪些源码、工具、入口和参数形成了什么字节”。
- 产品版本只表达用户发布，不再被内部阶段和绿灯推动。
- 受测资产与最终资产通过同一字节或可重复构建等价证据闭环，避免把未经相应验证的新字节提供给用户。
- 配置损坏、旧 schema、未来 schema、权限和并发冲突能够分别处理；多文件一致性和提交期并发不会被单文件原子替换掩盖。
- Tag、Release、资产和哈希形成可交叉复核的发布链。
- 编译引用和项目所有者实际 Terraria 场景分别记录，减少兼容结论升级。
- 发布说明保持面向用户，内部历史留在已有权威载体中。
- 规则规定最低信息而不预建自动化，便于在真实发布中校准成本。

## 代价

- 后续构建需要记录 commit、clean/dirty 及 dirty 输入、目标、工具链、入口、主要参数、引用与依赖、外部记录时间和资产哈希。
- 每个长期持久化合同需要明确 schema 状态和迁移失败行为。
- 安全迁移需要临时结果、目标验证、备份、单文件原子替换或多文件一致性协议，以及从来源复核延续到事实源切换的并发冲突保护，比直接覆盖更复杂。
- 正式发布前需要整理兼容、验证、许可证、恢复和资产信息。
- 需要实机证据的发布还要记录受测资产与最终资产的哈希关系；重建不能证明字节等价时需要重新验证最终字节。
- 同版本不能替换资产意味着小修复也通常需要新产品版本。
- 首次项目骨架和真实发布准备仍需决定程序集映射、Tag 命名、版本输入和工具实现。

## 后续验证门

本 ADR 仍为 Proposed。接受前必须完成：

- 一个未参与起草的全新 Codex 对话独立审查；
- 对六种身份是否真正互不冒充的反例检查；
- 对产品版本三段语义和构建输入身份是否可执行的检查；
- 对未知未来 schema、损坏、权限、多文件中断、并发修改和迁移失败的安全边界检查；
- 对受测资产与正式发布资产是否形成字节级闭环的检查；
- 对 Tag、Release、资产、哈希和撤回规则是否可复核且不过重的检查；
- 项目所有者对规则成本与产品边界的复核。

本 ADR 被接受后仍不表示版本系统已经实现。后续至少需要两个独立验证阶段：

1. 在获准的项目骨架任务中确定版本输入、程序集映射和来源元数据方式；
2. 在第一次真实发布准备中确定首个产品版本、Tag 命名、Release 过程、实际产物和验证矩阵。

配置迁移器必须等到具体数据合同和迁移任务获准后设计。第一次实现应以损坏、未来 schema、多文件切换中断、最终复核与切换之间的并发修改、落盘失败和重复执行为主要反例，不能只验证成功路径。

## 接受与替代方式

只有项目所有者明确接受后，才可将本 ADR 状态改为 `Accepted`。同一收口任务必须更新 `docs/README.md` 的正式入口，并将规则与 ADR 合并到 `main`；在此之前，规则保持草案且不生效。

若独立审查或项目所有者拒绝本方案，本 ADR 保持 `Proposed` 或改为 `Rejected`，不得以本草案授权实现。

若未来实质改变六种身份、产品版本推进与段位语义、构建身份最低输入、未知 schema 拒写、显式迁移及多文件一致性、来源条件式切换、受测资产与最终资产闭环、正式发布锚点或资产不可静默替换原则，应创建新的 Accepted ADR，明确替代范围，并将本 ADR 标记为 `Superseded`；不得静默改写原决定。
