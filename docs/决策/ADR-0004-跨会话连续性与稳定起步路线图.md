# ADR-0004：跨会话连续性与稳定起步路线图

- 状态：Accepted
- 日期：2026-08-30

## 背景

Codex 和网页 ChatGPT 的上下文有限，聊天可能被压缩或丢失。若项目方向、当前状态或授权边界只存在于对话中，新 Agent 无法可靠恢复工作，项目所有者也会逐渐变成多个 Agent 之间的人工传话者。

Legacy 曾同时使用大型 handoff、状态文件、更新记录和多个事实源，增加了检索、同步和冲突成本。JueMingR 已通过 [文档治理规则](../规范/文档治理规则.md) 和 [ADR-0001](ADR-0001-文档体系与受控演进.md) 将稳定事实放入 Git、动态任务状态放入 GitHub Issues；在正式代码起步前，还需要建立可由仓库和 Issues 独立恢复的连续性系统。

## 决策

1. 新增 `docs/计划/` 一级分类，保存已经批准、在相应活动期内有效的高层计划、阶段目标和退出条件；当前首份计划为 [稳定起步路线图](../计划/稳定起步路线图.md)。本路线图与稳定起步总跟踪 Issue 对应，达到稳定起步后按文档治理规则提炼长期结论并退出当前路由。
2. 稳定起步路线图只记录阶段、依赖、退出条件和稳定起步定义，不记录当前任务、阻塞或逐次更新。
3. 项目级动态状态只由 [“JueMingR：稳定起步总跟踪”Issue](https://github.com/Kuroneko2020/JueMingR/issues/7) 承担。
4. 具体任务状态和授权只由当前任务 Issue 承担。
5. Git commit 证明实际文件变化；聊天、对话摘要和本地 handoff 不是权威事实源。
6. 新 Codex 和网页 ChatGPT 使用同一冷启动顺序：仓库入口、文档入口、路线图、总跟踪 Issue、当前任务 Issue、任务所需规范与 ADR、Git 状态。
7. 路线图可以受控调整，不是永久施工合同。实质调整必须使用专门 Issue，并由项目所有者批准。
8. 不建立巨型 `AI_HANDOFF`、`CURRENT_STATUS` 或逐步骤更新记录，不让单个文件同时承担规则、历史、路线、当前状态和任务交接。
9. 项目所有者负责产品方向、可见结果和差异验收，不承担工程 Agent 之间的人工消息转发职责。
10. 达到稳定起步后，总跟踪 Issue 以 `completed` 关闭，本路线图退出当前路由；后续长期项目状态系统另行决定。

## 被拒绝的方案

### 继续依靠聊天记忆

拒绝。聊天会被压缩、截断或丢失，不能形成可审计的长期授权和当前状态。

### 建立包含全部状态和历史的巨型交接文档

拒绝。它会混合规则、路线、当前状态、历史和任务细节，并重新产生同步负担和多事实源冲突。

### 只使用 Issues，不建立高层路线图

拒绝。Issues 适合动态任务状态，但不能稳定表达多个阶段之间的大致依赖、退出门和“稳定起步”的共同定义。

### 预先写死所有未来阶段和精确时间表

拒绝。当前路线只是最佳预测；过早固定顺序和时间会迫使现实迁就旧计划。

### 每个内部步骤都生成交接或更新文件

拒绝。该方式会把协作过程变成长期文档债，并使实际产品方向更难辨认。

### 让项目所有者手工维护多份状态副本

拒绝。重复维护容易漂移，也把工程协调成本转移给不应承担该职责的项目所有者。

## 结果

优点：

- 任一新 Agent 可以从仓库和 Issues 恢复上下文；
- 当前状态与长期路线分离；
- 项目所有者不再需要人工传递技术上下文；
- 路线图可以随证据受控调整；
- 聊天消失不会使项目方向一同丢失。

代价：

- 必须维护一个长期总跟踪 Issue；
- 阶段定义发生实质调整时需要更新路线图，当前阶段发生变化时需要更新总跟踪 Issue；
- 若执行者把动态状态复制到多个载体，仍可能重新产生冲突；
- GitHub Issues 和 Git 暂时成为项目连续性的外部依赖；
- 稳定起步后需要重新决定长期项目跟踪方式。

## 演进与替代方式

路线图结构或连续性职责发生实质变化时，可以由新的 Accepted ADR 明确替代本 ADR 的相应范围。普通路线图内容调整不要求新增 ADR，但必须有专门 Issue 和项目所有者批准，并在同一变更中更新相关路由。

本 ADR 不替代 [ADR-0001](ADR-0001-文档体系与受控演进.md)、[ADR-0002](ADR-0002-Legacy平替策略与行为契约方法.md) 或 [ADR-0003](ADR-0003-原版同进程加载路线与兼容策略.md)，也不决定生产架构或工程治理细节。
