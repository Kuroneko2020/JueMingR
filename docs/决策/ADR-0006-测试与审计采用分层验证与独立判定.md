# ADR-0006：测试与审计采用分层验证与独立判定

- 状态：Accepted
- 日期：2026-08-30

## 背景

Legacy 同时存在有价值的测试与测试、诊断和审计膨胀。纯逻辑测试、stub/fake 下的组件测试、源码字符串检查、合成性能循环和真实 Terraria 行为回答不同问题；它们不能因同为绿色就合并成一个“全部通过”。

Legacy 中也存在重要正面机制，例如测试输出与真实用户目录隔离、按路径缩小审计范围、fail-soft 契约，以及明确写出“本地验证不等于用户实机验收”。但静态文档中出现这句话仍不能证明实机已执行；结构检查必须停留在其证据上限。

实现 Agent 可能同时修改实现、测试和完成措辞。这样的同时修改在新需求、缺陷修复或测试设施修正中可以合法，但若没有独立判定依据，也可能形成“实现定义答案、测试再证明实现正确”的闭环。测试绿灯因此不能自动证明用户结果。

项目所有者曾经历约十五小时的更新审计负担。该时长是项目所有者体验，不是仓库精确计时数据。漫长检查不等于严谨；如果所有普通任务都运行全量检查，治理本身会成为成本和新的失败源。

Phase 0-M 是[最小工程治理试运行计划](../计划/最小工程治理试运行计划.md)的第二个真实任务。本 ADR 记录测试与审计治理方法，不决定具体测试框架，不创建测试、CI 或审计工具，也不授权生产实现。

## 决策

JueMingR 采用以下测试与审计基线：

1. 采用风险触发和分层验证，不让所有任务运行全部检查。
2. 静态结构、编译、单元、组件或集成、Terraria 实机、多人、性能、项目所有者验收和发布分别记录；任一层不得冒充另一层。
3. 自动检查只证明其实际输入、断言和环境。测试或审计通过不能自动证明产品完成。
4. 行为目标和测试判定依据必须独立于刚完成的实现；实现 Agent 可以写测试，但不能独占定义正确答案。
5. 测试期待变化必须说明哪个合同或事实改变、旧断言为什么不再正确，以及新断言的独立依据；已获授权且保持用户可观察行为、失败语义和安全边界不变的重构，可以同步调整结构性测试、fixture、测试构造和旧内部边界断言，但必须说明保持不变的行为、发生变化的内部事实、独立结构依据和替代覆盖，不得弱化行为、错误或安全断言。
6. mock、stub 和 fake 只证明模拟边界下的逻辑，不能称为真实 Terraria、文件系统、网络或多人证据。
7. 所有需要启动或操作 Terraria 的游戏内实机测试均由项目所有者亲自执行；Agent 只负责获授权的测试准备、普通语言步骤设计和回传证据分析。自动输入、脚本、机器人、回放、远程控制或 Agent 操作不能替代玩家实机和体验验收。
8. 项目所有者可以按具体任务选择主环境、安装副本、独立测试目录或沙箱，以及日常或专用角色、世界和服务器；不因游戏内虚拟物资可以损失而强制使用副本或沙箱。Agent 对任何外部文件和环境的写入仍必须由具体任务明确授权，准备环境不构成启动或操作游戏的授权。
9. Legacy 始终永久只读；测试环境、数据副本或实机授权不得改变该边界。
10. 项目所有者亲自执行并回报的指定游戏内实机场景，与项目所有者对实际用户体验和可接受差异的验收分别记录；一次操作可以提供两种证据，但前者不得自动升级为后者。
11. 不使用自然语言精确字符串、源码方法名、类或文件存在来证明语义合规；确定性结构事实仍可用最窄结构检查保护。
12. flaky、测试基础设施失败、环境不满足和产品失败分别记录；不得用重试把未知或失败改写为通过。
13. 快速检查用于当前编辑和相关提交；慢检查按风险进入专项、夜间、发布、实机或多人阶段，不阻塞无关普通任务。
14. 长期昂贵检查必须记录触发、成本、owner、真实捕获、误报/flaky 和退休路径；稳定基础原则不建立大型台账。
15. 覆盖率、测试数量、绿灯数量和自动审查评论不能单独作为质量或产品进展目标。
16. 自动检查和 AI 审查不替代项目所有者对用户结果、差异、风险和体验的裁决。

具体规则见[测试与审计规则](../规范/测试与审计规则.md)。本 ADR 已由项目所有者接受；对应规则随包含本 ADR、规则和路由更新的提交合并到 `main` 后生效。

## 被拒绝的方案

### 只要求“多写测试”

拒绝。更多可见测试可能增加局部覆盖，也可能放大对代理指标的过拟合；数量不能替代独立判定依据。

### 所有任务运行全部测试和审计

拒绝。普通文档、局部代码、共享基础设施、实机兼容和发布风险需要的证据不同。统一全量流程会让检查成本脱离风险。

### 用源码或文档字符串证明功能正确

拒绝。字符串适合少量确定性结构或精确用户文本合同，不能证明运行语义、Hook、多人、性能或用户体验。

### 让实现 Agent 单独定义并验证正确答案

拒绝。实现、测试和完成结论由同一闭环控制时，绿色可能只表示实现适配了当前可见断言。

### 以覆盖率或测试数量作为主要质量目标

拒绝。它们可以帮助发现未执行区域或覆盖缺口，但不能证明断言、oracle 和用户结果正确。

### 用自动重试掩盖 flaky

拒绝。偶然通过会削弱失败信号并隐藏产品、测试或基础设施根因。

### 把 mock 测试称为实机或多人验证

拒绝。模拟边界未执行真实游戏、权限、网络或权威同步。

### 把测试通过称为产品完成

拒绝。编译、自动测试、实机、多人、性能、所有者验收和发布是独立状态。

### 现在建立完整 CI 和测试平台

拒绝。当前尚未批准项目骨架和总体架构，也没有真实代码任务数据支撑具体框架、固定预算或门禁实现。

### 每次事故都永久增加一套审计

拒绝。重复门会增加噪声、误报和等待；应优先保留最接近事实的主门，并为持续检查设置退出路径。

## 优点

- 每项检查的结论受输入、断言和环境约束，降低证据夸大。
- 独立判定依据与测试期待变更说明降低自证和测试过拟合风险。
- mock、结构检查、实机、多人和性能证据边界清楚。
- 普通任务只运行相关检查，慢检查留给真正命中的风险和阶段。
- 长期检查有成本与退休路径，能够删除无价值或重复的门。
- 项目所有者只需判断产品结果、体验和成本，不承担测试技术选择。

## 代价

- 标准和高风险任务需要说明判定依据、检查范围和未验证项。
- 修改测试期待需要额外解释与审查，不能只展示绿灯。
- 高风险外部边界仍可能需要昂贵的实机、多人或发布验证。
- 游戏内实机需要项目所有者投入时间；Agent 应把需要人工执行的场景压缩到真正有判断价值的最小集合，不得把能够由自动或静态证据解决的问题转嫁给项目所有者。
- 长期检查需要 owner 维护成本、误报、flaky、真实捕获和退休条件。
- 在真实代码任务出现前，具体测试框架、检查分组和预算仍保持未决定。

## 后续验证门

本 ADR 已由项目所有者接受；对应规则随本 PR 合并到 `main` 后生效。合并后仍需在后续真实代码任务中校准：

- 独立判定依据是否足以防止自证而不过度增加文档负担；
- 普通任务是否只触发最窄相关检查；
- 测试期待变化是否能准确区分合同改变、测试错误、获授权的行为不变重构和规避目标；
- 数据隔离是否在早期初始化前成立；
- flaky 与基础设施失败是否能够分类且不会被重试掩盖；
- 昂贵或重复检查是否实际删除、合并或降级。

本次接受不表示具体测试框架、测试项目、CI、项目结构、固定时间预算或覆盖率策略已经建立；这些事项由后续阶段基于真实任务证据决定。本 ADR 本身不授权创建生产代码、测试代码、CI、分析器或审计工具。

## 演进与替代方式

本 ADR 已由项目所有者明确接受；对应规则和最小路由随本 PR 合并到 `main` 后生效。

若未来实质改变风险触发、证据分层、独立判定或检查生命周期，应创建新的 `Accepted` ADR，明确替代范围，并按替代关系将本 ADR 标记为 `Superseded`，不得静默改写原决定。
