# ADR-0005：性能治理采用风险触发与分层证据

- 状态：Proposed
- 日期：2026-08-30

## 背景

Legacy 早期只有“注意性能”式要求，不能告诉 Agent 哪些改动进入性能风险、何时必须测量、什么证据能支持什么结论，也不能约束功能关闭后的常驻成本。

Legacy 后期为解决真实问题形成了大量测量、诊断、快照、日志和审计设施。部分机制具有明确价值，例如节流、关闭态早退和把本地验证与实机验收分开；同时，测量工具和治理链自身也可能持续增长。项目所有者曾经历约十五小时的审计负担，但仓库没有可核验的精确计时，因此该时长只作为所有者体验，不作为性能数据。

静态代码形态、微基准、组件测量和 Terraria 指定实机性能回答不同问题，不能互相替代。JueMingR 需要比“注意性能”更具体的规则，又不能让每个普通任务都运行全量性能矩阵或重新制造十五小时审计。

Phase 0-L 是 [最小工程治理试运行计划](../计划/最小工程治理试运行计划.md) 的第一次真实任务。本 ADR 只提出性能治理方法，不决定总体架构，不创建性能工具，也不授权生产实现。

## 决策草案

如果本 ADR 被项目所有者接受，则采用以下性能治理基线：

1. 采用风险触发，而不是让所有任务进入统一性能流程。
2. 只有新增相关运行路径，实质改变触发频率、输入或最坏规模、生命周期或常驻时间、功能关闭/不可用/降级时的运行成本，新增可能无界的集合、队列、缓存、日志或后台工作，或准备作性能声明时，才填写完整性能风险卡；低频、用户主动且明确有界的 I/O、序列化、反射、UI 或输入处理只作简短性能说明。
3. 静态 diff 可以直接支持限定到所检查路径的窄结构事实，无需运行统计；这类事实不得外推为总体运行收益。微基准、组件或集成测量、Terraria 实机、多人和项目所有者体验继续分层记录。
4. 运行时性能结论必须绑定对比基线、相同版本/构建/设置/输入、预热、样本、统计口径、环境和噪声；流畅度、卡顿或帧 pacing 结论还必须保留相适应的帧时间和慢帧信息，平均 FPS 单独不足以证明这些结论。
5. 功能关闭、不可用和降级路径的成本是性能合同的一部分；Hook 保留与领域工作是否继续执行分开判断。
6. cache、snapshot、queue 和无界集合必须定义 owner、容量、失效、生命周期、清理和观测；缓存不得成为第二事实源。
7. 一次性测量工具默认与生产和发布路径隔离，问题回答后删除或通过独立决定转为长期能力。
8. 慢检查只按已命中的性能风险进入专门 PR、组件测量、实机、多人或发布场景，不阻塞无关普通任务；数据、许可证、安全等非性能高风险不自动触发性能流程。
9. 当前不设置缺少实证基础的全项目统一 FPS、Hook 毫秒、零分配或缓存容量数字。
10. 只有长期自动检查、周期性测量、昂贵阻塞门、临时事故规则、长期性能基准和其他持续占用时间的检查，才维护触发、成本、owner、复核和退休记录；稳定基础原则只说明防止的错误、适用范围和替代条件。

具体规则草案见 [性能治理规则](../规范/性能治理规则.md)。在本 ADR 被接受前，该文件不是当前有效规则。

## 被拒绝的方案

### 只写“注意性能”

拒绝。它没有触发器、基线、证据层级和停止条件，无法约束 Agent，也无法判断任务是否完成。

### 所有修改都运行完整性能审计

拒绝。普通文档、低风险改动和高风险热路径需要的证据不同。统一全量流程会让检查成本脱离风险，并重新制造治理债。

### 未建立基线就设置统一毫秒或 FPS 阈值

拒绝。不同路径、场景、硬件、游戏版本和输入规模没有共同的实证基础。固定数字会产生假精度，也会诱使 Agent 优化指标而非用户结果。

### 用静态调用次数或微基准代替 Terraria 实机

拒绝。调用次数只能描述形态，微基准只覆盖被测代码和环境；两者都不能自动证明真实帧时、FPS 根因、多人性能或用户无感。

### 把一次性测量设施永久放入产品

拒绝。一次性工具会增加发布成本、隐私面和维护责任。只有通过独立决定证明长期价值后，才可以转为正式能力。

### 直到项目完成才第一次测量

拒绝。高频、规模增长、线程、I/O 和加载等高风险路径若长期不建立基线，后期修正成本可能扩大。测量应由风险和当前结论触发，而不是全部推迟。

### 每次性能事故都新增一套永久审计

拒绝。同一故障的重复检查会增加噪声、误报和等待时间。应优先修复最接近事实的主门，并为检查设置退休路径。

## 优点

- Agent 能用明确触发器识别风险，不会因为普通任务仅依赖 UI、输入、文件或序列化就普遍填完整风险卡。
- 结论与证据层级绑定，窄静态结构事实可以准确报告，同时不冒充总体运行收益或实机结果。
- 功能关闭、缓存和测量工具的隐性成本进入任务合同。
- 普通任务只承担最窄检查，高成本验证保留给真正相关的路径和阶段。
- 需要长期维护的检查具有成本和删除路径，可在试运行中继续压缩。

## 代价

- 命中完整风险卡触发条件的任务需要填写风险卡并说明当前不能证明什么。
- 高风险路径需要建立场景和基线，可能增加专门测量或实机时间。
- 性能预算不能在缺少数据时一次性定案，需要随代表性功能逐步校准。
- 需要完整生命周期记录的检查，其 owner 必须维护触发、噪声、复核和退休条件，否则治理仍可能膨胀。

## 后续验证门

本 ADR 当前只是 `Proposed`。独立审查和项目所有者批准前不生效，也不得据此阻塞其他任务。

若项目所有者接受并合并本 ADR 与规则，后续仍需在真实代码任务中验证：

- 风险触发器是否能覆盖真实高风险路径而不过度触发；
- 一屏风险卡是否足以支持任务判断；
- 关闭成本、缓存和测量工具规则是否可执行；
- 窄静态事实与运行时比较的边界是否清楚，微基准、集成、实机和多人分层是否避免结论升级；
- 流畅度和卡顿结论是否保留了帧时间与慢帧信息，而没有只依赖平均 FPS；
- 慢检查是否只由相关风险触发，并有可接受的等待成本；
- 无价值或昂贵规则能否在试运行复盘中删除。

具体性能数字需要等待总体架构、项目骨架和代表性功能出现，并由对应场景的真实测量建立。本 ADR 不授权创建基准工具、CI、项目骨架或生产代码。

## 接受与替代方式

项目所有者接受本 ADR 后，状态才可以在独立获准的修改中改为 `Accepted`，同时更新相关文档路由并合并到 `main`。本轮起草不得自行完成这些动作。

若独立审查或项目所有者认为规则过重、过轻或证据层级不合适，可以修改后再审，或放弃本提案。

本 ADR 若已接受后需要实质改变风险触发、证据分层、固定预算策略或检查成本原则，应创建新的 Accepted ADR，明确替代范围并更新规则；本 ADR 随后标记为 `Superseded`，不得静默改写历史决定。
