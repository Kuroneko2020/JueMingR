# ADR-0002：Legacy 平替策略与行为契约方法

- 状态：Accepted
- 日期：2026-08-28

## 背景

JueMingR 是对 Legacy 的完整重写。Legacy 永久只读，只能作为功能、行为、兼容性、测试案例和历史问题的参考，不能成为 JueMingR 的编译或运行依赖，也不能作为新版内部结构模板。

Legacy 的代码注册与用户功能不是一一对应：一个内部 ID 可能承载多个用户能力，一个用户能力也可能跨越多个 ID，跨功能行为还可能没有独立 ID。因此，按代码注册项逐项迁移会同时遗漏用户结果并复制不必要的内部结构。

要求项目所有者凭记忆重新描述全部旧需求同样不可行。入口、空态、刷新、持久化、失败、多人和性能等细节应由 Agent 从现有证据中恢复，项目所有者只裁决产品价值和用户体验差异。

Phase 0-D 和 Phase 0-E 分别通过自动增益、UI 缩放、足迹和自动堆叠验证了该方法。项目所有者接受“方法基本通过，但需进行指定修正”的结论；指定修正包括数据自然归属、资源不变量与允许转化、部分完成、多人权威和性能形态等边界。相关调查与裁决历史见 [Issue #1](https://github.com/Kuroneko2020/JueMingR/issues/1) 和 [Issue #2](https://github.com/Kuroneko2020/JueMingR/issues/2)。这些调查是本地静态研究，不是运行验收、多人验收、性能结论或用户验收。

## 决策

1. 采用“先平替、后改进”。当前先恢复 Legacy 中对用户有意义、稳定且可观察的行为；名称、布局、颜色、隐含规则和工作流的主动改进留给独立阶段。
2. 采用“产品模块—用户能力—用户可观察行为—Legacy 工程映射”四层模型。平替对象是用户结果和安全边界，不是 Legacy 内部架构。
3. Legacy 旧行为先形成带证据的临时平替基线。证据门可以由至少两种相互独立且适用的静态证据交叉满足，也可以由绑定明确 Legacy 版本、环境、初始状态和操作步骤的 V2/V3 直接观察满足；未覆盖范围继续保持未知。项目所有者证据可以直接确立其实际说明的用户目标、名称分组、记忆工作流和产品取舍，但不能单独证明技术正确性、资源安全、多人权威、性能或未描述边界。临时基线不等于正式功能合同、已实现、已验证或已验收。
4. 将证据来源与实际验收分轴记录。研究阶段可以使用 `A/B/C/D/U` 简写；验收使用 `V0–V4`，从静态提取逐步到项目所有者用户体验验收。正式结论必须展开具体证据及覆盖范围，同一文件中的多个代码片段不机械视为相互独立的证据。
5. 按风险使用轻量、标准和高风险合同。风险深度由失败后果、可恢复性、资源或权威状态修改、多人/身份/隐私、操作频率与数据规模以及证据不确定性共同决定，不因“Overlay”“逐帧”“文件”或“持久化”等关键词机械升级。简单有界 Overlay 可以保持轻量，普通偏好和可重建配置属于标准；不可恢复事实或身份数据、跨实体或跨存档持久化、外部文件修改、隐私与损坏风险，以及大规模、无界、复杂投影、明显动态分配或已有性能风险的高频路径才采用相应高风险深度。标准合同主体可以只增加适用的高风险附加字段，模板不要求全部填满。
6. 数据作用域按用户语义上的自然归属决定。玩家习惯与偏好默认全局共享；角色、世界、角色×世界、服务器和会话事实分别隔离，不由 Legacy 文件位置反推。
7. 高副作用能力必须记录来源、目标、适用的守恒或允许转化关系（即相应资源不变量）、部分完成、成功判据、回滚或补偿、幂等性和禁止结果。转移、消耗、转换或交易、世界状态修改以及有意删除或丢弃分别使用与其语义相符的关系，不统一要求操作前后不同资源类型的原始数量相等。多人写操作还必须分开记录提交、执行、观察、权威确认和最终回执。
8. 行为考古只记录性能形态和待测场景，不由静态结构宣称性能合格、FPS 根因或优化收益。
9. 采用差异验收：为相同场景比较 Legacy 与 JueMingR，隐藏证据充分且等价的项目，只把差异、冲突、风险和无法证明项交给项目所有者。满足既有裁决且证据充分的等价项可以按批次进入正式合同。
10. 项目所有者负责产品选择和最终用户体验验收，可以批准功能簇、批次或长期适用的裁决；Agent 负责恢复行为、组织证据、标明未知并执行获批的对照。不得要求项目所有者逐字段重述等价行为或决定内部代码组织。
11. 具体约束以 [Legacy 平替与行为契约规则](../规范/Legacy平替与行为契约规则.md) 为准。本 ADR 记录为何采用该规则，不承载具体功能合同或动态任务状态。

## 备选方案

### 1. 按 Feature ID 一对一迁移

拒绝。内部 ID 与用户能力不是一一对应，按 ID 迁移会遗漏跨 ID 行为、把伞形或历史 ID 误当产品功能，并使内部注册数量污染产品目录。

### 2. 让项目所有者重新逐项编写需求

拒绝。项目所有者不应凭记忆重述大量边界细节，也不应被迫理解 Legacy 内部术语。该方式认知成本高，且容易遗漏失败路径和历史修复。

### 3. 直接复制 Legacy 内部结构

拒绝。复制类、服务、Hook、Action、缓存和反射会把历史技术约束带入完整重写，并不能证明用户结果、安全或多人语义等价。

### 4. 所有功能使用同一份完整大模板

拒绝。简单只读能力和高副作用多人操作的风险不同。统一大模板会产生无关字段和维护负担，也可能让真正关键的守恒或允许转化关系与权威问题淹没在形式完整性中。

### 5. 一边迁移一边顺手重新设计用户体验

拒绝。平替与改进混在一起会使差异来源不可判读，扩大项目所有者的复核负担，也无法区分缺失、回归和有意变化。改进必须在平替基线之后独立批准。

## 结果

优点：

- 用户结果、证据和内部工程映射被分离，完整重写不必复制 Legacy 架构；
- Agent 可以恢复大部分行为细节，项目所有者只需裁决少量例外；
- 合同深度与风险匹配，简单能力保持轻量，高副作用能力获得明确安全边界；
- 静态证据、自动比较、实机和用户验收不再互相冒充；
- 差异验收可以集中展示真正需要产品决定的内容。

代价：

- 行为考古、证据映射和版本边界需要持续维护；
- 高风险能力必须投入额外的守恒或允许转化关系、多人和失败场景验证；
- 临时基线不能直接视为正式合同或实现完成，阶段边界会增加少量流程成本；
- “先平替”会暂时限制主动用户体验改进，改进必须等待独立阶段；
- 跨功能合同仍需在出现真实职责后另行批准和集中建立。

## 被替代方式

本 ADR 不替代 ADR-0001；ADR-0001 继续管理文档体系和结构演进，本 ADR 决定 Legacy 平替与行为契约方法。

本 ADR 生效后，不再把 Feature ID 一对一目录、Legacy 内部结构、项目所有者逐项回忆或统一完整大模板作为平替的主方法。

若后续方法、风险分级或平替策略需要实质改变，应创建新的 Accepted ADR，明确替代范围、迁移方式和对正式规则的更新。本 ADR 随后标记为 `Superseded` 并链接到新 ADR；不得静默改写原决策。具体功能合同的变化不自动替代本 ADR。
