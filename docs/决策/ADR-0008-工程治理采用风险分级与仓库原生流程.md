# ADR-0008：工程治理采用风险分级与仓库原生流程

- 状态：Proposed
- 日期：2026-08-31
- 对应任务：[Phase 0-O Issue #16](https://github.com/Kuroneko2020/JueMingR/issues/16)
- 对应规则：[工程治理规则](../规范/工程治理规则.md)

## 背景

JueMingZ 的长期 AI 开发曾积累范围、状态、Git、性能、测试、审计和恢复债。Phase 0-I 据此提出候选治理模型，但该研究没有直接升级为永久规则。

《最小工程治理试运行计划》随后安排性能、测试与审计、版本配置与发布三项真实规则任务。三次独立审查共发现 11 项起草阶段未完整处理的问题，说明任务契约、定向审查和窄修窄审具有实际价值；但三项试运行均为文档和规则任务，不能证明生产代码的完整分支、测试、回滚、实机、多人或 CI 流程已被验证。

Phase 0-O 总复盘推荐正式化仓库原生的最小核心。复盘期间曾发生一次上游任务目标错位：过渡期的外部解释工具被误当作候选永久流程。项目所有者在正式化前发现并纠正这一点，表明长期角色、权威和工具依赖必须经过明确授权门。

本次决策时对 GitHub 当前配置的核验没有发现 main branch protection、ruleset、required review、required status checks 或 CI。该事实只记录决策时背景，不作为长期动态配置流水；技术硬门是否存在，仍须读取届时 GitHub 配置和实际检查结果确认。

本 ADR 记录该重要选择及其理由，不复制本地复盘报告或完整的[工程治理规则](../规范/工程治理规则.md)。

## 决策草案

拟采用以下长期工程治理基线：

1. 采用仓库原生、工具无关的工程治理。
2. 仓库、正式文档、GitHub Issues 和 Git 构成项目事实源；聊天记忆、摘要、本地 handoff 和外部咨询不构成权威事实源。
3. 网页 ChatGPT 等外部咨询或解释工具仅为按需辅助，不是事实源、审批层、调度层或项目必需依赖；项目所有者可以直接与 Codex 或其他 Agent 协作。
4. 风险等级与变更表面是两个独立维度。风险仍分为简单、标准和高风险，只依据用户结果、已接受合同、数据、外部副作用、事实所有权和恢复难度判断，不由文件后缀、文件数量、代码行数或“是不是代码”单独决定；多文件只在实际增加共享事实、接口、owner、回滚或恢复复杂度时支持升级。低风险、行为不变的生产代码可以属于简单风险，但仍叠加生产表面的最低交付路径。
5. 所有写入任务均使用与风险相称、可扫描的一屏任务契约，并列出实际可写路径白名单。
6. 标准、高风险及长期规则任务使用任务 Issue、短生命周期分支、PR 和与风险相称的定向独立审查。
7. 简单非生产任务可以使用较轻流程，但直接写入 `main` 必须获得只适用于当前目标和精确路径的一次性明确授权，并由该 commit 留下 Git 可追溯、不可复用的授权使用记录；无法留下完整记录时改用分支和 PR，执行 Agent 不得凭旧聊天、旧任务或自行判断推定权限。
8. 在真实生产代码任务完成校准并由后续明确决定调整前，所有生产代码至少经由短生命周期分支和 PR；简单生产代码是否增加独立审查按实际风险决定，但小 diff 不构成例外。
9. 工程治理规则是 Agent 和任务授权必须遵守的程序性合同，不证明 GitHub 已启用 branch protection、ruleset、required review、required checks 或 CI；技术门必须按当前配置核验，没有硬门不授权绕过程序规则，技术门存在也不替代项目所有者批准。本 ADR 不授权创建这些技术门。
10. 执行 Agent 不独占批准权；在独立审查和相应授权门已通过后，可以代做获准的 Git/GitHub 机械操作。
11. 同一可独立验收、延期、取消和回滚的结果使用同一 Issue；审查后只修复明确问题，复审只检查这些问题及最小回归。
12. 稳定起步前，[Issue #7](https://github.com/Kuroneko2020/JueMingR/issues/7) 是唯一项目级动态投影；具体任务状态、授权、实际 diff 和长期规则分别留在其对应载体。
13. 实现、自动检查、Terraria 实机、多人、性能、项目所有者体验验收、打包和发布等验证与验收轴分别记录，任一轴不得冒充另一轴。
14. 项目所有者只裁决产品结果、用户体验、与 Legacy 的可接受差异、重大或不可逆风险及最终产品或发布批准；不承担日常工程术语和技术操作判断。
15. 所有需要启动或操作 Terraria 的游戏内实机仍由项目所有者亲自执行；Agent 只在授权范围内准备步骤并分析回传证据。
16. 对长期工作流、角色分工、权威来源、必需工具或审批依赖的改变，实施前必须以普通语言说明并取得项目所有者授权：是否形成长期规则、是否引入新的必需工具/角色/审批依赖、能否撤销，以及项目所有者不参与日常技术操作时项目能否继续运行。
17. 本地研究报告只服务于真正需要复杂考古、外部研究或跨证据综合的研究任务；普通实现、机械文档和小修复不默认创建报告或新的治理台账。
18. 生产代码特有的检查组合、CI、预算和工具不在当前预建，而在首批获准的真实任务中按风险校准；不为取得这些证据额外制造纯治理任务。
19. 新长期规则或 ADR 先以 Proposed/草案形成完整候选并接受独立语义审查；项目所有者接受被审查语义并授权机械最终化后，ADR 与规则在同一提交中转为 Accepted/有效并清理草案时态，再由独立上下文复核最终 head 和完整 diff。只有复核通过、head 未变化且 merge 权限明确时才可 squash merge，合并进入 `main` 后生效；最终化若改变实质语义，原授权失效并返回语义审查和项目所有者裁决。
20. 删除已完成使命的临时试运行计划，由本 ADR 和对应规则承载经试运行支持的长期结论。
21. 本 ADR 不授权生产代码、项目骨架、CI、第三方依赖、数据迁移、发布或下一阶段。

具体执行边界由[工程治理规则](../规范/工程治理规则.md)承载；本 ADR 不以复制规则正文取代该规则。

## 被拒绝的方案

### 完全不建立工程治理

拒绝。它不能处理已知的范围、状态、Git、证据和恢复债，也不能让新对话以仓库事实恢复任务边界。

### 将临时试运行计划永久保留为正式规则

拒绝。试运行计划的职责是验证候选方法，长期结论应提炼到 ADR 和规则；保留它会把活动期过程错误延长为永久授权。

### 所有任务使用同一套完整流程

拒绝。普通可撤销任务与数据、加载、多人或发布风险需要的门不同；统一完整流程会使治理成本脱离风险。

### 所有任务都直接写入 `main`

拒绝。它无法为标准、高风险和生产代码提供隔离、审查和可追溯恢复边界。

### 执行 Agent 在没有独立授权门时自行批准自己的标准或高风险改动

拒绝。实现、审查和批准集中在同一 Agent 会形成自证；执行 Agent 可执行获准的机械操作，但不因完成实现而获得批准权。

### 所有简单任务都强制完整独立审查和研究报告

拒绝。此类统一加码会为低风险工作制造等待和文档负担，反而重建治理债。

### 仅因生产代码改动很小就允许执行 Agent 直接 push `main`

拒绝。在生产流程获得真实任务校准前，小规模不能证明低用户或恢复风险，生产代码仍至少经过分支和 PR。

### 把网页 ChatGPT 或其他指定外部工具固化为必需调度或审批层

拒绝。外部工具的可用性和对话状态不能成为项目运行前提；仓库和 Issues 必须足以让获授权的 Agent 独立恢复工作。

### 现在就建立完整 CI、自动门、固定预算或企业级发布流程

拒绝。尚无生产代码和真实任务数据可校准这些能力；提前建设既越过当前授权，也会形成未证明价值的维护成本。

### 为本次目标错位建立新的事故文档和审计体系

拒绝。问题已由工具无关原则和长期依赖授权门直接约束；新增事故体系会复制过程、扩大台账，而非修复最接近事实的门。

## 结果

### 优点

- 新对话可以从仓库和 Issues 恢复。
- 分支和 PR 流程为 `main` 提供程序性的修改隔离和统一 diff 审查面；本 ADR 不声称 GitHub 已启用不可绕过的技术保护。
- 当前收益来自流程和授权层面的保护；未来技术硬门需要另行建立和验证，当前没有硬门也不构成绕过程序规则的许可。
- 独立审查按风险使用。
- 项目所有者不承担工程术语判断。
- 外部解释工具保持可选。
- 临时试运行计划不继续授权后续任务。

### 代价

- 标准和高风险任务增加 Issue、分支、PR 和审查成本。
- 生产代码在校准前即使简单也不能直接进入 `main`。
- 风险定级和任务契约要求执行 Agent 作出可解释判断。
- AI 独立审查仍不能从同一 GitHub 账号的平台元数据证明身份独立。
- 生产代码流程仍需真实任务继续校准。

## 后续验证门

本 ADR 当前仍为 Proposed。在独立审查完成且项目所有者批准最终 diff 前，它和对应规则均不生效。

首批真实生产代码任务应在不额外制造纯治理任务的前提下验证：

- 简单代码只使用分支和 PR 是否足够；
- 标准任务的独立审查是否发现真实问题；
- 高风险任务的回滚和恢复要求是否可执行；
- 任务契约是否与真实代码风险相称；
- 是否出现新的治理膨胀。

本轮不授权项目骨架、生产代码、CI、依赖、数据迁移、发布或下一阶段；上述校准不构成这些事项的隐含授权。

## 接受与替代方式

本 ADR 当前仍为 Proposed，对应规则仍为草案，当前 PR 未获得合并授权，也不自动关闭 Issue。正式化必须依次完成：独立上下文通过完整语义审查；项目所有者接受被审查语义并决定是否授权机械最终化及最终化复核后的代合并；同一任务分支用一个最终化提交同步把 ADR 转为 Accepted、规则转为有效并清理草案时态，且不改变实质语义；独立上下文复核新的 PR head 和完整最终 diff；只有被复核 head 未变化、文件范围与授权一致且 merge 权限明确时，才可 squash merge。

最终化若改变实质语义，原授权失效，必须返回语义审查和项目所有者裁决。ADR 和规则只有合并进入 `main` 后才正式生效；合并后再关闭任务 Issue，并更新 Issue #7。具体机械门和可复用边界见[工程治理规则](../规范/工程治理规则.md)，本 ADR 不复制其全部操作步骤。

若需要实质改变仓库事实源、角色职责、风险分级、生产代码的分支/PR 底线、独立审查边界或长期依赖授权门，必须以新的 Accepted ADR 明确替代范围；不得静默改写历史。
