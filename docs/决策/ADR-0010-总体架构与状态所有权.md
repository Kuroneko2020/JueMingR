# ADR-0010：总体架构与状态所有权

- 状态：Accepted
- 日期：2026-09-01
- 对应任务：[Phase 0-Q Issue #21](https://github.com/Kuroneko2020/JueMingR/issues/21)
- 对应设计：[总体架构与状态所有权](../设计/总体架构与状态所有权.md)
- 文档结构影响：新增 `docs/设计/`

## 背景

JueMingR 是独立重写。项目需要先建立能够承载后续项目骨架、最小加载链和代表性功能切片的总体架构，再开始生产代码与逐项功能实现。平台、原版 Terraria 同进程加载路线和兼容边界已经由既有正式决定确定；功能平替与 Legacy 用户数据导入也已经分开，旧实现和旧数据形状不能反向规定新版架构。

对 JueMingZ 的定向静态调查显示，长期演化使局部架构迁就逐步累积：状态 owner 不清，同一事实存在多份镜像，多个共享 Manager 承载跨域业务，动作链既有队列也有旁路，巨型快照混合原始观察、派生事实、错误与缓存，UI、Persistence 和 Diagnostics 也可能反向影响业务状态。这些现象是新版必须主动避免的风险证据，不是对 Legacy 的运行质量、性能或用户体验结论。

Legacy 同时提供了可保留的经验：部分状态确有自然归属；早期与晚期初始化应分离；宿主差异可通过强类型桥集中封装；绘制、命令和运行时动作之间可以形成单向链；有限、同 tick 的共享观察能够减少重复读取。JueMingR 应吸收这些原则，而不是复制旧模块和类名。

本任务形成了 JueMingR 第一份描述性系统设计。项目所有者已批准建立 `docs/设计/`，用于承载随当前系统演进的正式设计，而 ADR 继续记录选择理由和替代历史。现有流程试运行主要验证了文档、决策与审查机制，尚未通过生产代码、游戏加载、多人场景或性能测量验证本架构。

## 决策

本节记录项目所有者已经接受的总体架构选择。本决定只有随包含本文件的提交合并进入 `main` 后，才成为仓库当前有效架构决定。

1. 总体采用“端口与适配器约束下的分层模块化单体 + 功能纵向切片”。平台层提供少量跨功能机制，Feature 保有自己的规则与状态；物理项目边界只用于隔离确有不同依赖、生命周期或部署方式的部分。
2. 部署分为两个边界：Terraria 进程内的 JueMingR 包负责 Bootstrap、Host、Platform 和 Feature Runtime；进程外 Setup/Recovery 工具负责安装、静态先决条件与文件身份检查、修复、回滚与卸载。其预检不发布或替代进程内 Runtime capability，进程外工具也不得成为游戏内功能运行的控制面。
3. Early Bootstrap 保持 BCL-only，只做最小入口发现、加载桥建立、结构化失败记录和一次固定的 Host handoff。该 handoff 进入最外层 Composition Root；具体 Host Adapter 承担晚期激活、核心 probe、单一 Harmony 上下文和宿主回调。两者都不是第二个 Bootstrap 或第二次动态交接，也不得承载 Feature 规则、UI、持久化策略或诊断业务。
4. Terraria、ReLogic、XNA、Harmony 和具体游戏类型只允许进入 Terraria Host + Composition 项目；任何项目均不得依赖 tModLoader。Host-neutral Platform、Feature Collection、Early Bootstrap、Local Infrastructure 与 Setup/Recovery 不得直接引用游戏程序集。
5. 依赖方向固定为：Host/Composition 组装并依赖 Platform、Features 和 Local Infrastructure；Features 只依赖 Host-neutral Platform 中受控的端口与合同；Infrastructure 实现 Platform 端口；Platform 不反向依赖 Feature、Host 或 Infrastructure。Bootstrap 只能依赖自身最小合同或受控桥，不得成为通用依赖中心。Composition Root 位于最外层，首版落在 `Terraria Host + Composition`；它是唯一可同时认识具体 Host Adapter、Feature Collection、Local Infrastructure 和 Host-neutral Platform 的装配位置，只在装配与关闭阶段选择实现、验证依赖、构造对象图及启动或停止 Runtime，不拥有 Runtime、Session、Feature activation 或业务状态，也不提供运行期服务解析。Runtime / Session Lifecycle 属于 Host-neutral Platform，只依赖抽象 lifecycle、session、feature activation 与 capability 合同，唯一拥有 Runtime、Session、Feature activation 的状态与转换顺序；它不认识具体 Feature、Host Adapter 或 Infrastructure，也不拥有 Feature 产品清单或内部业务状态。
6. 每个 Feature 是纵向切片，拥有自己的启用策略、业务规则、派生状态、持久化语义和诊断投影。Feature Collection 的显式产品清单唯一声明产品包含的稳定 identity，composition 只枚举和验证，重复 identity 必须 fail closed。Feature 之间不得直接访问内部状态，也不得通过静态字段、共享可变容器或“顺手调用”耦合。
7. 每个权威事实必须有唯一语义 owner。其他模块只能持有带时效和来源的只读投影、缓存或派生值，不能形成第二个可写事实源。配置值、运行状态、能力状态、持久化数据与诊断记录必须分别命名和建模。
8. 游戏观察与游戏操作分离。Observation 产生不可变、分层、有 cadence 和新鲜度语义的读模型；Feature 只能读取其需要的窄视图。观察结果不是执行授权，缓存也不是新的业务 owner。
9. 所有游戏状态 mutation 通过薄的 typed Operation Coordinator 进入统一逻辑安全边界，再由 Host Adapter 调用 Terraria operation；该边界不等于单一物理队列或通用业务工作流。Feature 保留业务目标、目标选择、功能特有前置条件、资源守恒、幂等和部分完成后的处理；Coordinator 只承担跨功能通用的 Runtime/Session/generation/capability 有效性、线程交接、取消或过期、typed 有限冲突域、预算、调用 typed Host operation port 及结果分类，不得成为字符串业务分派、业务总线、全局调度器或 Feature 业务状态 owner。已满足安全复核且无需等待或协调的请求可在边界内即时执行；只有实际需要线程切换、未来完成、有限重试、真实冲突或预算背压时才延期，冲突域不得默认全局串行。
10. UI 只消费只读 ViewModel，并把用户意图转换为命令；它不直接修改游戏、配置文件、持久化数据或 Feature 内部状态。输入采集属于 Host 边界，按当前 UI 焦点与会话状态转换为受控命令。
11. 持久化的机械读写由 Local Infrastructure 提供，schema 与内容语义仍由自然业务 owner 决定。配置 owner、玩家/世界/配对身份和业务数据不得因为共用文件或 serializer 而合并为一个状态域。
12. Diagnostics 只记录、聚合和投影既有事实，默认有界、可降级且非权威。诊断开关不得暗中成为业务设置，诊断面板不得直接执行游戏动作；诊断失败不能改变功能的正确性。
13. Runtime、Session 和 Feature 生命周期分开，并由 Host-neutral Platform 内的 Runtime / Session Lifecycle 唯一拥有相应状态与推进、清理顺序；进入、离开和重连必须显式清理 session-scoped 状态。游戏对象只在游戏线程读取或修改，后台工作只处理不可变 DTO、纯计算和受控 I/O，绑定其 Runtime 或 Session generation，并通过显式交接返回结果。
14. Capability 分为核心与可选 Host capability；Host probe 只产生证据，Capability owner 统一发布这些宿主事实。Feature 基于声明的依赖能力和自身业务前置条件，唯一拥有自身可用、降级、不可用等结论；Runtime activation 另行拥有初始化结果与是否实际激活，初始化失败不得反写 capability。设置中的 `Enabled` 不等于能力可用或功能正在运行。
15. 下一阶段建议的最小物理边界仍为六项：Early Bootstrap、Host-neutral Platform、Feature Collection、Terraria Host + Composition、Local Infrastructure、Setup/Recovery。其中 Composition Root 的首版落点为 `Terraria Host + Composition`，Runtime / Session Lifecycle 的首版落点为 `Host-neutral Platform`；该划分是骨架输入，不增加第七个生产项目，不在本 ADR 中创建项目，也不预先规定最终程序集名。
16. 架构通过可执行边界逐步验证：项目引用白名单、禁止程序集引用、命名空间/类型边界检查、唯一 Composition Root、Host-neutral Runtime / Session Lifecycle、禁止静态可变跨域状态、线程交接检查和代表性纵向切片测试。具体门禁脚本与测试在获得后续生产授权时实现。
17. `docs/设计/` 在本 ADR 被项目所有者接受、设计最终化、正式路由更新并合并到 `main` 后，承载当前有效的描述性系统设计和功能设计。它不承载动态任务状态、历史决策理由、临时调查或实现日志。设计应随当前系统更新；失效设计应被更新、替代或删除并退出默认路由，确需保留精选历史时另行批准，ADR 则保留历史选择及理由。
18. 本 ADR 以及对应设计不授权创建项目骨架、生产代码、测试项目、CI、依赖、安装器、原型或下一阶段 Issue，也不证明加载、运行、多人、性能或用户验收。

## 候选方案比较

### 分层模块化单体 + 功能切片（采用）

该方案用少量稳定平台边界约束宿主依赖、线程、观察、操作、持久化和诊断，同时让功能按纵向切片保有规则和状态。它能在单进程 mod 的现实约束下提供明确依赖方向与状态 owner，又不要求为每个功能建立程序集或独立服务。

本方案吸收纯纵向切片的局部自治、端到端可验证和按功能演进优点；也吸收中央内核方案中“单一组合根、统一 typed 安全边界、受控能力目录”的有限优点，但拒绝让中央机制拥有 Feature 业务或成为无边界消息总线。

### 纯功能纵向切片（不单独采用）

纯纵向切片能降低功能之间的直接耦合，也利于按功能恢复行为合同。但若没有宿主边界和共享机制约束，每个切片会重复解决 Terraria 访问、线程、输入、存储、诊断和操作冲突；最终可能形成多套事实源和不一致的安全语义。因此只吸收功能自治，不放弃受控平台层。

### 中央 Runtime/Event Bus/Plugin 内核（不采用）

中央内核可集中生命周期、发现和调度，早期看似易于扩展。但它容易把状态、业务路由、动作和诊断汇入一个全知 Runtime 或 Event Bus，使所有模块能够互相观察和影响，重现 Legacy 的 Manager 扩张与 owner 模糊。只保留与 Runtime / Session Lifecycle 分离的 Composition Root、能力目录和薄 typed 操作安全边界，不建立通用插件内核或全局 Event Bus。

## 被拒绝方案

### 直接复制 Legacy 当前模块

拒绝。Legacy 是行为和风险证据，不是新版模块边界；照搬会固化历史迁就、重复 owner 和宿主泄漏。

### 一个大程序集只靠命名空间自律

拒绝。关键的游戏程序集依赖、Bootstrap 纯度和进程外边界需要物理引用约束，命名约定不足以阻止回流。

### 一个功能一个程序集

拒绝。现阶段没有证据证明 77 个功能需要对应物理程序集；这会制造项目、构建和版本管理负担。Feature Collection 内的逻辑切片已经足够，只有真实隔离需求出现时才拆分。

### 所有功能直接访问 Terraria

拒绝。这会让宿主版本、线程和对象生命周期扩散到每个功能，无法建立一致的观察、操作与失败降级边界。

### 万能 ActionManager、通用业务工作流或全局队列

拒绝。统一逻辑安全边界只处理跨功能通用安全；若它吸收各 Feature 的目标、规则、幂等或部分完成策略，就会成为新的全知 owner。若把所有 mutation 强制进入同一队列或全局串行，又会让无关冲突域互相等待；因此只按真实需求建立 typed、有限的延期与冲突协调。

### 全局 Event Bus 和巨型快照

拒绝。无边界广播扩大隐式依赖，巨型快照把不同 cadence、时效和错误语义捆绑在一起。采用窄合同、显式协调和分层观察。

### 把 UI、Diagnostics 或 Persistence 当业务 owner

拒绝。这些都是适配、投影或机械能力；让它们拥有业务事实会形成多写者与反向依赖。

### 现在就为所有未来功能建立抽象

拒绝。只为已识别的架构风险建立最小边界；新的共享抽象必须由至少两个真实切片证明共同语义和生命周期。

### 建立通用外部控制面

拒绝。Setup/Recovery 仅做本机安装恢复，不常驻、不远程控制游戏内 Runtime，也不构成新的服务或协议承诺。

## 结果

### 优点

- Terraria 依赖、游戏线程和部署边界可被物理约束；
- Feature 保有自然业务 owner，减少共享 Manager 和重复事实；
- 具体装配与长期 Runtime / Session 生命周期的职责和物理落点可以分别验证；
- 观察、操作、UI、持久化与诊断的职责可分别验证；
- 可从最小骨架和一个代表性切片开始，不需要一次实现完整平台；
- 失败与降级状态可以对用户和诊断如实表达。

### 代价

- 需要维护显式生命周期合同、装配边界、typed operation 请求/结果语义，以及按真实需求建立的有限冲突协调；
- 简单功能仍不得绕过 typed 安全边界直接调用 Terraria；这使路径更显式，但符合条件时可以即时执行，不要求全局排队；
- 项目引用、线程和所有权门需要后续实现并持续维护；
- 六个候选物理边界仍需在真实骨架中验证是否恰当。

### 尚未验证

- 目标原版 Terraria 宿主加载条件下 Early Bootstrap、Host 晚期激活与唯一 handoff 是否可行；
- 六个物理项目能否在实际工具链中保持目标引用关系；
- Composition Root 与 Runtime / Session Lifecycle 能否在实际装配、启动、停止和故障清理中维持既定分工；
- 代表性功能切片能否在不过度抽象的前提下使用 Observation、Operation、UI、Persistence 与 Diagnostics，并证明即时与有界延期两条路径；
- 多人权威性、重连和服务器确认的具体状态模型；
- 性能预算、更新 cadence、缓存收益和诊断成本；
- Setup/Recovery 的安装、恢复和回滚流程；
- Terraria 实机、多人、长期运行和用户验收。

### 下一阶段得到的输入

本 ADR 与对应设计合并进入 `main` 后，下一阶段将得到：候选项目边界、允许和禁止依赖方向、Composition Root 与 Runtime / Session Lifecycle 的不同位置和职责、状态 owner 原则、观察与操作分离、线程和生命周期规则，以及首个代表性纵向切片必须验证的架构问题。项目骨架阶段只建立最小 typed operation contract 与 Host-neutral/Host 引用边界，保留即时执行和有界延期两种实现可能；不得预建通用 Action 框架、工作流引擎、全局优先级或覆盖未来功能的冲突域，最小 Coordinator 实现留到首个真实 mutation 纵向切片。它不会得到已实现骨架、完整接口、schema、UI 视觉或生产可用声明。

## 后续验证门

当前结论只经过文档与 Legacy 的定向静态调查。独立审查能够检查设计内部一致性、证据边界与可执行性，但不能替代生产验证。

1. 下一阶段创建项目骨架时，验证项目引用、禁止程序集引用、Composition Root 唯一具体装配且无运行期解析、Runtime / Session Lifecycle 保持 Host-neutral，以及类型可见性边界。
2. 建立最小加载链时，验证 Early Bootstrap、Composition Root、Host Adapter、Runtime / Session Lifecycle 的交接与失败降级，不携带任何 Feature 业务。
3. 建立代表性纵向切片时，同时验证 Feature 隔离、UI 命令、持久化 owner、Observation、Operation 和 Diagnostics，并用失败案例检查 mutation 旁路、强制全局排队或跨无关冲突域串行是否被阻止。
4. 多人、性能、安装恢复和长期运行必须在各自获准任务中取得相称证据，不能由静态设计推断。
5. 若生产代码证据表明边界错误或代价不合理，应按正式决策流程修正设计；首次设计不是永久不可变架构。

## 生效、验证与替代方式

项目所有者已经接受本 ADR 与对应设计承载的总体架构语义。本 ADR 和对应设计只有随包含它们的提交合并进入 `main` 后，才成为仓库当前有效架构决定与正式设计。

本次接受只完成静态架构语义裁决：不等于项目引用、编译、加载、Terraria 实机、多人或性能验证，也不授权项目骨架、生产代码、测试、依赖、构建、CI、安装器、原型或下一阶段 Issue。后续真实生产代码、项目骨架、加载链和代表性纵向切片可以形成受控修订证据。

未来若实质改变模块边界、依赖方向、状态 owner 或唯一游戏操作出口，必须创建新的 Accepted ADR 说明替代范围和迁移理由。当前设计文档应随有效架构更新；本 ADR 不得通过静默改写来重写历史选择。
