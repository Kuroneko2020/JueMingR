# 性能治理规则

- 状态：草案
- 生效条件：只有 ADR-0005 被项目所有者接受、相应文档路由更新并合并到 `main` 后，本规则才生效。
- 当前效力：本文件当前不得视为已授权的性能门禁，也不授权创建性能工具、基准项目、CI 或生产代码。

## 一、目的与范围

本草案用于把“注意性能”转换为可执行、可验证且成本受控的规则。若本草案生效，它只管理：性能风险识别、性能任务的最小信息、证据与结论的边界、基线与测量、功能关闭成本、热路径、扫描、分配、日志、I/O、cache、snapshot、queue、测量工具，以及性能检查的触发、成本和退出。

本草案不管理：总体架构或模块划分、具体功能实现、固定硬件矩阵、当前 Terraria 版本流水、完整测试或发布体系，以及当前任务、阻塞或动态进度。

具体用户行为和安全边界继续遵循 [Legacy 平替与行为契约规则](Legacy平替与行为契约规则.md)，平台、宿主和多人拓扑继续遵循 [技术平台与兼容规则](技术平台与兼容规则.md)。

## 二、基本原则

1. 命中性能风险触发器不等于已经存在性能缺陷，只表示任务必须记录风险并选择与结论匹配的最窄证据。
2. 静态形态、微基准、组件或集成测量、Terraria 实机、多人和项目所有者体验不得互相替代。
3. 没有对比基线时，只能报告风险或观察到的形态，不能报告改善。
4. 数值预算必须绑定具体路径、场景、输入规模、版本、构建、设置和硬件；本阶段不设全项目统一数字。
5. 功能关闭、不可用和降级路径的成本属于性能合同的一部分。
6. 性能检查本身有成本；普通任务只承担能支持本轮结论的最窄检查。
7. 一次性测量设施默认与发布路径隔离，回答问题后删除或通过独立决定转为长期能力。

## 三、性能风险触发器

任务新增、修改或依赖以下任一形态时，应记录性能风险：

- 每 Tick 执行；
- 每帧更新或绘制；
- Hook、patch 或宿主回调命中；
- 输入轮询或输入事件；
- 网络发送、接收、重试或同步；
- 背包、实体、世界、箱子、Tile 或地图扫描；
- UI 搜索、过滤、布局、测量和绘制；
- 高频或无界日志；
- 文件 I/O；
- JSON 或其他序列化、反序列化；
- 反射、动态调用或程序集装载；
- 锁、线程、异步工作或后台任务；
- cache、snapshot、queue、历史缓冲或其他可能无界集合；
- 功能关闭、不可用或降级后仍执行的工作；
- 声称“更快”“更少分配”“低开销”“近零成本”“零成本”或“性能优化”。

简单任务只记录适用项。无法说明触发频率、输入规模和主要工作时，不得直接声称性能安全。

## 四、性能风险卡

命中触发器的任务，应在任务 Issue 中填写以下短卡；不适用项可以写“不适用”并简述理由：

```text
触发位置和线程：
预计触发频率：
输入规模和最坏规模：
主要工作：
分配、I/O、反射、锁、网络和日志：
开启时成本：
关闭或不可用时成本：
缓存或快照：
当前基线：
本轮目标：
需要哪种证据：
测量工具放在哪里、何时删除：
当前不能证明什么：
```

风险卡是调查入口，不是固定大表。未命中性能触发器的普通文档任务不需要填写。

## 五、证据分层

### 静态风险审查

静态审查可以定位调用频率、循环、规模增长、分配、锁、I/O、日志、缓存和关闭路径等风险形态。它不能证明：

- FPS 根因；
- 性能合格；
- 优化收益；
- 多人性能；
- 用户无感。

### 微基准

微基准只覆盖被测代码、输入、运行时、JIT、构建、硬件和基准配置。它可以比较局部算法或分配形态，但不能自动外推为 Terraria 帧时、完整 Hook 成本、多人延迟或用户体验。

### 组件或集成测量

组件或集成测量可以覆盖真实依赖组合、线程、I/O 或较完整调用链，但仍只证明所用宿主、数据和环境。若未运行 Terraria，它不能写成 Terraria 实机结论。

### Terraria 指定实机场景

实机证据必须绑定精确游戏版本、JueMingR 版本或 commit、构建、设置、机器、场景、初始状态、采样区间和指标。单一场景不能外推为所有世界、UI、硬件或渠道。

### 多人与项目所有者体验

多人证据必须记录拓扑和本地客户端、主机或服务器权威角色。项目所有者主观体验只证明实际体验过的场景；它不能替代帧时、分配或延迟测量，测量也不能替代项目所有者验收。

## 六、基线与性能结论

任何“更快”“更少分配”“低开销”等比较结论，必须说明：

- 对比对象；
- 相同的版本、构建和设置；
- 相同的输入规模；
- 预热方式；
- 样本数量；
- 统计口径；
- 运行环境；
- 噪声、误差和无法区分的范围。

没有稳定基线时，只能写“存在风险”“观察到某种形态”或“当前无法区分”，不能写“改善”。

本阶段不得写死：

- 全项目统一 FPS；
- 所有 Hook 的统一毫秒预算；
- 所有 Tick 路径零分配；
- 所有缓存的统一容量；
- 所有任务必须通过相同基准。

后续有真实测量后，可以在对应功能、场景或发布规则中建立局部预算，不反向升级为无条件全局门。

## 七、Tick、帧、Hook 与扫描

高频或规模增长路径必须记录：为什么必须以该频率运行；是否可以由状态变化、事件或较低 cadence 触发；是否在同一时点重复采集等价状态；扫描规模是否随世界、实体、箱子、Tile、地图或玩家增长；是否每次全量遍历；是否有明确早停；关闭、不可用或降级时是否停止领域工作；以及单次平均成本之外的突发最坏情况。

不得机械规定“事件一定比轮询好”。选择轮询时必须说明 cadence、规模边界和停止条件。Hook 是否保留与 Hook 命中后是否执行领域工作必须分开判断。

## 八、功能关闭成本

必须区分：

- 功能不产生用户行为；
- 功能不执行领域扫描；
- Hook 仍存在但只作最小早退；
- Hook 已完全卸载。

功能关闭后默认应避免：

- 领域扫描；
- 构造快照；
- 分配列表和字符串；
- 文件 I/O；
- 业务日志；
- 网络请求；
- 后台排队。

共享 Hook 必须保留时，应记录最小早退路径及其触发频率，并按相应风险选择证据。没有测量时不得声称“零成本”或“完全无影响”。

## 九、分配、GC、字符串与动态能力

静态审查应关注：

- 高频临时 `List`、`Dictionary` 和其他集合；
- LINQ 枚举与物化；
- 字符串拼接、插值和格式化；
- 装箱和闭包；
- JSON；
- snapshot；
- UI 布局对象；
- 日志参数；
- 缓冲区；
- 反射、动态调用和程序集装载。

本规则不禁止所有分配、LINQ、反射或动态调用。高频分配必须说明目的和生命周期；存在可复用方案时说明为何不复用；需要作性能结论时，使用与真实路径匹配的分配、GC 或时序证据。

## 十、缓存、快照、队列与集合

缓存不是默认优化。新增缓存必须说明：

- owner；
- key；
- value；
- 容量或有界条件；
- 失效规则；
- 可容忍的陈旧程度；
- 生命周期；
- 功能关闭和世界切换时的清理；
- 并发方式；
- 观测方式；
- 不使用缓存时的基线。

缓存不得成为第二事实源。snapshot、queue 和历史缓冲同样必须定义 owner、容量、丢弃或合并策略、清理和失败行为。

多个消费者需要同一时点状态时，应优先考虑一次采集、多方只读；具体接口和模块归属由后续架构阶段决定，本规则不提前定案。

## 十一、日志、I/O 与诊断

- 高频路径不得无界写日志。
- 调试字符串和日志参数不得在日志关闭时仍无条件构造。
- 文件 I/O 不得无理由进入 Tick 或帧路径。
- 后台写入不能自动证明没有主线程准备、排队、分配、锁或失败处理成本。
- 诊断采集必须记录 cadence、容量、隐私、失败行为和关闭成本。
- 长期支持能力与一次性测量工具必须分开。

## 十二、线程、锁、异步与网络

把工作放到后台不等于消除成本。相关任务应记录谁创建和取消工作、队列是否有界、工作是否可能积压/重复/迟到、锁争用与主线程等待点、结果何时回到主线程、关闭/世界切换/断线/异常时如何停止，以及网络重试、同步与序列化的规模边界。

## 十三、测量工具的隔离与退出

一次性测量工具默认放在 `.local/`、独立测试或基准项目、实验分支或条件编译路径。

一次调查不得直接把工具放入正式发布路径。工具必须记录要回答的问题、owner、输入和输出、隐私、运行成本、到期和删除条件。

问题回答后，工具应删除，或通过独立决定转为有明确用户或支持价值的长期能力。

## 十四、性能检查的触发与成本

以下情况至少需要性能风险审查，并按结论选择更高层证据：

- 新增或修改 Tick、帧、Hook、网络或文件 I/O；
- 扫描规模随外部数据增长；
- 新增常驻缓存、快照、诊断或后台任务；
- 声称性能改善、低开销或关闭近零成本；
- 修改加载、GC、锁或线程路径；
- 已有用户实机性能反馈；
- 高风险任务进入合并或发布门。

命中项不表示必须立即运行完整 Terraria 实机矩阵。任务应选择能支持本轮结论的最窄证据。

性能检查按成本分为：

1. 编辑或任务内静态风险审查；
2. 专门微基准；
3. 组件或集成测量；
4. Terraria 实机；
5. 多人；
6. 发布场景。

普通文档和无性能触发器的任务不得运行完整性能检查。慢检查必须由相关路径或风险触发，并记录时间预算、失败解释、owner、退出和退休条件。不得让性能检查自然扩张为全仓同步审计。

## 十五、何时停止优化

出现以下任一情况，应停止当前优化并重新调查：

- 无法建立稳定基线；
- 测量噪声大于变化；
- 行为合同被改变；
- 改动引入第二事实源或复杂缓存；
- 连续两轮修改没有可解释收益；
- 优化成本超过已证明影响；
- 只能通过扩大工具、诊断或审计继续证明自己。

停止不等于失败。可以准确记录为“未证实”“无明显收益”“工具不足”“场景不稳定”或“不值得继续”。

## 十六、结论措辞

使用与证据匹配的表述，例如：

- “静态上存在每 Tick 全量扫描风险”；
- “微基准中该纯函数分配下降”；
- “指定 Terraria 场景的帧时得到改善”；
- “多人性能未验证”。

证据不足时禁止写：

- “性能问题已解决”；
- “零开销”；
- “不会影响 FPS”；
- “多人性能等价”；
- “缓存一定更快”。

## 十七、防止性能治理膨胀

- 一个性能故障尽量只有一个主要检查。
- 一次低风险事故不自动新增永久全仓规则。
- 规则或检查必须说明防止什么、何时触发和成本。
- 长期无真实捕获、误报高、噪声高或成本过大的检查应删除或降级。
- 不使用自然语言精确字符串证明性能治理合规。
- 不为性能审计故障默认增加更多性能审计。
- 项目所有者等待时间也是性能治理成本。

具体任务授权与试运行方式继续遵循 [最小工程治理试运行计划](../计划/最小工程治理试运行计划.md)，文档权威和生命周期继续遵循 [文档治理规则](文档治理规则.md)。
