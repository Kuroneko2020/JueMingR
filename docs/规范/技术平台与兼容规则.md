# 技术平台与兼容规则

## 一、目的与适用范围

本规则管理 JueMingR 的产品运行平台、原版同进程加载边界、兼容声明、依赖与游戏文件边界，以及安装、恢复和卸载的最低安全要求。

本规则适用于涉及 Terraria 版本、Windows、Steam/GOG、多人拓扑、加载链、程序集、第三方依赖和安装恢复的调查、设计、实现与验证任务。

本规则不是总体架构、代码设计、加载器实施计划、精确 Hook 清单、当前版本流水或兼容测试报告，也不规定完整性能、测试、发布、数据迁移或具体功能合同。

研究材料只能为本规则提供证据；不得把 Phase 0-G 报告或其差异矩阵整篇复制为正式合同。

## 二、产品平台与身份

- JueMingR 是 Windows 桌面环境中的原版 Terraria 客户端辅助工具。
- 游戏内桥加载到原版 `Terraria.exe` 的同一进程。
- 产品不依赖 tModLoader，也不要求玩家安装 tModLoader。
- JueMingR 只作为 Terraria 客户端产品分发和安装；不向独立 `TerrariaServer.exe` 部署组件，也不建设 JueMingR 专用服务器组件。
- 不修改、重打包或分发替换版 `Terraria.exe`。
- 保持原版 Terraria 的启动、进程和联机身份；具体渠道集成必须由实测证明。

## 三、原版同进程最小职责链

加载链以以下职责级顺序为基线：

```text
受控 Terraria.exe.config
→ 最小 AppDomainManager 入口
→ 最小早期初始化
→ 明确的程序集与核心能力门槛
→ 可审计、单一上下文的 Harmony 可达性
→ 经目标版本验证的宿主回调
→ 一次性 Runtime 交接
```

该顺序是职责链，不是对 TerrariaHelper 或 JueMingZ 类名、文件结构和调用链的复制。

- `AppDomainManager` 早期入口只承担建立后续安全初始化所必需的最小职责。
- 早期入口不得访问尚未安全初始化的 Terraria 静态状态。
- 程序集就绪不能只依赖简单名；核心门槛必须核对预期程序集身份和必需能力。
- Harmony 必须在明确、单一且可审计的装载上下文中可达。
- 精确宿主回调和 Hook 目标必须由目标游戏版本验证决定。
- Runtime 交接只能成功一次；部分安装、重复激活和假成功都必须被阻止。
- 不继承固定 12 次重试魔数。
- 不继承多安全点、fallback 或反射兜底，除非后续现实证据证明其必要性。
- 开发环境变量可以作为隔离、受控且显式的开发工具。
- 普通用户加载路径以受控 config 和正常 Terraria 启动流程为基线。

## 四、来源、clean-room 与第三方许可证

- TerrariaHelper 是设计路线和用户行为的上游基线。
- TerrariaHelper 的反编译源码、资源、二进制实现、混淆实现及其他无授权实现不得复制到 JueMingR。
- 不得把 TerrariaHelper 的反编译控制流程翻译或改名后当作 clean-room 实现。
- JueMingZ 只作为历史故障、用户行为和兼容案例的证据来源；新版只吸收其中有现实证据证明必要的增量。
- JueMingR 不复制 JueMingZ 当前全套复杂加载链，也不在编译期或运行时引用 JueMingZ。
- clean-room 实现可以依据已批准的产品要求，Microsoft、Harmony 等官方文档，公开 API，项目所有者合法取得的目标 Terraria 安装文件，独立读取的程序集身份、PE/CLR 元数据、符号和方法形状，不复制受保护实现的独立静态分析结论，经授权执行的受控运行观察和实机验证，JueMingZ 中已有现实故障和行为证据，以及重新编写的 JueMingR 代码。
- 使用 Terraria 私有或内部 ABI 不自动违反本项目的 clean-room 规则，但每个使用点都必须由目标版本的独立证据建立并纳入兼容能力门。
- “不是公开 API”不得被错误解释为禁止调查或使用目标游戏的实际 ABI。
- 采用第三方组件时，必须从其官方上游获取并遵守该组件自身许可证。
- 一个第三方组件的许可证不得外推到 TerrariaHelper、JueMingZ 或其他整包材料。
- 依赖 notice 和适用的许可证文件属于发布最低要求。

## 五、宿主位数、框架与语言边界

- 所有同进程代码必须匹配目标 Terraria 版本和渠道的实际宿主运行时、位数和 ABI；确认目标宿主前，不得仅凭历史基线假定 x86 或 x64。
- Phase 0-G / G.1 检查的当前研究基线是 32 位 CLR，因此该基线下不得加载 x64-only 同进程代码。
- 每个准备支持的新 Terraria 版本都必须重新检查 PE 类型、CLR 标志、进程位数和 Native/PInvoke ABI。
- 若 Terraria 将来改变宿主位数或运行时，必须重新评估 AppDomainManager、目标框架、PlatformTarget、Native 依赖以及加载和安装路线，不得静默沿用旧产物。
- 纯托管游戏内桥是否显式使用 x86，由后续项目骨架和目标版本验证决定。
- 游戏内桥的目标框架必须与目标 Terraria 宿主兼容；当前研究基线的宿主是 .NET Framework。
- `net472` 可以作为初始候选，但精确 TFM 与 SDK 锁定必须在项目骨架前由验证或架构决策确定。
- C# 语言版本不是产品兼容硬约束，应由获批工具链和目标框架能力决定。
- 同进程桥以外的未来辅助工具另行确定位数和框架，不得被本规则永久锁定为 x86。

## 六、Terraria 版本与兼容声明

- 产品默认面向 Terraria 官方最新稳定版。
- 每项“已支持”声明必须绑定精确游戏版本、环境、渠道和实际覆盖场景。
- 兼容记录必须保存 Terraria 程序集身份、相关文件表面和被验证的能力。
- 编译引用版本与实机验证版本可以不同，但必须分别记录，不能互相代替。
- 编译成功不等于目标版本可以加载、运行或完整兼容。
- 未测试的新版本不得冒充完整支持。
- 版本未知不自动拒绝，也不自动放行全部能力。
- 加载前或启动时必须形成核心能力门和功能级能力门。
- 核心条件失败时，JueMingR 整体不激活。
- 单项条件失败时，只关闭相应功能，并保持其他已满足能力可用。
- 普通用户必须能看到未激活或功能关闭的具体原因。
- 日志必须记录实际检测结果、失败层级和适用版本，不得静默假兼容。
- 精确当前游戏版本由兼容记录、发布元数据或验证证据承载，不在本规则累积版本流水。

## 七、Windows 兼容

- Windows 10 和 Windows 11 是主要测试、维护和发布说明范围。
- 操作系统版本号不得作为唯一拒绝条件。
- 旧 Windows 在所需能力满足时可以尝试运行，但属于未完整测试范围。
- 能力检查至少考虑所需 .NET Framework、Windows API、文件系统权限、Terraria 宿主和依赖位数。
- 缺少实际必需能力时可以拒绝激活，但必须向用户说明具体缺失项。
- Microsoft 的系统安全生命周期不直接等于 JueMingR 的程序兼容范围，也不得单独形成版本封锁。
- 旧 Windows 的实测支持只能由绑定系统、游戏版本和场景的证据建立。

## 八、Steam 与 GOG 渠道

- Steam 和 GOG 默认共用一套产品实现。
- 渠道、安装路径、文件哈希和运行 ABI 是不同维度，必须分别记录。
- 安装流程可以按渠道定位合法游戏安装；运行时兼容仍以实际程序集身份和能力为准。
- 只有发现真实程序集、符号、依赖或运行行为差异时，才拆分渠道兼容记录。
- 无 DRM 或未加密不能单独证明两个渠道的二进制相同。
- 缺少某一渠道样本或实测时，必须标记未验证，不得猜测相同或不同。

## 九、单人与多人拓扑

- 单人模式以客户端本地完整功能为目标。
- Steam Host & Play 必须进入兼容验证矩阵。
- 客户端连接独立专用服务器必须进入兼容验证矩阵。
- JueMingR 只作为客户端产品分发和安装；不向独立 `TerrariaServer.exe` 部署组件，远程服务器和其他玩家不需要安装 JueMingR。
- Host & Play 中，安装 JueMingR 的同一 Terraria 进程可能同时承担本地客户端角色和主机或服务器权威角色。
- Host & Play 的行为合同和验证必须分别记录本地客户端观察、本地客户端请求、同进程主机权威执行、对远程客户端的同步和最终可见结果。
- 不得因为客户端与主机权威角色物理上处于同一进程，就把客户端提交和主机权威确认合并为一个状态。
- 功能不得仅因“可能受服务器限制”而在未经调查时全局禁用。
- 每项多人相关能力必须分别记录本地显示、客户端请求、主机或服务器执行、权威确认、最终同步和用户可见结果。
- 客户端本地变化、请求已发送或调用原版动作都不等于服务器成功。
- 结果未确认时，功能必须安全停止或显示未确认，不得向用户报告成功。
- 具体多人功能合同继续遵守 [Legacy 平替与行为契约规则](Legacy平替与行为契约规则.md)。

## 十、游戏文件、编译引用与依赖装载

- Terraria、ReLogic 和 XNA 文件不得进入 JueMingR Git 仓库。
- 默认不得随 JueMingR 包分发 Terraria、ReLogic 或 XNA 游戏文件。
- 开发者从其合法 Terraria 安装提供编译引用。
- 仓库只保存引用要求、版本或程序集身份 manifest，以及不包含游戏文件的验证逻辑。
- 正式文件不得保存私人绝对路径；定位必须从仓库根、安装元数据或显式参数开始。
- Harmony 必须从官方上游获取，并明确记录版本、哈希、许可证和 notice。
- 不得按简单名从多个任意目录加载未知 DLL。
- 依赖解析只允许明确白名单、预期程序集身份和受控来源。
- 最终依赖装载必须保持单一、可审计的上下文。

## 十一、安装、恢复与卸载最低安全要求

- 安装前必须定位并验证合法 Terraria 安装及预期宿主能力。
- 安装前必须检查目标文件和目录权限。
- 必须检测已有 `Terraria.exe.config` 及其中已有的 AppDomainManager 或其他用户配置。
- 不得静默覆盖其他 AppDomainManager、未知配置或无法证明所有权的文件。
- 配置和拥有文件必须通过原子写入或原子替换落盘。
- 每次被允许的替换必须产生唯一备份，不能覆盖上一份备份。
- 备份必须带有清单、哈希、来源和版本，足以恢复精确原状。
- 安装中断或加载失败后，用户必须能在 Terraria 进程外执行恢复。
- 恢复或卸载前必须重新核对当前 config、安装清单和安装后身份；若安装后出现外部修改，不得覆盖当前文件或直接还原旧备份。
- 只有能够精确移除 JueMingR 自有配置并保留外部内容时，才允许自动修改共享 config；否则必须停止自动恢复、保留证据并提供明确的人工处理路径。
- 卸载只能删除 JueMingR 自己拥有且可由清单和身份验证的文件。
- 卸载必须幂等；重复执行不得破坏 Terraria 或其他用户文件。
- 默认保留用户数据；数据删除和 Legacy 数据迁移必须由独立规则或明确选择授权。
- 不得使用通配恢复、通配删除或仅按文件名删除。
- Terraria 更新后必须重新执行能力探测，并在作出支持声明前完成相应实机验证。
- 游戏内日志不能替代进程外恢复能力。

## 十二、失败分层与可见结果

每一层失败都必须规定原版游戏能否启动、JueMingR 是否激活、恢复路径、用户可见信息和日志内容；任何层级都不得假成功。

第一层失败发生在 JueMingR 游戏内代码能够可靠运行之前，不能依赖游戏内 UI、Runtime 或游戏内日志完成说明和恢复；若原版 Terraria 因此无法启动，不得声称 JueMingR 已正常进入降级模式。

| 失败层级 | 原版游戏与 JueMingR | 恢复要求 | 用户与日志 |
| --- | --- | --- | --- |
| CLR/config/AppDomainManager 装载阶段失败（进入 JueMingR 代码前） | 原版游戏可能无法启动；JueMingR 游戏内代码尚不能可靠运行 | 必须由进程外预检、安装清单和恢复入口承担检测与恢复 | 用户通过进程外入口获得说明；进程外日志记录配置、文件身份和恢复结果 |
| AppDomainManager 初始化失败 | 不得进入部分激活；应尽可能保留或恢复原版启动 | 通过进程外工具撤销自有配置和文件 | 用户看到初始化失败原因；日志记录异常、阶段和宿主身份 |
| 核心 Hook 失败 | 原版游戏应保持可运行；JueMingR 整体不激活 | 撤销已安装的部分核心状态，必要时提示进程外恢复 | 用户看到核心能力缺失；日志记录目标、探测和回滚结果 |
| 单项能力失败 | 原版游戏和其他已满足能力继续运行；该功能关闭 | 清理该功能的部分状态并允许安全重检 | 用户看到功能关闭及原因；日志记录能力门和影响范围 |
| 运行时功能失败 | 在安全可行时保持游戏和无关功能运行；故障功能停止 | 防止重复副作用，按功能合同回滚、重试或保持未确认 | 用户看到失败或未确认而非成功；日志记录触发、状态和实际结果 |

## 十三、明确延期与进入条件

以下事项不在本规则定案：

- 精确首个 Hook 方法、备用 Hook 数量和重试次数；
- Harmony 最终采用合并包还是显式旁置依赖；
- 项目完整模块架构和代码组织；
- 性能预算、测试体系和发布版本体系；
- Legacy 数据迁移和具体功能合同；
- 旧 Windows 实测矩阵；
- Steam/GOG 二进制一致性；
- 多人逐功能验证。

延期不等于忽略。进入相应实施前，必须建立独立 Issue、明确授权范围，并以与风险相匹配的证据通过相应验证门。

## 十四、规则边界与演进

本规则只管理平台和兼容边界，不继续追加完整性能、测试、编码、版本发布或总体架构规则。

新增职责应由独立规范承载，并按 [文档治理规则](文档治理规则.md) 受控进入当前路由。

本规则中的当前版本事实不得演化为更新流水。路线选择及理由见 [ADR-0003](../决策/ADR-0003-原版同进程加载路线与兼容策略.md)。
