# 工程治理规则

- 状态：草案
- 生效条件：只有 [ADR-0008](../决策/ADR-0008-工程治理采用风险分级与仓库原生流程.md) 被项目所有者接受、相关路由和引用更新并合并到 `main` 后，本规则才生效。
- 当前效力：本文件当前不得作为已生效的合并、审查或生产代码授权；它也不授权创建项目骨架、代码、测试、CI、依赖、构建、发布或数据迁移。
- 对应任务：[Phase 0-O Issue #16](https://github.com/Kuroneko2020/JueMingR/issues/16)
- 决策依据：[ADR-0008](../决策/ADR-0008-工程治理采用风险分级与仓库原生流程.md)

## 一、目的与范围

本规则只管理跨任务的最小工程治理：任务风险分级、单次任务契约、实际写入路径白名单、Issue 与 Git/PR 授权、独立审查边界、角色职责、停止条件、状态与证据的基本分离、新会话与交接、长期流程和依赖的授权门，以及治理成本与退出。

本规则不规定具体功能合同、总体架构、性能测量细节、测试框架或检查组合、版本/schema/发布实现、Terraria 当前版本流水、当前任务动态状态，或具体 CI、工具实现。它不得演变为总体架构、性能、测试或发布手册。

## 二、仓库原生与工具无关

- 仓库及其中的正式文档、GitHub Issues 和 Git 是项目事实源；各自的唯一职责仍以 `AGENTS.md`、[文档治理规则](文档治理规则.md)及任务路由为准。
- 聊天记忆、摘要、本地 handoff、外部咨询和解释工具都不是权威事实源。
- Agent 必须能从 `AGENTS.md`、[文档入口](../README.md)、[稳定起步路线图](../计划/稳定起步路线图.md)、[总跟踪 Issue #7](https://github.com/Kuroneko2020/JueMingR/issues/7)、当前任务 Issue 和 Git 状态恢复任务。
- 网页 ChatGPT 或其他外部工具仅为项目所有者按需选择的辅助；它们绝不成为事实源、审批者、调度者、Prompt 唯一来源或项目运行依赖。普通开发、审查、测试、Git 操作和任务恢复不得依赖某个指定产品。
- Prompt 可以由项目所有者、执行 Agent 或辅助工具形成；Prompt 来源不决定任务授权。当前任务 Issue、有效长期合同和 Git 状态共同决定授权边界。

### 程序性合同与 GitHub 技术硬门

- 本规则建立的是 Agent 和任务授权必须遵守的程序性合同；它本身不证明 GitHub 已启用 branch protection、ruleset、required review、required status checks、CI 或自动合并。
- 技术门是否存在，必须读取当前 GitHub 配置和实际检查结果确认。没有技术门不表示执行 Agent 获得绕过本规则的权限；技术门存在也不能自动替代项目所有者的产品或重大风险批准。
- branch protection、ruleset、required checks、CI 或自动合并是否建立，由未来真实生产任务、实际风险和仓库权限条件另行决定。本规则不授权创建或启用这些技术门。

## 三、角色职责

### 项目所有者

项目所有者负责产品结果、用户体验、与 Legacy 的可接受差异、重大风险是否值得、不可逆或高副作用取舍、Terraria 人工实机，以及最终产品或发布批准。所有需要启动或操作 Terraria 的游戏内实机，均由项目所有者亲自执行。

项目所有者不负责内部代码组织、Git 命令、测试框架、mock/fixture/断言结构、构建和 CI 技术、`AssemblyVersion` 或 schema 的实现，也不需要在多个 Agent 之间人工转述完整技术上下文。

### 执行 Agent

执行 Agent 负责从权威载体恢复任务，调查并说明目标、非目标和风险，在授权范围内修改，先搜索已有能力再增加抽象，提供与结论相称的证据，并在获准后完成 Git/GitHub 的机械操作。遇到冲突、越界或证据不足时必须停止。

### 独立审查 Agent

独立审查 Agent 使用未参与起草的独立上下文，对照任务契约、完整 diff 和相关风险检查，寻找范围扩张、重复实现、事实所有权、失败恢复、证据越级和旧路径残留。独立审查不替代项目所有者的产品或体验验收。

## 四、风险等级与变更表面

每项任务必须独立判断两个维度：风险等级回答“实际后果有多大”，变更表面回答“修改进入哪条工程或交付路径”。两个维度共同决定最低流程；文件后缀、文件数量、代码行数或“是不是代码”都不能单独代替风险判断。

### 风险等级

| 等级 | 适用情形 |
| --- | --- |
| 简单 | 目标单一且范围明确，容易验证和撤销；不触碰用户数据或未授权外部环境，不改变持久化 schema、多人权威、安全边界、加载安装机制、长期跨任务合同、正式规则或 ADR，不引入新的依赖、事实 owner 或难以恢复的副作用，也不命中高风险领域。用户可观察行为不变，或只恢复已经明确接受且边界清楚的现有行为；出错后的影响局部，可通过单一 revert 或窄修恢复。简单风险可以包括低风险、行为不变的生产代码修改。 |
| 标准 | 改变普通用户可观察行为、正式功能合同、测试 oracle 或测试期待的真实含义、共享项目结构、构建/打包/CI 合同、正式规则、ADR、跨任务合同，或改变多个事实 owner、模块接口或共享不变量；风险能够理解并设计明确回滚，但不满足简单条件。 |
| 高风险 | 涉及加载、安装、用户数据、schema 或配置迁移、多人权威或网络写操作、安全、许可证、核心运行时、性能敏感路径、正式发布、难以回滚、可能阻止 Terraria 启动，或其他可能造成显著外部副作用的变化。 |

风险等级依据用户结果、已接受的行为或长期合同、用户数据、外部环境和副作用、事实所有权、恢复与回滚难度，以及安全、许可证、多人、加载、安装和性能风险判断。多文件、跨目录或较大 diff 只是一项检查线索；只有它们实际增加共享事实、接口、owner、回滚或恢复复杂度时，才支持升级风险。两个 Markdown 文件同步修同一链接，或行为不变的小型重命名同时修改实现与测试，仍可属于简单风险；单文件中的安装、迁移、用户数据或核心加载修改仍可属于高风险。Agent 必须说明风险升级依据，不能只写“修改了多个文件”，也不得建立文件数、行数或 diff 大小的全局阈值。

Agent 可以依据新证据升级风险，但不得为了减少流程自行降级。小 diff、单文件或“行为不变”的声明不能自动证明简单。项目所有者不需要理解分级术语，Agent 必须用普通语言说明最坏后果。

### 变更表面与最低流程

- **生产或发布路径**：会进入产品运行、安装、迁移、打包或发布结果的代码、脚本、项目配置和资源。
- **受控工程路径**：测试、构建、打包和 CI 等工程修改；它们不因“不进入运行 DLL”就自动属于简单任务。
- **长期权威路径**：正式规范、ADR 和跨任务合同；默认至少按标准任务处理。
- **机械性非生产路径**：链接、错字、无语义格式修正或同类仓库维护；满足简单风险条件时可以属于简单非生产任务。

| 风险与表面 | 最低流程 |
| --- | --- |
| 简单非生产任务 | 可以使用轻量流程；直接 `main` 仍须一次性明确授权和 Git 可追溯记录。 |
| 简单生产代码 | 必须使用短生命周期分支和 PR；是否增加独立审查按实际风险判断。 |
| 标准任务 | Issue、短生命周期分支、PR 和独立审查。 |
| 高风险任务 | 标准流程，加与风险相称的设计、回滚、恢复、专项证据及项目所有者风险批准。 |

一项任务可以同时是“简单风险 + 生产代码表面”；“简单风险”不构成绕过生产代码最低 Git 路径的理由。风险等级和变更表面必须分别记录，再共同选择不低于上表的流程。

## 五、一屏任务契约

每个写入任务开始前，应以可扫描的形式清楚说明：

```text
任务：
用户或项目会得到什么：
本轮不做什么：
允许修改什么：
禁止或只读什么：
风险和最坏后果：
怎样证明完成：
什么情况必须停止：
允许哪些 Git/GitHub 动作：
最终需要项目所有者决定什么：
```

简单任务可以压缩不适用项，但不得省略唯一目标、写入范围、完成依据、停止条件和 Git 权限。契约追求信息完整且易读，不建立机械行数审计。

## 六、Issue 与状态职责

- 一个 Issue 对应一个能够独立验收、取消、延期和回滚的结果；同一结果内部的起草、审查、修订、窄审与收尾留在同一个 Issue。
- 只有新的用户结果、独立风险、架构决定或范围外缺陷才新建 Issue。
- Issue 记录任务目标、授权、当前阻塞和结论；PR 记录实际 diff、审查和合并现场；总跟踪 Issue #7 仅记录项目级当前阶段、当前任务、阻塞、下一候选阶段和未授权事项。
- 不在 Issue、PR 和 Issue #7 三处逐轮复制同一状态全文；稳定规则不得记录当前任务动态状态。
- 简单、单次、可撤销且已明确授权的非生产任务可以不建立独立 Issue；跨会话、需要批准、需要追踪或涉及标准/高风险的任务必须有 Issue。

## 七、Git、分支、commit、PR 与合并

### 简单非生产任务直接 `main` 的轻量记录

只有同时满足以下条件时，才可直接 commit 或 push 到 `main`：

- 任务属于简单风险，并且只是非生产、非发布、非测试期待、非构建/CI 合同、非正式规则/ADR 的机械修改；
- 项目所有者或当前权威任务契约明确授予本次直接 `main` 权限，并限定唯一目标和精确路径；
- 工作区和暂存区干净，修改可以通过单一 revert 恢复；
- 当前仓库没有相冲突的任务、分支或保护要求。

没有明确授权时，默认改用短生命周期分支和 PR。发现目标、路径、风险或实际结果变化，或发现用户行为、长期合同、测试 oracle、外部副作用、生产/发布路径、受控工程路径变化后，原直接 `main` 授权立即失效并停止该路径。

授权只适用于当前唯一目标和精确路径，由完成该次 commit 消费；不能被下一次任务、下一次对话或额外文件重复使用。不得从旧聊天、旧 Issue、旧 commit，或“项目所有者以前同意过类似事情”推定当前权限。

直接 `main` 的 commit 标题和正文必须单一、自足。正文至少记录：

```text
Task: <本次唯一目标>
Classification: simple / non-production
Authorized-Paths: <精确路径>
Direct-Main-Authorization: project-owner one-time authorization, consumed by this commit
Authorization-Basis: <稳定 Issue/评论引用；若没有，则准确概括本次明确授权内容>
Actual-Change: <实际完成的修改>
Verification: <执行的最窄验证>
```

该 commit 本身是最小、Git 可追溯的授权使用记录，记录 Agent 当时依据的授权，但不声称 Git 元数据能够密码学证明操作者身份。有稳定 GitHub Issue 或评论时优先引用；没有稳定引用时，正文必须完整概括本次明确授权，不能只写“用户已同意”。新对话应能只从 commit 理解目标、范围、实际修改，以及授权为何只适用于该提交。

push 前必须确认实际 diff 与 `Authorized-Paths` 严格一致。无法留下上述记录时，禁止直接 `main`，改用分支和 PR。不得为简单任务建立永久授权总表、授权日志目录、Excel 或数据库，不在 Issue #7 逐项记录，也不得把一次授权写成长期通配授权。

### 生产代码的校准前边界

在首批真实生产任务完成校准、并由新的明确决定调整前，所有生产代码至少使用短生命周期分支和 PR；执行 Agent 不得直接把生产代码 commit 或 push 到 `main`。简单生产代码是否需要独立第二审查，依实际风险决定；该保守边界不得由执行 Agent 自行删除或降级。

### 标准与高风险任务

标准任务使用任务 Issue，从稳定 `main` 建立短生命周期任务分支；commit 应表达一个可理解、可验证的结果，随后 push 任务分支、创建 PR，并在满足审查和授权门后合并。

高风险任务除标准流程外，增加与风险相称的设计、回滚、恢复和专项验证。合并前必须保留项目所有者对产品结果和重大风险的明确批准。

自动验证通过不扩大 Git 权限；执行 Agent 不得把完成实现当作批准实现。独立审查和明确授权门通过后，Agent 可以代做合并、关闭等机械动作。不得 force push、改写共享历史或自行删除远程分支；已进入 `main` 的错误优先通过可追溯修复或 revert 处理，不静默改写历史。

## 八、独立审查边界

- 长期跨任务规则、ADR、标准任务和高风险任务默认需要独立审查。
- 简单非生产任务不默认增加完整第二审查；简单生产代码依实际风险决定是否增加独立审查，但仍必须经过 PR。
- 独立审查使用未参与起草的独立 Agent 或独立上下文，只读取任务契约、完整 diff 和当前风险路由要求的材料，不无目的重新调查全项目。
- 审查发现问题后，执行 Agent 只处理明确问题；修订后的复审只检查这些问题和最小回归，不重新全量审计。没有审查问题时不机械增加窄审。
- AI 独立审查不替代项目所有者的产品验收。

## 九、长期规则与 ADR 的正式化闭环

本节适用于新正式规范、新 ADR、跨任务长期治理的实质修改，以及 Proposed ADR 与草案规则共同进入同一 PR 的情况。

### 候选与语义审查

- ADR 保持 Proposed，对应规则保持草案、未生效；完整语义候选在同一任务分支和 PR 中形成，不因 PR 可合并而生效。
- 未参与起草的独立上下文审查任务契约、完整语义 diff 和相关风险。发现问题时保持 Proposed/草案，由原起草上下文只做明确窄修，再由原独立审查上下文只复审修订和最小回归。
- 独立语义审查通过后，项目所有者应基于普通语言说明决定：是否接受被审查的长期方向和实际语义；是否授权仅做机械最终化；是否预授权在最终化窄审通过后由 Agent 代做 squash merge。项目所有者不负责判断 Git 命令或状态字段实现。

### 机械最终化

只有取得上述授权后，执行 Agent 才可在同一任务分支：

- 将 ADR 从 Proposed 改为 Accepted，将对应规则从草案改为有效，并在同一最终化提交中保持两者状态一致；
- 同时清理与草案状态冲突的时态，保留“只有合并进入 `main` 后才正式生效”的边界；
- 只更新已经获准的路由和链接，不改变已经审查通过的实质语义。

### 最终化复核、合并与生效

最终化提交 push 后，必须由原独立审查上下文或其他未参与最终化起草的独立上下文检查当前 PR 新 head、完整最终 diff、ADR 与规则状态一致性、草案措辞清理、路由和链接、实质语义不变，以及文件范围和授权仍一致。

若最终化修改改变实质语义，原项目所有者预授权立即失效；不得合并，必须返回独立语义审查和项目所有者裁决。只有以下条件同时满足，才可 squash merge：

- 独立语义审查通过；
- 项目所有者已经接受语义并授权机械最终化；
- 最终化窄范围复核通过；
- PR head 与被复核 head 完全一致；
- merge 权限已经明确授予；
- `main` 没有出现无法解释的新变化。

合并进入 `main` 后，ADR 和规则才正式生效；随后关闭任务 Issue，再更新 Issue #7 的里程碑和稳定提交。PR 合并不得自动关闭 Issue，除非当前任务明确授权并在合并后执行。

项目所有者可以提前授权：“最终化仅限状态、时态、路由和链接；窄范围复核通过且没有实质语义变化后，由 Agent 代做合并。”该预授权只适用于被审查的当前 PR 和明确的机械最终化；head、文件范围或语义改变后失效，不能被其他 PR 或任务复用。

## 十、写入白名单与停止条件

所有写入任务必须列出实际允许路径。出现以下任一情况必须停止：

- 需要修改白名单之外的路径；
- 出现无法解释的工作区改动；
- 仓库、路线图、Issue #7 和任务 Issue 互相冲突；
- 任务出现第二个独立结果；
- 需要新增第三方依赖、改变已批准架构或长期规则但未授权；
- 风险升级但尚未取得对应授权，或无法建立可靠验收依据；
- 需要修改 Legacy，或需要接触 Terraria 安装或用户数据但没有精确授权；
- 连续两轮修订仍无明确根因，准备进入第三轮盲试；
- 只能通过扩大工具、报告或审计继续证明当前工作。

停止后保留已有证据，在任务 Issue 说明冲突或缺少的授权；不得把停止、未知或未验证写成完成。文件数、diff 和时间只能作为任务内软警戒，不能形成无证据的全局机械配额。

## 十一、证据与完成状态

以下状态必须分开记录：实现完成、编译或指定自动检查通过、Terraria 指定实机通过、多人场景通过、性能测量通过、项目所有者体验验收通过、已打包、已发布。任一状态不得自动升级为另一个状态；未做或未授权的验证必须明确写为未做或未知。

具体证据标准分别遵循 [Legacy 平替与行为契约规则](Legacy平替与行为契约规则.md)、[技术平台与兼容规则](技术平台与兼容规则.md)、[性能治理规则](性能治理规则.md)、[测试与审计规则](测试与审计规则.md) 和 [版本、配置与发布规则](版本配置与发布规则.md)，本规则不复制其正文。

## 十二、新会话、交接与沟通

- 新任务、新独立审查、任务目标变化、权限变化或执行者更换时，使用新上下文并重新冷启动。
- 同一 Issue 内的窄范围修订默认留在原执行上下文；窄范围复审可以回到原独立审查上下文。只有上下文污染、状态不明或执行者变化时，才为同一任务额外冷启动；对话数量不是成功指标。
- 直接向项目所有者请求授权或裁决前，Agent 必须以普通语言说明当前阶段、任务目的、现在为何需要做、完成后会发生什么、真实风险，以及当前仅需项目所有者决定什么。
- 若确实通过聊天传递完整 Prompt，完整 Prompt 必须放在一个可一次复制的代码框中；不以越短越好为目标。这只是通信格式，不是项目运行依赖。

## 十三、长期流程、角色与工具依赖授权门

任何会改变长期工作流程、角色分工、权威来源、必需工具、审批依赖，或项目能否在项目所有者不参与日常技术操作时继续运行的任务，在实施前必须以普通语言回答：

1. 是否形成长期规则；
2. 是否引入新的必需工具、角色或审批依赖；
3. 完成后能否撤销；
4. 项目所有者不参与日常技术操作时，项目能否继续运行。

随后必须取得项目所有者明确授权。一次过渡期协作方式或工具习惯不得自动升级为永久项目机制。

## 十四、研究报告、治理成本与校准

- 本地研究报告只用于复杂考古、外部研究或跨证据综合；普通实现、机械文档和小修复不默认创建研究报告。
- 原始研究留在 `.local` 或未来 CI 工件，正式文件只提炼当前有效结论；不为每轮审查新建 Markdown、Excel、数据库或状态台账。
- 一个故障尽量只有一个最接近事实的主要门。长期没有真实捕获、误报高、与更强门重复或成本超过收益的检查应删除或降级。
- 项目所有者的等待、理解和实机时间属于治理成本；没有记录时不得猜测数值。
- 三次试运行只验证了长期规则类文档任务。生产代码的 TDD、编译、测试、回滚、实机、多人和 CI 组合仍属暂定，应在首批获准真实生产任务中自然校准，不另外制造一系列纯治理任务。
- 校准后如需改变生产代码的分支、PR 或独立审查边界，必须通过新的明确决定，不由执行 Agent 自行放宽。
