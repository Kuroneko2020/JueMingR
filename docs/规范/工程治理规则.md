# 工程治理规则

- 状态：草案
- 生效条件：只有 [ADR-0008](../决策/ADR-0008-工程治理采用风险分级与仓库原生流程.md) 被项目所有者接受、相关路由和引用更新并合并到 `main` 后，本规则才生效。
- 当前效力：本文件当前不得作为已生效的合并、审查或生产代码授权；它也不授权创建项目骨架、代码、测试、CI、依赖、构建、发布或数据迁移。
- 对应任务：[Phase 0-O Issue #16](https://github.com/Kuroneko2020/JueMingR/issues/16)
- 决策依据：[ADR-0008](../决策/ADR-0008-工程治理采用风险分级与仓库原生流程.md)

## 一、目的与范围

本规则只管理跨任务的最小工程治理：任务风险分级、单次任务契约、实际写入路径白名单、Issue 与 Git/PR 授权、独立审查边界、角色职责、停止条件、状态与证据的基本分离、新会话与交接、长期流程和依赖的授权门，以及治理成本与退出。

本规则不规定具体功能合同、总体架构、性能测量细节、测试框架或检查组合、版本/schema/发布实现、Terraria 当前版本流水、当前任务动态状态，或具体 CI、工具实现。它不得演变为总体架构、性能、测试或发布手册。

## 二、仓库原生与工具无关

- 仓库及其中的正式文档、GitHub Issues 和 Git 是项目事实源；各自的唯一职责仍以 `AGENTS.md`、[文档治理规则](文档治理规则.md)及任务路由为准。
- 聊天记忆、摘要、本地 handoff、外部咨询和解释工具都不是权威事实源。
- Agent 必须能从 `AGENTS.md`、[文档入口](../README.md)、[稳定起步路线图](../计划/稳定起步路线图.md)、[总跟踪 Issue #7](https://github.com/Kuroneko2020/JueMingR/issues/7)、当前任务 Issue 和 Git 状态恢复任务。
- 网页 ChatGPT 或其他外部工具仅为项目所有者按需选择的辅助；它们绝不成为事实源、审批者、调度者、Prompt 唯一来源或项目运行依赖。普通开发、审查、测试、Git 操作和任务恢复不得依赖某个指定产品。
- Prompt 可以由项目所有者、执行 Agent 或辅助工具形成；Prompt 来源不决定任务授权。当前任务 Issue、有效长期合同和 Git 状态共同决定授权边界。

## 三、角色职责

### 项目所有者

项目所有者负责产品结果、用户体验、与 Legacy 的可接受差异、重大风险是否值得、不可逆或高副作用取舍、Terraria 人工实机，以及最终产品或发布批准。所有需要启动或操作 Terraria 的游戏内实机，均由项目所有者亲自执行。

项目所有者不负责内部代码组织、Git 命令、测试框架、mock/fixture/断言结构、构建和 CI 技术、`AssemblyVersion` 或 schema 的实现，也不需要在多个 Agent 之间人工转述完整技术上下文。

### 执行 Agent

执行 Agent 负责从权威载体恢复任务，调查并说明目标、非目标和风险，在授权范围内修改，先搜索已有能力再增加抽象，提供与结论相称的证据，并在获准后完成 Git/GitHub 的机械操作。遇到冲突、越界或证据不足时必须停止。

### 独立审查 Agent

独立审查 Agent 使用未参与起草的独立上下文，对照任务契约、完整 diff 和相关风险检查，寻找范围扩张、重复实现、事实所有权、失败恢复、证据越级和旧路径残留。独立审查不替代项目所有者的产品或体验验收。

## 四、风险分级

| 等级 | 适用情形 |
| --- | --- |
| 简单 | 范围极小、容易撤销、不改变用户功能或可观察行为、不触碰用户数据、外部环境或长期权威，且不改变生产代码、测试期待、依赖、构建、CI、正式规则、ADR 或路线图。 |
| 标准 | 改变普通用户行为、修改多个相关文件、修改正式规则或跨任务合同、修改测试期待/项目结构/共享工程设施，且风险可理解并能够回滚。 |
| 高风险 | 涉及加载、安装、用户数据、配置迁移、多人权威或网络写操作、安全、许可证、核心运行时、性能敏感路径、难以回滚或可能阻止游戏启动、正式发布，或其他可能造成显著外部副作用的变化。 |

Agent 可以依据新证据升级风险，但不得为了减少流程自行降级。不得按文件数、diff 行数或“看起来简单”机械定级；应依据用户结果、数据、外部副作用、事实所有权和恢复难度。项目所有者不需要理解分级术语，Agent 必须用普通语言说明最坏后果。

## 五、一屏任务契约

每个写入任务开始前，应以可扫描的形式清楚说明：

```text
任务：
用户或项目会得到什么：
本轮不做什么：
允许修改什么：
禁止或只读什么：
风险和最坏后果：
怎样证明完成：
什么情况必须停止：
允许哪些 Git/GitHub 动作：
最终需要项目所有者决定什么：
```

简单任务可以压缩不适用项，但不得省略唯一目标、写入范围、完成依据、停止条件和 Git 权限。契约追求信息完整且易读，不建立机械行数审计。

## 六、Issue 与状态职责

- 一个 Issue 对应一个能够独立验收、取消、延期和回滚的结果；同一结果内部的起草、审查、修订、窄审与收尾留在同一个 Issue。
- 只有新的用户结果、独立风险、架构决定或范围外缺陷才新建 Issue。
- Issue 记录任务目标、授权、当前阻塞和结论；PR 记录实际 diff、审查和合并现场；总跟踪 Issue #7 仅记录项目级当前阶段、当前任务、阻塞、下一候选阶段和未授权事项。
- 不在 Issue、PR 和 Issue #7 三处逐轮复制同一状态全文；稳定规则不得记录当前任务动态状态。
- 简单、单次、可撤销且已明确授权的非生产任务可以不建立独立 Issue；跨会话、需要批准、需要追踪或涉及标准/高风险的任务必须有 Issue。

## 七、Git、分支、commit、PR 与合并

### 简单非生产任务

只有当前任务契约明确授权时，才可直接 commit 或 push 到 `main`；没有明确直接 `main` 权限时不得自行推定。发现用户行为、长期规则、测试期待、外部副作用或代码变化后，必须升级风险并停止直接 `main` 路径。

### 生产代码的校准前边界

在首批真实生产任务完成校准、并由新的明确决定调整前，所有生产代码至少使用短生命周期分支和 PR；执行 Agent 不得直接把生产代码 commit 或 push 到 `main`。简单生产代码是否需要独立第二审查，依实际风险决定；该保守边界不得由执行 Agent 自行删除或降级。

### 标准与高风险任务

标准任务使用任务 Issue，从稳定 `main` 建立短生命周期任务分支；commit 应表达一个可理解、可验证的结果，随后 push 任务分支、创建 PR，并在满足审查和授权门后合并。

高风险任务除标准流程外，增加与风险相称的设计、回滚、恢复和专项验证。合并前必须保留项目所有者对产品结果和重大风险的明确批准。

自动验证通过不扩大 Git 权限；执行 Agent 不得把完成实现当作批准实现。独立审查和明确授权门通过后，Agent 可以代做合并、关闭等机械动作。不得 force push、改写共享历史或自行删除远程分支；已进入 `main` 的错误优先通过可追溯修复或 revert 处理，不静默改写历史。

## 八、独立审查边界

- 长期跨任务规则、ADR、标准任务和高风险任务默认需要独立审查。
- 简单非生产任务不默认增加完整第二审查；简单生产代码依实际风险决定是否增加独立审查，但仍必须经过 PR。
- 独立审查使用未参与起草的独立 Agent 或独立上下文，只读取任务契约、完整 diff 和当前风险路由要求的材料，不无目的重新调查全项目。
- 审查发现问题后，执行 Agent 只处理明确问题；修订后的复审只检查这些问题和最小回归，不重新全量审计。没有审查问题时不机械增加窄审。
- AI 独立审查不替代项目所有者的产品验收。

## 九、写入白名单与停止条件

所有写入任务必须列出实际允许路径。出现以下任一情况必须停止：

- 需要修改白名单之外的路径；
- 出现无法解释的工作区改动；
- 仓库、路线图、Issue #7 和任务 Issue 互相冲突；
- 任务出现第二个独立结果；
- 需要新增第三方依赖、改变已批准架构或长期规则但未授权；
- 风险升级但尚未取得对应授权，或无法建立可靠验收依据；
- 需要修改 Legacy，或需要接触 Terraria 安装或用户数据但没有精确授权；
- 连续两轮修订仍无明确根因，准备进入第三轮盲试；
- 只能通过扩大工具、报告或审计继续证明当前工作。

停止后保留已有证据，在任务 Issue 说明冲突或缺少的授权；不得把停止、未知或未验证写成完成。文件数、diff 和时间只能作为任务内软警戒，不能形成无证据的全局机械配额。

## 十、证据与完成状态

以下状态必须分开记录：实现完成、编译或指定自动检查通过、Terraria 指定实机通过、多人场景通过、性能测量通过、项目所有者体验验收通过、已打包、已发布。任一状态不得自动升级为另一个状态；未做或未授权的验证必须明确写为未做或未知。

具体证据标准分别遵循 [Legacy 平替与行为契约规则](Legacy平替与行为契约规则.md)、[技术平台与兼容规则](技术平台与兼容规则.md)、[性能治理规则](性能治理规则.md)、[测试与审计规则](测试与审计规则.md) 和 [版本、配置与发布规则](版本配置与发布规则.md)，本规则不复制其正文。

## 十一、新会话、交接与沟通

- 新任务、新独立审查、任务目标变化、权限变化或执行者更换时，使用新上下文并重新冷启动。
- 同一 Issue 内的窄范围修订默认留在原执行上下文；窄范围复审可以回到原独立审查上下文。只有上下文污染、状态不明或执行者变化时，才为同一任务额外冷启动；对话数量不是成功指标。
- 直接向项目所有者请求授权或裁决前，Agent 必须以普通语言说明当前阶段、任务目的、现在为何需要做、完成后会发生什么、真实风险，以及当前仅需项目所有者决定什么。
- 若确实通过聊天传递完整 Prompt，完整 Prompt 必须放在一个可一次复制的代码框中；不以越短越好为目标。这只是通信格式，不是项目运行依赖。

## 十二、长期流程、角色与工具依赖授权门

任何会改变长期工作流程、角色分工、权威来源、必需工具、审批依赖，或项目能否在项目所有者不参与日常技术操作时继续运行的任务，在实施前必须以普通语言回答：

1. 是否形成长期规则；
2. 是否引入新的必需工具、角色或审批依赖；
3. 完成后能否撤销；
4. 项目所有者不参与日常技术操作时，项目能否继续运行。

随后必须取得项目所有者明确授权。一次过渡期协作方式或工具习惯不得自动升级为永久项目机制。

## 十三、研究报告、治理成本与校准

- 本地研究报告只用于复杂考古、外部研究或跨证据综合；普通实现、机械文档和小修复不默认创建研究报告。
- 原始研究留在 `.local` 或未来 CI 工件，正式文件只提炼当前有效结论；不为每轮审查新建 Markdown、Excel、数据库或状态台账。
- 一个故障尽量只有一个最接近事实的主要门。长期没有真实捕获、误报高、与更强门重复或成本超过收益的检查应删除或降级。
- 项目所有者的等待、理解和实机时间属于治理成本；没有记录时不得猜测数值。
- 三次试运行只验证了长期规则类文档任务。生产代码的 TDD、编译、测试、回滚、实机、多人和 CI 组合仍属暂定，应在首批获准真实生产任务中自然校准，不另外制造一系列纯治理任务。
- 校准后如需改变生产代码的分支、PR 或独立审查边界，必须通过新的明确决定，不由执行 Agent 自行放宽。
