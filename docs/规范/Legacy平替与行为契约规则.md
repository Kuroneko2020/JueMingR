# Legacy 平替与行为契约规则

## 一、目的与适用范围

本规则用于约束 JueMingR 对 Legacy 的行为考古、用户能力建模、临时平替基线、正式产品合同形成和差异验收。凡涉及 Legacy 功能恢复、兼容差异、高副作用操作、多人行为或用户验收，均适用本规则。

Legacy 永久只读，只是 UI、配置、实现、测试源码、文档和历史修复的证据来源，不是新版代码模板。JueMingR 平替的是用户结果、可观察行为和安全边界，不复制 Legacy 的类、注册器、服务、Hook、Action、缓存、反射或调用链。

旧行为应先形成带证据的临时平替基线。临时基线不等于已经实现、已经运行验证、已经与 Legacy 等价或已经通过用户验收。具体功能只有在相应证据、风险边界和产品裁决完成后，才能形成正式产品合同。

本规则不是具体功能说明、候选功能目录、动态任务状态、实施计划、架构设计、测试报告或完整性能规范，也不复制本地研究过程。

## 二、基本原则

1. JueMingR 最终完整平替 Legacy 中对用户有意义的功能。
2. 当前采用“先平替、后改进”：先恢复 Legacy 已有、稳定、可观察的用户行为，再在独立阶段讨论易用性优化和视觉重新设计。
3. 稳定的名称、布局、颜色、隐含规则和操作习惯，在平替阶段先按证据记录；不得仅因存在更现代的方案而擅自修改。
4. 保留用户可观察表现不等于复制内部实现。
5. 已知 Bug、不可达行为、无法合理实现的行为，以及可能导致复制、丢失、误移、越权、隐私泄露或多人权威错误的行为，不因 Legacy 当前如此而自动成为平替合同。
6. 改进建议可以作为非阻塞候选记录，但必须与当前平替合同分开。改进阶段使用独立 Issue、独立批准和明确的差异说明。

## 三、角色职责

### 项目所有者

项目所有者负责裁决：

- 产品名称和分组；
- 用户目标；
- 可接受差异；
- 某项表现是否属于 Bug；
- 默认值、工作流和其他产品取舍；
- 最终用户体验验收。

项目所有者可以针对单项、功能簇、批次或长期适用的产品原则作出裁决，不需要逐字段批准所有证据充分且符合既有裁决的等价行为。

### Agent

Agent 负责：

- 定位 Legacy 的普通用户入口、自动触发和实际实现；
- 恢复 UI、交互、状态、持久化、失败与降级行为；
- 映射配置、测试源码、多人风险和性能形态；
- 区分事实、推断、冲突和未知，并写明证据覆盖范围；
- 设计并在获得授权后执行自动、截图、录屏或实机对照；
- 隐藏证据充分且等价的内容，只把真正需要产品裁决的差异、冲突、风险和无法证明项交给项目所有者。

不得要求项目所有者判断 Feature ID、Registrar、Service、Manager、Hook、Action、内部配置类、测试源码组织或新版内部模块拆分。

## 四、四层行为模型

| 层级 | 定义 | 记录要求 |
| --- | --- | --- |
| 产品模块 | 用户认知中的功能大类 | 使用普通产品语言，不按代码目录命名 |
| 用户能力 | 用户能够理解并直接使用的目标 | 说明用户为什么使用，以及完成后得到什么结果 |
| 用户可观察行为 | 用户能够操作、看到或感知的入口、状态、结果和失败 | 按条件、触发、可见结果和禁止结果描述 |
| Legacy 工程映射 | 支持上述结论的 UI、配置、实现、测试和历史证据 | 供 Agent 追溯，不要求项目所有者理解，也不成为新版架构合同 |

四层之间是多对多关系：

- 一个内部 ID 可以包含多个用户能力；
- 一个用户能力可以由多个内部 ID 共同实现；
- 一个跨功能行为可能不对应任何独立 Feature ID；
- 内部类、注册项或测试数量不能作为产品功能数量。

## 五、证据来源与验收轴

### 证据来源

研究阶段可以使用以下简写，但正式结论必须同时写明具体来源、版本和覆盖范围，不能只写字母：

| 标记 | 证据来源 | 使用边界 |
| --- | --- | --- |
| A | 项目所有者明确提供或确认的用户体验 | 可以直接确立所有者实际说明的用户目标、名称或分组偏好、记忆中的工作流和产品取舍 |
| B | 当前有针对性的测试源码 | 只证明测试意图和静态断言存在；是否运行另行记录 |
| C | 当前 UI、配置或实现 | 证明当前静态实现形态，不自动证明实机可用 |
| D | 当前说明、历史修复或历史验证记录 | 可能陈旧，必须与当前证据交叉核对 |
| U | 当前无法证明 | 保持未知，不用推测补齐 |
| 冲突 | 多个证据对同一用户语义不一致 | 保留冲突双方和覆盖范围，不按材料数量多数表决 |

事实来源优先级遵循项目入口规则。证据来源越多不代表验收等级越高。

A 类证据不能单独证明内部技术正确性、资源安全、多人权威、性能或项目所有者未实际描述的边界；这些结论仍需与其风险相匹配的其他证据或实际验收。

### 验收轴

| 等级 | 含义 |
| --- | --- |
| V0 | 仅完成静态提取 |
| V1 | 完成自动逻辑或结构比较 |
| V2 | 完成截图或录屏对照 |
| V3 | 完成指定实机场景 |
| V4 | 项目所有者按用户体验完成验收 |

必须明确：

- 测试源码存在不等于测试已经运行；
- 测试通过不等于实机、多人、性能或用户验收通过；
- V0 可以形成研究基线，但不能声称实际等价已经证明；
- 每项结论只能覆盖实际使用的版本、环境和场景。

## 六、临时平替基线

临时平替基线必须存在当前用户入口、自动触发或明确的用户可观察结果，并通过以下任一证据门。这里的路径 A、B 是证据门路径，不等同于前节的证据来源标记 A、B。

**路径 A：静态交叉证据。**

- 至少两种相互独立、适用于该行为的静态证据基本一致；
- 适用组合例如 UI 与实现、配置与测试源码、当前实现与当前说明；
- 同一文件中的两个代码片段不得机械视为两类独立证据。

**路径 B：直接观察证据。**

- 已完成绑定明确 Legacy 版本、环境、初始状态和操作步骤的 V2 截图或录屏对照，或者 V3 指定实机场景；
- 观察结果明确，且没有关键反例或相反证据；
- 未覆盖的环境和边界仍保持未知。

无论采用哪条路径，还必须同时满足：

1. 没有关键反例；
2. 没有已知 Bug、资源损失、越权或尚未澄清的重大多人风险；
3. 继承的是用户结果，不要求复制 Legacy 内部架构；
4. 已明确适用范围和禁止结果；
5. 尚未验证的范围继续明确标记。

项目所有者的 A 类证据可以直接确立其实际说明的用户目标、名称或分组偏好、记忆中的工作流和产品取舍，但不能单独证明内部技术正确性、资源安全、多人权威、性能或未被实际描述的边界。

以下内容不得自动继承：

- 仅存在于旧类、旧 ID 或未接入控件中的行为；
- 纯内部预检、缓存、调度和诊断结构；
- 不可达入口、已知错误或历史残留；
- 复制、丢失、误移、越权、隐私泄露和假成功；
- 未澄清的服务器权威行为；
- 静态上明显不可实现或不安全的行为。

调查结论至少区分：

- **临时平替基线**：满足上述条件，可以继续进入差异验收；
- **保留现有表现**：用户结果暂按 Legacy 记录，但不复制内部实现；
- **有意兼容差异候选**：可能必须改变，等待证据或产品裁决；
- **无法证明**：当前证据不足，不得宣称等价。

临时基线升级为正式功能合同时，必须应用适合的风险深度，处理冲突和禁止结果，并写明仍未覆盖的范围。项目所有者可以批准一个功能簇、批次或长期裁决；满足既有裁决且证据充分的等价项可以按批次进入正式合同，不要求项目所有者逐字段重述或重复批准。只有差异、冲突、风险和无法证明项需要再次提交项目所有者裁决。不得把本地研究报告整体直接升级为正式合同。

## 七、合同深度按风险分级

合同深度由失败后果、数据是否可恢复、是否修改资源或权威状态、是否涉及多人/身份/隐私、操作频率和数据规模，以及证据不确定性共同决定。不得仅因为出现“Overlay”“逐帧”“文件”或“持久化”等关键词机械升级。

合同模板是字段库，不是所有字段一律必填。只填写对能力适用的字段；不适用项应简要说明原因。风险或证据发生变化时，应提升合同深度。

### 轻量合同

适用于简单开关、只读信息，以及数据有界、绘制简单、没有大规模扫描、没有明显逐帧动态分配、没有资源修改、没有多人写入和没有不可恢复状态的简单 Overlay。这类 Overlay 即使每帧绘制，也可以保持轻量合同。

至少记录：

- 用户目标；
- 入口；
- 显示内容；
- 刷新条件；
- 空态或不可用状态；
- 配置；
- 具体证据；
- 平替结论。

### 标准合同

适用于有状态 UI、用户选择、普通用户偏好和可重建配置的持久化，以及只需在角色/世界/会话切换时保存、恢复或重置普通 UI/配置状态的跨功能协作。快捷键、功能开关、UI 偏好、普通选择名单和可从默认值恢复的本地设置通常属于标准合同。

在轻量合同基础上增加：

- 控件与交互；
- 状态机；
- 保存与恢复；
- 数据自然归属；
- 错误与降级；
- 输入焦点；
- 差异验收场景。

### 高风险合同

适用于失败后果重大或难以恢复的物品、货币或其他资源修改，世界状态修改，输入模拟、自动化动作和多人权威操作。

持久化或数据能力只有在涉及以下风险时，才因这些风险采用高风险深度：

- 不可轻易重建的历史或事实数据；
- 角色、世界、角色×世界或服务器身份数据；
- 跨实体或跨存档持久化；
- 外部文件修改；
- 隐私敏感数据；
- 存在串档、碰撞、损坏或不可恢复风险的数据。

高频或逐帧路径只有在大规模、无界、包含复杂投影、存在明显动态分配或已有证据表明性能敏感时，才因性能风险采用高风险深度。

在标准合同基础上增加：

- 来源与目标；
- 适用的资源不变量、允许转化关系和部分完成；
- 成功判据和回滚边界；
- 幂等性和禁止结果；
- 提交、执行、观察和权威确认；
- 取消、超时、断线、重连和迟到结果；
- 性能形态和待测场景。

一个能力可以使用标准合同作为主体，只增加适用的高风险附加字段。不得为了形式完整而把全部高风险字段强制填满。

## 八、数据自然归属

每项持久数据必须先按用户语义判断自然归属，再决定存储方式：

- 玩家习惯与偏好；
- 角色事实；
- 世界事实；
- 角色×世界事实；
- 服务器事实；
- 单次会话状态；
- 可重新计算的派生缓存。

玩家习惯、操作偏好和功能选择默认全局共享；与具体实体绑定的事实按其自然归属隔离。不得用 Legacy 当前文件路径代替自然归属判断。

涉及身份和持久化时，必须检查稳定身份、fallback、重名、重命名、删除重建、云存档、服务器重连、迁移、碰撞和串档风险。一个用户能力可以同时包含不同作用域的数据，必须分别记录。

## 九、资源不变量、允许转化与部分完成

所有高副作用资源操作必须定义适用的：

- 来源和目标；
- 资格条件；
- 数量或价值单位；
- 允许变化和禁止变化；
- 部分完成；
- 成功判据；
- 回滚或补偿边界；
- 幂等性；
- 用户可见结果。

不同操作使用不同的不变量或允许转化关系：

- **转移操作**：同类资源在所有受控来源和目标范围内总量守恒，只允许位置和堆叠形态变化；
- **消耗操作**：只减少明确允许的数量，必须确认预期效果或动作成立，不能重复扣除，也不能在未生效时报告成功；
- **转换或交易操作**：明确输入、输出和允许的换算关系，不要求不同资源类型的原始数量相等，但必须验证输入扣除和输出产生之间的对应关系；
- **世界状态修改**：明确背包资源变化与世界状态变化的允许关系，不以单纯物品总量相等作为唯一标准；
- **有意删除或丢弃**：只允许删除明确选中的对象和数量，不得波及未授权资源，用户可见结果必须与实际结果一致。

“请求已提交”“来源数量减少”或“执行器返回成功”都不能单独证明适用的资源不变量或允许转化关系成立。没有端到端证据时，资源结果必须保持为无法证明；不得将控制流程的临时基线扩大为资源安全已经成立。

## 十、多人权威与回执

多人写操作必须分别记录：

- 客户端提交；
- 本地执行；
- 主机或服务器执行；
- 本地可观察变化；
- 权威确认；
- 最终回执。

合同必须说明谁拥有最终事实，未确认和超时如何处理，断线、重连和迟到结果如何处理，是否可能假成功，是否允许重试，以及如何防止重复执行。

“使用原版动作路径”或元数据声明支持多人，不等于多人已经验证。没有权威确认时，应安全停止或保持未确认状态，不得把本地提交或本地变化写成最终成功；在幂等性未证明前，不得无界重试。

## 十一、性能形态

行为考古阶段只记录：

- 功能关闭成本；
- 正常 cadence；
- 扫描对象和最大规模；
- 每 Tick 或每帧路径；
- 重复分配和重复快照；
- 缓存及其失效条件；
- 突发操作；
- 需要后续测量的场景。

不得由静态调用频率、循环或缓存直接宣称性能合格、FPS 根因、优化收益或多人性能等价。完整性能预算和测量规则由未来单独批准的性能规范承担；本规则只要求记录形态和待测场景。

## 十二、用户反馈与诊断反馈

行为契约必须分别记录：

- 普通用户能够看到的成功、失败、空态和不可用提示；
- 只存在于日志、快照、事件或诊断界面的信息。

诊断中存在原因不等于普通用户已经得到反馈，也不能用诊断结果替代用户可观察行为或 V4 验收。

## 十三、用户结果与内部预检

若内部预检、缓存、候选范围和最终实际动作不一致：

1. 以用户可观察结果和安全边界为合同对象；
2. 不把内部范围自动升级为产品能力；
3. 只有内部差异造成可见错误、资源风险、性能问题或无法实现时，才进入差异裁决。

## 十四、跨功能合同

窗口与 DPI、输入所有权、游戏输入隔离、Overlay 层级、文本与滚动、配置、身份、多人、诊断等跨功能行为，应在出现真实职责并获批准后集中定义一次。具体功能合同只引用适用的跨功能合同，不重复复制全文。

当前尚未建立这些正式跨功能合同。不得因本规则而预建新的一级目录、空文件或占位合同。

## 十五、差异验收

1. 从指定 Legacy 版本提取带证据的临时行为合同；
2. JueMingR 在另行获得实现授权后，按用户结果和安全边界实现；
3. 为相同初始状态、操作或触发生成 Legacy 与 JueMingR 对照；
4. 将结果标记为：等价、有意改进、有意收窄、缺失、冲突或无法证明；
5. 隐藏证据充分且等价的项目；
6. 只把差异、冲突、风险和无法证明项交给项目所有者；
7. 项目所有者按用户体验裁决，而不是从零复述全部旧需求。

自动逻辑比较、测试、截图、录屏、指定实机和项目所有者验收应按其实际覆盖范围分别记录，不得互相替代。项目所有者可以对功能簇、批次或长期适用的差异原则作出批准；满足既有裁决且证据充分的等价项可以按批次形成或更新正式产品合同，无须逐字段再次批准。只有新的差异、冲突、风险和无法证明项需要再次提交裁决。

## 十六、研究材料与正式合同生命周期

- 初步清点、考古笔记和方法试点保存在 `.local/`，不进入 Git；
- `.local/` 报告不是正式合同，也不独立裁定产品事实；
- 只有经过项目所有者批准的长期结论才进入正式文档；
- 正式文档只保留当前规则、决定或合同，不复制完整研究过程；
- 动态进度只记录在 GitHub Issues；
- 研究完成后不创建更新记录、文档更改历史或全量研究归档；
- GitHub Issue 和 Git 历史承担过程追溯。

文档类型、权威和替代方式遵循[文档治理规则](文档治理规则.md)；采用本方法的原因见 [ADR-0002](../决策/ADR-0002-Legacy平替策略与行为契约方法.md)。

## 十七、向项目所有者提问

只在以下情况提问：

- 证据冲突；
- 行为可能是 Bug；
- 无法确认普通用户是否可达；
- 新版必须改变用户工作流；
- 存在重大成本或产品取舍；
- 必须由用户记忆或实机体验裁决。

不得询问可继续静态查证的事实、只是 Agent 尚未搜完的内容、内部代码组织、测试实现方式或架构拆分方式。问题必须使用普通用户语言，并说明触发问题的证据或风险。
