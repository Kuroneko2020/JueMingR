# 测试与审计规则

- 状态：草案
- 生效条件：只有 ADR-0006 被项目所有者接受、相应路由更新并合并到 `main` 后，本规则才生效。
- 当前效力：本文件当前不得视为已授权的测试或审计门禁，也不授权创建测试项目、CI、分析器、审计脚本或生产代码。

## 一、目的与范围

本规则只管理：测试和审计何时触发、每种证据能够证明什么、测试判定依据、测试数据隔离、mock/stub/fake、flaky 与基础设施失败、快速与慢速检查、检查成本与退出和退休，以及完成结论的准确措辞。

本规则不管理：具体测试框架、CI 实现、项目总体架构、当前任务状态、具体功能测试清单、性能数值和发布版本体系。

测试仍需服从对应产品或行为合同。涉及 Legacy 行为、平台兼容、性能和文档事实时，分别遵循第十八节引用的现有规则。

## 二、基本原则

1. 自动检查只证明其实际断言、输入和运行环境覆盖的范围。
2. 编译、自动测试、Terraria 实机、多人、性能、项目所有者验收和发布必须分别记录，任一状态不得冒充另一状态。
3. 测试通过不能自动证明产品完成；审计通过不能自动证明用户行为正确。
4. 检查按实际改动和风险触发；普通任务只承担能够支持本轮结论的最窄相关检查。
5. 一个故障尽量只保留一个最强、最接近事实的主要门；重复检查必须有独立检测价值。
6. 检查自身的运行时间、维护时间、误报、flaky 和项目所有者等待均属于治理成本。
7. 不能安全运行、不能解释失败或不能说明判定依据时，应停止并保留未知，不得制造绿灯。

## 三、检查与证据分层

### 静态和结构检查

可以证明：

- 文件、格式和明确结构；
- 项目引用和依赖方向；
- 机器可读配置中的字段；
- 禁止依赖、禁止路径和明确的源代码结构事实。

不能证明：运行行为、Terraria Hook 可用、用户体验、多人同步或性能。

### 编译

编译通过只证明当前工具链和输入下可以编译。它不证明游戏可以加载、运行逻辑正确、功能可用、多人正确或性能合格。

### 单元测试

单元测试可以证明被隔离逻辑在给定输入下符合断言。它不证明完整 Terraria 环境、真实文件权限、Hook、UI 或多人行为。

### 组件或集成测试

组件或集成测试可以证明实际覆盖的组件组合、边界和环境。它不能自动外推为完整游戏、所有机器、所有渠道或所有服务器均正确。

### Terraria 实机

实机结果必须绑定：

- Terraria 精确版本和渠道；
- JueMingR commit 或构建；
- 机器和设置；
- 初始状态；
- 操作步骤；
- 实际结果和未覆盖范围。

一次实机只证明指定环境和场景，不自动证明其他版本、机器或玩法。

### 多人

多人验证必须按实际拓扑分别记录：

- 本地客户端观察与请求；
- Host & Play 的主机权威执行；
- 远程客户端观察；
- 连接独立专服时的结果；
- 最终权威同步与用户可见结果。

单人、mock 网络、请求已发送或本地状态变化均不能冒充多人验收。

### 性能

性能证据遵循[性能治理规则](性能治理规则.md)。自动功能测试不能代替性能基线、帧时、分配、延迟或指定场景测量。

### 项目所有者验收

项目所有者验收只覆盖项目所有者实际体验和明确裁决的场景。自动绿灯、AI 审查和工程人员推断均不能代替该裁决。

## 四、最小验证卡

标准或高风险的行为、测试和审计任务，应能在一屏内说明：

```text
本次要证明什么：
产品或行为依据来自哪里：
准备运行哪些检查：
每项检查能够证明什么：
每项检查不能证明什么：
是否修改了测试期待，原因是什么：
判定依据是否独立于本次实现：
测试数据写在哪里：
是否会接触真实游戏、网络或用户目录：
是否有慢检查，为什么触发：
失败如何区分产品、测试和环境：
哪些内容仍需实机、多人、性能或项目所有者确认：
```

简单文档任务不填写完整卡，只需使用任务契约中的目标、范围、相关静态检查和未执行项。

## 五、独立判定依据

- 测试判定依据可以来自已批准行为合同、已确认缺陷复现、用户确认的 Legacy 观察、规格、性质、不变量、变形关系或用户验收场景。
- 判定依据应在实现完成前明确；无法提前明确时，至少必须独立于实现结果重新建立。
- 新实现本身不能成为自己正确的唯一证据。
- 实现 Agent 可以编写测试，但不能独占定义正确答案。
- 独立审查 Agent 不得只检查测试是否绿色，还必须检查输入、断言和环境是否代表真实目标，以及是否存在关键反例。
- 没有单一完整判定依据时，可以组合多个部分依据，但必须明确各自缺口，不能用数量掩盖未知。

## 六、修改测试的合法与禁止情况

允许在以下情况修改测试：

- 已明确的新需求改变了合同；
- 旧测试的判定或 fixture 错误；
- 游戏或依赖版本的真实合同发生变化；
- 测试基础设施存在缺陷；
- 增加新的边界、性质、错误或回归覆盖。

每次改变期待必须说明：哪个合同或事实改变、旧断言为什么不再正确，以及新断言由什么独立证据支持。实现和测试可以在同一个任务或 PR 修改，但测试变化必须单独说明并审查。

禁止：

- 为让实现通过而弱化断言；
- 删除失败场景或无理由跳过；
- 扩大误差或时间窗口直到变绿；
- 吞掉异常或把失败改成日志；
- 保留两套实现只为同时满足新旧测试；
- 把“暂时无法测试”改写成“通过”。

## 七、mock、stub 与 fake

- mock、stub 和 fake 只证明模拟边界下的逻辑，不证明被替代依赖的真实行为。
- mock 调用成功不等于 Terraria、文件系统、网络或服务器实际成功。
- mock 多人不能称为多人验收；fake 文件系统不能证明真实路径、权限、锁定或恢复行为。
- mock 数量不是测试质量指标。
- 对高风险边界，应按实际风险补充真实组件、集成、实机或多人证据。
- 本规则不禁止合理替身；使用时必须说明替代了什么，以及因此不能证明什么。

## 八、测试数据隔离

- 测试不得默认读取或写入真实用户 `Documents`。
- 测试不得修改真实 Terraria 配置、安装目录、角色、世界或服务器数据，也不得修改 Legacy。
- 测试使用唯一、明确且可清理的临时根；并行测试不得共享可变输出根。
- 输出位置和测试宿主判定必须在会初始化默认路径的静态成员或启动逻辑之前确定。
- 正常结束和失败路径都应尽可能清理；崩溃后可能残留时必须说明位置和删除方式。
- 无法安全隔离时停止，不得冒险执行。
- 使用用户数据副本时，必须记录授权来源、脱敏方式、只读或复制边界和删除方式。

## 九、flaky、重试和环境故障

结果必须区分：

- 产品失败；
- 测试断言或 oracle 失败；
- 测试基础设施失败；
- 环境不满足；
- 不支持的版本；
- flaky 或当前无法稳定复现。

禁止通过无限重试把失败变绿、用一次偶然通过关闭缺陷、把基础设施故障写成产品通过，或静默忽略 flaky。

临时隔离或降级检查时，必须建立对应 Issue，说明影响，指定 owner 和恢复或删除条件；被隔离检查不得计入完整通过。重试仅可用于收集复现信息或处理已分类的瞬时基础设施问题，并须保留全部尝试结果。

## 十、字符串、源码和文档审计

可以自动检查确定性事实，例如：

- 必须存在的文件和 UTF-8；
- 相对链接和结构化字段；
- 项目引用、依赖方向和机器可读 manifest；
- 禁止路径；
- 明确资源键或用户可见精确文本合同。

不得用以下代理证明语义正确：

- 文档包含某句自然语言；
- 源码包含某个方法名；
- 测试文件包含某个断言字符串；
- 某个类或文件存在；
- 精确说明措辞没有改变。

若精确用户可见文本本身就是产品合同，应直接检查用户资源或实际输出，不检查说明文档是否包含该句。优先使用编译器、类型、结构化配置、行为测试和实机结果。

## 十一、检查分层

| 层级 | 典型内容 | 触发边界 |
| --- | --- | --- |
| 编辑或任务内快速检查 | 最窄结构、格式、类型或行为检查 | 当前编辑直接相关 |
| 提交前相关检查 | 受影响编译、测试、diff 和路径边界 | 准备形成提交 |
| PR 相关检查 | 受影响集成、依赖、安全和独立审查 | 标准/高风险或受保护分支 |
| 专项慢检查 | 跨组件、兼容、迁移或高风险边界 | 具体风险命中并获任务授权 |
| 夜间或周期检查 | 趋势、全量、兼容矩阵和 flaky 探测 | 已决定的长期周期任务 |
| 发布检查 | 工件、安装恢复、许可证和发布场景 | 发布候选 |
| Terraria 实机 | 指定游戏、渠道和用户场景 | 功能或兼容风险 |
| 多人与项目所有者验收 | 指定拓扑和实际用户结果 | 对应产品结论需要 |

不要求所有任务运行全部层级。共享基础设施、高风险行为和发布才逐步扩大范围；慢检查必须由具体风险触发。无关普通任务不等待夜间、发布或实机矩阵。本规则不直接决定 CI 实现。

## 十二、时间和成本边界

每项昂贵或持续性检查必须说明：防止什么故障、什么改动触发、预计或允许的时间范围、超出后怎么办、失败怎样解释、谁维护、是否与其他检查重复，以及何时降级或删除。

检查超出任务声明的时间边界时：

1. 停止无限等待并保存已有结果；
2. 判断是产品失败、检查故障还是范围过大；
3. 缩小检查或将其移到专项、夜间、发布或实机阶段；
4. 不为修复检查系统而默认增加更多检查。

安全、数据损坏和其他不可逆风险不能因为检查慢而伪装通过；应通过缩小、隔离或专门授权处理，而不是阻塞所有无关任务。项目所有者报告的约十五小时经历只作为治理负担，不作为仓库精确计时数据。

## 十三、覆盖率、测试数和绿灯

- 覆盖率是发现未执行区域的辅助信息；高覆盖率不证明断言正确。
- 测试数量不等于质量；绿灯数量不等于产品进展。
- 当前不设置没有数据依据的全项目统一覆盖率门、测试数量门或统一测试时长门。
- 不允许为了覆盖率执行无意义代码、制造空断言或拆分重复测试。

## 十四、原始证据与正式结论

- 完整日志、视频、测试输出和生成报告保留在本地或未来 CI 工件，不默认进入 Git。
- Issue 和 PR 只保存足以复核的命令、结果摘要、环境和证据范围。
- 不为每次测试生成新的正式 Markdown 更新记录；正式规范不累积测试流水。
- 路径、机器、角色名、世界名和服务器信息必须按需要脱敏。
- 原始数据由负责人解释，工具本身不具备裁定权。

## 十五、完成用语

应使用范围准确的状态，例如：

- “静态结构检查通过”；
- “编译通过”；
- “指定单元测试通过”；
- “指定组件测试通过”；
- “Terraria 1.x.x 指定单人场景通过”；
- “Host & Play 未验证”；
- “性能未测量”；
- “项目所有者已验收指定场景”。

不得仅写“全部完成”“完全通过”“生产可用”“多人支持”或“性能没问题”，除非对应的全部证据确实存在并明确列出范围。未做或未授权的轴必须写为“未做”“未验证”或“未知”。

## 十六、检查生命周期与退休

稳定基础原则只需说明防止什么错误、适用范围和何时被替代。

以下检查必须有完整生命周期记录：长期自动审计、周期性测试、昂贵阻塞门、临时事故规则、flaky 隔离、长期维护的回归数据集，以及持续占用 Agent、CI 或项目所有者时间的检查。

记录至少包括：触发、成本、owner、误报和 flaky、真实捕获、复核，以及删除、合并或降级条件。长期没有真实捕获、误报或 flaky 高、与更强检查重复、维护成本超过已证明收益，或适用架构已经退役时，应删除或降级。

不得为此新建 Excel、数据库或巨型规则台账。一次事故不自动产生永久全仓检查。

## 十七、停止条件

测试或审计任务出现以下情况时停止扩张：

- 无法说明判定依据；
- 测试设施规模超过当前行为目标；
- 连续两轮修改仍无法解释失败，准备进入第三轮无根因试错；
- 只能通过弱化测试继续；
- 检查之间互相矛盾；
- 慢检查超出预算；
- 需要建立新框架、CI 或架构；
- 需要修改任务白名单之外文件；
- 只能通过更多文档和审计证明现有审计。

停止时准确记录已有证据、未知和缺少的授权，不得将停止改写为通过。

## 十八、与其他规则的边界

- Legacy 行为、用户结果和验收轴见 [Legacy 平替与行为契约规则](Legacy平替与行为契约规则.md)。
- Terraria 版本、加载链、安装和多人拓扑见 [技术平台与兼容规则](技术平台与兼容规则.md)。
- 性能风险、测量和性能结论见 [性能治理规则](性能治理规则.md)。
- 文档权威、原始证据和生命周期见 [文档治理规则](文档治理规则.md)。
- 当前试运行授权与收口方式见 [最小工程治理试运行计划](../计划/最小工程治理试运行计划.md)。

本规则只引用上述职责，不复制其完整内容，也不因当前草案预建测试、CI、发布或架构设施。
