# Legacy 数据迁移规则

- 状态：草案
- 生效条件：只有 ADR-0009 被项目所有者接受、相关路由更新并合并到 main 后，本规则才生效。
- 当前效力：本文件当前不授权读取项目所有者真实数据正文、实现或运行迁移器、修改 Legacy、写入目标数据、建立目标 schema、创建项目骨架或生产代码。
- 对应任务：[Phase 0-P Issue #18](https://github.com/Kuroneko2020/JueMingR/issues/18)
- 决策依据：[ADR-0009：Legacy 数据迁移采用只读复制、幂等导入与显式冲突处理](../决策/ADR-0009-Legacy数据迁移采用只读复制、幂等导入与显式冲突处理.md)

## 一、目的与范围

本规则规定未来把 JueMingZ 的可保留数据导入 JueMingR 时必须遵守的数据安全、用户确认、身份、重复、冲突、一致性、失败和隐私边界。它只建立长期合同，不列举项目所有者当前实际文件，不决定具体类、数据库、JSON 结构、hash 算法、文件锁、事务、manifest 或 UI 实现。

本规则适用于 Legacy 标准数据根、用户明确选择的其它 Legacy 根，以及用户主动选择的受支持导出文件。它不授权扫描整块磁盘、读取与预检无关的私人内容、启动 Terraria、修改世界或执行任何真实迁移。

## 二、Legacy 永久只读

Legacy 从发现、预检、候选生成、提交、重试到迁移完成始终只读。迁移只能把所需数据复制到隔离候选并转换为 JueMingR 自有格式，不得：

- 在 Legacy 文件或目录中增加迁移标志；
- 修改内容、文件名、时间戳或权限作为完成标记；
- 移动、整理、覆盖或删除 Legacy 文件与目录；
- 让 JueMingR 在编译期或运行时依赖 JueMingZ；
- 因来源损坏、未知或导入成功而清理原件。

导入完成、失败、批次和重复身份只能记录在 JueMingR 自有数据中。来源不可写不是最佳努力目标，而是迁移资格的前置条件；无法维持只读时不得开始或继续提交。

## 三、Legacy 导入与普通 schema 升级

Legacy 导入与 JueMingR 自身 schema 升级是两个流程：

- Legacy 导入跨产品边界，必须识别来源产品、来源 schema、自然归属、目标实体、目标 schema、冲突和用户确认；
- JueMingR schema 升级只处理已经属于 JueMingR 的受支持旧 schema，遵循[版本、配置与发布规则](版本配置与发布规则.md)的兼容和拒写边界；
- Legacy 文件可被解析，不代表它是 JueMingR 的旧 schema；
- 一次 Legacy 导入成功，不代表未来 JueMingR schema 升级已经完成；
- 产品版本、Terraria 版本、来源 schema、目标 schema 和导入批次不得互相冒充。

两类流程可以复用未来经批准的安全基础能力，但不得共享一个含糊的“已迁移”状态。

## 四、数据自然归属

目标归属由数据代表的用户事实决定，不能由 Legacy 文件夹、文件名、旧 hash、当前角色、显示名或读取时上下文机械决定。

至少分别考虑：

- 全局：跨角色和世界共享的设置、功能开关、快捷键、普通 UI 偏好和个人创作库；
- 角色：只属于一个角色的事实；
- 世界：不依赖具体角色的世界事实；
- 角色×世界：由某角色在某世界产生的历史、坐标、实例或状态；
- 服务器：与明确服务器身份关联的事实；
- 会话：只对当前运行有效、默认不应成为长期迁移输入的状态。

全局习惯默认按全局迁移，不因用户当时选中的角色而拆分。角色、世界、角色×世界和服务器事实必须在目标身份可证明时按自然归属隔离。静态证据不能建立服务器身份时，不得用地址、显示名或运行模式猜测。

## 五、数据类别和迁移资格

迁移计划不得只使用“迁移/不迁移”二元结论。每类至少从以下资格中选择并说明原因：必须提供保留/导入能力、默认建议导入、可选导入、等对应功能或合同存在后再导入、不进入运行迁移、当前无法证明。

| 数据类别 | 自然归属基线 | 长期资格基线 | 主要前置或限制 |
| --- | --- | --- | --- |
| 映射明确的设置、功能开关、快捷键和普通 UI 偏好 | 全局 | 默认建议导入 | 目标设置合同、合法值、重复配置源的确定性优先级 |
| 笔记 | 全局个人创作 | 必须提供保留/导入能力 | 索引与正文作为一致性单元；不从正文猜归属 |
| 蓝图模板 | 全局个人创作 | 必须提供保留/导入能力 | 来源/内容版本与可映射能力；冲突时保留候选 |
| 蓝图世界实例 | 角色×世界 | 等对应功能和合同存在后再导入 | 目标身份、坐标、Terraria/内容兼容与实例快照 |
| 地图标记 | 角色×世界用户事实 | 默认建议或可选导入 | 目标地图功能、身份与坐标合同 |
| 死亡事件、游玩时间和足迹 | 角色×世界长期事实 | 可选导入 | 事实级去重、共同基线、时间/坐标语义与目标功能 |
| 死亡或探索等派生摘要 | 随其事实源 | 不作为独立事实源 | 优先从已导入原始事实重算；不能与原始记录重复计入 |
| 旅行恢复状态 | 角色×世界恢复状态 | 等语义等价的对应功能/合同存在后可选 | 可能改变难度、模式或恢复结果 |
| 行为记忆 | 按实际语义为角色或角色×世界 | 可选、deferred 或 not applicable | 只有身份和目标行为语义等价时提供，默认不选 |
| 日志、诊断、缓存、性能快照、临时、测试与构建产物 | 非运行迁移输入 | 不进入运行迁移 | 不自动导入、扫描、上传或删除 |
| 用户自行导出的受支持文件 | 由其格式内事实决定 | 用户主动选择后评估 | 单独核验来源、schema、身份和隐私；失败不改原文件 |
| 损坏、未知较新 schema 或证据不足的数据 | 未确定 | 当前无法证明 | 保留来源，报告 failed、deferred 或 conflict，不猜测 |

当前源码证据支持此分类，不代表项目所有者实际拥有任何一种文件，也不把实际文件数量写入稳定合同。

## 六、用户创作数据与内部缓存

笔记、蓝图模板、地图标记及其它用户明确创建、命名或长期积累且难以重建的内容，优先获得保留与导入能力。保留优先不等于无条件自动导入：身份、schema、目标能力和冲突门仍须通过。

缓存、诊断快照、性能采样、临时文件、可重算摘要、测试输出以及仅服务 Legacy 内部自适应的状态，不得因具有文件或 schema 就被当作用户事实。派生数据只有在不能可靠重算且其用户价值、语义和安全合并合同已确认时，才可单独评估。

当用户创作内容与显示名、排序、派生统计或缓存冲突时，应优先保护内容和可追溯来源，不能为了保留外围元数据而丢弃正文或主体。

## 七、迁移入口和用户确认候选

迁移入口属于项目所有者待接受的产品策略。当前草案推荐以下组合：

1. 首次只在明确的标准 Legacy 根被检测到时显示只读迁移预览，不自动写入；
2. 用户明确确认所选类别后才允许导入；
3. 设置中保留可重新打开的“导入旧版数据”入口；
4. 用户可以主动选择其它 Legacy 根或受支持导出文件；
5. 不选择、取消或关闭预览时不写入，未来仍可重新预检；
6. 不采用首次启动无提示全量迁移或其它静默迁移。

用户确认面向设置与快捷键、笔记、蓝图、地图与足迹、死亡与游玩历史、其它功能状态等可理解类别。不得要求用户理解 JSON 类名、hash 算法、schema 类、store/service、内部 Feature ID、事务或 Git 操作。

本节在 ADR-0009 和本规则被接受前只是候选，不表示产品入口已经批准。

## 八、来源发现和禁止全盘扫描

自动发现只允许检查产品合同明确列出的标准 Legacy 根，不得递归扫描整块磁盘、用户主目录、云盘或所有 JSON 文件来寻找旧数据与 exports。

非标准根、用户自行导出的文件和位于任意位置的外部候选，只能由用户通过明确的目录或文件选择入口提供。选择一个根不授权读取该根以外的路径；选择一个导出文件不授权枚举同目录其它文件。

发现阶段只收集形成分类预检所需的最少元数据。任何读取正文的必要性必须由具体格式合同和实现任务重新证明；本规则本身不需要也不授权读取真实正文。

## 九、预检与迁移计划

任何写入前必须生成只读预检和面向用户的迁移计划。预检至少记录：

- 找到的来源根和受支持类别；
- 每类来源身份、可识别 schema、来源文件或逻辑项数量；
- 每类数据数量或可安全计算的范围；
- 目标功能、目标 schema 和目标实体是否存在；
- 目标是否已有数据及预检时的目标基线；
- 预计 `imported`、`skipped`、`conflict`、`failed`、`deferred`、`not applicable`；
- 不会迁移、无法映射和需要用户确认的内容；
- 损坏、截断、未知较新 schema、部分缺失和多文件不一致；
- 提交前必须再次成立的来源与目标条件。

预检不得修改来源或目标，也不得把“可解析”写成“可安全导入”。预检结果变化后，旧确认不能自动扩大到新增类别、不同来源或更高风险的覆盖行为。

## 十、来源、schema、目标和导入批次身份

每个导入单元必须分别记录或可复核：

- Legacy 产品与来源根身份；
- Legacy 数据类别与来源 schema；
- 来源文件或逻辑项身份，以及预检时来源条件；
- Terraria 或内容环境中与语义映射有关的版本证据；
- JueMingR 目标实体身份与目标 schema；
- 导入实现或工具版本；
- 本次导入批次身份；
- 预检时目标基线、最终目标写入结果与分类状态。

来源指纹必须识别合同要求的“相同来源、相同内容、来源新增、来源修改和中断重试”，但本规则不决定具体 hash 或 manifest。文件时间、显示名、旧目录名或单一旧 hash 均不足以独自证明同一来源与同一实体。

## 十一、目标功能和目标 schema 前置门

一类数据只有同时满足以下条件才允许真正导入：

- JueMingR 对应用户功能或正式数据合同已经存在；
- 自然归属与目标实体身份已经确定；
- 目标 schema 已按项目规则批准；
- 来源到目标的语义映射、不可映射项和兼容限制已经明确；
- 重复、冲突、失败、恢复和已有目标数据处理已经定义；
- 对应自动验证、审计或项目所有者实机验证已经获得独立任务授权。

目标门未通过时只能报告 `deferred` 或 `not applicable`，不得先塞入临时字段、通用 JSON、未批准数据库或隐藏目录等待以后解释。数值 Tile/Object ID 可读、旧 hash 可计算或旧文件存在，都不能替代目标合同和 Terraria/内容兼容门。

## 十二、幂等和重复导入

重复执行同一预检或导入不得重复创建、重复追加、重复累加或静默改写已导入事实。每个单元至少区分：

- 来源完全相同且已成功导入；
- 同一来源新增了可识别数据；
- 来源被外部修改；
- 目标被 JueMingR 修改；
- 来源和目标同时变化；
- 旧批次失败、中断或结果不可证明。

合同必须防止重复笔记、蓝图、地图标记、死亡事件、足迹段/点和游玩时间累加。原始事实与派生摘要不得各自作为独立来源产生双计数；仅文件时间变化不得触发全量再导入。

内容完全相同且来源/目标身份可证明时可报告 `skipped`。无法建立事实级重复身份时，不得以名称、计数、最后时间或目录 hash 猜测相同。

## 十三、增量导入

增量导入只有在同一来源、同一目标实体、共同基线、顺序或事实级唯一身份均可证明时才可自动执行。实现必须能够说明哪些项目是此前已导入、哪些是来源新增、哪些在双方分别变化。

追加事件按来源事件身份或经审计的等价键去重；累积计数不得在每次运行时再次相加；派生摘要优先从目标事实重算；列表和创作内容只有在合并规则保持全部用户结果时才可增量合并。

无法证明共同基线、来源发生改写、目标已独立编辑或旧批次状态不完整时，停止自动增量，把完整候选留在隔离位置并报告 `conflict` 或 `failed`。

## 十四、身份映射和歧义

Legacy 的路径、路径 hash、cloud/local 标志、GUID、world ID、map 文件名、显示名、别名和旧 pair ID都是来源身份证据，不自动成为 JueMingR 永久身份。目标身份由未来正式数据合同决定。

身份映射必须显式处理：重名、重命名、路径移动、云端与本地切换、复制角色或世界、删除后重建、世界 GUID 复制、fallback、服务器世界、证据碰撞和无法唯一映射。不同证据互相冲突、只有显示名相同或旧 hash 语义不足时，状态保持 `conflict`，目标不变。

不得自动把两个可能不同的实体合并，也不得把同一实体的多个候选静默拆成不同永久身份。需要用户确认时，界面应说明可理解的角色/世界候选与结果，不要求用户裁决 hash 或字段映射。

## 十五、冲突和安全合并

冲突判断至少区分：

- 内容完全相同；
- 目标不存在；
- 目标已存在且可证明是同一来源；
- 来源与目标各自有新增内容；
- 名称相同但身份不同；
- 身份相同但内容不同；
- 身份无法证明；
- 目标 schema 或功能不能表达来源语义。

默认禁止静默覆盖 JueMingR 已有数据。只有数据类别具有确定、可验证、不会丢失任何一方用户结果的安全合并规则时，才允许自动合并，并在结果中报告。

无法安全合并时，保持现有目标不变、保留隔离的 Legacy 候选并报告 `conflict`。产品入口应允许用户选择另存、跳过或显式替换；替换必须展示范围、将被改变的目标和恢复边界。不得让用户逐项处理确定性规则可以安全解决的纯重复。

## 十六、多文件一致性单元

单个文件原子替换不能冒充多文件迁移安全。未来设计至少应为下列关系定义一致性单元：

- 笔记索引与正文；
- 蓝图模板、实例、快照和正式引用；
- 原始事实与派生摘要；
- 玩家/世界/角色×世界 identity 与对应事实；
- 导入 manifest 或等价批次记录与实际目标数据。

每个单元必须先在隔离位置形成完整候选，整体校验，明确目标事实源的单一切换点，识别中断状态，并保证失败后可恢复或继续。只有整个单元的提交条件成立才能报告 `imported`；部分文件写入或单一 replace 成功不得代表整体成功。

本规则不决定使用数据库事务、文件事务、锁、generation、manifest 或其它具体实现。

## 十七、并发与条件式提交

来源和目标都可能在预检后被 Legacy、JueMingR、另一个进程、云同步或用户操作改变。迁移实现必须：

- 把来源预检条件延续到提交点，而不是只在开始检查一次；
- 提交前重新核对目标实体、目标 schema 和已有目标数据基线；
- 只在来源与目标均满足已确认条件时提交；
- 无法建立条件式提交或安全排他窗口时拒绝自动覆盖；
- 发现任一侧并发变化时保留候选并报告 `conflict`；
- 不用比当前来源更旧的备份声称完整恢复。

具体锁、compare-and-swap、事务或重试实现延期到架构和迁移器任务。

## 十八、原子提交、失败和恢复

失败必须以一致性单元为边界处理：Legacy 原件始终不变；未提交候选不成为目标事实源；已经完整提交的单元保持可识别；未完成单元可安全重试；目标原有数据不因失败消失。

若提交需要修改已有目标数据，设计必须在写入前说明可恢复边界并通过相应故障测试。本规则不承诺未经实现、掉电、中断和并发验证证明的“完整回滚”，也不以保留临时文件冒充恢复成功。

全局批次可以包含多个独立单元并得到混合结果，但不能把部分单元成功写成全部成功。重试必须从可复核批次状态和当前来源/目标条件重新判定，而不是盲目重放全部写入。

## 十九、导入结果状态

每个数据类别和一致性单元使用以下结果之一，并提供不含私人正文的原因：

| 状态 | 含义 |
| --- | --- |
| `imported` | 该单元完整通过目标门、校验和提交条件，并成为可识别的目标事实 |
| `skipped` | 无需写入，例如完全相同且已导入、用户未选择或确定性重复 |
| `conflict` | 身份、内容、共同基线、并发或安全合并条件无法证明，目标保持不变 |
| `failed` | 读取、解析、校验、候选生成或提交失败；不得把空默认值写成成功 |
| `deferred` | 目标功能、schema、身份合同、兼容门或验证尚未就绪 |
| `not applicable` | 该类别按批准合同不属于此目标或不进入运行迁移 |

批次摘要必须保留各状态计数和单元级可复核原因；“检测到”“可解析”“候选生成”“单文件已写”都不是 `imported`。

## 二十、隐私和脱敏

迁移只读取完成所选类别预检与转换所必需的最少信息。长期规则、Git、Issue、PR、迁移报告或支持材料不得保存或上传：

- 笔记正文或蓝图具体内容；
- 玩家名、世界名、服务器地址或其它真实身份；
- 私人绝对路径、账号或机器名；
- 日志正文、诊断包正文；
- 角色或世界文件内容；
- 与迁移结果无关的用户导出内容。

本机 UI 如为用户辨认候选而显示必要名称或路径，仍须遵循最少显示、明确用途和不进入持久报告的边界。审计材料优先使用类别、脱敏来源 ID、schema、计数和状态。需要支持证据时走独立的用户选择与脱敏流程。

本规则依据源码与模型即可完成，不需要读取项目所有者真实数据正文。

## 二十一、日志、诊断、缓存和测试产物

日志、诊断包、运行快照、性能趋势、recent buffer、缓存、临时文件、备份残留、测试输出、构建输出和 TestPackage 默认不进入 JueMingR 运行数据迁移。迁移流程不得自动扫描、导入、上传或删除这些内容。

来源备份只有在具体类别合同证明其身份、时序和恢复资格时才可作为候选；备份文件存在不等于它比主文件更新或完整。支持人员需要日志或诊断时，由用户通过独立入口明确选择，且该过程不改变迁移结果。

## 二十二、用户自行导出的文件

用户导出可能位于任意位置，JueMingR 不扫描磁盘寻找它们。只有用户主动选择一个文件或受控目录后，导入流程才可接触该候选。

每个候选必须单独核验格式 kind、来源产品、schema、内容/环境版本、逻辑身份、目标功能和冲突策略。选择文件名相同、扩展名相同或 JSON 可解析不足以证明受支持。读取或导入失败不得修改、移动、重命名或删除原文件，也不得扩大扫描到同目录其它文件。

## 二十三、清理旧数据的独立授权

本规则不授权清理 Legacy。未来若提供“清理旧数据”，它必须是与导入分离的独立用户操作：

- 不因导入成功自动执行或默认选中；
- 明确展示将影响的路径、类别和范围；
- 取得单独确认并说明恢复边界；
- 不把迁移记录或本规则当作删除授权；
- 由专门合同和实现任务定义，迁移器不得自行决定。

## 二十四、实现、测试和实机边界

本规则不授权总体架构、目标 schema、迁移器、项目骨架、生产代码、依赖、测试、构建、CI、打包、发布或真实迁移。实现任务必须重新取得精确路径和行为授权，并遵循[工程治理规则](工程治理规则.md)。

未来验证至少分别覆盖：格式/schema 与未来版本拒写、身份歧义、事实级幂等、增量、冲突、并发变化、多文件中断、部分失败、恢复、隐私脱敏和来源只读。测试通过、静态审查、单文件原子写入或本地候选成功不能单独证明 Terraria 实机、多人、云同步、性能、真实私人数据兼容或项目所有者验收。

所有需要启动或操作 Terraria 的验证由项目所有者亲自执行，并须在独立任务中给出最小步骤与脱敏回传要求。没有该授权时，Agent 不得运行 Terraria 或真实迁移。

## 二十六、规则演进与替代

本文件在 ADR-0009 被项目所有者接受、相关稳定路由更新、最终 head 复核通过并合并到 `main` 前始终是未生效草案。起草、独立审查、PR 通过或项目所有者讨论都不单独使它生效。

生效后的实质变更应由新的任务、相称审查和项目所有者授权完成；改变只读边界、默认范围、身份/冲突结果、清理权限或隐私边界时，应通过新的 Accepted ADR 明确替代或修订。实现细节可以在不改变本规则用户结果和安全边界的前提下演进，但不能以实现方便弱化合同。

本规则可在合并前直接放弃；合并后也可由新的 Accepted ADR 与对应规则明确替代。任何替代都不得追溯授权已经被禁止的 Legacy 修改、私人数据读取或静默覆盖。
