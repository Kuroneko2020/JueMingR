# 版本、配置与发布规则

- 状态：有效
- 决策依据：[ADR-0007：版本、配置与发布采用分层身份和显式迁移](../决策/ADR-0007-版本配置与发布采用分层身份和显式迁移.md)
- 生效边界：本规则自包含本文件和 ADR-0007 的提交合并到 `main` 后生效。
- 授权边界：本规则规定版本、构建身份、配置 schema、迁移和发布边界；它本身不分配产品版本，也不授权创建 Tag、Release、Changelog、发布资产、迁移器、构建、打包、CI、项目骨架或生产代码。

## 一、目的与范围

本规则用于把源码状态、构建产物、用户看到的产品版本、持久化数据格式、Terraria 兼容环境和正式发布记录分开管理，并建立它们之间可复核的追溯关系。

本规则只规定信息、状态和安全边界，不实现版本生成、配置迁移、构建、打包、发布或 CI 工具。当前没有分配 JueMingR 的首个实际产品版本，也没有授权任何正式发布。

平台、安装恢复和多人拓扑继续遵循[技术平台与兼容规则](技术平台与兼容规则.md)，验证证据继续遵循[测试与审计规则](测试与审计规则.md)，性能声明继续遵循[性能治理规则](性能治理规则.md)，文档职责继续遵循[文档治理规则](文档治理规则.md)。本规则的选择理由见 [ADR-0007](../决策/ADR-0007-版本配置与发布采用分层身份和显式迁移.md)。

## 二、六种身份分别管理

以下六种身份回答不同问题，必须分别记录，不得互相冒充。

| 身份 | 回答的问题 | 最低记录 | 不能替代 |
| --- | --- | --- | --- |
| 源码身份 | 哪一份源码和仓库状态 | Git commit、分支或 PR、工作区 clean/dirty | 产品版本、构建产物、发布批准 |
| 构建身份 | 哪些受控输入通过什么受控工具和入口形成了哪些字节 | 来源 commit、clean/dirty、构建类型、目标、工具链、入口、主要参数、引用与依赖、构建记录时间、产物 SHA-256 | 用户版本、运行验证、正式发布 |
| 产品版本 | 用户把哪次发布识别为哪个版本 | 获准发布准备中确定的 `MAJOR.MINOR.PATCH` | commit、Issue、Phase、配置 schema |
| 配置或数据 schema | 持久化数据采用什么格式 | schema 身份、可读版本、可写版本和迁移边界 | 产品版本、程序集版本、Terraria 版本 |
| Terraria 兼容记录 | 哪些游戏环境和场景实际受支持 | 精确游戏版本、渠道、Windows、编译引用、实机场景和限制 | 编译成功、产品版本、泛称“1.4.x” |
| 正式发布记录 | 用户实际可以下载和核验什么 | 产品版本、Tag、Release、commit、资产、SHA-256、说明、验证范围和批准 | 本地包、测试包、文档或自动绿灯 |

### 源码身份

- Git commit 标识仓库中已经提交的精确源码状态。
- 分支和 Pull Request 用于协作、审查和合并，不是产品版本。
- 每次构建都必须记录工作区是 `clean` 还是 `dirty`。
- `dirty` 表示产物包含不能只由所记录 commit 还原的本地变化；不得省略或伪装成 clean。
- Issue、Phase 名称和提交数量都不能充当源码内容的唯一身份。

### 构建身份

完整构建身份回答：“哪些受控输入，通过什么受控工具和入口，形成了哪些具体字节？”每个需要交给他人使用或长期判断的构建，至少记录：

- 来源 Git commit；
- 工作区 `clean` 或 `dirty`；
- Debug、Release、专用诊断或其他明确的构建类型；
- 目标框架、PlatformTarget、进程位数和必要运行目标；
- .NET SDK、Visual Studio Build Tools、MSBuild、编译器或等价工具的可复核版本；
- 使用的解决方案、项目、正式脚本或命令入口；
- 影响输出的主要参数，包括 Configuration、Platform、TFM、条件编译常量、版本输入、依赖模式，以及会实际改变产物的环境变量或显式参数；
- Terraria、ReLogic、XNA 等受控编译引用的身份；
- 第三方依赖的锁定身份、来源和必要哈希；
- 产物清单及每个产物的 SHA-256；
- 构建记录生成时间和时区。

构建时间默认保存在外部构建记录中。除非后续通过独立决定，不要求把不断变化的时间戳嵌入二进制，也不得因嵌入当前时间而无意破坏确定性或可重复构建。

获准的 `dirty` 诊断构建不能只记录一个 `dirty` 标签；未提交输入必须具有补丁、diff 或等价不可歧义摘要的可复核身份，具体形式延期到项目骨架阶段决定。无法建立未提交输入身份时，该构建只能支持当次探索性诊断，不能把其结论直接迁移为 clean 候选证据，也不得成为正式发布候选。

记录 commit 不等于自动证明实际由该 commit 构建；确定性构建也不等于来源身份自动可信。SHA-256 只标识具体文件字节，不证明作者、正确性、安全性、实机验证或发布批准。当前不决定具体 SDK、MSBuild 属性、构建 manifest 或自动生成方式。

### 产品版本

- 产品版本是用户看到并用于区分发布的版本。
- 产品版本只在明确获准的真实发布准备中确定和推进。
- 内部任务、Phase、Issue、PR、commit、文档、测试、审计、构建和打包完成，都不自动推进产品版本。
- 产品版本不表达配置 schema、程序集绑定身份、Terraria 版本或某次构建的全部细节。

### 配置或数据 schema

- schema 描述持久化数据合同，而不是软件整体成熟度。
- 产品版本和 schema 必须分开；产品不变时 schema 仍可能因受控修复演进，产品升级也可能不改变 schema。
- 不同长期数据合同可以独立演进，例如全局偏好、快捷键、笔记索引和蓝图不必共享同一机械版本。
- 日志、缓存、诊断快照和可删除临时文件不因存在结构就必须拥有长期 schema。

### Terraria 兼容记录

兼容记录必须分别说明：

- Terraria 精确版本和程序集身份；
- Steam、GOG 或其他实际渠道；
- Windows 版本和必要能力；
- 编译引用使用的 Terraria 版本；
- 项目所有者亲自执行的实际 Terraria 版本与场景；
- 单人、Steam Host & Play、连接独立专服分别验证到哪里；
- 未验证范围和已知限制。

编译引用版本可以与实机版本不同，但必须分别记录。编译成功、版本探测或静态兼容表不能冒充项目所有者实际执行的游戏内验证。

### 正式发布记录

每个正式发布至少关联：

- 产品版本；
- 指向精确 commit 的 Git Tag；
- 对应 Tag 的 GitHub Release；
- 来源 commit；
- 发布资产清单；
- 每个资产的 SHA-256；
- 用户可读发布说明；
- 自动、Terraria 实机、多人、性能和项目所有者验收的实际范围；
- 项目所有者明确发布批准。

## 三、产品版本

JueMingR 使用用户可理解的 `MAJOR.MINOR.PATCH` 作为项目自己的正式产品版本规则，但本规则不分配首个实际版本。当前不宣称严格遵守 Semantic Versioning 所定义的 public API 兼容模型；三段数字仍具有以下稳定的项目含义：

| 段位 | 项目语义 | 典型变化 |
| --- | --- | --- |
| `MAJOR` | 需要用户明确注意和接受的不兼容产品变化 | 产品身份或核心使用方式发生破坏性改变；主要用户工作流不再按原合同工作；已承诺的用户数据、升级路径或回退边界发生不兼容改变；旧版本用户无法通过受支持迁移继续使用重要数据；需要明显且不可忽略的破坏性迁移或重新配置 |
| `MINOR` | 保持既有用户合同和受支持升级路径的新增用户价值 | 新增向后兼容的用户能力；现有功能获得显著但不破坏旧行为的扩展；新增受支持的 Terraria、Windows、渠道或多人能力；增加可选的新配置或数据能力，且旧数据仍有明确、安全的升级路径 |
| `PATCH` | 不破坏既有用户合同的修复 | 缺陷、稳定性、性能或安全修复；恢复已经声明支持的 Terraria 或 Windows 兼容；不改变用户合同的内部实现修正 |

段位判断必须遵守：

- schema 版本变化不能机械决定产品版本段位；
- Terraria 兼容记录变化也不能机械决定产品版本段位；
- 判断依据是用户行为、数据、升级路径和支持范围实际发生了什么；
- `0.x` 阶段仍必须遵守已经明确承诺的用户行为和数据边界，不能把“未到 1.0”当作任意破坏合同的理由；
- 同一变化同时包含不同级别时，以最高实际用户影响为准；
- 无法判断时，Agent 必须列出实际用户影响和推荐段位，由项目所有者裁决该次用户发布意义；
- 项目所有者不负责判断内部代码、`AssemblyVersion` 或 schema 实现。

- JueMingZ 的版本号不延续到 JueMingR。
- `Phase 0-N` 是内部阶段名称，不是产品版本。
- 多个 commit 可以共同形成一次发布；一个 commit 也可以永远不发布。
- 修正文档、通过测试、完成审计、生成测试包或推进内部阶段都不自动改变产品版本。
- 何时进入 `1.0` 由后续产品成熟度、实际用户合同和项目所有者决定。
- 若未来宣称严格遵守 Semantic Versioning，必须先明确其所要求的 public API 以及兼容性判断对象；不能用 SemVer 代替配置、存档、运行行为、多人、Terraria 或性能合同。
- 预发布标识、Tag 命名和首版编号在第一次真实发布准备中决定，本规则不提前定案。

## 四、程序集版本

以下概念必须区分：

| 概念 | 主要用途 |
| --- | --- |
| `AssemblyVersion` | CLR 程序集身份、引用和适用的绑定策略 |
| `FileVersion` | Windows 文件属性中显示的文件版本 |
| `InformationalVersion` | 可携带用户版本和来源信息的说明性字符串 |
| 产品版本 | 用户识别一次发布的版本 |
| Git commit | 精确源码身份 |

当前不决定这些字段的最终映射方式。后续项目骨架必须做到：

- 使用一个权威版本输入，避免多处手工同步；
- 让产物能够显示产品版本和精确 commit；
- 根据 CLR 与宿主约束决定 `AssemblyVersion`，不为了每个 commit 无意义地改变它；
- 分别验证程序集元数据、Windows 文件属性和用户显示结果；
- 不把 `InformationalVersion`、文件名或包内文本当作来源 commit 的唯一证明。

精确 MSBuild 属性、自动生成方式和 Source Link 是否采用，延期到项目骨架阶段决定。

## 五、开发包、项目所有者测试包和正式发布

### 本地开发包

- 只用于开发、调试和诊断，不构成正式版本。
- 必须能够追溯到来源 commit；工作区 dirty 时必须明确标记。
- 可以包含不适合发布的诊断信息，但必须受任务授权、隐私和清理边界约束。
- 本地构建成功不能写成测试、实机、多人、性能、验收或发布通过。

### 项目所有者测试包

- 只用于项目所有者亲自执行获授权的 Terraria 实机场景。
- 必须绑定来源 commit、完整构建身份、项目所有者实际运行资产的 SHA-256 和普通语言测试说明。
- 默认应来自可复现的 clean commit；若获准使用 dirty 诊断包，必须显著标记且不得转为正式发布候选。
- 必须写明覆盖与未覆盖的 Terraria 版本、渠道、单人、Host & Play、独立专服、性能和恢复场景。
- 它不是正式发布；测试通过不自动产生产品版本或发布授权。

### 正式发布

- 必须具有已经获准的产品版本。
- 必须具有不可歧义地指向来源 commit 的版本 Tag 和 GitHub Release。
- 必须具有发布资产、SHA-256、依赖与许可证信息、发布说明和实际验证范围。
- 必须来自 clean 源码状态，并由项目所有者明确批准。
- 正式发布不能只把本地包或测试包改称为正式发布并跳过发布准备门；同一字节的 clean 测试资产可以在重新满足全部发布准备门后提升为正式发布资产。

### 受测资产与正式发布资产闭环

所有需要项目所有者 Terraria 实机证明的支持声明，都必须回答：“项目所有者实际运行的字节，与最终提供给用户的字节是什么关系？”只允许以下两条安全路径：

**路径 A：直接提升同一份最终候选资产。**

1. 从 clean 的发布候选 commit 和受控构建输入生成候选资产；
2. 记录候选资产的完整构建身份和 SHA-256；
3. 项目所有者亲自测试该精确资产；
4. 完成自动检查、许可证、发布说明、批准等其余发布门；
5. 正式 Release 使用完全相同的资产字节，并补齐产品版本、Tag、Release 页面和批准记录，不修改资产内容。

如果文件名、压缩内容、配置、签名、内嵌版本或其他处理导致资产字节变化，就产生新的资产身份，不再属于这条路径。单纯改变称呼不能跳过任何发布门。

**路径 B：通过可重复构建证明重新生成的资产等价。**

1. 项目所有者先测试候选资产；
2. 最终资产从相同 commit 和完整受控输入重新生成；
3. 通过确定性或可重复构建证据证明最终资产与受测资产字节等价；
4. 若最终 SHA-256 不同，就不能视为字节等价，也不能仅因来源 commit 相同就视为已经实机验证；无法证明字节等价时，必须对最终字节重新执行相关验证。

项目所有者的 Terraria 实机仍由项目所有者亲自执行。Agent 只能准备资产、步骤和证据分析，不能通过自动操作 Terraria 代替该证据。

## 六、配置 schema 与读取状态

每个需要长期维护的结构化配置或数据合同，应明确：

- schema 的稳定身份和版本；
- 当前程序能够读取的版本集合；
- 当前程序会写出的版本；
- 每个已知旧版本到当前写入版本的迁移路径；
- 未知较新版本的处理；
- 文件损坏和部分字段非法的处理；
- 备份、恢复和冲突处理；
- 是否支持降级；未明确承诺时视为不支持。

读取至少区分以下结果，不得压成一个“加载失败”或直接变成默认配置：

| 读取结果 | 最低处理边界 |
| --- | --- |
| 文件不存在 | 可以在合同允许时使用默认值或创建首份配置；记录这是首次缺失，不是损坏 |
| 当前 schema 且合法 | 正常读取；只有真实修改或获准规范化时才写回 |
| 已知旧 schema，可迁移 | 进入明确的有序迁移；迁移完成前不覆盖来源 |
| 未知较新 schema | 拒绝旧程序写回；保留原件并说明需要更新程序或人工处理 |
| 文件损坏 | 保留原件；报告损坏；不得用空默认配置覆盖 |
| 权限失败 | 报告读取或写入权限问题；不得伪装成文件不存在 |
| 部分字段非法 | 按该合同明确的拒绝或隔离恢复策略处理；保留可复核原件和具体错误 |
| 外部并发修改 | 停止提交并报告冲突；不得覆盖读取后由其他程序或用户产生的变化 |
| 迁移失败 | 保留来源或备份；报告失败阶段；不得写成成功或当前 schema |

禁止：

- 把解析失败当成没有配置；
- 用空默认配置覆盖损坏文件；
- 旧程序读取未知新 schema 后重新写回；
- 静默丢弃无法识别的数据；
- 把迁移失败写成成功；
- 只因反序列化器给字段填入默认值，就认定缺失字段合法；
- 只因未知字段被库默认忽略，就认定能够无损降级写回。

## 七、配置迁移

配置迁移必须满足：

1. 将来源作为只读输入，不在原文件上就地修改；
2. 明确起始 schema 和目标 schema；
3. 使用按版本排列、可单独解释的迁移步骤；
4. 在迁移前验证来源结构、版本和适用条件；
5. 在内存或隔离目标中形成迁移结果；
6. 在落盘前验证目标结构、不变量和必要数据；
7. 明确迁移对象是单文件还是多文件一致性单元，并按下述相应合同提交；
8. 保留来源原件或唯一、可识别的备份；
9. 失败时不覆盖仍可恢复的原件；
10. 分别报告成功、无需迁移、跳过、冲突和失败；
11. 重复执行不得重复生成数据、重复应用转换或损坏结果；
12. 来源身份条件必须从最终复核原子地延续到事实源切换完成；发现外部并发修改时停止。

### 单文件迁移

单文件迁移必须在同一受控文件系统边界内使用同目录临时文件，完整验证目标后再原子替换，并同时满足：

- 保留来源原件或唯一、可识别的备份；
- 保护来源身份到事实源切换完成之间的并发边界；
- 失败不覆盖可恢复原件；
- 重复执行保持幂等。

### 多文件一致性单元

多个文件共同表达一个事实时，逐个文件原子替换不等于整组迁移原子。每个具体多文件合同必须在实现前声明：

1. 哪些文件属于同一个一致性单元；
2. 是否允许新旧版本文件混合存在；
3. 哪些文件必须保持同一 schema 或同一提交世代；
4. 是否先在隔离目录完整生成全部目标文件；
5. 怎样对整个候选文件组进行完整验证；
6. 怎样表示未开始、正在准备、候选已完整、已切换、切换中断和需要恢复；
7. 哪一个动作是把新文件组切换为当前事实源的提交点；
8. 中途失败后怎样识别当前状态；
9. 怎样恢复到旧文件组或继续完成；
10. 重复执行怎样避免重复导入、混合版本和重复副作用；
11. 何时允许清理旧文件组和迁移状态；
12. 备份和清理失败如何报告。

具体合同以后可以选择 manifest、版本指针、目录切换、事务日志、提交标记或其他可恢复协议；本规则不预先选择实现。单个文件全部原子不证明文件组整体一致。新文件组只有在整体验证和明确切换完成后才能成为当前事实源；无法证明文件组一致性时，必须保留隔离候选并报告，不能把半迁移状态写成成功。

### 并发冲突与事实源切换

“检查来源未变”和“把新结果切换为当前事实源”是两个动作。仅在替换前紧邻执行一次 hash、mtime、长度或等价检查，不能单独证明不存在并发覆盖。

- 迁移依据的来源身份条件必须从最终复核一直原子地延续到事实源切换完成；
- 切换必须具有排他所有权或排他写入窗口、条件式提交、compare-and-swap 式版本条件、在同一事务或受控临界区中核对并切换，或其他能够证明“只有来源仍是预期身份时才提交”的等价保证；
- 具体文件锁、操作系统 API、事务或实现类延期到持久化和项目骨架任务决定；
- 普通的“先检查、后替换”两步流程不能声称已经消除竞态；
- 无法保证条件式或排他切换时，不得自动覆盖当前事实源；必须保留隔离迁移候选并报告外部并发冲突，等待后续明确流程决定重试或处理；
- 冲突后不得把旧快照生成的候选写成成功；备份也不能只保留比并发新内容更早的来源并据此声称可以完整恢复。

迁移步骤必须按相邻或明确支持的版本路径执行，不能直接把任意旧结构反序列化成当前对象后写回并称为迁移。

未知未来 schema 默认拒绝旧程序写回。配置降级不是默认承诺；只有对明确版本对、数据损失和恢复路径完成设计与验证后，才能声明支持。

从 JueMingZ 导入数据与 JueMingR 自身 schema 升级是两种不同操作，必须分别记录来源、目标、冲突、备份和验证。本规则不设计各类 Legacy 数据的实际映射，也不授权读取或修改用户的 Legacy 数据。

配置迁移没有适用于所有软件和所有数据的统一通用答案。上述要求是结合 JueMingR 的用户数据、降级和恢复风险形成的项目合同，不应伪装成某个序列化库自动提供的保证。

## 八、Tag、Release、资产与哈希

正式发布建议采用：

- 指向精确来源 commit 的 annotated 版本 Tag；
- 基于该 Tag 的一个主要 GitHub Release 记录；
- Release 中列出的全部发布资产；
- 每个资产的文件名、大小和 SHA-256；
- 与资产一致的用户可读发布说明。

Tag 标记源码历史点；GitHub Release 负责面向用户组织说明和可下载资产；SHA-256 负责识别具体资产字节。三者职责不同，必须交叉关联。

正式发布后：

- 不得在同一产品版本下静默替换不同文件；
- 修复通常使用新的 `PATCH` 版本；
- 已发布版本 Tag 不得移动到另一个 commit；
- 不得通过删除或改写历史假装没有发布过；
- 需要撤回时，明确标记“已撤回”或“不推荐”，说明原因、替代版本和恢复边界；
- 需要替代时，创建新的产品版本、Tag、Release 和资产哈希；
- 若平台支持并在发布准备中获准，可以启用 GitHub immutable releases，但平台设置不能替代本规则和本地哈希核验。

## 九、发布说明与内部历史

发布说明面向用户，只记录与用户有关的变化：

- 新功能；
- 用户可见修复；
- 行为变化；
- 配置 schema 和迁移影响；
- Terraria、Windows 和渠道兼容变化；
- 已知问题；
- 回退或降级限制；
- 用户必须执行的安装、更新、恢复或清理步骤。

发布说明不复制：

- 每个 commit；
- 每次内部审查；
- 所有内部重构；
- 每份文档修改；
- 完整测试、审计或性能日志。

内部过程由 Git、Issue、Pull Request 和 ADR 保存。当前不创建 `Changelog` 文件；未来只有出现稳定用户需求并获独立授权时才决定是否需要。

## 十、Terraria 兼容记录

每个准备声明支持的发布，必须建立与该候选构建绑定的兼容记录。记录至少包含：

- JueMingR 来源 commit、构建身份和产品版本候选；
- 项目所有者实际测试的资产清单及 SHA-256；
- 最终 GitHub Release 资产清单及 SHA-256；
- 受测资产与最终资产是相同字节、由可重复构建证明字节等价，还是因无法证明等价而完成了重新验证；
- 编译引用的 Terraria 精确文件和程序集身份；
- 项目所有者实际运行的 Terraria 精确版本、渠道和 Windows 环境；
- 单人、Steam Host & Play、连接独立专服各自的场景和结果；
- 安装、加载、恢复和卸载实际验证到哪里；
- 性能测量是否执行及其证据范围；
- 未验证环境和已知限制。

兼容记录不能写成宽泛的“支持最新版本”而没有精确证据。Terraria 更新后，旧记录仍是历史证据，但不能自动证明新版本兼容。

## 十一、正式发布准备最低条件

正式发布准备至少要能说明：

- 发布范围；
- 产品版本；
- 来源 commit；
- 工作区干净；
- 完整构建身份；
- 项目所有者实际测试的资产 SHA-256；
- 最终 Release 资产 SHA-256，以及与受测资产的同字节或可重复构建等价证据；
- 若最终资产无法证明与受测资产字节等价，对最终字节重新执行了哪些相关验证；
- 自动检查的实际命令、环境和结果；
- 项目所有者亲自执行的必要 Terraria 实机场景；
- 多人和性能哪些已验证、哪些未验证；
- 配置 schema、迁移、降级和数据损失影响；
- 安装、更新、恢复和卸载风险；
- 产物清单和 SHA-256；
- 第三方许可证和 notice；
- 已知限制；
- 项目所有者明确发布批准。

未执行或未授权的验证必须写为未验证，不得从其他绿灯推导。发布准备发现不能恢复的数据风险、来源不明的产物、无法对应 commit 的资产，或无法建立受测资产与最终资产闭环时，必须停止发布。

## 十二、防止版本治理膨胀

- 不为每个 commit 写发布记录。
- 不为每个文档任务、Issue、PR、测试或审计推进产品版本。
- 不建立第二套 Git 历史或版本更新流水。
- 一个正式发布只维护一个主要 GitHub Release 记录。
- 不用发布数量、版本号大小或 Changelog 长度证明产品进展。
- 没有实际价值、长期无真实捕获或只重复其他门的发布检查应删除或降级。
- 只在真实发布风险触发时执行发布级检查，不让普通任务承担完整发布流程。
- 项目所有者等待、实机、下载、安装和恢复时间都属于发布成本。
- 本规则只保留稳定边界，不累积当前版本、最新包或动态发布状态。

## 十三、验证与演进

本规则已由项目所有者批准，并自包含本文件和 ADR-0007 的提交合并到 `main` 后正式生效。当前正式化不分配实际产品版本，也不授权创建 Tag、Release、Changelog、发布资产、配置迁移器、构建、打包、CI、项目骨架或生产代码。

第一次真实项目骨架、具体配置迁移和第一次真实发布准备仍需分别建立任务，验证：

- 版本输入能否保持单一，三段项目语义能否形成一致的用户影响判断；
- 完整构建身份能否记录工具链、入口、主要参数和依赖，产物是否真实携带并可读出来源 commit；
- schema 状态机、单文件与多文件迁移、并发切换和迁移失败是否保留可恢复原件；
- Tag、Release、受测资产、最终资产和哈希是否能交叉复核；
- 兼容记录与测试规则能否分开记录各证据轴；
- 发布检查是否在控制风险的同时保持足够轻量。

若未来实质改变六种身份、产品版本推进与段位语义、构建身份最低输入、未知 schema 拒写、单文件或多文件迁移一致性、来源条件式切换、受测资产与最终资产闭环，或正式发布不可静默替换原则，应通过新的 Accepted ADR 明确替代范围，不得静默改写本规则的决策依据。
