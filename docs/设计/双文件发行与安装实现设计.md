# 双文件发行与安装实现设计

- 状态：有效；所有者已接受双文件及无备份政策与本次实现，自 [PR #152](https://github.com/Kuroneko2020/JueMingR/pull/152) 合并进入 `main` 起生效。
- 权威边界：[ADR-0021](../决策/ADR-0021-双文件发行与无备份直接安装.md)；双文件机制执行与验证查 [Issue #151](https://github.com/Kuroneko2020/JueMingR/issues/151)，简洁单页 UI 委托与验证查 [Issue #158](https://github.com/Kuroneko2020/JueMingR/issues/158)。本文说明机制，不宣称未执行的图形、安装或体验已成功。

## 产物和身份

标准目录仅有 `JueMingR.dll` 与 `Terraria.exe.config`。手动 ZIP 根目录恰两成员，Setup EXE 内嵌相同字节，许可证和运行清单内嵌在容器中。游戏、ReLogic、XNA 不入包。包外 build record 保留源码、完整输入、资格、内部成员、payloadId、两文件、ZIP 和 Setup 长度/哈希。

外层 `schemaVersion=1` 增加 `distributionFormat=two-file-1`；`packageDirectory.name` 为空、`files` 为标准两文件。`bundle` 记录 payloadId、实际入口 identity、资源名和两文件身份；`setup` 记录 fileName/length/sha256 与嵌入成员身份。payloadId 是 `JueMingR.Bundle.index` 原始 UTF-8 字节 SHA-256 小写；索引以 `schemaVersion=1` 加换行开头，各行按 Ordinal 名称列出 `name|length|SHA256`，末尾换行。不将外层 DLL/Setup 自身最终哈希递归嵌入。

## 加载、目录与成本

Bootstrap 仅依赖 Framework BCL，对外程序集名 `JueMingR`。资源 `JueMingR.Bundle.payload.zip`、`JueMingR.Bundle.index`、`JueMingR.Bundle.config` 由本批构建产生。入口准备完整自有组件后才进入生产 AssemblyLoad 订阅/扫描及回调外一次安装流程；失败停止激活，不从旧 Validation、开发 bin 或任意扫描目录补载。

程序展开目录固定为游戏根下 `JueMingR.Runtime/<payloadId>`；config 精确绑定同批目录。Host 以自身真实文件位置取得内部路径，用户数据仍取准确游戏根下 `JueMingRData`，不随 payloadId 迁移。内部文件完整核验后复用，缺失/损坏由当前容器重建；不备份旧字节、不自动选择旧批次、不在帧循环解压或算整文件哈希。

Worker 仍是受控独立 EXE，自己的 config、依赖和真实文件租约随内部组件展开；不继承游戏 AppDomainManager 环境。既有游戏对象就绪门、唯一加载对象核验与一次 Runtime 交接不由容器替代。

## 构建和正式消费者

`scripts/build-phase0s-validation-package.ps1` 是正常包入口，顺序为内部 Release/net472/x86 组件 → bundle → 冻结标准两文件 → 手动 ZIP/Setup。旧 profile 也必须委派同一两文件包装。普通 `scripts/build.ps1` solution 编译显式传 `JueMingRBundleLogicOnly=true`、`JueMingRSetupLogicOnly=true`；这些只编译逻辑，不产生可交付载荷。最终包装传本批 `JueMingRBundleDirectory` 和 `JueMingRSetupPayloadDirectory`，缺资源拒绝，不能拾取上轮产物。

`verify-existing-package.ps1 -ZipPath <ZIP> -BuildRecordPath <记录> -ExpectedSourceCommit <SHA> -ExpectedZipSha256 <SHA256> [-SetupPath <EXE>]` 静态读取当前两文件格式、索引、载荷、config 和 Setup 资源；Setup 默认由记录所在目录的 setup.fileName 定位。通过只证明包身份与两渠道一致，不执行包内脚本，不证明游戏启动。旧 schema 的分散 archive 分支仅为只读历史核验。

`Read-Phase0SPackage` 识别标准目录后委派同一新 reader；旧布局保留历史/fixture读取。普通 `development-candidate-1` 保持 `ContinuousProcessing/ORDINARY_COMPLETE`，`package.distributionFormat` 必须为 `two-file-1`，原始 FAIL、Full/Related INCOMPLETE 和 releaseEligible=false 按真实情况保留。

## 安装、更新与移除

Setup 是独立 net472/x86 WinForms EXE，不依赖旁置 config/DLL、仓库、PowerShell或联网下载。UI 和 CLI 调同一服务：`--install --game-dir <目录> --json`、`--uninstall --game-dir <目录> --json`。无参数打开中文窗口。

窗口按实际设备的Steam注册表路径及声明的 `libraryfolders.vdf` 多库、`appmanifest_105600.acf` 安装目录发现游戏，复用安装的普通路径/原版身份判据；不全盘扫描。唯一可信目录自动填入，多个结果保留列表供选择，始终可浏览。`--ui --game-dir <目录>` 可直接打开指定副本的窗口，不执行安装。

安装器使用项目所有者最终上传并选定的图标。源码保留PNG原始字节、由完整画布机械转换的多尺寸ICO及[来源记录](../../src/JueMingR.Setup/Assets/logo-prompt.txt)，不冒称保存其原始生成提示词。按所有者最新界面决定，页头只显示左对齐的“决明”，不加载或嵌入页头PNG；ICO继续用于窗口和应用图标，无外置图片依赖。

### 简洁单页与状态归属

`SetupForm` 保留系统标题“决明安装程序”；页头为绿色“决明”、细分隔线与本 Setup 内嵌 DLL 的完整产品版本，成功时只显示原始版本号、不加“待安装版本”前缀，没有副标题或页头大图。目录下以无底框的灰色文字显示 Terraria 版本和已安装决明版本，窗口采用约640×360逻辑内容区的固定紧凑比例，随系统DPI缩放，禁用拖动改大小和最大化。长开发版本不撑窗，单行原生文本保留完整原值，可水平定位、选择复制并查看完整提示；无法确认和错误原因仍准确保留。左下“卸载决明”“清空配置”为相邻灰色原生 LinkLabel，默认无下划线、保留焦点和键盘交互；右下是唯一突出的“安装 / 更新”主按钮，文字放大加粗，未安装时为“安装决明”。维护资格仍为 `CanMaintain`，不与完整 pair 或 `CanInstall` 绑定。清配置仍单独确认，卸载不新增确认。路径可直接输入、选择已发现项或通过与路径框同高的紧凑“…”按钮浏览；忙碌时禁改目标、防重入并禁止中途关闭，不设全窗默认安装按钮。整体区块与上下留白保持紧凑，底部维护文字和主按钮在同一操作行自然对齐，缩小底边距离但保留原点击面积与日志最小视口。

`SetupVersionReader` 每窗仅在首次显示时后台读取一次精确资源 `JueMingR.Setup.Payload.JueMingR.dll`，以随机唯一、CreateNew 的普通临时 DLL 读取 `FileVersionInfo.ProductVersion`，不加载执行载荷。临时路径及祖先拒绝重解析点，finally 只删除本次创建且仍匹配原字节的文件；清理失败如实保留原因。完整原值可选择复制；缺载荷、无有效版本和读取失败分别表达。窗口关闭后不发布结果，目录变化不触发重读，版本失败不替换操作结果。该显示不改变 `SetupPayload.Version` 的 `payload-<id>` 协议、回执、安装资格或服务的独立载荷重验。

只读 `SetupTargetState.Read` 复用 `TargetSafety`、`OwnedFiles` 与 `ConfigOwnership`。目录可维护资格和锁定原版可安装资格分别计算：安装按精确原版身份门，维护不因版本不再满足新安装门而消失，实际操作仍由服务重验。成对状态区分未安装、完整、不完整和无法确认：完整需要真实 bundle 与其内嵌 config 哈希匹配，无回执的手动 pair 可以识别；只有 DLL 简单名、未知文件或损坏 XML 不足以宣称完整或未安装。状态不是本次操作成功证明。

已安装版本由同一个只读状态承担：仅确认完整 pair 后，从所选目标的实际 `JueMingR.dll` 读取 `FileVersionInfo.ProductVersion` 到 `InstalledVersion`，以“已安装决明版本：…”呈现原始值。明确可维护且未安装时直接显示“当前未安装决明”，不套用已安装版本前缀；不完整和状态无法确认分别表达；已证 pair 的版本缺失或无信息的 `0.0.0.0` 为无法确认，读取异常为读取失败并保留原因，不倒改 pair 或资格。不读取 Setup 自身或待安装版本代替，不加载执行目标 DLL，也不改变原拥有权判断。

路径编辑用短去抖触发有限读取，同窗仅一个检查在飞；目标 generation 拒绝旧目录的迟到结果，忙碌或已关闭窗口也不接收旧回写，不设后台持续扫描。`RunOperation` 在首次异步等待前冻结 operation 和原始 selected path，随后禁用控件；服务继续规范化并核验目标。完成后单独刷新当前 pair，不覆盖本次服务结果。

`SetupResultPresentation` 直接解释真实 `SetupResult` 的 success／noop／partial／failure，不把 Task 返回当成功。摘要明确部分完成及关键原因，详情优先显示结果的实际 `gameDirectory`、operation、status、exitCode、completed、failedStep、retained 和读回 hash；若目标核验未完成，保留原选择并明确标记。pair 完整而回执写入失败仍是 partial。更换目标会退休旧结果显示，A 的结果不能套到 B。internal seam 仅供隔离 STA 检查创建同一生产 Form，不改变正常发现、GUI／CLI 服务或安装门。

日志区默认可见并保留空白空间，不在未检查时编造“准备就绪”。操作后摘要和详情同时显示，版本和日志均无可见滚动条箭头；详情为可选择复制、自动换行并可通过滚轮、PageDown／Ctrl+End 等键盘操作翻阅的原生只读 TextBox。隐藏滚动条后，原生edit默认不处理滚轮位移，故同一只读文本控件在MouseWheel入口按Windows行数／整页／禁用设置转换为原生行／页滚动消息，逐控件累计不足一格的delta；保持原生选区、光标和键盘复制，不创建第二份日志或自绘滚动器。`UpdateLayoutMetrics` 保留字体相关的六行日志视口，版本、邻近目标反馈和结果摘要均为固定单行高度，不再按开发版本或长原因提高窗口下限。完整目标反馈保留在自身可水平定位／复制的原生文本及完整提示中；真实操作长原因、partial和保留项仍由原操作详情保全，目标状态刷新不写入或替换操作日志。正常窗口MinimumSize／MaximumSize固定在设计内容区对应外框；极小工作区仅钳制外框并用根容器滚动兜底，不更改系统显示设置。更换目标仍退休旧结果，日志空间始终存在。这一固定版式替代旧可拖拉窄窗／长版本撑窗偏好，不构成全部 DPI／字体已验证的声明。

“清空配置”与 `--clear-config --game-dir <目录> --json` 共用有限清理：仅处理实际Host使用的 `JueMingRData/config` 按键、窗口与各功能偏好文件，连同对应 `.bak/.tmp/.lock` 及四份实际迁移 `.schema1-original`。先统一检查占用、普通文件及祖先重解析路径，再逐项删除；失败如实区分未开始和部分完成。不删整个数据目录，不删笔记、蓝图库（包括交换序号和场景历史）、首次提示历史或未知未来文件。卸载本身仍保留全部这些设置；清空须单独选择并确认。

仅修改安装器时，可用 `scripts/build-setup-from-existing-pair.ps1 -PayloadBuildRecord <已核原记录> -StandardDirectory <冻结两文件目录> -OutputDirectory <新outputs目录>`。先用现有严格reader核原pair/原Setup，单独Release构建Setup，再核同对内嵌资源；原DLL/config/ZIP不改。`setup-rebuild-record.json` 分列真实 `payloadSource`、`installerSource` 与原记录hash，不把新安装器提交冒称旧载荷重编。用于现有消费者的 `payload-package-record.json` 保留原载荷sourceCommit，并显式附加安装器来源；两份记录均不代签游戏体验。

安装检查合法目标、普通文件/目录、占用、权限与完整新载荷；仅临时保存新字节，核验后先替换 DLL、最后替换 config，一次读回。已有 config 可覆盖，不创建旧字节备份、不运行 Restore。途中失败报告已完成和未完成步骤，不假报回滚；重新安装可修复。`scripts/phase0s/Install-Phase0S.ps1 -TerrariaDirectory <目录> -SetupPath <EXE>` 为 CLI 薄委派；同目录 Restore 名称入口默认委派卸载，不恢复第三方。`-HistoricalFixture` 仅供旧文件层夹具复现原协议，不属于正常换装路线。

卸载识别当前 R 入口和自有文件，保留后来被其他工具替换的 config；手动安装不因无回执拒绝识别。旧分散版本仅按有效旧回执/身份有限清理已确认 R 组件，未知非活动文件留在原位并报告，不能作为新 loader 后备。所有用户数据、世界角色及已有历史材料保留。

## 验证责任

必要证据覆盖首次真实 CLR 配置入口、同名依赖污染、缓存复用/重建、受控 Worker、精确两成员和错配反例、Setup 同源、直接覆盖第三方 config、更新/移除/旧布局迁移及部分写失败后的重装修复。`test-phase0s -Scope PackageIntegrity` 使用正式包 reader；`InstallRecovery` 使用新生产 Setup 测试，旧夹具只显式历史使用。`tests/TwoFileDistribution/PackageConsumerChecks.ps1 -StandardDirectory <标准目录> -SetupExecutable <EXE>` 读取真实容器和 Setup 并检查成对错配、重复记录、不同内嵌 config 反例。

`collect-blueprint-autobuild-diagnostic.ps1 -Mode CurrentIdentity -TerrariaDirectory <目标>` 为当前安装的只读证据定位入口：从实际双文件确定 payloadId，核展开成员后返回 Host、runtime manifest、evidence 和匹配新回执的准确位置，不扫描最新目录。它不生成诊断包、不启动游戏、不换装。原 `StageB` 已退出实际 Restore→Install 路线，`PrepareOnly/CollectOnly` 仅保留原任务隔离fixture；旧 `Start-InputDiagnostic` 仅保留 CandidateOnly/MetadataOnly 历史读取，不能启动旧分散载荷。未来另获准诊断候选沿统一 bundle/Setup，不复活旧启动协议。

有限启动工作与稳定帧无包 I/O 由相应代码/机制证据判断，不新建 FPS 诊断。未改业务依据实际输入复用，不因新外形自动重跑整个历史矩阵。夹具/原生专项/包验证/实际安装/本人游戏体验分别表达；图形环境受限和历史失败原件如实保留。

首次机制检查由 tests/Phase0S/Invoke-TwoFileColdStartChecks.ps1 -Run 运行独立CLR驱动：默认只验证锁定原版程序集加载、准确Hook和真实Worker；显式 -NativeContentDirectory 才在静音、Social.None、隔离SavePath中运行原版Initialize/base.Update，并核五事件及一次交接。驱动器只模拟原版内嵌游戏依赖解析，不供应R/Harmony；正式生产加载器没有fixture放行分支。程序缓存仍受Framework普通路径长度约束；本任务未增加长路径兼容承诺。

容器准备早于运行清单/Host证据文件；准备失败另保留一个有限JueMingRData/logs/bootstrap-error.txt（时间、阶段、异常类型和有限原因）及Trace出口。该出口不依赖Runtime，不逐帧重试，也不冒称已经进入正常降级UI；目标本身不可写时日志可能同样不可写。
