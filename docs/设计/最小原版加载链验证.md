## 1. 目的与授权边界

本设计只实现和验证 Terraria 1.4.5.8 的最小 clean-room 同进程加载职责链：

```text
受控 Terraria.exe.config
→ 最小 AppDomainManager
→ 同步程序集就绪与核心身份门
→ 单一、可审计的 Harmony 装载上下文
→ Terraria.Main.Initialize postfix
→ 一次性空 Runtime 交接
```

该原型回答三个问题：

1. CLR 能否从受控 config 进入最小 AppDomainManager；
2. Harmony Hook 能否在 `Terraria.Main.Initialize` 首次执行前同步安装完成；
3. 精确的 `Main.Initialize` postfix 能否只完成一次空 Runtime 交接并留下可区分证据。

本设计不实现完整 Runtime、Session、Coordinator、Feature、UI、持久化业务、安装器产品或用户功能，不决定未来长期 Tick Hook，也不产生 Terraria 兼容或正式发行声明。

Agent 只在仓库、系统 TEMP 和其它明确隔离目录中构建、测试和准备验证包。Agent 不启动或操作 Terraria，不执行脚本指向真实 Terraria 安装；真实安装、启动、观察和恢复只由项目所有者按测试卡亲自完成。

## 2. 已核验的目标程序集与真实调用顺序

### 2.1 Terraria 身份

当前目标来自项目所有者合法安装并已进入构建 baseline 的 Terraria：

| 项目 | 值 |
| --- | --- |
| 精确版本 | `1.4.5.8` |
| Assembly simple name | `Terraria` |
| Assembly version | `1.4.5.8` |
| SHA-256 | `960A03BFF6050CF7BE16DFC1A7B19E10FC2C4F8F835A6A3B135A50DD9E6BA2F3` |
| MVID | `2c29f6c3-4bd9-4add-9c58-da159804e083` |
| PE/CLR | PE32、I386、ILOnly、Requires32Bit |

这些值绑定本次验证输入，不自动证明另一渠道、另一版本或未来更新兼容。

### 2.2 Main.Initialize 与 LoadContent

只读检查必要的 PE/CLR 元数据和 IL 调用、分支、返回形状，不复制 Terraria 方法实现。确认结果为：

- `Terraria.Main.Initialize`：MethodDef `0x06000CDE`，RVA `0x0036C040`；
- 普通客户端尾部先调用 `Main.LoadContent_TryEnteringHiDef()`，再调用 `Main.ClientInitialize()`，随后调用 `Microsoft.Xna.Framework.Game.Initialize()`；
- dedicated-server 分支调用 `Initialize_AlmostEverything()` 后直接返回，不进入上述客户端尾部；
- 当前 `Microsoft.Xna.Framework.Game.dll` 的 `Game.Initialize` 是 MethodDef `0x06000062`；在 graphics service/device 非空分支中，它通过虚调用进入 `Game.LoadContent()`；
- `Terraria.Main.LoadContent` 是该虚方法的覆写，MethodDef `0x06000CF2`。

因此 Terraria 1.4.5.8 普通客户端实际顺序是：

```text
Main.Initialize 前半段
→ LoadContent_TryEnteringHiDef
→ ClientInitialize
→ base Game.Initialize
→ virtual Main.LoadContent
→ base Game.Initialize 返回
→ Main.Initialize 返回
→ Harmony Main.Initialize postfix
```

`Main.Initialize` postfix 不早于 `LoadContent`；在已检查的普通客户端路径中，它发生在 `LoadContent` 返回之后。因为 dedicated-server 和 graphics-device 条件分支仍存在，postfix 本身不得被扩张为跨环境的通用 `LoadContent` 完成证明。

### 2.3 ReLogic 就绪前提

V1 实机证据确认：`WindowsLaunch.Main` 先注册 Terraria 自有的内嵌程序集 resolver，再调用 `Program.LaunchGame`；`LaunchGame` 在 `RunGame`、`Main` 构造和 `Game.Run` 前首次引用 `ReLogic.OS.Platform`。因此只看到 `Terraria` AssemblyLoad 不能证明 Harmony 已可安全解析 `Main.Initialize`；Bootstrap 必须等待同一 AppDomain 中精确的 `ReLogic` 对象实际加载。

当前 ReLogic 门绑定 `ReLogic, Version=1.0.0.0, Culture=neutral, PublicKeyToken=null`、MVID `ee258be9-88a4-423d-b3ce-84b6c35b141a`，以及已核验 Terraria 对象中的资源 `Terraria.Libraries.ReLogic.ReLogic.dll`（长度 `176128`，SHA-256 `E1C5DCCEFFF5FD1C789FF712BABFA1A305FCED0D03C96EF30F2C14D99AA0AF29`）。该程序集由 Terraria 自己的 resolver 通过 `Assembly.Load(byte[])` 载入，`Location` 可以为空；JueMingR 不提取、复制或自行加载它。

## 4. 当前验证布局与未来用户发行布局

### 4.1 Phase 0-S 隔离验证布局

Microsoft 对 `AppDomainManager` 的文档要求 manager 程序集位于 GAC 或启动应用目录。Phase 0-S 排除更具侵入性且不适合作为当前验证前提的 GAC，因此只批准以下布局：

```text
Terraria.exe.config
JueMingR.Bootstrap.dll
JueMingR.Validation\
  JueMingR.TerrariaHost.dll
  JueMingR.Platform.dll
  JueMingR.Features.dll
  JueMingR.Infrastructure.dll
  0Harmony.dll
  phase-0-s-runtime.manifest
  phase-0-s-install-manifest.json
  phase-0-s-evidence.log           # 只在运行时产生
```

`ReLogic.dll` 不属于根目录、sidecar、普通构建输出或验证包 payload；runtime manifest 只携带其精确身份和 Terraria 内嵌资源身份。

来源：<https://learn.microsoft.com/en-us/dotnet/api/system.appdomainmanager?view=netframework-4.8.1>

这是一次性、可恢复的项目所有者验证布局。它不是未来正式用户发行布局，不构成长期产品决定，也不得被描述为比 `config + 单个 DLL` 更干净或更简单。

安装脚本负责从验证包建立固定层级；项目所有者不手工选择、复制或排列上述内部文件。

### 4.2 未来正式发行目标

未来正式发行必须满足：

- 用户不需要理解 JueMingR 内部程序集或目录层级；
- 优先提供一次明确操作即可完成的安装方式；
- 若保留手工安装，复杂度原则上不得高于 TerrariaHelper/JueMingZ 的 `config + 单个 DLL`；
- 六个生产项目继续作为源码和编译期架构边界，不等于部署时必须暴露六个 DLL；
- 如果单 DLL 因装载上下文、Harmony 或恢复安全确实不可行，必须在本验证通过后的独立任务中带着实际证据交由项目所有者裁决。

Phase 0-S 不引入程序集合并器、Costura、`Assembly.Load(byte[])`、多装载上下文或 fallback，也不提前选择未来打包技术。

## 5. 组件职责和源码边界

### 5.1 JueMingR.Bootstrap

Bootstrap 继续无 ProjectReference，只依赖 .NET Framework BCL。它负责：

1. 由 CLR 构造唯一 `AppDomainManager`；
2. 在 `InitializeNewDomain` 中同步订阅 `AppDomain.AssemblyLoad`；
3. 同步订阅后扫描当前 AppDomain 已加载程序集，并在扫描完成前禁止开始安装；
4. 以 `Waiting / Installing / Installed / Failed` 终态门接受任意先后到达的精确 Terraria 与唯一 ReLogic 对象；
5. 核对 Terraria 位置、identity、MVID、SHA-256，并把 ReLogic 绑定到该 Terraria 的精确内嵌资源；
6. 创建第一项本地证据；
7. 用固定完整程序集 identity 和固定 public static 方法形状 normal-load、late-bind Host，并传入两个已核验 Assembly 对象；
8. 错误 ReLogic identity 或第二个不同 ReLogic 对象立即失败关闭，不回退到后续候选；
9. 失败时停止激活并留下最小错误证据。

Bootstrap 不访问 Terraria 静态状态，不引用 Terraria、Harmony、Platform、Feature、Infrastructure 或 Setup，不实现 Runtime，也不主动加载入口 EXE。

### 5.2 JueMingR.TerrariaHost

TerrariaHost 保持唯一游戏/Harmony 直接引用边界。它负责：

1. 重新核对自身、Terraria、ReLogic 及其 Terraria 内嵌资源与 runtime manifest 的 identity、MVID、位置和 SHA-256；
2. 在任何 Harmony 类型使用前检查当前 AppDomain 不存在同名已加载实例；
3. 从固定 sidecar 以完整 identity normal-load 官方 `0Harmony`；
4. 证明 AppDomain 中恰有一个与 manifest 完全匹配的 Harmony Assembly 实例；
5. 核对目标 `Terraria.Main.Initialize` 的 declaring assembly、metadata token、实例/静态属性、返回值和参数；
6. 同步安装唯一 postfix；
7. 通过 Harmony patch info 核对 owner 和 patch method 唯一；
8. 在 postfix 中完成一次空 Runtime handoff。

当前空 handoff 只是 Host 内部的单次状态门和证据提交，不构造 Runtime 对象图，不在 Platform 中预建完整 Runtime 合同，不触碰 Features 或 Infrastructure。

### 5.3 其它项目

- Platform 保持现有 host-neutral 最小 contract，不因本验证预建 Runtime/Session/Coordinator；
- Features、Infrastructure 和 Setup 不新增产品行为；
- PowerShell 安装/恢复脚本是 Phase 0-S 项目所有者验证工具，不把 Setup marker 升级为正式安装器产品。

## 6. 首次 Initialize 前的同步保证

Microsoft 文档说明 `InitializeNewDomain` 在 AppDomainManager 构造后立即调用，并可在其中注册 AppDomain 事件。Microsoft Reference Source 显示 CLR 直接调用 `InitializeNewDomain`，`AssemblyLoad` 触发路径也直接调用事件委托：

- <https://learn.microsoft.com/en-us/dotnet/api/system.appdomainmanager.initializenewdomain?view=netframework-4.8.1>
- <https://github.com/microsoft/referencesource/blob/main/mscorlib/system/appdomain.cs#L455-L543>
- <https://github.com/microsoft/referencesource/blob/main/mscorlib/system/appdomain.cs#L2853-L2860>

本地 x86/.NET Framework 合成进程使用真实官方 Harmony 2.4.2 的独立核验重复得到：

```text
InitializeNewDomain
→ 同步订阅 AssemblyLoad
→ entry EXE AssemblyLoad handler
→ Terraria identity ready，等待 ReLogic
→ entry point 注册 Terraria resolver
→ Terraria 以 Assembly.Load(byte[]) 载入唯一 ReLogic
→ ReLogic AssemblyLoad handler 同步完成双对象 readiness gate
→ Host normal-load
→ Harmony ready
→ Harmony.Patch 返回
→ patch owner / HOOK_INSTALLED 核验完成
→ AssemblyLoad handler 返回
→ entry type initializer
→ entry point
→ 首次 Initialize
→ postfix fired
```

完整序列重复 `25/25`，精简 config 重复 `10/10`，均为 exit code `0`；关键步骤在同一线程。对 handler 人为阻塞约 250 ms 时，触发方同步等待约 255–270 ms 后才返回。

正式实现只使用该同步链。禁止 `Task.Run`、`Thread`、timer、异步委托、延迟队列和后台安装；也不把 `Assembly.Load(entry EXE)` 作为替代路线。若生产形状的隔离 fixture 不能重新证明该顺序，任务停止。

## 7. 固定 runtime manifest 与核心身份门

验证包构建器生成一个严格、无个人绝对路径的 runtime manifest。它至少绑定：

- schema 和唯一 package id；
- 来源 clean commit；
- Terraria simple name、version、MVID、SHA-256；
- ReLogic simple name、version、public key token、MVID；
- Terraria 内嵌 ReLogic resource name、长度基线和 SHA-256；
- `Terraria.Main.Initialize` type name、method name、metadata token、实例形状、返回值和参数数；
- Host simple name、version、MVID、SHA-256；
- Harmony simple name、version、MVID、SHA-256；
- 唯一 Harmony patch owner；
- 固定 evidence 文件名。

生产验证包只能使用当前 Terraria baseline 形成上述值。自动组件测试可以为隔离的假 `Terraria` entry EXE 生成独立 fixture manifest；该 fixture 只验证同步装载和失败行为，不能替代真实游戏身份或实机。

manifest 使用固定相对位置和严格字段集合；缺失、重复、未知或非法字段均失败关闭。Bootstrap 与 Host 不接受任意探测目录、简单名搜索或环境变量提供的额外装载路径。

## 8. 五项事件与唯一成功判据

每次验证使用 create-new evidence 文件。若文件已存在，不覆盖、不合并、不重试，本次激活停止。

必须按顺序、分别提交：

| 序号 | 事件 | 提交条件 |
| --- | --- | --- |
| 1 | `TERRARIA_ASSEMBLY_READY` | 目标位置、程序集 identity、MVID、SHA-256 均匹配 |
| 2 | `HARMONY_READY` | Terraria、唯一 ReLogic 及其内嵌资源已复核，且 AppDomain 中恰有一个来自固定 sidecar、与 manifest 完全匹配的 Harmony Assembly |
| 3 | `HOOK_INSTALLED` | `Harmony.Patch` 已同步返回，patch info 中目标/owner/postfix 唯一且匹配 |
| 4 | `MAIN_INITIALIZE_POSTFIX_FIRED` | 目标 postfix 首次实际进入 |
| 5 | `RUNTIME_HANDOFF_COMPLETE` | 空 Runtime handoff 的单次门成功提交 |

只有第 5 项存在、五项顺序完整且 package id 一致，才算本阶段最小加载交接成功。编译、自动测试、前三项事件、游戏打开或进入主菜单均不能代替第 5 项。

错误记录使用有限错误码、阶段和有效内部异常类型，不保存个人绝对路径、用户目录、stack trace 或 Terraria 内部状态。Patch primary 始终先写；cleanup 只允许作为第二条可选错误，不能占用或替换 primary。缺失依赖只在等于受控 ReLogic 完整程序集 identity 时保留该安全字段。evidence 是本地原始证据，不进入 Git；项目所有者按测试卡回传后，由 Agent 解释。

## 9. 失败、清理与无 fallback

- config/AppDomainManager 进入 JueMingR 代码前失败：依赖进程外恢复脚本；不得声称游戏内降级成功。
- Terraria identity 失败：不加载 Host/Harmony，不写后续事件。
- ReLogic 未出现：只保留已成立的 Terraria ready，不加载 Host/Harmony；错误 identity 或第二个不同对象进入唯一失败终态且不 fallback。
- Host/Harmony/target/patch 核验失败：不做 Runtime handoff；如果当前 owner 已产生部分 patch，只撤销该 owner 的部分状态，不尝试其它 Hook。
- `Main.Initialize` 未命中：保留最多到 `HOOK_INSTALLED` 的证据并停止。
- postfix 重入：单次门直接拒绝后续 handoff，不重复写成功。

任何失败都不得自动增加 `Main.LoadContent`、`Main.Update`、`Draw`、`DoUpdate`、第二安全点、反射 fallback、重试链或版本猜测。新增这些路线需要独立证据和项目所有者重新裁决。

## 11. 验证包、安装和恢复

### 11.1 包边界

项目所有者验证包必须来自 clean commit，并包含：

- 固定 payload；
- package/install/runtime manifest；
- `Install-Phase0S.ps1`；
- `Restore-Phase0S.ps1`；
- 普通语言测试卡；
- Harmony license/notice；
- 每个资产的 SHA-256 和构建身份。

它是项目所有者测试包，不是产品版本、Tag、Release 或正式发行资产。

### 11.2 安装顺序

安装脚本只接受显式 Terraria 目录。解析并确认目录存在后，第一项目标文件检查必须是 config；所有目标写入前依次只读检查：

1. `Terraria.exe.config` 不存在；若存在，立即只读报告其 SHA-256 并停止，不再进行其它目标检查；
2. `Terraria.exe` 存在且精确 identity 匹配；
3. Terraria 进程未运行；
4. 根目录 Bootstrap、sidecar、固定 staging 和固定 temp 路径均不存在；
5. 包 manifest 与所有 payload 文件完整匹配。

任何冲突均零目标写入；不覆盖、不合并、不删除、不改名，也不自动备份后继续。

无冲突后：

1. 在固定 staging 中用 create-new 写完整 sidecar 并核验；
2. 原子切换 staging 为 `JueMingR.Validation`；
3. 用 create-new temp + 同目录原子移动提交根目录 Bootstrap；
4. 用 create-new temp + 同目录原子移动最后提交 config。

这里的“原子”只指每个对象各自以 no-replace move 提升，不表示 sidecar、Bootstrap 和 config 构成一个整体原子事务。config 是唯一激活点；它最后提交，使此前中断不激活加载链。脚本不会要求项目所有者手工排列层级。

### 11.3 恢复顺序

恢复脚本先完成全量只读预检：

- 原始包 manifest 与安装 manifest 必须匹配；
- config、Bootstrap、sidecar、staging/temp 中每个现存静态文件都必须与 manifest hash 匹配；
- runtime evidence 只能出现在声明的固定位置，并具有本 package id；
- 不允许未知文件、未知目录、reparse point 或外部修改。

任何所有权或 identity 无法证明时，恢复不删除任何目标并报告冲突。全部证明后，按以下顺序删除精确自有对象：

1. config；
2. config temp；
3. Bootstrap 与其 temp；
4. 完整 sidecar；
5. 可证明属于本包的 staging。

sidecar 和 staging 只逐个删除已证明的文件，最后使用非递归目录删除；若目录中出现未知内容，目录删除失败而不会转为递归或强制清理。重复执行恢复在没有自有对象时返回安全的“无需恢复”。脚本不使用通配删除，不处理用户数据，也不恢复或覆盖任何验证前已有 config。

## 12. 自动证据与项目所有者实机门

### 12.1 自动检查

本任务建立最窄相关证据：

### 12.2 项目所有者测试卡

最终包提供普通语言步骤，项目所有者只需：

1. 关闭 Terraria；
2. 对自己的 Terraria 目录亲自运行安装脚本；
3. 亲自正常启动 Terraria 并观察能否进入主菜单；
4. 关闭 Terraria，保留并回传 evidence；
5. 亲自运行恢复脚本；
6. 亲自再次启动原版 Terraria，确认恢复结果；
7. 分别裁决实机结果和是否接受。

如果 `MAIN_INITIALIZE_POSTFIX_FIRED` 或 `RUNTIME_HANDOFF_COMPLETE` 缺失，测试卡要求停止、保留证据并恢复；不要求用户重试或选择其它 Hook。

PR 在项目所有者完成上述测试并明确接受前保持 OPEN。本任务不自动合并、不关闭 Issue #26、不勾选 Issue #7 里程碑，也不创建下一阶段 Issue。
