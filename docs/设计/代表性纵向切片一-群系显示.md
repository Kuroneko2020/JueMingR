# 代表性纵向切片一：群系显示

- 状态：有效 / 已完成项目所有者实机与体验验收
- 适用范围：Terraria 1.4.5.8、Steam、Windows、x86 .NET Framework、当前项目所有者机器上的普通单人世界
- 对应任务：[Phase 0-T Issue #28](https://github.com/Kuroneko2020/JueMingR/issues/28)
- 上位架构：[总体架构与状态所有权](总体架构与状态所有权.md)
- 加载链：[最小原版加载链验证](最小原版加载链验证.md)

## 1. 目的与证据边界

本切片只建立第一条可见纵向链路：固定加载链 → 唯一 Update postfix → 最小 Runtime/Session → 类型化群系观察 → 群系 Feature → 缓存 ViewModel → 唯一 UI interface layer。它不建立通用 Feature Registry、Event Bus、Service Locator、完整 Runtime、设置系统或通用 UI 框架。

自动测试与静态审查只能证明固定输入下的逻辑、边界和安装恢复；真实 Terraria 中的文字观感、遮挡、输入互不干扰、世界进出与跨群系体验必须由项目所有者实机确认。不得将本切片外推为多人、其它版本/渠道、性能或正式发布结论。

本验证包的固定 `phase-0-s-evidence.log` 表示最近一次 Terraria 进程运行，不是安装锁或永久历史日志。每个新进程建立 sequence 01 时重建该受控文件，sequence 02–05 仍只在本次 01 成功后严格追加；因此旧进程的完整、部分或零字节 evidence 不会冒充或阻止当前运行。重建失败继续 fail closed，不激活 Runtime；项目内不轮转、不扫描、不产生无界历史文件，需要调查旧运行时由 Agent 在覆盖或恢复前复制到游戏目录外。

### 项目所有者实机与体验验收

固定接受的生产实现 head 为 `a645d76d551d2eb6c53a2bdb07d177da6395968a`。项目所有者在本文件“适用范围”所列环境中，将同一个修复包只安装一次并连续启动 Terraria 两次：两次主菜单均不显示群系文字；两次进入普通单人世界后均正常显示 `群系: …`，跨区域移动后正常更新，返回主菜单后正常消失；未发现输入异常、明显闪烁、残影或重复绘制。项目所有者已接受当前群系文字、更新结果、显示位置和整体体验，分别形成指定场景实机证据与体验验收。

第二次启动的固定 evidence 已核验为第二个 Terraria 进程重新生成的当前证据，包含唯一、有序、完整的 sequence 01–05，`ERROR` 为 0；保存副本 SHA-256 为 `4C190E4F97F6ED9E39F038B3C02B31E1A1D7B7D55F4F551EBD70A4CB3DD18FF8`。

本次实机未逐项访问全部群系，也未验证多人、其它版本或渠道以及正式发行。项目所有者报告“未发现明显卡顿”只代表本次指定场景的主观体验，不是 FPS 或帧时测量结论。

## 2. 玩家行为合同

- 主菜单、世界加载、本地玩家不存在或不活跃时不显示，并清除旧世界 ViewModel。
- 有效世界中只显示一行 `群系: <当前群系>`；无法识别时显示 `群系: N/A`。
- 特殊群系按以下顺序收集并以 ` / ` 分隔：沙漠、地下沙漠、雪原、丛林、地牢、海洋、腐化、猩红、神圣、神圣、发光蘑菇、陨石、花岗岩、大理石、蜂巢、神庙、墓地；相同中文结果去重。
- 随后最多追加一个高度语义：天空；否则地狱；否则洞穴；否则地下；否则仅在地表且没有特殊群系时显示森林。
- 验证包默认启用；本轮不提供 F5、玩家可见开关、快捷键、拖动、样式配置、配置文件、持久化或 Legacy 设置迁移。内部仍保留明确启停状态，停用时不读取 Zone、不生成 ViewModel、不绘制。

特殊 Zone 的宿主读取依次为 `ZoneDesert`、`ZoneUndergroundDesert`、`ZoneSnow`、`ZoneJungle`、`ZoneDungeon`、`ZoneBeach`、`ZoneCorrupt`、`ZoneCrimson`、`ZoneHallow`、`ZoneHoly`、`ZoneGlowshroom`、`ZoneMeteor`、`ZoneGranite`、`ZoneMarble`、`ZoneHive`、`ZoneLihzhardTemple`、`ZoneGraveyard`。固定目标程序集没有 `Player.ZoneHoly`；纯 Feature 合同保留该兼容位，1.4.5.8 Host 将它明确置为 false，而 `ZoneHallow` 仍产生同一“神圣”结果，不使用反射猜测别名。

## 3. 生命周期与刷新

- Platform 提供宿主无关的单 Feature Runtime、Session 探针、Feature 生命周期和不可变 `BiomeObservation`。
- Runtime 每次由现有唯一 `Terraria.Main.Update(GameTime)` postfix 驱动，只做 Session 状态门与一个 Feature 调用。
- Session 刚进入、Feature 从停用转为启用时立即观察；其余观察最多每 30 个正常 Update ticks 一次。
- 观察由固定数量的 typed Zone 读取组成，不扫描世界、Tile 或实体。
- observation 未变化时不重新构造文字或发布 ViewModel；Session 退出、Feature 停用或错误时清空。
- Update/读取异常只让本 Feature fail closed，不重试、不建立后台工作、不影响原版 Update 返回。

## 4. 唯一绘制入口

Terraria 1.4.5.8 固定程序集的 `Main.SetupDrawInterfaceLayers()` 是私有实例、无参数、返回 `void` 的一次性界面层构建方法；它建立 43 个 `GameInterfaceLayer`，随后 `DrawInterface(GameTime)` 按顺序调用。当前版本存在唯一 `Vanilla: Map / Minimap` 锚点。

同一个已验证 Harmony 实例与 owner 在安装唯一 Update postfix 时，同时为这个精确方法安装一个 postfix。回调只在一次性构建完成后通过 Harmony 的私有字段注入取得 `List<GameInterfaceLayer>`，要求锚点恰好一个，并在其前插入唯一 `LegacyGameInterfaceLayer("JueMingR: Biome Display", ..., InterfaceScaleType.UI)`。没有候选方法、候选锚点、高层 fallback 或第二绘制 Hook；形状或锚点不符即停用本 Feature。

由于加载链按既有合同在 AssemblyLoad 回调外异步安装 Hook，一次性界面层构建可能先于 Hook。现有唯一 Update postfix 因此只在首次 Runtime handoff 时，于游戏线程检查同一个精确 `_gameInterfaceLayers`：若列表已经构建且尚无本 layer，则按同一锚点插入一次；若列表尚未构建，则不写入并继续由后续 setup postfix 插入；若已有唯一且位置正确的 layer，则保持不变。后续 Update 不重复检查、不重插，也不建立第二绘制入口或 fallback。

绘制回调只读缓存 ViewModel，使用 Terraria 已加载的 `FontAssets.MouseText` 路径（经 `Utils.DrawBorderString`）、当前 UI scale 坐标域、`#90EE90`/alpha 255、scale `0.72`、X `20`，Y 为客户区高度约 `45%` 并做垂直边界收敛。无背景、资源加载、输入捕获、反射、I/O、日志或业务观察。绘制异常只停用本 Feature并返回 `true`，不阻断后续原版 UI layer。

## 5. 项目职责

- Bootstrap：保持 Phase 0-S 加载与一次性交接职责，不承载 Feature、Runtime 或 UI。
- Platform：只新增本切片需要的宿主无关观察、Session 与单 Feature Runtime 合同；不引用 Terraria、ReLogic、XNA 或 Harmony。
- Features：拥有映射、顺序、去重、`N/A`、30-tick 门、启停与 Session 清理，以及 immutable ViewModel。
- TerrariaHost：唯一宿主引用边界与 Composition Root，直接读取 Terraria 类型、复用 Update postfix、注册唯一 UI layer并绘制缓存模型。
- Infrastructure 与 Setup：无真实需求，不改。

## 6. XNA 编译引用

编译探针已证明仅有既存 `Microsoft.Xna.Framework.Game.dll` 时，`Vector2`/`Color` 和 `SpriteBatch` 分别缺少 `Microsoft.Xna.Framework.dll` 与 `Microsoft.Xna.Framework.Graphics.dll`。因此 Host 可增加这两项 XNA 4.0 Refresh 本地编译引用，必须使用批准机器的固定 GAC_32 文件、记录精确 identity/SHA-256、`Private=false`，并由包禁带检查保证它们不进入 Git、构建输出或分发包。

## 7. 失败与停止边界

- 安装期无法精确验证两个 Hook，必须清理同 owner Patch 并沿用 Phase 0-S 失败证据；不得部分成功。
- 首次 Update 的 handoff、late setup 补入或完成证据写入任一步失败，均立即清空并停用已创建的群系 Runtime；不得出现正式 handoff 失败但功能仍半激活。
- 运行期 Session、观察或绘制失败，清空并停用群系 Feature；不得显示旧值、重试、换 Hook 或传播到原版循环。
- 若无法保持 Host 唯一宿主引用、唯一 Update postfix、唯一绘制入口、固定规模热路径或安全安装恢复，则停止并回到 Issue #28 报告，不扩张架构。
