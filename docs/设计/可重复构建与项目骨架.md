# 可重复构建与项目骨架

- 状态：草案
- 生效条件：只有 ADR-0011 经独立审查、机械最终化并随本任务合并进入 `main` 后，本设计才成为当前正式构建设计。
- 当前效力：本文件当前不授权加载链、安装器、UI、持久化业务、用户功能、Tag、Release 或正式发布。
- 对应任务：[Phase 0-R Issue #23](https://github.com/Kuroneko2020/JueMingR/issues/23)
- 决策依据：[ADR-0011：可重复构建与项目骨架](../决策/ADR-0011-可重复构建与项目骨架.md)
- 上位架构：[总体架构与状态所有权](总体架构与状态所有权.md)

## 1. 目的与非目标

本设计把已批准的六个生产边界映射为第一版真实解决方案，并固定可以从合法本地游戏安装恢复的构建输入。目标是让开发者能够明确回答“用什么工具、用哪些本地引用、构建了哪一个 commit、产生了哪些字节”，同时让机器检查阻止游戏依赖、Legacy 依赖和项目引用方向越界。

本设计只证明构建和结构。它不证明 Terraria 能加载 JueMingR，不证明 Terraria 1.4.5.8 已受支持，也不实现 AppDomainManager、Harmony、Hook、Composition Root、Runtime、Session、安装器、UI、持久化、Diagnostics 或任何用户功能。

## 2. 精确工具链

当前构建选择来自 Phase 0-R 的本机探针，不是从 Legacy 复制：

| 项目 | 本轮选择或已验证身份 |
| --- | --- |
| .NET SDK | `10.0.203`；`global.json` 使用 `rollForward: disable`、`allowPrerelease: false` |
| MSBuild | SDK 内置 `18.3.3.22005` |
| Roslyn | SDK `10.0.203` 内置编译器；探针产品身份 `5.3.0-2.26219.105`，build record 记录文件版本 |

| PowerShell | 正式脚本最低 Windows PowerShell 5.1；验证版本 `5.1.26100.9223` |

`dotnet` 自带 MSBuild/Roslyn 是唯一正式入口。已调查的 Visual Studio MSBuild `18.5.4.18101` 不在 PATH，也没有成为替代入口；SDK `6.0.428` 和 AnyCPU 探针能够工作，但增加第二工具链/输出身份没有本轮收益。仓库不使用 `PackageReference`、NuGet reference assemblies 包、Source Link 包、第三方测试框架或第三方构建工具。

## 3. 系统前置条件

正式构建要求：

- Windows PowerShell 5.1 或兼容实现；
- 精确的 .NET SDK `10.0.203`；
- Microsoft .NET Framework 4.7.2 Developer Pack / Targeting Pack；
- Git；
- 当前用户有合法的本地 Terraria 安装，且所选文件身份与正式 baseline 一致；
- Microsoft XNA Framework 4.0 Refresh 已安装，或显式提供含匹配程序集的 XNA 引用目录。

缺少任何前置条件时脚本必须在编译前明确失败。脚本不安装工具、不下载游戏文件、不修改 Terraria 安装、不从 JueMingZ/TerrariaHelper 取引用，也不扫描整块磁盘。

## 4. 解决方案和项目清单

`JueMingR.sln` 精确包含七个项目：

| 项目 | 性质 |
| --- | --- |
| `JueMingR.Bootstrap` | 生产 class library |
| `JueMingR.Platform` | 生产 class library |
| `JueMingR.Features` | 生产 class library |
| `JueMingR.TerrariaHost` | 生产 class library |
| `JueMingR.Infrastructure` | 生产 class library |
| `JueMingR.Setup` | 生产 class library |
| `JueMingR.ArchitectureTests` | 非生产 console executable |

这六个生产项目是已经批准的物理边界，不是六个已经实现的产品子系统。不得为了空职责增加项目，也不得把测试项目变成生产依赖。

## 5. 项目职责

- `JueMingR.Bootstrap`：只有无状态、无行为的 internal assembly marker；BCL-only。
- `JueMingR.Platform`：Host-neutral；只有 assembly marker 和第 12 节最小 typed operation seam。
- `JueMingR.Features`：只含 marker；没有具体 Feature、catalog、registry 或 manager。
- `JueMingR.Infrastructure`：只含 marker；没有文件系统、日志、配置、数据库或 Diagnostics 实现。
- `JueMingR.TerrariaHost`：只含 marker 和三个 `typeof(...)` getter 的无状态编译引用探针；不实例化游戏对象、不访问 Terraria 静态状态、不反射扫描、不安装 Hook。
- `JueMingR.Setup`：本轮只建立无行为源码/引用隔离边界；没有 EXE、CLI、UI、安装、检测或恢复逻辑。
- `JueMingR.ArchitectureTests`：用自有 runner、XML、文件系统、Git 跟踪事实和 Platform 程序集元数据执行结构检查。

## 6. 项目引用图

正式 `ProjectReference` 图为：

```text
JueMingR.Bootstrap        -> 无
JueMingR.Platform         -> 无
JueMingR.Features         -> JueMingR.Platform
JueMingR.Infrastructure   -> JueMingR.Platform
JueMingR.TerrariaHost     -> JueMingR.Platform
                             JueMingR.Features
                             JueMingR.Infrastructure
JueMingR.Setup            -> 无
JueMingR.ArchitectureTests-> JueMingR.Platform
```

当前不建立 Host → Bootstrap 编译引用。已批准总体架构中的固定 late handoff 和 Composition Root 仍等待加载链阶段的独立授权。

## 7. TargetFramework 与 PlatformTarget

七个项目都在自己的 `.csproj` 中显式声明 `TargetFramework=net472`、`PlatformTarget=x86`、`OutputType`、`AssemblyName`、`RootNamespace`、`GenerateAssemblyInfo=true`、`AllowUnsafeBlocks=false` 和 `TreatWarningsAsErrors=true`。

选择 x86 的依据是：当前合法 Terraria、ReLogic 和 XNA Game 输入均为 I386/PE32，Terraria/ReLogic/XNA Game 需要 32 位 CLR；SDK 风格 net472 x86 class library 与 executable 也已实际构建为 `ILOnly, Requires32Bit`。统一 x86 比混合 solution platform 更直接地表达当前同进程边界。它不锁定未来进程外 Setup/Recovery 工具的最终框架或位数。

## 8. Bootstrap BCL-only

Bootstrap 没有 `ProjectReference`、`PackageReference` 或游戏 `Reference`，也没有配置入口、程序集加载、AppDomainManager、Harmony 或 Terraria 访问。ArchitectureTests 直接检查这些机器事实。后续加载链任务若要改变 Bootstrap，必须由独立 Issue 授权并保持 BCL-only 约束。

## 9. TerrariaHost 的唯一游戏引用

只有 `JueMingR.TerrariaHost` 直接引用：

- `Terraria.exe`；
- 从 `Terraria.exe` 精确嵌入资源提取的 `ReLogic.dll`；
- Microsoft XNA 安装/GAC_32 的 `Microsoft.Xna.Framework.Game.dll`。

三项都使用本地 `TerrariaReferencesDirectory` 和 `<Private>false</Private>`。实际最小编译探针为 `typeof(Terraria.Main)`、`typeof(ReLogic.OS.Platform)`、`typeof(Microsoft.Xna.Framework.Game)`。删除 XNA Game 会因 `Terraria.Main` 基类无法解析而以 `CS0012` 失败；XNA Framework/Graphics 对该最小探针不是必需输入，所以不进入 baseline。

ArchitectureTests 证明 TerrariaHost 是唯一物理游戏引用承载项目；由于本轮禁止 Composition Root 实现，它不声称一个具体 Root 已经存在或已验证唯一。

## 10. Setup 骨架为何暂为无行为边界

正式总体架构把 Setup/Recovery 定义为未来进程外独立部署单元。本轮故意只建立无行为 class library，以验证它不依赖任何游戏内项目或游戏程序集。当前结果只证明源码和引用隔离，不证明最终 executable、安装检测、修复、回滚或卸载已经实现；未来输出类型和运行时必须由真实 Setup 任务决定。

## 11. 架构检查项目

`JueMingR.ArchitectureTests` 不使用测试 NuGet 包，只接受正式 build entry 传入的 repository/configuration、锁定 SDK/Targeting Pack 根和 owned tool-state root；缺少这些正式输入或自身继承的变量集合不精确等于 `closed-allowlist-v1` 都会 fail closed。它检查：解决方案中只含精确七个 C# 项目、物理项目精确集合、无重复项目、精确 ProjectReference 图、无循环、Bootstrap/Platform 纯度、Features/Infrastructure 依赖、Host 恰好三个直接程序集引用及其精确 HintPath/`Private=false`、其它项目零直接程序集引用、Setup 隔离、Legacy/TerrariaHelper 隔离、Git 二进制文件名/基线内容哈希/托管程序集身份边界、无 PackageReference/COM/native reference、仅有锁定 SDK 自带 Analyzer、项目 SDK、未条件化的原始项目属性、实际求值后的 TFM/x86/C# 7.3/精确输出与中间路径/compiler 与 build side-effect/确定性属性、operation 完整 public API 面、生产项目不引用测试、唯一物理游戏引用承载位置，以及正式 build entry/baseline 存在。它的 Git 与 dotnet 子进程使用已验证绝对可执行文件，从零构造只含所需 Windows 基础与相应 Git 或 dotnet/MSBuild 锁定值的环境，并把全部可写用户/临时状态限制在正式 owned root。

检查从仓库根递归查找 `.csproj` 并排除明确生成目录；带版本的 `Reference Include` 与 `HintPath` 文件名都会被识别。除仓库根的 `Directory.Build.props` 和空 `Directory.Build.targets` 外，任何项目祖先目录中的嵌套 `Directory.Build.props/targets` 都会失败；根共享文件和项目 XML 都使用显式元素白名单，不得注入 ProjectReference/Reference/PackageReference/Analyzer/COM/native reference/Target/Sdk，项目也不得使用显式 `Import`、第二 SDK、外部 XML namespace、条件或 item metadata 属性绕过直接可审计事实。正式 build 锁定根共享文件和 SDK import hook，在任何 restore/build 前按正式全局参数逐项目断言有效 properties、五类输出/中间路径及 `OutDir`、compiler side output、build event/pack/deploy/restore graph、ProjectReference、direct Reference、PackageReference、Analyzer、COMReference 和 NativeReference。检查不匹配 README/ADR 自然语言，也不靠某个生产类名存在来冒充运行行为。

## 12. 最小 operation 合同

Platform 当前只有三个 public 类型：

- 空 marker interface `IGameOperationRequest`，请求身份由具体 CLR 类型表达；
- `GameOperationOutcome`，底层类型固定为 `int`，以 `0..6` 七个互异数值精确区分 `Rejected`、`Succeeded`、`PartiallySucceeded`、`Failed`、`Cancelled`、`TimedOut`、`Unconfirmed`；
- sealed `GameOperationResult`，通过一个必需且不可选的构造参数接受已定义 outcome，并只读返回同一值。

合同没有字符串 action ID、payload、executor、目标 Feature、Host port、Coordinator、队列、线程、时间、重试、优先级、冲突域、持久化、诊断或全局错误框架，也不引用 Terraria/ReLogic/XNA/Harmony。真实 Feature 和加载链以后校准请求 payload、失败原因和执行边界。

## 13. 合法 Terraria、ReLogic 与 XNA 来源

`scripts/prepare-terraria-references.ps1` 可以接受显式合法目录；未传 Terraria 目录时，只通过当前用户 Steam 注册表根、`libraryfolders.vdf` 和 app `105600` manifest 定位完整安装。它不写入源安装。

脚本用 BCL reflection-only 上下文读取 `Terraria.exe` 的精确资源 `Terraria.Libraries.ReLogic.ReLogic.dll`，只打开资源流并写入临时文件，不调用入口点、方法或静态字段，也不实例化游戏类型。XNA 默认从已安装 XNA Framework 4.0 Refresh 的 GAC_32 特定程序集目录取得；不搜索整盘。

源路径只进入被 Git 忽略的本地 marker，正式 baseline、文档、Issue 和 PR 不记录个人绝对路径。编译引用不是再分发许可，也不构成加载、运行、渠道或兼容支持声明。

## 14. baseline manifest

`eng/TerrariaReferences.baseline.json` schema 1 的 profile 为 `terraria-steam-1.4.5.8-xna-4.0.20823.0-compile-refs`，baseline SHA-256 在每次 build record 中按 UTF-8、统一 LF 换行的文本身份重新计算，避免 Git checkout 换行策略改变同一 manifest 的身份。它记录 Steam app/build 证据范围和以下三项身份：

| 逻辑文件 | 程序集/文件版本 | PE/CLR | SHA-256 |
| --- | --- | --- | --- |
| `Terraria.exe` | `1.4.5.8` / `1.4.5.8` | I386, PE32, ILOnly, Requires32Bit | `960A03BFF6050CF7BE16DFC1A7B19E10FC2C4F8F835A6A3B135A50DD9E6BA2F3` |
| `ReLogic.dll` | `1.0.0.0` / `1.0.0.0` | I386, PE32, ILOnly, Requires32Bit | `E1C5DCCEFFF5FD1C789FF712BABFA1A305FCED0D03C96EF30F2C14D99AA0AF29` |
| `Microsoft.Xna.Framework.Game.dll` | `4.0.0.0` / `4.0.20823.0` | I386, PE32, ILOnly, Requires32Bit, StrongNameSigned | `A0347E9D9A646779A9BB1BD512AF333AE07A3DB65B3259FAE3220ED87A80E756` |

每项还记录程序集简单名、public key token、来源类别、`redistributableByJueMingR=false` 和 `copyLocal=false`。普通脚本没有覆盖正式 baseline 的参数。

## 15. 引用准备命令

从仓库根运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\prepare-terraria-references.ps1 -InspectOnly
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\prepare-terraria-references.ps1
```

需要显式来源时使用 `-TerrariaInstallDirectory` 和可选 `-XnaReferenceDirectory`；`-DestinationDirectory` 默认是被忽略的 `external/TerrariaRefs`。`-VerifyOnly` 只验证已准备目录。正常重复运行在目标完整且身份一致时直接 PASS 并保持字节不变。

脚本先确认规定的同级 Legacy 仓库存在，并把 Legacy、来源、目标和 repository root 解析为 Windows 最终物理目录路径；在读取源哈希、创建 TEMP、早退、`-Force` 或 staging 之前，要求 Terraria/XNA 来源与仓库双向不重叠，且目标与两个来源及 Legacy 双向不重叠。目标可以位于仓库内，但不能等于或包含仓库；Legacy 不作为引用输入，也不允许被目标、staging、backup 或清理根触及。只有 reproducibility 入口创建的系统 TEMP clean clone 因没有 sibling 时，才显式传入由外层已验证的真实 Legacy 物理根，作为单纯 no-write protected path；clone 脚本不读取其 Git、源码或构建产物。例外还必须同时满足：repository parent 物理等于显式 verifier root、verifier root 是 system TEMP 的直接 `JueMingR-Repro-<32 hex>` 子目录、repository leaf 是两个固定 clone 名之一。普通 clone 不能只靠传入任意末级名为 `JueMingZ` 的目录进入例外；若 repository 自己已有 sibling，显式参数必须物理等于该 sibling。marker 必须保存两个完整绝对来源目录、布尔 `sourceHashesUnchanged=true` 和匹配的 Steam 证据；`-VerifyOnly` 会重新检查 marker 结构、来源目录中 Terraria/XNA 文件仍与 baseline 相同，以及 refs 与来源/仓库/Legacy 边界。

随机 TEMP scratch 本身也必须与两个来源、destination、repository 和 Legacy 双向不重叠；prospective staging/backup 在创建前也分别通过同一类隔离门。通过这些门后，脚本才在 scratch 完成三项复制/提取与逐字段校验，再在目标父目录创建 staging，验证完整后切换正式目标。失败不发布半套 refs；`-Force` 只接受仅含 marker 和三项批准文件、没有子目录或 reparse point，且 marker schema/generator/profile/baseline/来源身份、来源当前内容和记录文件元数据均可核验的既有目标，不能凭一个可复制字符串覆盖用户目录。物理路径解析使用 Windows `GetFinalPathNameByHandle` 处理现存祖先，因此 junction/symlink、SUBST 和 8.3 表示不能靠不同字符串绕过；外部传入的 extended/device path 前缀直接拒绝。本门不声称能抵御检查完成后由恶意本机进程并发替换目录的竞态。

## 16. 正式构建命令

从仓库根运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\build.ps1 -Configuration Debug -RequireClean
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\build.ps1 -Configuration Release -RequireClean
```

参数还包括 `-TerrariaReferencesDirectory`、`-OutputDirectory`、`-NoRestore`，以及只供定位问题的 `-SkipArchitectureTests`。`-NoRestore` 仅作为明确的 fail-closed 诊断入口保留：任何请求都会在写入前拒绝，正式模式始终执行 fresh restore，不接受缓存 restore graph 作为构建输入。`OutputDirectory` 必须是仓库 `artifacts` 下的专用子目录；正式验证不得跳过 ArchitectureTests。

入口先验证 refs marker、来源文件身份和其中的两个来源目录，再要求 output root 与 configuration root 都是仓库 `artifacts` 下的专用子目录，且不等于、不位于也不包含 refs、Terraria 来源或 XNA 来源。该门使用最终物理路径并早于 owned output 替换和任何输出目录创建；`-NoRestore` 更早直接拒绝，不进入清理或复用。已有 configuration root 只有在无 tracked 文件、根层只含正式 marker/build record/work，且 work 内只含无 reparse point 的 bin/obj 时才允许由下一次 fresh build 清理。

入口先确认并物理解析同级 Legacy 根，再从调用环境的 TEMP 根推导随机专用状态根；在创建 scratch 前，先要求 prospective 根与 repository、refs、output/configuration、两个合法来源和 Legacy 物理隔离。在清空环境前只接受并解析精确 `dotnet.exe` 与 `git.exe` 的绝对、非 reparse 路径及 Windows/SpecialFolder 工具根，扩展名省略的 command wrapper 不构成正式工具。随后入口完整快照当前 Env、清空所有变量，只重建固定 Windows 基础路径、以正式 Git 目录为首项且只含已验证工具/Windows 目录的 PATH、指向 owned TEMP 的 `USERPROFILE/HOME/APPDATA/LOCALAPPDATA/TEMP/TMP`、受控 Program Files/ProgramData，以及锁定的 .NET CLI/NuGet/Git/MSBuild 值；ArchitectureTests 只接受 PATH 首项的 regular `git.exe`，从而与正式入口使用同一工具。不继承任何其它普通名称，因此 `ErrorLog`、`OutDir`、`CodeAnalysisTargets`、build event 或未来新增的合法 MSBuild 属性名都不能从调用环境进入子进程。Git 全局/系统配置、hooks、pager、replacement objects 和可选索引写入关闭；入口在创建 scratch 前先以仅有 `-C` 的 discovery 探针把 Git 报告的 work tree 物理绑定到 repository，保存 linked worktree 专属 git-dir 和 common-dir，要求两者与 refs/output/configuration/prospective scratch/Legacy 双向不重叠，创建 scratch 后立即复核同一 binding，再让全部身份命令显式使用经验证的 `--git-dir/--work-tree`。dirty identity 的两次 diff 还显式使用 `--no-ext-diff --no-textconv`；recorded source paths 必须全部处于普通 tracked 索引模式，且 `filter`、`ident`、`working-tree-encoding`、textconv 等内容转换/外部处理属性不得设置。仓库本地 `core.worktree`、位于 owned output 内的 separate git-dir、`diff.external`、assume-unchanged/skip-worktree 或 attributes 不能改变身份、输入字节、执行外部命令或触发元数据删除。`COREHOST_*`、`COMPlus_*`、`COR_*` 和其它 host/runtime 控制变量因不在允许列表而不存在。

路径门通过后，入口依次验证原始 solution/project/shared build 定义、global.json SDK、由 Windows SpecialFolder 而非可修改环境变量取得的 4.7.2 Targeting Pack、Git 二进制边界和 clean/dirty 身份，并锁定根 `Directory.Build.props`、空 `Directory.Build.targets`、批准的 SDK 补充 import、所有 CustomBefore/After hook、compiler side output、build event、pack/deploy、restore graph 与 `OutDir`；solution 级 `Directory.Solution.props/targets` 自动导入则显式关闭且路径清空。tracked 与 non-ignored untracked 路径共同构成 recorded source inventory；根正式输入（含 `.gitattributes`、`.editorconfig` 和 `.globalconfig`）以及 `eng/src/tests` 中除 guarded `bin/obj` 外的每个物理文件都必须在该 inventory 中且不能是 reparse。任何 restore/build 或输出写入前，入口按正式参数求值并断言七个项目的 properties、五类输出/中间路径及 `OutDir`、ProjectReference、direct Reference、PackageReference、Analyzer、COMReference 与 NativeReference；`Compile/EmbeddedResource/AdditionalFiles/EditorConfigFiles/AnalyzerConfigFiles` 的 pre-target 求值项必须分类为 recorded repository input、由 locked SDK 定义且位于该项目精确 intermediate roots 的 generated input，或 locked SDK input，其它父目录/用户目录/外部/ignored 输入全部拒绝。该数组/digest 只描述 target 执行前求值事实；locked SDK 在 target 执行期生成的 AssemblyInfo、editorconfig 等输入不逐项进入此数组，也不被称为完整 Csc 输入闭包，它们继续受锁定 targets/import 与精确 guarded intermediate/output 约束。随后才清理/创建 owned output、以 `nodeReuse=false` fresh restore/build、运行同样禁用 node reuse 的对应 configuration ArchitectureTests，扫描 forbidden output，断言精确 26 项 DLL/EXE/PDB 声明输出，再复核来源哈希、Legacy 隔离、Git 索引/属性、物理 Git 绑定、正式输入盘点及 HEAD/完整工作树身份未在构建期间变化，最后形成待提交的 build record。Git 与输出扫描同时使用禁止文件名、三项 baseline 内容 SHA-256 和托管程序集简单名，改名不会绕过 Terraria、ReLogic、XNA、Harmony、TerrariaHelper 或 Legacy 边界。finally 分别尝试完整清除当前环境并恢复原始快照，以及只清理由 system TEMP 物理前缀和专用名称验证的状态根；原本存在但值为空的环境变量也通过 Windows API 恢复并逐键核对存在性与精确值。cleanup 在物理规范化前从父目录取得原始 root entry 并拒绝 root 自身 reparse，避免删除 junction/symlink 目标；删除后立即并在 250 ms settling interval 后继续从原始路径父目录枚举精确 entry 名，确认普通文件、目录和 dangling reparse entry 均不存在。环境恢复、清理或不存在性验证任一步失败都不写 build record/PASS。入口不清理合法 refs、不修改游戏安装、不打包。

## 17. 构建身份

`Directory.Build.props` 使用 `Deterministic=true`、portable PDB、UTF-8 code page、稳定 PathMap、显式 `SourceRevisionId` 和非发布占位版本 `0.0.0-dev`。`AssemblyVersion/FileVersion=0.0.0.0` 只是构建系统占位，不是首个产品版本，也不规定未来永久版本策略。

`artifacts/build/<Configuration>/build-record.json` 记录：

- source commit、clean/dirty、dirty diff SHA-256、传入二进制的 source revision，以及不含绝对路径的物理 Git/正式输入盘点策略；
- configuration、`closed-allowlist-v1` 环境策略，以及逐项目由 MSBuild 实际求值的 TFM、PlatformTarget、LangVersion、OutputType、程序集/命名空间、SDK、确定性属性、compiler/build side-effect、相对化的五类输出/中间路径、ProjectReference、direct Reference、PackageReference、批准的 SDK Analyzer 与空 COM/native reference；同时记录五类 pre-target 求值项的相对路径/来源、规范化 input-set SHA-256 和 `ignoredPreTargetEvaluatedInputCount=0`，但不把它称为完整 Csc 输入闭包。顶层 TFM/x86/C# 版本由七个一致的实际求值结果派生，不使用硬编码值；
- SDK、MSBuild、compiler、PowerShell、Developer Pack 和有效参数；原始环境名、值、个人目录和工具绝对路径不进入记录；
- baseline profile/SHA-256 与三项 refs SHA-256；
- 每个声明 DLL/EXE/PDB 的相对路径、大小和 SHA-256；
- ArchitectureTests 结果、外部开始/结束时间、耗时和未验证轴。

时间只在 ignored JSON 中，不进入二进制。build record 本身不是声明可重复输出。

## 18. clean 与 dirty 构建边界

clean 构建把精确 commit 作为 `SourceRevisionId`。dirty 构建仍可用于本地诊断，但会把 tracked diff、staged diff 和未跟踪文件哈希合成为 `dirtyDiffIdentitySha256`，并在 source revision 中明确标记 dirty；不得把它称为发布候选。

`-RequireClean` 对任何未提交、未暂存或未忽略文件 fail closed；无论是否使用 `-RequireClean`，能影响正式构建的 ignored 物理文件或 ignored 实际 MSBuild input 都会在输出写入前失败。正式构建每次使用 fresh restore、新的 owned output root 和独立 obj，不依赖项目目录已有的 bin/obj；任何 `-NoRestore` 请求都会明确失败。

## 19. 可重复构建定义

本设计的声明范围是正式 build entry 列出的全部 DLL、EXE 和 portable PDB；不含带执行时间的 build record。相同 commit、锁定 SDK/MSBuild、相同且已记录身份的 .NET Framework 4.7.2 reference assemblies、相同 refs baseline、configuration、x86 和参数下，两个路径不同且 obj/bin 独立的 clean clone 必须逐文件大小和 SHA-256 相同，差异为 0。当前 build entry 会验证 4.7.2 pack 存在并记录 `mscorlib.dll` 文件版本，但不宣称已经对所有可能机器的完整 Developer Pack 内容建立仓库 baseline。

`scripts/verify-reproducible-build.ps1` 要求源 commit clean，预先锁定绝对、非 reparse 的精确 `git.exe`，确认并物理解析同级 Legacy 根，用同样的未绑定 discovery/显式 bound Git 契约核对当前物理 work tree，要求 git-dir/common-dir、Legacy、summary 和 temporary clone 根互相隔离，并拒绝当前正式输入范围内的 ignored 或 reparse 文件（含根 `.gitattributes`/`.editorconfig`/`.globalconfig`）以及异常 Git 索引标志/内容转换属性。它通过 `git clone --no-local --no-hardlinks --no-checkout` 创建两个独立副本；两个副本都确认没有继承 `external/TerrariaRefs`，把外层已验证的真实 Legacy 根只作为禁止写入路径显式传入，分别从合法 Terraria/XNA 来源运行 prepare 与 RequireClean build，再复核七个逐项目 pre-target evaluated item arrays/digest 完全相同、build record 和物理文件哈希。副本不读取 Legacy Git、源码或产物，不以 Legacy 恢复构建。摘要输出只允许位于仓库 `artifacts/reproducibility` 内，并在最终写入前重新核对源 Git 绑定/身份、Legacy 隔离、索引/属性、正式输入盘点、摘要物理父目录及与显式 Terraria/XNA 来源的隔离。summary 使用同目录随机 `CreateNew` 普通文件完成 write-through/flush，验证其非 reparse 后删除旧 destination 目录项并原子 move；既有 hardlink/symlink 不会被原地 truncate。所有原始 `GIT_*` 键按“存在性 + 精确值”恢复，存在但为空的值通过 Windows API 恢复，不被误作 absent。Git pack 的只读属性只在经前缀和 TEMP 根双重验证的临时目录内清除，成功和失败都清理 clone。

正式命令：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify-reproducible-build.ps1 -Configuration Release
```

摘要保存在 `artifacts/reproducibility/Release/reproducibility-summary.json`。

## 21. 缺失引用和身份不符的失败方式

新 clone 没有 refs 时，build entry 在编译前明确报告 prepared reference directory missing。目录存在但 marker、profile、baseline SHA、来源路径/来源文件身份、程序集名/版本、文件版本、public key token、PE/CLR、Requires32Bit、来源类别或文件 SHA 不符时也会明确失败。普通 MSBuild 的含糊 missing-DLL 诊断不是正式失败接口。

正式 baseline 变化只能通过新的 Git 任务和 PR；当前脚本不能把任意本地文件提升为新 baseline。

## 22. 游戏文件不进入输出和 Git

`.gitignore` 已忽略 `external/TerrariaRefs`、bin、obj、artifacts、outputs 和 `.local`。ArchitectureTests 与 build entry 都扫描 Git 跟踪文件；build entry 和 reproducibility 脚本扫描输出。机器门同时检查文件名、baseline 内容 SHA-256 与托管程序集身份，禁止 Terraria、ReLogic、Microsoft.Xna.Framework、Harmony、TerrariaHelper 和 Legacy 文件，即使它们被改名也不能通过。

所有 Host 游戏引用 `Private=false`，实建输出未复制游戏文件。仓库只跟踪机器可读身份 baseline，不跟踪或再分发专有二进制。

## 24. 工具链升级方式

升级前在新任务中重新调查已安装稳定 SDK/MSBuild、net472 Developer Pack、Windows PowerShell 最低兼容和 x86 输出；在 TEMP 完成 class library/executable 探针，再更新 global.json 和正式身份说明。必须重跑 Debug、Release、ArchitectureTests、clean clone、全部负向控制和双副本逐字节比较。

如果 SDK 补丁升级改变编译器、PDB、输出身份或长期恢复边界，应更新 ADR；仅机械补丁且完整证据证明边界不变时，是否需要新 ADR 由工程治理任务判定。不得静默 roll forward 或把机器“最新 SDK”冒充相同构建身份。

## 25. 游戏引用基线更新方式

Terraria、嵌入 ReLogic 或 XNA 身份变化时，创建独立 Issue/分支/PR，重新证明合法来源、提取安全、最小 XNA 集、程序集/文件版本、public key token、PE/CLR、Requires32Bit、SHA-256 和源安装未修改。更新 baseline 后必须重跑引用反例、Host 编译探针、Debug/Release、clean clone、架构负向控制和 reproducibility。

baseline 更新只改变“允许用于编译的输入身份”，不能自动宣称新 Terraria 版本已经加载、兼容或受支持。

## 26. 当前没有实现什么

当前没有 AppDomainManager、config 加载入口、程序集加载、Harmony、Hook、Composition Root、Runtime、Session、Coordinator、Operation executor、Feature、文件系统/日志/配置/数据库/Diagnostics、Setup executable、CLI、UI、安装恢复、多人逻辑、性能探针、CI、Tag、Release、安装包或测试包。没有启动 Terraria，也没有修改 Terraria 或 Legacy。

## 27. 下一阶段可使用的输入

经本任务最终合并后，下一候选阶段可以使用：精确锁定的构建入口、三个本地编译引用的合法准备和 identity gate、六个生产物理边界、Host 唯一游戏引用边界、最小 typed operation 终态分类，以及会对依赖越界 fail closed 的 ArchitectureTests。

## 28. 设计演进方式

本设计描述当前真实构建和物理边界。普通任务不得增加生产项目、改变主工具链/TFM/PlatformTarget、改变游戏引用来源模型或放宽可重复构建定义。上述变化需要新的 Accepted ADR；实现细节变化也必须同步更新本设计和机器检查。

真实加载链、Setup 和代表性 Feature 出现后，应以运行证据校准当前最小 seam，而不是预建万能 Manager、Service Locator、Event Bus、全局队列或 Legacy schema。无效说明应被更新或替代，动态任务状态继续只存在于 GitHub Issues。
