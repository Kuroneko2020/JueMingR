# 钓鱼与配装

## 0. 结论与证据边界

本专题覆盖原执行指令附录 **16、17、18**：完整鱼获与过滤鱼获显示、过滤名单与预设、自动钓鱼、真实过滤与切杆跳过、自动存放鱼、自动换装、自动配装、快捷改名。

主要结论：

1. Legacy 已接通观察、名单编辑、自动收杆与重抛、两种存鱼模式、两种装备策略及单人改名。但“预览候选”“已经执行收杆”“确实获得物品”“确实存入容器”是不同证据层级。
2. 自动换装是原版三套装备组的启发式评分与切换；自动配装是直接交换背包、虚空袋、时装栏和当前装备格中的物品。两者都不等于计算真实最优渔力。
3. Legacy “所有”存鱼依赖自动收杆请求关联的上钩物品 ID；“任务鱼”模式会在钓鱼会话内检查背包已有任务鱼，二者来源契约不同。
4. 当前 Terraria 1.4.5.8 已补证消饵、断线、敌怪、鱼获落袋、原版换装和角色保存链。Legacy 登记的 `SupportedByOriginalAction` 不能代替多人验证，尤其不能替直接数组换装提供同步证明。
5. R 固定基线尚未接入本专题功能。现有 F5、输入、信息显示、物品所有权、附近存放和会话生命周期可分别承接窄职责；不能把 Legacy 静态状态或巨型服务整体搬入。

## 2. 完整鱼获、过滤鱼获：实际观察与候选全集定义

### 2.1 入口到显示链

`信息页开关 → AppSettings → InformationStatusLineService.GetLines → 本地鱼漂定位 → InformationFishingCatchResolver → 候选物品 → 完整／过滤两条文字 → 信息文字层绘制`。

两条显示同时开启时共享本轮候选求解；过滤显示另用声呐状态和当前过滤设置。它们不会调用自动收杆，也不会直接调用原版 `FishingCheck`。

服务有 **30 tick** 的状态行缓存。无本地鱼漂时不显示鱼获条目。完整与过滤条目分别从顺序号 40、45 开始；长列表按约 **38 个字符**拆行，用顿号连接，长单个名字不会被拆成两个物品。这里是文字行，不是可点击物品来源页，也没有专用“查看完整鱼获”的全屏窗口。

证据：Z [InformationStatusLineService](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Information/InformationStatusLineService.cs#L14)，14、34–51、80–145 行；[InformationFishingStatusLineBuilder](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Information/InformationFishingStatusLineBuilder.cs#L51)，51–149、239–279 行；[信息页入口](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/UI/Legacy/LegacyMainWindow.Information.cs#L76)，76–78 行。

### 2.2 候选不是写死的“全部鱼名表”

完整候选的定义是：

1. 找到当前本地鱼漂及其位置，取得玩家、世界、鱼竿、鱼饵、任务鱼、群系等环境。
2. 按 Legacy 自己的水体扫描和渔力近似构造若干 `FishingAttempt/FishingContext`。
3. 从当前加载原版 `Main.FishDropsDB` 的规则列表按注册顺序读取规则。
4. 对每个构造情形调用 `MeetsConditions(context, true)`；匹配时收集该规则 **全部 `PossibleItems`**，按正整数 ID 去重。
5. 当前情形遇到 `IsStopper` 即停止继续读后续规则；总候选达到 **96 种**停止。
6. 最终按 **显示名 Ordinal → ID → Kind** 排序输出。

因此，“完整”指此近似观察范围内、此上限内的候选集合，不能解释为精确枚举当前原版所有真实概率分支，也不提供概率或下一次保证结果。

**原版 1.4.5.8 当前规则全集来源及顺序**：

`AnyEnemies stopper → LavaDrops → HoneyDrops → JunkDrops → CrateDrops → RareDrops → RemixDrops → DungeonDrops → CorruptionDrops → CrimsonDrops → HallowedDrops → GlowingMushroomsDrops → SnowDrops → JungleDrops → OceanDrops → DesertDrops → FloatingIslandDrops → SurfaceDrops`。

每一组的完整 ID、条件与分数定义位于已锁原版 `GameContentFishDropPopulator` 32–247 行；候选运行时依照这份规则数据库，不应把某次结果导成永久产品白名单。

当前原版 `FishDropRule.MeetsConditions` 53–64 行只遍历 `Conditions[].Matches`；`forDisplay` 参数在该基类实现内没有另行分支，**不判断概率，也不检查 `Rarity.Matches`**。真正 `Attempt` 31–50 行另做概率抽取、稀有度检查、随机挑一个结果。`IsStopper`：空 `PossibleItems` 为停止规则；非空时要求 `Rarity.HackedIsAny` 且概率分子等于分母。Legacy 复用的是条件与停止语义，不是执行一次钓鱼。

证据：Z [InformationFishingCatchResolver.ResolveCatchCandidates](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Information/InformationFishingCatchResolver.cs#L46)，46–206 行；[InformationFishDropRuleEvaluator](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Information/InformationFishDropRuleEvaluator.cs#L12)，12、17–82、165–185 行。原版 FishDropRule（本地原版证据 `.local/全功能调查/原版/Terraria.GameContent.FishDropRules.FishDropRule.cs:15`），15–64 行；FishDropRuleList（本地原版证据 `.local/全功能调查/原版/Terraria.GameContent.FishDropRules.FishDropRuleList.cs:10`），10–45 行；GameContentFishDropPopulator.Populate（本地原版证据 `.local/全功能调查/原版/Terraria.GameContent.FishDropRules.GameContentFishDropPopulator.cs:10`），10–247 行。三份原版文件哈希见第 10–15 节。

### 2.3 Legacy 构造的情形全集及限制

| 维度 | Legacy 枚举／取值 |
|---|---|
| 常规高度层 | 按鱼漂所在层得到 0／1／2／3／4；常规划分为天空、地表、地下、洞穴、地狱 |
| Remix 高度 | 使用另一套 0／1／3／4／2 判定；得到 2 时还枚举 1 |
| 腐化、猩红 | 同时存在时枚举两个互斥结果；Remix 层 0 强制二者 false |
| 蜂蜜 | 一般保持实际蜂蜜；`notTheBees` 的蜂蜜情形枚举 true、false |
| 雪地、沙漠、感染沙漠 | 相关条件开启时枚举 false、true，关闭时只有 false |
| 丛林 | 保持实际丛林值 |
| 匣子 | 枚举 false、true |
| 垃圾 | 只有被认定可能产生垃圾时枚举 false、true，否则 false |
| Remix 海洋 | 固定 false |
| 常见／不常见／稀有／很稀有／传奇字段 | 构造时全部 false；规则条件求值不等于真正稀有度随机判定 |
| 鱼漂种类、waterQuality、atmo、已有掉落／敌怪结果 | 构造时设为 0／0f；不复刻原版完整实时状态 |
| 饵料包 chums | 水体扫描结果固定为 0 |

水体扫描从鱼漂所在液体行左右扩张，再对每列向下计数，直到干燥、阻挡或世界边界；液体类型优先熔岩，再蜂蜜，再水。蜂蜜计数乘 1.5 后取整。水体少于 75、有效渔力不足等返回原因文字；松露虫 2673 不列普通鱼获。此扫描不是固定半径小格子扫描，大连通水体时工作量随实际扫描范围增长。

原版两端核对的重要差异：

- 原版 `Fishing_GetBestFishingPole` 优先有效的当前选中鱼竿；Legacy 显示环境的补全会比较背包更高钓力鱼竿，并考虑鼠标物品，可能显示与手持鱼竿不同的候选。
- 原版鱼饵从 **54–57，再 0–49** 找第一份有效鱼饵；Legacy 早期显示环境还考虑鼠标上的鱼饵。虚空袋不是原版此选饵函数的来源。
- 原版无合格鱼竿／鱼饵会得到零渔力；Legacy 反射失败或补全路径会用简化公式估计，不能承诺与原版一致。
- 原版任务鱼探测还检查渔夫 NPC 369 是否存在；Legacy 候选任务鱼读取检查今日完成与背包已有，但没有这一 NPC 条件。
- 原版读取真实饵料包数量、运气随机变化、地牢解锁、特殊世界丛林／雪地／沙漠组合、Remix 海洋等分支；Legacy 只枚举表中近似情形。尤其固定 `RolledRemixOcean=false`、固定 chums=0 不能称为原版全覆盖。
- 完整鱼获 HUD 的这条求解链 **只输出 Item**。精确名单“添加当前”会额外加入六个 NPC 候选，不能据此说完整鱼获 HUD 已包含全部敌怪。

## 3. 过滤规则：完整模式、优先级、类别与未知处理

### 3.1 规则求值总顺序

1. 设置／候选缺失、过滤关闭、候选 Kind 不认识或 ID≤0：**保留**。
2. 若候选是匣子，先看匣子特殊规则；不是 Follow 就在此形成决定。
3. 仍未形成决定且候选是任务鱼，看任务鱼特殊规则。
4. 仍未形成决定且候选是 NPC 敌怪，看敌怪特殊规则。
5. 三类均未形成决定，才按当前普通白名单／黑名单求值。

特殊规则不是无条件压过显式名单：

| 特殊规则 | 当前匹配范围内的例外 | 结果 |
|---|---|---|
| Allow／要 | 当前为黑名单且当前名单命中 | 跳过 |
| Allow／要 | 其他情况 | 保留 |
| Deny／不要 | 当前为白名单且当前名单命中 | 保留 |
| Deny／不要 | 其他情况 | 跳过 |
| Follow／跟随 | 无特殊决定 | 继续后面的类别／普通名单 |

普通名单：

- 白名单：命中保留，不命中跳过。
- 黑名单：命中跳过，不命中保留。
- 精确：以 **Kind + ID** 匹配，显示名快照不参与运行决定。
- 关键词：对当前本地化显示名做 `CurrentCultureIgnoreCase` **子串**匹配，按保存顺序找第一个命中。不是通配符、正则、分词或内部名匹配。
- 白名单与黑名单的另一份非活动名单不参与本次决定；精确与关键词的另一种非活动方式也不参与。

证据：Z [FishingFilterDecisionService](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Fishing/Filtering/FishingFilterDecisionService.cs#L10)，10–189 行。

### 3.2 三类候选的完整定义

- **匣子**：当前 `ItemID.Sets.IsFishingCrate` 或 `IsFishingCrateHardmode` 标识。不是名字包含“匣”的字符串集合。
- **实际收杆时的任务鱼**：当前渔夫任务 ID，且当前 `Main.anglerQuestFinished` 为 false。不是全部任务鱼。
- **全球搜索的任务鱼标识**：`Main.anglerQuestItemNetIDs` 中的全部任务鱼 ID。与实际收杆分类口径不同。
- **实际收杆时的 NPC 类候选**：`localAI[1]` 为负数时，取相反数作为 NPC ID，标记 `IsEnemy=true`；没有再按敌对／友善复核。
- **全球搜索与“添加当前”额外 NPC 定义全集**：`ZombieMerman`、`EyeballFlyingFish`、`GoblinShark`、`BloodEelHead`、`BloodNautilus`、`TownSlimeRed`。最后一个是友好城镇史莱姆，也被纳入该“敌怪”规则标识。
- `localAI[1]` 必须是有限且可转换的数字；0 或不认识的观测不能当作已知鱼获处理。正值为 Item，负值为 NPC。

**声呐条件**：真实过滤还要求当前玩家存在 **Buff 122 且剩余时间>0**。没有声呐时，自动钓鱼继续保留并收取本次鱼获；本专题代码不会替玩家自动喝声呐药水。原版在没有声呐时也能写入 `localAI[1]`，所以这里是 Legacy 的功能规则，不是“原版无声呐无法获知”的技术定律。

## 4. 自动钓鱼的真实入口、会话与确认链

### 4.1 从手动抛竿到自动循环

实际链路：

`玩家手动抛竿 → 原版鱼漂 AI Hook／本地鱼漂补扫 → FishingBobberObserver → FishingAutomationService.Tick → 会话判定 → 上钩候选与过滤 → InputActionQueue → UseSelectedItemActionExecutor → ItemUseBridge → Player.ItemCheck → 原版收杆／消饵／鱼漂回收 → 终态回执与鱼漂消失观察 → 重抛请求 → 新鱼漂观察`。

业务服务不直接生成鱼，也不通过改 `ai` 直接完成收获。一次请求的入队成功不能代替后面各层确认。

调度只在自动钓鱼、自动换装、自动配装、自动存鱼至少一项开启，或仍有清理／回执／恢复残留时需要运行。**只开过滤规则或鱼获显示，不会独立启动自动钓鱼循环。**

会话的主要规则：

- 玩家必须在世界内、存在、active、未死亡、非 ghost。
- 通常需要本地有效鱼漂实际进入液体才开始；鱼漂还在空中不先换装备。
- 会话记录鱼竿槽位、鱼竿类型、鱼漂身份、抛竿目标和生命值。目标优先当时鼠标世界坐标，否则用鱼漂中心。
- 正常要求仍持有开始时那一槽、那一类型鱼竿。受控过滤切杆和自动捕捉保护允许临时偏离。
- 观测到生命值比上次低，即结束会话；不是根据伤害事件来源区分，所以任何净生命下降都符合该判断。
- 原鱼漂暂时消失而仍在等重抛、捕捉保护或装备恢复条件内时可保留会话；普通丢失超时后结束。
- 当前选用松露虫时，自动换装与自动配装被禁用；自动钓鱼仍有特殊会话观察分支。不能把普通水域预览支持推成猪龙召唤预览支持。

鱼漂身份读取兼容旧 `identity` 与新 `ProjectileKey` 的完整整数转换，**只有 -1 被当作无身份哨兵，不能把所有负值当无效**。本地筛选同时要求 active、bobber、owner==Main.myPlayer；不能用共享槽号 `whoAmI` 代替完整身份。当前已有形状测试覆盖 .6/.7 模型，但不代表 .8 多人实机验证。

观察选择方面：补扫结果按最新观察 tick 选，平局保留后出现者；Observer 有自己的最新值维护。过滤“添加当前”选扫描第一条，不能假定这些入口在多鱼漂情形完全等价。

证据：Z [FishingAutomationService.Tick 与会话](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Fishing/FishingAutomationService.cs#L164)，164–291、477–742、1486–1580、1756–1765 行；[TerrariaFishingCompat](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/TerrariaFishingCompat.cs#L31)，31–172、454–564、895–984 行；[RuntimeSettingsSnapshot](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Runtime/RuntimeSettingsSnapshot.cs#L152)，152–173 行。

### 4.2 普通收杆、回执与重抛

- `ai[1] < 0` 表示上钩观察；同一处理身份不会重复提交本轮收杆。
- 正常保留鱼获时，提交普通优先级 ItemUse 请求，合并同类待处理请求；排队超时约 **0.5 秒**，动作超时 **3 秒**。
- 请求指定原鱼竿槽位和类型，并要求在原版 ItemCheck 窗口应用使用输入及必要鼠标状态。
- `UseSelectedItemActionExecutor` 先确保支持的物品槽；实际 ItemUse 只支持快捷栏与鼠标物品槽，不把任意背包槽伪装成正常手持使用。
- `ItemUseBridge.TryBeginFromItemCheck` 再检查本地玩家、活跃／死亡、选槽、物品类型和正堆叠、动画、itemTime、reuseDelay；必要时先释放 `delayUseItem` 再等待。
- Hook 捕获输入与鼠标目标，应用本次覆盖，原版 ItemCheck 返回后恢复；桥接终态在输入恢复之后报告。
- 桥接 `Succeeded` 的依据是观察到动画、itemTime、reuseDelay、物品数量／类型、生命／魔力／Buff 等任一使用相关变化。它**没有以“新鱼已经入袋”作为成功条件**；无可见变化则为 `AttemptedButUnverified`。
- 自动钓鱼按具体 Pull RequestId 回收回执，不只读“最新动作结果”；动作队列每次更新后还有 `AfterActionQueueUpdate`，用于调度被 UI 挡住时仍回收终态。
- 观察到旧鱼漂确实消失，且对应 Pull 终态／队列条件合格，才进入正常重抛路径。
- 旧鱼漂等候常量为 **90 tick**；普通路径超时有一个后续调度的安全间隔后尝试重抛，不应宣称所有重抛均已有确定消失证明。
- 重抛后最多等 **120 tick** 观察新鱼漂；失败有最多 **3 次**的有界恢复，之后结束会话。
- 切杆过滤后的重抛有内部短延迟；普通已确认消失路径可在第一个安全调度机会提交。

特殊清理交接不是通用“忽略未知结果”：

- 仅对本次 Pull 的 `AttemptedButUnverified`，且已被 ItemCheck 消费、来源／场景／RequestId／鱼漂身份均吻合、确认旧鱼漂消失时，可以把这一条清理资格交给关联重抛。
- 不是任意请求都能释放 ItemUse 通道；也不是证明收获成功、重抛成功或多人已确认。
- 会话结束会先回收可取得的 Pull 终态；没有取得的具体请求 ID 不被简单丢掉，避免后来的新会话误领旧回执。

### 4.3 真实跳过：自然等待与切杆是两条不同链

**自然等待：**

- 过滤决定不要，且切杆开关关闭时，不提交使用／选槽动作。
- 记录本次已处理上钩，等待原版这次咬钩自然结束，或者鱼漂消失。
- 原版同一鱼漂 `ai[1]` 回到非负时会解除自然等待，下一次咬钩仍能再判定。
- **自然等待不因达到 90 tick 自动收杆**。这是已有测试保护的历史边界。

**切杆跳过：**

- 需要原鱼竿在快捷栏 0–9。
- 候选槽完整优先级：先按 0→9 找除原鱼竿槽以外的第一个空格；没有空格再按 0→9 找第一个正堆叠的非鱼竿物品。
- 不因收藏、武器类型等排除这第二类槽；该动作是临时选择，不是使用该槽物品。
- 鼠标正拿物品、原版阻挡 UI 等属于暂时阻挡，会延后；没有安全槽、无法准入等退回自然等待。
- 提交 `SelectHotbarSlot`，普通优先级，排队约 0.5 秒、动作 4 秒；尽可能立即切换，至少持有 1 tick，等指定鱼漂消失，最长内部等待 90 tick，然后恢复原槽。
- 执行器通过实际选槽读回判断是否已切换；不能把“发出了数字槽位请求”写成已经切杆。
- 超时恢复也可能产生 `AttemptedButUnverified`。其恢复记录是开始时原槽，不是完整的玩家手动接管所有权；中途玩家自行选槽时，不应承诺一定保留玩家后来选择。
- **切杆跳过超时且鱼漂仍未消失的分支，会提交一次普通强制 Pull。** 因而“被过滤的鱼获绝不会收上来”不是当前实现保证。这与自然等待不强制收杆必须分开记录。

原版鱼漂 AI 在手持鱼竿不合格、控制受限、不可用物品、鱼竿的弹幕类型不符、滑轮、死亡等条件会 Kill；Legacy 切杆借此使旧鱼漂结束，不直接写掉落。原版未收杆咬钩计时本身也会自然归零。

### 4.4 输入限制的事实与文档差别

已确认的限制：

- Runtime 自动操作提交层要求世界内、原版输入可用、不是主菜单或聊天；原版失焦通常使输入不可用。
- `UseSelectedItemActionExecutor` 还拒绝 NPC 对话，但其 CombatInput 条件不把普通背包打开或开箱一律列为禁止。
- 切杆使用更严格的 WorldInput 条件，包含箱子／个人银行等阻挡界面。
- **F5 可见的显式判断位于“新的上钩→过滤／普通 Pull”之前。**

不能扩大为已验证的保证：

- 同一函数中“等待旧鱼漂消失”“重抛延迟”“重抛重试”等分支位于 F5 显式判断之前。
- `UiStateReader.HasBlockingUi` 由原版主菜单、聊天、箱子、NPC 对话组成，没有将 F5 可见直接填入。
- `TerrariaMainCompat.AllowsInputProcessing` 是前台／焦点判断，不等于 F5 已关闭。
- 自动换装、自动配装、存鱼服务没有各自统一的 F5 可见拒绝条件。

因此，Legacy 文档“F5 可见暂停相关自动动作”不能直接升级为**全部在途阶段、装备和存鱼都已证实暂停**。静态可确认新咬钩入口的阻挡；其他阶段应在 R 产品合同中明确，并在实机组合验证中检查。这里不把静态差异写成已复现的游戏故障。

## 5. 原版实际消耗、产物与多人边界

原版 1.4.5.8 的收杆链有如下必要条件，不能由 Legacy 上钩 ID 或桥接回执省略：

1. `Player.ItemCheck_PullFishingBobbers` 扫描原版最多 1000 个弹幕槽，筛出本地拥有的活动鱼漂；选中鱼竿合格，鱼漂满足可收杆阶段时启动回收。
2. 只有上钩、`localAI[1] != 0`，并成功找到该次对应鱼饵，才继续收取。
3. `ItemCheck_CheckFishingBobber_ConsumeBait` 按鱼漂记录的 `localAI[2]` 鱼饵类型查库存，顺序 **54–57 → 0–49**。找不到不收获。
4. 普通鱼饵消耗概率受 bait 值及 tackle box 影响；特殊分支包括 `localAI[1]==-1` 强制消耗、负稀有度物品不消耗、2895 的独立概率、松露虫必耗，以及瓢虫／金瓢虫相关世界幸运效果。它不是每次收杆固定消耗一份。
5. 正物品鱼获可能断线：没有防断线效果时有原版 **1/7** 分支使本次物品收取失败。
6. 负 NPC 鱼获走敌怪生成；松露虫有猪龙生成路径。单人与客户端路径不同，客户端使用原版消息 130／61 等请求；不是得到普通物品。
7. 普通物品在鱼漂结束时，只有本地 owner 且 `ai[1]` 为合法正物品 ID，才 `AI_061_FishingBobber_GiveItemToPlayer`，再 `QuickSpawnItem → GetOrDropItem → GetItem`。背包放不下的余量会请求生成保留给本地玩家的世界物品。
8. 某些鱼获有原版随机堆叠量；不能按上钩 ID 默认新得 1 件。

这说明：

- 自动钓鱼遵循原版使用动作，不免鱼饵、不免断线，也不保证每次上钩都有背包增量。
- `ConsumedByItemCheck` 只是进入原版使用窗口；桥接 `Succeeded` 只是使用相关状态变化；鱼漂消失也可能是切杆、死亡、其他失效原因。
- 多人中原版投射物／生成物品／NPC 同步是基础机制，但本专题没有服务器 ACK 到钓鱼业务结果的完整关联验证。不能以注册表 `SupportedByOriginalAction` 宣称已测多人成功。

证据：原版 Player.ItemCheck_PullFishingBobbers（本地原版证据 `.local/death-history-world-time/Terraria.Player.cs:53008`），53008–53165 行；Projectile 鱼漂产物（本地原版证据 `.local/全功能调查/原版/Terraria.Projectile.cs:54795`），54795–54848、73119–73127 行；Player.QuickSpawnItem/GetOrDropItem（本地原版证据 `.local/death-history-world-time/Terraria.Player.cs:7191`），7191–7203 行。

## 6. 自动存放鱼：两种来源契约、执行与失败

### 6.1 任务鱼模式

实际条件和顺序：

1. 必须开启该模式、钓鱼会话 active、本地玩家可用、队列空闲。
2. 菜单、聊天、NPC 对话、鼠标拿物品时暂停；普通背包打开不是禁止；本模式也没有按自动堆叠的规则一律禁止开箱。
3. 最多按 **10 tick** 节奏检查；当前渔夫任务未完成，当前任务 ID 必须被标记为任务鱼。
4. 在 inventory **0–57** 找同 ID、正堆叠、非收藏候选。
5. 只有原版“附近箱子／银行范围”内已有同类任务鱼时，才提交选择性 QuickStack。
6. 低优先级 Chest 请求，排队 2 秒、动作 3 秒；携带任务鱼 ID 和源槽列表。

**这不是仅针对刚钓到的那条鱼。** 它不要求这次已有自动 Pull 的回执，也不要求背包数量刚增长；会处理 active 钓鱼会话中已有的当前任务鱼。UI “只在钓上当前任务鱼时存放”比实际条件窄，应记录为文案与实际行为差异。

### 6.2 所有模式

“所有”不是全背包整理，其完整来源链是：

`已识别的正 Item 鱼获 → 普通自动 Pull 入队时记录 RequestId→ItemID → 对应终态回收 → 允许提升为待存 ID → 观察该 ID 的可移动背包槽 → 一次选择性 QuickStack`。

详细边界：

- 不从任意背包增长推断本次鱼获；不自动涵盖手动收杆、负 NPC、未知鱼获。
- 提升待存 ID 接受 `Succeeded` **或 `AttemptedButUnverified`**，且要求业务允许当前会话接收；这比“确实获得新物品”宽。
- 它没有记录真实新得数量、原版产物对象身份或 `EntitySource_FishedOut` 因果范围。
- 待存的是 **类型 ID**。一旦背包已有相同 ID 非收藏库存，选择性存放可能连旧库存一起移动；不能声称只移动本次新得的那一份。
- 背包暂时找不到该 ID 的可移动物品时，最多等 **120 tick** 的落袋窗口；超时丢弃未提交待存。
- 一旦成功入队，清空待存 ID 集合；随后存放失败不会把这一轮自动无限重试。
- 自动配装应用／恢复、自动换装切换／恢复的结果到来，会清掉尚未提交的鱼获待存集合，避免把换装搬回背包误当待处理来源。
- 会话结束清未提交待存，但先保留尚需读取的 Pull 关联和已提交存放请求；后续关闭／无 active session 的 Tick 还有 ResetAllTracking。需区别“保留回执关系”与“允许旧会话继续存鱼”。

### 6.3 执行器、范围和确认

- `QuestFishStorageCompat` 通过原版 `NearbyChests.GetChestsInRangeOf(player.position, 0f)` 和 `GetBanksInRangeOf(player, 0f)` 取得当前原版可达集合；不是固定扫描全世界箱子，也不是本专题重新定义银行无限距离。
- 执行前再核对正物品、正堆叠、非收藏和类型；构造限制源槽的原版 QuickStack 上下文。
- 调用 `QuickStacking.QuickStackToNearbyChests(player, context, false)`；不是手工直接塞箱子数组。
- 钓鱼 All 的源资格没有套自动堆叠“必须可堆叠”的额外限制；不可堆叠候选能否移动仍由原版 QuickStack 规则决定。
- 执行器立即比较库存总数或源槽堆叠减少：观察到减少为 `Succeeded`，否则 `AttemptedButUnverified`。
- **没有等待多人服务器关联回执的钓鱼专用确认链。** 不能把本地数量减少当成远端容器最终权威提交，也不能在未知时无条件重发。
- `ChestActionExecutor` 的 `AutoStackSourceContractService` 只在自动堆叠模式使用；钓鱼模式没有因此继承同等精细的来源契约。

证据：Z [FishingQuestFishStorageService](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Fishing/FishingQuestFishStorageService.cs#L96)，96–217、219–390 行；[QuestFishStorageCompat](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/QuestFishStorageCompat.cs#L111)，111–280、357–439、524–608、958–1000 行；[ChestActionExecutor](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Actions/Executors/ChestActionExecutor.cs#L17)，17–90、186–238、439–463 行。R 对应关系与 .8 原版近箱操作边界见第 10–15 节。


## 7. 自动换装：原版装备组评分与恢复

### 7.1 实际用户结果

自动换装在钓鱼会话进入有效液体后，从原版最多三套装备组中选评分最高者，调用原版 `Player.TrySwitchingLoadout`。它不把背包、虚空袋或时装栏物品搬入装备格；这些属于下一节自动配装。

完整选择规则：

1. 读取原版装备组数量，最多 3；读取失败的兼容退路按 3 处理。
2. 对每组前 10 个 Armor 格取候选。
3. 只认可第 8.2 节固定钓鱼装备目录；还要满足正物品、正堆叠、原版格子可用、对应头／身／腿／饰品资格，普通难度排除 expertOnly。
4. 评分不是目录中 10000、9000 等配装权重直接相加：**钓鱼衣服每件 5，符合条件的饰品每件 10**。使用 Unknown 液体评分，因此只有熔岩可用的独立 LavaFishingHook 不计入。
5. 总分必须大于 0；分高者优先，**同分选编号较高的装备组**，即第三套优于第二套优于第一套。
6. 不完整消重可叠加／不可叠加效果；代码有信息设备效果组去重分支，但当前固定目录没有该类条目，不能把它描述成完整效果模拟。
7. 第一次处理时保存进入前装备组编号；稳定钓鱼期间仍重复评分。
8. 队列忙时等待；切换有 60 tick 的重试节奏。

UI“渔力高的配装”只能作为启发式简称。当前实现没有计算真实 fishingSkill、套装效果、词缀、原版共享装备、当前鱼竿／鱼饵组合的最终渔力。

### 7.2 执行与确认

执行器调用原版 `TrySwitchingLoadout` 后读取 `CurrentLoadoutIndex`。未读到目标时，在 12 tick 等候范围内按每 4 tick 重试，仍不吻合为 `AttemptedButUnverified`。

原版 .8 的切换会：

- 对本地玩家要求未处于使用／重用物品、未 CC、未死亡。
- 交换当前与目标 Loadout 的装备。
- 更新 `CurrentLoadoutIndex`。
- 更新 client clone、鼠标释放状态、ItemSlot 记录、声音和粒子。
- 发送原版消息 **147**。

Legacy 读回本地编号，不等于收到了远端 ACK。它确实走原版切换方法，但本调查未运行多人验证。

### 7.3 恢复规则与 .8 差异

关闭功能或离开会话后：

- 以最初记录的装备组编号为目标恢复。
- 队列忙／玩家不可用时等待；无法使用原记录时有清理记录分支。
- 已在原编号时清恢复债务。
- 恢复动作 `Succeeded` 或 `NotApplicable` 清记录；`AttemptedButUnverified` 只有读回确实在原编号时才清；其他失败仍可重试。
- 不能把自动配装“玩家改过格子则不覆盖”的保证套给整组换装。此服务仍持有原始装备组编号；**玩家后来手动选了别组，不会自动把这个新意图改成恢复目标。**

当前 .8 还存在两处需要重新适配的读取问题：

1. Legacy 先取 `Loadouts[index].Armor`，仅当它为 null 且 index 是当前组才退回 `player.armor`。原版切换通过 `Loadout.Swap` 交换当前穿戴与存储；不能把“当前组的存储数组总等于当前有效穿戴”视为已证实。
2. 原版 `.8 Player.GetEffectiveArmor` 在当前格为空时可以使用其他装备组被收藏且允许共享的物品；Legacy 用原始 Armor 数组评分，没有按这条有效装备规则取值。

这里已确认两端读取语义不同；具体某个存档将选错哪一套，仍需构造原版状态验证，不能仅凭方法名断言所有换装都失效。

证据：Z [FishingLoadoutScorer](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Fishing/FishingLoadoutScorer.cs#L21)，21–60 行；[FishingLoadoutService](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Fishing/FishingLoadoutService.cs#L46)，46–233、263–283 行；[FishingLoadoutCompat](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/FishingLoadoutCompat.cs#L20)，20–149 行；[InventorySlotActionExecutor](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Actions/Executors/InventorySlotActionExecutor.cs#L57)，57–124、178–237 行。原版 Player.TrySwitchingLoadout / GetEffectiveArmor（本地原版证据 `.local/death-history-world-time/Terraria.Player.cs:5655`），5655–5704 行。

### 8.3 完整计划顺序

**衣服：**

- 对头、身、腿分别选择严格高于当前格评分的候选；同分不替换当前衣服。
- 候选同分按来源优先级：时装→背包→虚空袋；再按较低槽位。
- 不做跨部位全局搜索或完整套装收益优化。

**饰品：**

1. 收集当前可用装备格和全部来源中的固定目录候选。
2. 每个效果组取最优项。
3. 在去重后的候选集合中，只要有任一钓具袋，就剔除独立防断线、钓具箱；只要有防熔岩钓具袋，就剔除独立熔岩鱼钩。
4. 两种钓具袋属于不同效果组，可以同时入选；耳环仍保留，不能误写成“有钓具袋就排除耳环”。
5. 候选排序：**分数降序 → 同分已装备优先 → 来源优先级 → 槽位升序 → 物品类型升序**。
6. 按当前可用饰品槽数量截取最高项；已经在身上的入选项原位保留。
7. 要替换的目标槽顺序：**未保留的旧钓鱼目录饰品 → 空格 → 其他饰品**；组内旧分数较低者先，再按槽位升序。
8. 因而存在“先替掉冗余钓鱼饰品、后用空格”的实际规则；不是始终空格优先。旧独立熔岩鱼钩识别为旧钓鱼饰品时用熔岩口径计分，以便退出当前液体需求后替换。

### 8.4 会话、申请失败与手动交互

- 实际有入液鱼漂时才产生新的应用计划；松露虫分支禁用此策略。
- 记录开始时鱼竿槽位／类型／堆叠／prefix 和装备组编号。
- 有本地鱼漂时继续保持；没有鱼漂时，只要仍持原鱼竿且没有记录到手动拿物交互，也能跨收杆／重抛间隙保持装备。
- 鼠标拿物品时暂停，并记录手动交互；该标记影响“无鱼漂但仍持原竿”的保持，不代表有鱼漂时立即恢复。
- 若本会话没有应用动作但仍有鱼漂／仍持原竿，服务不会每 tick 重新制定计划；中途新拿到更好装备不会当然立即被采用。
- 计划尝试有 30 tick 间隔；`StartSession` 在队列准入之前发生。计划未产生有效移动、队列拒绝等情形与会话保持组合时，不应假定同一次抛竿一定自动重试到成功。

### 8.5 执行、部分失败与多人

应用请求为普通优先级 `InventorySlot`，排队 2 秒、动作 3 秒。执行前重新核对来源与目标签名、格子可用和鼠标物品等条件。

真实写入是：

`SetIndexed(player.armor, target, sourceItem) → SetContainerItem(source, originalTargetItem) → 读回目标签名 → 记录成功交换`。

这不是原版 `ItemSlot` 装备操作。该兼容文件没有为这些直接数组交换建立明确的 NetMessage 发送／服务器回执链；注册表的多人声明不能补足这项证据。

两次写入也不是事务：第二次写入失败没有与第一步配套的普遍回滚证明。若多项计划中只完成一部分，会记录实际完成项，并可能报告部分已应用。需要将“部分成功、有待恢复”呈现给用户，不能只报告整体成功。

### 8.6 恢复全集与例外

恢复时保留逐项记录，签名由 **Type + Stack + Prefix** 组成；Name 不参与，Air 与 Air 视为相同。不是对象身份，多个同类型／同词缀／同数量物品可能互相匹配。

恢复分支：

- 鼠标拿物品：暂停。
- 当前装备组不是开始时记录组：暂停恢复，保留记录。
- 受控目标格仍是本次钓鱼装备：继续检查原物位置。
- 目标格已经是原装备：把该项算作已恢复。
- 目标格已被玩家换成其他物品：不覆盖，保留待恢复记录。
- 原目标是空格：先尝试把钓鱼装备送回原来源空格；不可用时按原来源类别找替代空格。背包找背包，虚空袋先本银行再背包，时装来源退回背包。
- 原目标非空：原持有位置仍匹配签名则交换回；若原物被搬走，依次查 **背包 0–49 → 虚空袋全部 → 时装栏 10 到末尾**，找到第一份同签名物品再交换回。
- 找不到原物、玩家改变受控格、鼠标阻挡、装备组不同等暂缓，不强覆盖。
- 恢复约每 30 tick 尝试；实际失败有最多 3 次计数。部分安全暂停会退还尝试次数。
- **无空间／写失败等消耗尝试次数，达到上限后会放弃并清掉恢复记录。** 因而“所有故障始终保留恢复债务直到成功”不符合当前实现。
- 死亡时记强制恢复需要，但等玩家可用后再尝试；不能在死亡状态直接完成装备恢复。
- 这些恢复记录只在内存中，没有长期保存；也未绑定 R 式角色／世界／连接世代，跨会话风险见第 10–15 节。

证据：Z [FishingAutoEquipmentService](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Fishing/FishingAutoEquipmentService.cs#L80)，80–233、405–495 行；[FishingAutoEquipmentCompat](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/FishingAutoEquipmentCompat.cs#L59)，59–153、154–507、656–752、835–1078、1214–1270 行；[FishingAutoEquipmentModels 的签名比较](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Fishing/FishingAutoEquipmentModels.cs#L23)，23–55 行。

## 9. 快捷改名：独立单人操作，不是装备功能的一环

### 9.1 UI 与名字算法

- 钓鱼页显示当前名字。
- 双击输入区才进入编辑；共享原生文本输入和 IME；按钮从“快捷改名”变为“确定”。
- 未编辑时直接点击按钮：给当前名字的连续 **ASCII 0–9 后缀**加一。
- 没数字后缀则追加 `1`；例如 `名字 → 名字1`，`Test009 → Test010`，`名字9 → 名字10`。
- 采用字符串进位，避免把整个后缀转固定宽度整数导致溢出。
- CR/LF 去除，Tab 换空格，Trim；空名或长度超过 20 拒绝，超长不截断。
- 因此原本 20 字符名字再加 `1` 可能拒绝；“快捷”不保证每次都能改。
- 只有确认按钮／直接按钮接通提交；共享单行输入本身没有本专题专用 Enter 提交保证。关闭 F5、切页会清焦点与草稿，不是保存名字。

### 9.2 入口到结果链

`钓鱼页命令 → HandleFishingQuickRename → 归一与排队 → PlayerRenameActionExecutor → PlayerRenameCompat → Main.ActivePlayerFileData.Rename → 原版 Player.SavePlayer → 读回 player.name → 按 anglerWhoFinishedToday 刷新 anglerQuestFinished → 动作结果`。

请求普通优先级，排队 1 秒、动作超时 2 秒；UI 固定写入 `AllowMultiplayer=false`。执行器要求世界内、非主菜单／聊天／NPC 对话，并拒绝 netMode!=0。

成功／失败的细分：

- 优先调用原版 `PlayerFileData.Rename`。
- 原版方法调用失败，或调用后名字不吻合时，兼容层还会尝试直接赋 `Player.name`。
- 最终名字读回吻合才视为改名已调用成功。
- 根据新名字与 `Main.anglerWhoFinishedToday` 的 **Ordinal 精确匹配**重新计算今日任务完成状态。
- 不删除今日已完成名字列表，也不保证选到的另一个名字今天没有交过任务。
- 名字改变或今日完成标志刷新可以使动作 `Succeeded`；名字未变且没有相关变化可为 `NotApplicable`。
- UI 记录“已排队”不等于名字已改；运行时名字已改也不等于角色存档保存成功。

### 9.3 原版保存与身份影响

当前 .8 `PlayerFileData.Rename` 的实际内容是 Trim 后赋 `Player.name`，然后 `Player.SavePlayer(this)`。它不是只改 HUD，也不是把角色文件路径重命名成新名字。

`SavePlayer` 有保存锁、成就／地图保存及玩家文件保存流程；根据角色路径、云端／本地和服务器角色条件处理，序列化写入名字。Legacy 兼容层捕获异常后仍可用直接字段 fallback 获得名字读回成功，故 **动作成功不证明磁盘／云端保存成功**，也可能发生前面的部分保存步骤已执行。

改名会影响以名字判定的原版渔夫今日资格及所有依赖显示名的观察；不应作为 R 角色永久身份。R 当前运行会话探针以对象／世界／连接身份生成 token，而不是名字，见第 10–15 节。未来若支持改名，应区分显示名、原版任务名键、角色文件／UUID 和当前运行会话。

证据：Z [钓鱼页改名行](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/UI/Legacy/LegacyMainWindow.Fishing.cs#L80)，80–137 行；[HandleFishingQuickRename](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Input/LegacyUiActionService.FishingFilter.cs#L53)，53–193 行；[PlayerRenameActionExecutor](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Actions/Executors/PlayerRenameActionExecutor.cs#L14)，14–57 行；[PlayerRenameCompat](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/PlayerRenameCompat.cs#L35)，35、72–153、156–220 行。原版 PlayerFileData.Rename（本地原版证据 `.local/death-history-world-time/Terraria.IO.PlayerFileData.cs:210`），210–217 行；Player.SavePlayer（本地原版证据 `.local/death-history-world-time/Terraria.Player.cs:55332`），55332–55411 行。


## 10. UI、输入、状态与保存

### 10.1 真实界面及输入边界

钓鱼页包括顶层功能开关、存鱼模式、切杆开关、改名行、过滤作用域、匹配方式、三个特殊规则、活动名单和候选／预设浮层。窄窗口上下排，宽窗口把设置与名单分栏；没有另建钓鱼独立主窗口。

完整交互边界：

- 精确候选浮层固定 **两列**；候选区、预设区、名单区分别拥有滚动偏移。
- 鼠标滚轮优先由鼠标所在的候选浮层消费，其次预设，再名单；边界处无法继续滚动时不虚报已消费。
- 名单和候选不是拖拽排序；顺序来自加入次序、搜索排序或预设保存次序。
- 关闭候选不提交勾选；加入按钮才写活动名单。预设应用直接覆盖，清空与删除直接修改，没有另建二次确认。

- 本专题没有独立按 Enter 提交改名／关键词的保证；确认按钮和取消按钮才是已追到的业务入口。
- 信息鱼获颜色、字号使用现有信息文字样式系统；其位置／整体输入归共享信息显示层，本专题不另建一份 HUD 输入所有者。

### 10.3 身份、世代与退出缺口

Legacy 鱼漂观察包含完整弹幕身份和 scan generation，但**钓鱼业务会话没有绑定角色对象、世界对象或网络连接世代**。自动配装恢复记录只含原装备组、槽位和物品签名；不能阻止另一会话刚好出现相同签名时被误认成旧恢复对象。

已读生产调用点中，没有找到把这些静态钓鱼服务的 `ResetForTesting` 当作正式退出世界清理使用的链。Runtime 的 ActionSubmitting 层在主菜单／失焦等情形可能不分派业务 Tick；不能只凭 `Tick` 内部存在“玩家不可用→EndSession”就证明每次退出世界必然执行到它。

这是一项**静态生命周期保护缺口／需验证的组合风险**，不是本调查已经复现了跨角色写错装备。R 应使用现有运行会话世代与受控操作出口承接，不继承“进下个世界后再靠相同鱼竿或签名推断”的边界。

## 11. 高频工作量、关闭成本与已有旧坑

### 11.1 缓存与失效全集

鱼获候选有两层 FIFO 缓存：

- 早期缓存最多 **8** 条；命中发生在水体扫描、原版 `GetFishingConditions`、条件组合和名字构建之前。
- 完整查询缓存最多 **16** 条；查询命中可回填早期缓存。
- 两层没有独立 TTL；测试重置不是生产失效保证。

早期键包含：

- 世界键、鱼漂完整身份、鱼漂 tile 坐标。
- 鱼竿类型和 power、鱼饵类型和 power、当前任务鱼 ID。
- 玩家记录键；缺失时退回运行对象哈希／whoAmI／名字组合。
- luck、fishingSkill、熔岩钓鱼能力、玩家高度和群系布尔。
- 当前有效 Buff 类型集合，最多读取 64 项；不逐 tick 以剩余时间生成不同键。
- 世界 hardMode、expertMode、masterMode、昼夜、血月、日食、南瓜／霜月、雨、Remix、notTheBees、drunk、forTheWorthy、anniversary、dontStarve、zenith、圣诞、万圣、史莱姆雨等标志。
- 月相、世界尺寸、地表／岩层、`floor(time/3600)` 时间桶、语言标识。

完整查询键另有液体类型、水量、chums、所需水量、垃圾资格、最终／有效渔力、熔岩能力及过滤签名等。

**失效不完整的事实**：

- 早期键没有水体／Tile 修订号。在鱼漂 tile 等键不变时，玩家改水体仍可能直接命中旧候选；完整键虽有水量，也因为早期命中而不会重新计算。
- 世界键只列已知布尔和时间桶，不等于全部鱼获条件依赖。不能声称所有 NPC 解锁／世界进度变化都会及时失效。
- NPC 搜索候选的定义／名字有静态缓存，不能仅凭物品候选键包含语言，就宣称所有名字在切语言后均即时更新。
- 精确规则不依赖显示名，关键词依赖当前语言／资源包显示名；名字快照不能消除这项行为差异。

证据：Z [InformationFishingCatchCache](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Information/InformationFishingCatchCache.cs#L8)，8–16、28–105 行；[InformationFishingCatchSignatureBuilder](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Information/InformationFishingCatchSignatureBuilder.cs#L56)，56–94、97–132、144–191 行；[InformationFishingCatchResolver](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Information/InformationFishingCatchResolver.cs#L46)，46–206 行。

### 11.2 按情形区分成本

| 情形 | 已确认静态工作 |
|---|---|
| 自动化全关、无残留 | Runtime 不分派钓鱼 Tick；但已安装鱼漂 Hook 的回调仍存在，不等于钓鱼相关零工作 |

| 存鱼 | 10 tick 常规检查，All 待存可更快跟进；对选中类型扫描背包、附近容器，再走原版 QuickStack |

#### 名单一端的精确差异

R `ItemSelection.Open` 绑定 `Runtime.Generation`，退出会话取消；新增是多选后确认并合并**最新设置**，替换一项是立即提交，失败保留选择。有效类型要求 `0<type<ItemID.Count` 且非钱币。`HostItems.PickerTypes` 从 inventory 0–57 取类型，但跳过 50–53 钱币槽。

Z 鱼获选择采用 Kind+ID，来源不限当前库存，允许 NPC，并会被模式／语言等影响。因此候选数据、规则所有者与确认语义不能强行合并；视觉上相似不等于同一业务选择器。

证据：R [ItemSelection](https://github.com/Kuroneko2020/JueMingR/blob/df8a029873176276d0f620d32b0ac02ae9ea7744/src/JueMingR.TerrariaHost/Items/ItemSelection.cs#L11)，11–68 行；[HostItems.PickerTypes](https://github.com/Kuroneko2020/JueMingR/blob/df8a029873176276d0f620d32b0ac02ae9ea7744/src/JueMingR.TerrariaHost/Items/HostItems.cs#L84)，84–100 行；Z 全球鱼获搜索及 Picker 见第 3.3 节。

#### 产物与原版消耗的精确关系

R `ItemSourceHooks.GetBefore` 明确要求当前有 `Origin`，且其 Player 与本次 GetItem 玩家相同；只有完成拾取／开容器来源范围并观测到增量，才 `RegisterAcquisitions`。钓鱼 QuickSpawnItem 不建立这个 Origin。新功能应记录真正落袋或溢出拾取的有限来源，不能把“这段时间相同 ID 增长”当万能来源证明。

R 已有防护把原版消饵方法中的物品数组读取替换成 `ReadSelectionSlot`；受保护库存槽返回不可用哨兵，避免晚回包中的原库存被另一动作消耗。鱼获处理和钓鱼动作都必须接受这个约束。

证据：R [ItemSourceHooks.Install/GetBefore/OriginAfter](https://github.com/Kuroneko2020/JueMingR/blob/df8a029873176276d0f620d32b0ac02ae9ea7744/src/JueMingR.TerrariaHost/Items/ItemSourceHooks.cs#L19)，19–26、36–70、85–95 行；[ItemPendingGuards](https://github.com/Kuroneko2020/JueMingR/blob/df8a029873176276d0f620d32b0ac02ae9ea7744/src/JueMingR.TerrariaHost/Items/ItemPendingGuards.cs#L29)，29–41、58–69、101–102 行；[ItemGuardTranspilers.SelectionReads](https://github.com/Kuroneko2020/JueMingR/blob/df8a029873176276d0f620d32b0ac02ae9ea7744/src/JueMingR.TerrariaHost/Items/ItemGuardTranspilers.cs#L13)，13–27 行；原版产物与消饵证据见第 5 节。

#### 存放操作的精确关系

R `ItemNearbyStorage` 已绑定 .8 `QuickStacking.SourceInventory` 的字段和非公开静态重载；执行前核对有限源组、当前会话、玩家、源对象／类型／prefix／数量与保护状态。单人比较目标增量和源减少是否守恒，保留部分完成和未知；多人按本次源组接收原版消息 5 实际应用前后结果，**消息 85 或锁清除不作为成功 ACK**。

600 tick 超时后保留有限源组接晚回包，不重发、不强解原版锁。这些边界比 Legacy 钓鱼“立刻看源减少”更强；新增鱼获触发应调用它，不能回退为更弱的即时猜测。

证据：R [ItemNearbyStorage](https://github.com/Kuroneko2020/JueMingR/blob/df8a029873176276d0f620d32b0ac02ae9ea7744/src/JueMingR.TerrariaHost/Items/ItemNearbyStorage.cs#L33)，33–114、117–153、172–200 行；[ItemHostObservation](https://github.com/Kuroneko2020/JueMingR/blob/df8a029873176276d0f620d32b0ac02ae9ea7744/src/JueMingR.TerrariaHost/Items/ItemHostObservation.cs#L35)，35–51、69–105 行。

#### 捕捉、战斗与防摔两端

Z 自动捕捉有真实钓鱼保护链：

- 记录原竿槽／类型、鱼漂身份，优先沿用正在钓鱼会话的抛竿目标。
- 捕捉结束稍等后检查指定鱼漂。
- 鱼漂还在：确保恢复原竿后清保护。
- 鱼漂不在：先恢复原竿，再提交自己来源的 ItemUse 重抛，使用 UseItem、BridgeItemUse、MouseTarget 通道；不是钓鱼服务伪造捕捉完成。
- 钓鱼服务见捕捉保护在途，允许临时离竿／鱼漂缺失而不立刻按普通退出处理。

Z ItemCheck Hook 在有效 Bridge 可开始时让其拥有本窗口；否则交仲裁器选其他受控写入，战斗连点／专用武器作为后备。输入恢复后才终态通知，但它仍是共享物理输入，必须测试手动攻击、快捷物品、捕捉、收杆同帧与退出组合。

Z 防摔临时装备与钓鱼配装分别直接写装备／物品容器，都有独立恢复记录。防摔高优先级只能说明排队优先，不证明两个记录不会跨动作冲突。

#### 身份与现有渔夫显示

R 运行会话由 `ItemSessionProbe` 在玩家对象、世界文件对象、socket 或 netMode 变化时换 token；Shared Runtime 对 token 变化增加世代、退出旧会话。显示名字改变不会自动代表换了一个玩家对象。

R 死亡／世界时间持久身份使用带域前缀的角色文件路径、local/cloud 和世界 UUID；原版 Rename 不改变该路径，所以不能用“改名了”自动清死亡记录或给其创建另一份世界历史。

R 渔夫信息读取已经处理渔夫资格、当前映射 ID、今日是否提交、完成次数和本地化任务地点；这与 Legacy 预览漏 NPC 条件的差异，适合通过当前 R 观察契约解决，不应让旧候选代码绕过现有信息来源。

## 14. 已确认事实、适配候选、待决定与动态未知

### 14.1 已确认事实

- 本专题全部顶层入口在 Legacy 生产 UI／命令／服务／执行器中可追到，不仅是登记项。
- 手动抛竿后自动循环；真实过滤需要声呐；精确是 Kind+ID，关键词是显示名子串。
- 默认特殊规则、唯一内置垃圾预设、六种 NPC 候选、装备固定目录及排序已完整列出。
- 自然等待与切杆跳过不同；后者有强制 Pull 退路。
- 两种存鱼模式来源不同；All 回执资格不等于真实新产物证明。
- 两种装备策略、手动让路和恢复失败处理不同。
- 快捷改名当前真实 UI 拒绝多人，会调用原版角色保存，并有直接字段 fallback。
- R 没有这些功能的生产接入；已有能力只能按第 12 节的实际职责复用。

### 14.2 窄适配候选，尚非实施授权

- 独立的只读鱼获候选观察，明确原版版本、动态规则范围与失效依据；与真正收杆决策分开。
- 钓鱼自己的会话状态，绑定 R 现有世代；所有临时动作携带具体 RequestId、鱼漂身份与所有权。
- 以原版实际产物边界补充有限来源观察，然后复用 R 已有物品处理／存放操作。
- 装备操作复用当前操作与会话边界，分别定义整组切换和逐格交换；不新建无真实需求的通用大服务。
- 名单 UI 复用公共输入／滚动／草稿保护原则；鱼获候选模型与规则仍由钓鱼拥有。
- 改名独立建操作结果，至少区分运行时名字、原版保存结果、今日任务标志刷新，不塞进装备服务。

### 14.3 需要所有者在后续功能任务确定的产品选择

1. “完整鱼获”是原版条件候选，还是必须覆盖全部特殊世界／敌怪／真实可达结果；达到上限或观察不完整时的名字与提示。
2. 声呐作为真实过滤前提是否继续保留；失去声呐或识别失败时保持收取的规则。
3. 切杆默认值与超时强制 Pull 是否保留；不能静默继承旧迁移默认开启。
4. Quest 模式是否处理旧任务鱼；All 是否允许连同类型旧库存；手动钓鱼产物是否纳入；与自动出售／丢弃／普通堆叠的顺序。
5. 自动配装目标是旧固定启发式、实际渔力、综合安全性或用户指定方案；虚空袋可达资格、收藏保护、两钓具袋、幸运币／马蹄铁等是否保留。
6. 玩家手动换装备组／换格／换竿、F5 打开、失焦、死亡后哪些操作暂停、取消、继续收回执或恢复；恢复失败不得仅用笼统“安全恢复”代替具体行为。
7. 快捷改名是否保留为单人功能，是否要求保存成功才成功反馈，以及按新名字重算渔夫今日资格的明确用途。
8. 设置按全局还是角色保存，旧名单／预设是否需要迁移。原版名称快照与当前语言如何显示，不自动导入旧 JSON。

以上是待决定项，不是本调查申请立即改代码或扩大迁移范围。
