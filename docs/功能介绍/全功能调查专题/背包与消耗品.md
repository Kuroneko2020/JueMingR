# 背包与消耗品

> Legacy 固定源码：`6ac6356c0c564f43284590c168855e96c50e13f7`。R 固定生产基线：`df8a029873176276d0f620d32b0ac02ae9ea7744`。下述 Z 文件路径如无特别说明，相对 `src/JueMingZ/`。本专题只读源码、已有文档与测试源码；没有构建、执行测试、运行游戏或验证多人/FPS。

本专题覆盖附录 10–12：保持收藏、快捷物品使用、自动存钱及主动取出保护、自动回血/回蓝/增益。R 已接受的自动存/卖/扔仅核其接口和接受边界，不全面复审。

建议进入产品讨论时分为“背包意图与明确使用”“钱币存放与主动取出”“恢复与增益维持”。这是按真实行为与资源冲突整理的候选分组，不是 R 页面、类划分或实施次序的决定。

## 1. 保持收藏

### 1.1 玩家结果、范围及默认值

Legacy 默认关闭。开启后，观察原先收藏的物品在换装、替换或垃圾桶往返中是否丢失收藏，并尝试恢复 `favorited=true`。它不搬动物品，不增加数量，也不应成为自动出售、丢弃或存放的新获得来源。

恢复目标只包括主背包前 50 槽、当前 `Armor`、`MiscEquips`。基础快照读取上限为 58 个 inventory、20 个 armor、5 个 miscEquip，但收藏恢复没有因此覆盖钱币栏、弹药栏、鼠标槽、四类银行或未激活装备组。垃圾桶是往返证据来源，不是自动补收藏的目标容器。

### 1.2 实际识别与例外

`KeepFavoritedCompat` 持有四类运行记录：

- 容器+槽号+物品签名的收藏记录；
- 全局物品签名记录；
- 同槽水桶形态家族记录；
- 垃圾桶往返记录。

签名为 `type|prefix|name`，不包含 stack、物品对象实例、玩家或世界身份。同类同前缀同名物品可以共享全局收藏记忆，不能把它解释成准确追踪某一件物品。

识别到目标缺少收藏时，满足以下任一条件即可提出恢复：原位置相同签名曾收藏；全局签名曾收藏；同位置符合水桶变形家族。水桶家族的完整硬编码集合为 `205、206、207、1128`，没有自动扩展为所有容器或所有可变形工具。

手动取消收藏识别采用窄条件：在 inventory 容器、背包界面开启、上一观察中同位置相同签名为收藏、现在未收藏、没有垃圾桶往返标记时，才按玩家取消处理。该动作删除当前位置/形态记录、全局签名和垃圾桶记忆；不代表扫描删除所有其它位置的同签名历史记录。装备容器没有使用这套 `allowManualUnfavorite=true` 判定。

观察到收藏物品进入垃圾桶时保存往返线索；未收藏物品进入垃圾桶但签名已知时也保留相应线索。此机制是启发式意图恢复，不是完整的物品所有权或跨容器交易证明。

### 1.3 触发到结果链

`KeepFavoritedService.TickCore` 在启用后每 2 tick 检查，要求世界内有效且活着、非幽灵的玩家及 inventory 快照。鼠标拿物、聊天、NPC 对话、主菜单会阻止；旧动作队列存在 pending/running，或 `ItemUseBridge` 有请求时等待。

找到第一个需要补收藏的目标后，提交低优先级 `InventorySlot` 请求，排队期限 100 毫秒、执行期限 700 毫秒；请求带容器、槽号、itemType、签名。动作间自身冷却为 2 tick。

执行前重新读槽，要求同类型、正数量、签名一致。已经收藏可直接视为达成；否则通过兼容层直接写 `favorited=true` 并回读。这里没有原版 UI 收藏点击的完整输入过程，也没有将该行为登记成一次新拾取。

### 1.4 UI、数据及生命周期

实际 F5 物品页有“保持收藏”开/关行及统一主开关键入口；没有独立收藏名单、逐物品禁用、世界范围或保存历史编辑器。

持久化的是总开关。四类记忆都是运行状态，各自最多 512 项，过期上限 36000 tick，并在 tick 无效/倒退时清理；达到容量时按较老记录淘汰。关闭入口明确调用 `ClearState`。服务在不适用状态也有清理分支，但外层调度会提前跳过部分场景，因此不能仅凭服务内部代码宣称所有离开世界路径必然清理。

已读状态中未见玩家×世界身份键或独立 Session 世代。新角色/世界的静态状态隔离需要明确合同，不能假定“全局签名”天然不会误关联。

### 1.5 消费、多人及失败边界

本功能不消费物品，但会直接改变物品标记，进而影响自动处理资格、UI 排序/整理及玩家意图。目标槽或签名变化时拒绝恢复；不能靠写回旧物品快照来“修正”。

没有读取到服务器 ACK 或逐次收藏同步确认链。Feature Catalog 的实现登记不能代替多人实机证据，也不能证明其它玩家或服务器持有相同标记。

### 1.6 工作量与旧坑

关闭时外层调度跳过主要服务；开启时有每 2 tick 的容器观察、历史查找、首目标选择及过期/容量维护。稳定状态仍需要观察；没有产生动作不等于没有扫描。记忆上限限制存储量，不代表全部清理/排序和反射读取没有成本。

必须保留的反例包括：两个同签名物品、槽位交换、同族水桶变化、装备栏取消收藏、垃圾桶往返、界面开启时普通位置变化、超出 36000 tick、超过 512 条、身份不明及换 Session。静态代码不证明 FPS 成本或玩家体验。

### 1.7 R 映射与候选

R 已有的物品实例/成员资格、实际来源观察及 `ItemOperationOwnership` 可以提供保护边界，但现有所有者只定义出售、丢弃、附近存放，不拥有收藏意图。新收藏能力需要独立的意图所有者，并在改变真实 favorite 后让依赖它的资格观察正常失效。

收藏恢复与装备/右键变形、自动处理是运行时资源和资格关系；不应为了复用旧静态字典，将收藏塞进自动处理总服务。是否保留同签名共享、如何识别主动取消、记忆是否按角色持久化，均待产品决定。

## 2. 快捷物品使用

### 2.1 玩家结果、完整配置与默认

默认关闭，快捷物品绑定列表默认空。每条绑定保存 `Hotkey`、`ItemTypes`、`DisplayName` 和 `Enabled`（条目默认 true）。条目动态添加，不是固定八个动作槽。配置规范化遍历全部条目，没有在已读代码中施加固定条目上限。

一次有效按下尝试使用匹配物品一次，成功入队后使用全局 220 毫秒防抖；不是按住连续使用。界面最右主开关键切换整个能力，具体条目的使用键才执行物品。

### 2.2 完整物品匹配与形态家族

普通物品按用户配置 itemType 匹配，不限定为消耗品、工具或传送道具；找不到实际正数量物品则不产生成功动作。匹配不按 prefix 或收藏过滤。

搜索优先顺序：

1. 当前选中槽（若属于支持槽）；
2. 快捷栏 `0..9`；
3. 主背包 `10..49`；
4. 槽 `58`。

不扫描钱币/弹药槽 `50..57`、银行、装备或其它玩家。配置可带多个 ItemTypes，匹配时扩展所有类型所属家族；真正想切换到的目标形态取列表中的第一个正类型。

完整硬编码家族为：

| 家族完整 ID 集合 | 旧代码用途 |
| --- | --- |
| `2611,5526` | 同族武器形态 |
| `4131,5325` | 虚空袋开启/闭合形态 |
| `4346,5391` | 负重石/不负重石形态 |
| `4767,5453` | 小动物保护指南启用/停用形态 |
| `5059,5060` | 摩羯套装腿部/尾部形态 |
| `5309,5454` | 环境保护指南启用/停用形态 |

UI 可选形态排除 `5437`，运行匹配仍包含。魔法海螺、恶魔海螺作为各自物品使用，不是“任意传送工具都能互相替换”的一个大组。家族转换调用真实 `ChangeItemType(int)` 并回读，不直接改 ID 字段。

### 2.3 实际 UI 和所有输入

物品页支持开/关、添加条目；条目卡片有选择/替换物品、使用键录入、删除。物品选择器根据当前背包可见类型去重，再展开可见家族形态；快照路径只从前 58 槽中接纳 `0..49`，不从该快照提供槽 58。选择器打开时才维护候选，缓存约 120 毫秒。

选择一个物品会把该条 `ItemTypes` 写成仅这个 ID，更新显示名称，启用条目并立即 `SaveAll`。删除条目同时关闭相关选择器/捕获。录入只在前台采样，Esc 取消、Backspace 清空，另有显式取消按钮；不得把取消录入视为关闭整个功能。

旧配置还有专门识别某个历史单条 `Ctrl+Alt+B` 默认项的迁移清理。它是旧数据迁移分支，不是当前默认赠送的快捷动作。

### 2.4 触发、选槽、使用及恢复

`QuickItemHotkeyService` 通过统一热键运行时按绑定序号查询 pressed edge；遍历启用条目，找到第一个成功入队的动作便停止这一轮。队列请求为 `UseHotbarItem`、Normal 优先级、`SupersedePending`，排队期限 400 毫秒、执行期限 5 秒；记录目标槽、来源热键、目标形态，并指定 ItemCheck 时需要主鼠标左键意图。

`UseHotbarItemActionExecutor` 的实际过程是：

1. 核对世界/UI、本地玩家、目标槽，并保存原选中槽；
2. 请求切换到目标槽并等待确认；
3. 必要时将找到的同族物品切到用户选定形态，回读类型；
4. 向 `ItemUseBridge` 提交真实原版物品使用，携带原选中槽、恢复要求、`SkipSelectInItemCheck=true` 与鼠标意图；
5. 不论桥接成功或失败，都进入最终恢复路径；
6. 最多 3 次请求恢复旧槽，选择确认等待最多 45 tick；最终使用空闲等待上限 90 tick，并在选择确认过程中按 4 tick 间隔复核；
7. 取消会取消 bridge 并尝试恢复原槽；使用看似成功但原槽无法确认恢复时，将结果降为 `AttemptedButUnverified`。

**恢复的是选中槽，不是物品形态。** 已读路径没有把同族物品转换回原形态的步骤；使用失败后也不能假定形态已还原。玩家最终手里留下哪种形态属于产品行为，必须明确。

### 2.5 所有权、消费、原版结果与多人

绑定偏好归配置；按下沿、防抖、当前使用、选槽及恢复属于运行期临时状态。旧 bridge/动作队列承担选槽和使用阶段协调；它们不是精确的玩家×世界物品事务日志。

真正物品由原版使用路径决定是否消费、投射、传送或改变状态。动画、物品数量和位置等观察各有局限，不能把一次 bridge 成功统一等同于所有工具最终结果已确认。原槽恢复失败会降级，但不自动撤回已经发生的物品效果或消费。

该能力可能与持续武器、钓鱼、捕捉、收获、防摔工具、建造和其它快捷项争夺 selectedItem、鼠标目标及使用输入。真实资源的交接和恢复必须保留，不能把各方静态 `IsEnabled` 当作所有权。

Feature Catalog 的 `SupportedByOriginalAction` 不是每个绑定物品的多人服务器确认。单机、Host & Play、本地客户端连他人服务器、工具各自的网络副作用需要按具体物品能力核验。

### 2.6 工作量与错误边界

启用时按条目数查询热键，当前实现没有配置条目硬上限；收到有效按下才进入类型扩展与槽搜索。选择器候选构造只在窗口开启时维护，稳定 UI 仍有缓存刷新和类型去重工作。

动作最长等待、恢复次数与防抖有界，但需要分别验证：物品消耗完、目标同类型被替换、移动槽位、玩家手动切槽、形态转换失败、已转换但使用失败、原版使用仍未空闲、取消/失焦/死亡/换世界、两个绑定同键及与持续武器重叠。不能从这些静态上限推断 FPS 或“不会打断任何动作”。

### 2.7 R 映射和待决定事项

R 已有统一物理输入、热键捕获、消费/释放与失焦重新武装基础；应复用 `HostInputState` 的真实输入 epoch。现有 `ItemOperationOwnership` 只覆盖存/卖/扔受影响的槽范围，没有定义 selectedItem、鼠标或物品使用所有权，不能直接宣称现有所有者已经支持快捷物品。

候选是独立“明确使用一次”的能力端口，与武器/工具消费者协调实际选槽和恢复。需讨论绑定是固定类型还是形态目的、形态是否保持、玩家手动切槽是否优先、使用结果如何说明，以及哪些具体类别应先纳入多人验证。Legacy 九族表可以作为已知行为来源，不能未经判断变成新版永久硬编码合同。

## 3. 自动存钱与主动取出保护（附录 11）

### 3.1 玩家结果、完整对象集合与默认边界

**已确认 Legacy 行为：** 开关默认关闭；开启后，靠近银行类容器时，尝试把身上的铜币、银币、金币、铂金币存入可达个人银行。它是当前背包钱币的整理行为，不要求钱币刚刚获得。普通世界箱子不属于存钱目标；银行或世界箱子的主动取出都可能建立保护。

| 完整集合 | 规则 |
| --- | --- |
| 钱币类型 | `71` 铜币、`72` 银币、`73` 金币、`74` 铂金币；铜币价值分别是 `1 / 100 / 10000 / 1000000`。没有其它物品白名单。 |
| 来源槽 | 快照和精确钱币签名读取背包 `0..57`，正类型、正数量、上述四类、未收藏；排除槽 `58`。因此热点栏、主背包、钱币栏及实际放有钱币的其它受读槽均可进入；不从装备、鼠标、四类银行向外取款。 |
| 银行目标 | `player.bank` 存钱罐账户、`bank2` 保险箱、`bank3` 护卫熔炉、`bank4` 虚空保险库；按银行对象引用去重，同账户多个入口不会成为多个余额。 |

| 便携入口 | `NearbyChests` 通过当前投射物的 `TryGetContainerIndex` 取得银行；本轮同版本 `.8 Terraria.Projectile.cs` 明确投射物 `525 / 960 → -2`、`734 → -5`，对应旧版飞猪/切斯特一类个人银行入口与虚空入口。该映射已用当前 .8 原件80443–80457行核对。 |
| 当前打开的银行 | Z 兼容层还按 `player.chest = -2/-3/-4/-5` 把对应银行补入集合。但正常自动存钱服务和执行契约均阻止箱子界面开启时执行，不能把此兼容补充解释成“开着银行也自动存”。 |

这里的“范围”须准确表达：Z 反射调用 `GetBanksInRangeOf(player)` 或 `GetBanksInRangeOf(player, 0f)`，不是传入 `true`。本地 `.8` 精选实现将非正范围取 `600f`，再计算 `(int)(600/16+2)=39`，围绕玩家中心生成 **79×79 格的矩形**，扫描最多 1000 个投射物与该矩形 tiles；银行路径不是普通世界箱子的 600 像素圆形距离判断。入口发现顺序为投射物数组顺序，再区域 tile 顺序；Z 没有自行按“最近银行/币种/玩家偏好”排序。

### 3.2 触发到结果：正常存钱、首次放币和拒绝分支

1. 调度入口启用后进入 `AutoDepositCoinsService.TickCore`。观察设置世代与取出保护，内部每 15 tick 才进行一次主要检查。需要在世界内、玩家有效且非死亡/幽灵；菜单、聊天、NPC 对话、箱子界面、鼠标持物均会阻止；单独背包界面开启不等于阻止。
2. 取得明确玩家/世界身份；读取附近银行。如果读取失败，不把未知伪装成“不在范围”；没有银行则等待；存在取出保护则整个自动存钱等待。
3. 等待 `AutoStackService.HasPendingAutomationWork` 清空，同时等待整个旧动作队列及 `ItemUseBridge` 没有未完成动作。再扫描全部钱币候选，形成 `slot:type×stack` 精确签名；同一已提交签名至少间隔 180 tick 才重试。
4. 提交低优先级 `Chest` 请求，合并待处理重复项，排队期限 2 秒、执行期限 3 秒；请求携带玩家/世界身份、设置世代、来源版本、保护版本、取出保护编号及状态、银行读取状态与数量、币种/槽列表、精确钱币签名。
5. `ChestActionExecutor` 执行前重新读取并核对全部契约，拒绝关闭、换人换世界、来源/保护/设置版本变化、租期变化、未知/零银行、银行数量变化、钱币签名变化及 UI/鼠标状态变化。银行数量相同仅是其中一个核验项，不能称为验证了完全相同的银行对象集合。
6. 正常路径依次对可达银行调用原版 `ChestUI.MoveCoins(inventory, targetChest)`。传入的是真实完整 inventory 数组，候选槽列表用于 Z 的授权/签名/结果检查及首次放币路径，不是传给原版的裁剪数组。调用前后捕获玩家钱币域与去重银行钱币域的签名和铜币总值，累计原版返回值并检查溢出。
7. **首次放币补充路径只针对 `ReferenceEquals(target, player.bank)` 的存钱罐账户。** 先证明原版已调用、返回值恰为零、前后状态均可读、钱币状态未变、没有溢出，才允许考虑该路径。原版 raw zero 但状态改变、状态读不到、值溢出或未实际调用，都不能进入补充路径。
8. 存钱罐账户须“没有任何钱币栈且有空槽”；允许已有非钱币物品，并不要求整个账户为空。选择来源中币种最高的一整栈，顺序为 `74 > 73 > 72 > 71`，同币种取候选顺序最前者；不是每种存一枚，也不是只存单个币。
9. 首次放币先构造独立完整 clone 和独立 Air 替身，验证真实 `Clone`、`SetDefaults(int, ItemVariant=null)`、数组写入和回退可行性、前后铜币总值与槽位对象身份；再把来源槽替换为 Air、目标空槽替换为 clone。只有目标与来源精确回读且总价值守恒才标 `CommitVerified`。失败时尝试恢复原始两个对象引用并核验价值；不能确认回退则启用故障保护，后续自动存钱停住，不猜着补币或重放。
10. 正常 `MoveCoins` 路径以 Z 可观察的玩家钱币数量或原候选槽数量减少判定搬动；首次放币另要求 `CommitVerified`。正常路径这一级成功条件不是整个原版交易的完整双方守恒证明，不能把首次放币的强证明扩大到所有存钱结果。原版调用异常可能已经发生部分作用，本兼容层没有对整轮所有银行作通用回滚。

本轮 `.8 ChestUI.MoveCoins` 静态提取补充解释了为何需要首次放币：它先收集目标银行已有钱币，无任何钱币就返回零；存在钱币才取玩家非收藏钱币（跳过槽 58），合并并按 100 进位，重用银行原币槽和空槽，装不下的金额回到刚清出的来源槽。本轮重新提取的 .8 ChestUI.cs 与既有 .7 该文件同字节，已核对993–1205行；本地代码仍不证明多人实际接受。

### 3.3 主动取出的完整保护规则

**玩家能力是“拿出来的钱先留在身上”，不是一个几秒后自动失效的数量余额。**

- 来源观察覆盖当前打开的普通世界箱子、存钱罐、保险箱、护卫熔炉、虚空保险库。`LootAll` 和受观察的 `ItemSlot` 转移都需要容器实际减少及背包/鼠标实际增加证据；不是只因背包币数增加就认定取出。
- 容器直接进入背包记录直接取出；容器进入鼠标记录鼠标来源，后续落入背包沿来源传递。钱币取出推进共同的 `CoinWithdrawalSeedRevision`，激活新递增保护编号。
- 一个有效保护会阻止 **全部自动存钱**，不仅是某个币种、某一槽、已取出的那一部分，也包括此后新获得的钱币。它不消耗“保护额度”。
- 仍有任一银行在范围内时保护持续；换一个便携银行、关闭再打开容器，不构成离开全部范围。银行查询失败仍保留保护，不能以超时替代明确离开。
- 唯有一次成功银行查询证明数量为零，才按 `leftAllBankRanges` 释放这一范围保护。明确的新玩家/世界身份会重置旧保护。主动关闭再开启自动存钱是显式重置；实现同时记住已观察取出版本，避免同一旧种子立刻重复激活。
- 暂时读不到玩家/世界身份会保留旧保护，等待明确身份。设置世代的其它变化不是自动清除首次放币故障保护的理由；故障保护只在明确新身份或自动存钱 false→true 时重置。

因此产品讨论必须把“何时自动存”和“玩家主动留下钱”一起决定。只移植附近银行搬币而遗漏取出保护，会直接破坏手动取钱、付款或接下来消费的意图。

### 3.4 可见入口、反馈和持久化

- 旧物品页有“自动存钱”开/关行，提示“靠近容器主动存放货币”，可从统一功能主开关键切换；默认关闭。没有在已读实际 UI 上发现银行偏好顺序、保留金额、币种名单、范围或保护时长设置。
- 存钱转移动画只在正常原版返回正搬动值，或首次放币已核验提交后尝试播放。内部诊断记录被 UI 阻止、等待自动堆叠、无银行、保护持续/释放、签名或版本漂移、原版状态变化、首次放币失败和回退是否确认。不能把诊断字段本身写成现有玩家页已经解释所有阻止原因。
- 持久化的是 AppSettings 的启用偏好；取出编号、签名、请求、保护版本、银行观察和故障保护为运行期状态，不应被误写成玩家配置 schema 或跨启动交易恢复机制。

### 3.5 状态所有权、身份、失败恢复与多人边界

- 旧功能把决策放在 `AutoDepositCoinsService`，真实搬动在 `AutoDepositCoinsCompat`，首次放币事务在 `AutoDepositCoinSeedTransactionCompat`；取出保护和故障保护各有唯一静态服务。请求绑定玩家/世界身份及多个版本，执行层再次读取，能够拒绝已过时的授权。
- 银行对象引用去重防止同一个人账户被多入口重复计入前后价值；价值域含玩家前 58 槽与实际去重银行的全部钱币，金额使用受检运算。收藏钱币虽不是搬动候选，仍属于守恒总值域。
- 候选扫描不等于钱币所有权锁。旧队列全局空闲及等待整个 AutoStack 是较粗的并发屏障；新增 R 设计需要写清售卖获得的钱、护士收费、钱币枪/武器消费、手动存取、开袋/提炼产币与该动作同时出现时，谁保护实际受影响的钱币槽和银行。
- 这一路主要调用本机玩家的个人银行与本机原版路径；已读 Z 执行层没有服务器 ACK/事务回执证据。首次放币的本地价值守恒也不能证明远端接受或退出重进后的保存结果。多人权限和消费/余额同步仍须新契约与对应实机验证，不能从 Feature Catalog 的登记状态推导为已验证多人能力。

### 3.6 自动工作量与关闭成本

- 关闭时运行调度不调用主要服务；统一运行设置仍保留开关读取。主检查每 15 tick，同钱币签名重试 180 tick；这些只是代码节奏，不是 FPS 或耗时成绩。
- 在银行查询之前并未先通过“没有钱币”直接跳出：开启后符合基本条件，即使当前无可存钱币，也可能进行附近银行扫描并维护取出保护。`.8` 精选银行查找的 1000 投射物加 79×79 tiles 是可枚举工作量；Z 没有在本分支用稳定场景缓存来消除每轮此调用。
- 来源签名扫描上限 58 槽；执行前会再核验银行/来源，真正搬动前后会读多个银行的钱币域。首次放币还需预构建物品对象、受检金额扫描、槽身份比较及失败回退验证。银行对象最多是四种个人账户，实际扫描仍取集合去重后内容。
- UI/队列繁忙、失败签名、反射异常和不确定状态都有诊断/重试支路。不能只报“每 15 tick 一次”而忽略附近范围和每次完整观察的成本，也不能从静态次数直接声称该能力拖慢帧率。R 后续若获授权，工作量契约应覆盖关闭、无币稳定、处于银行范围、保护持续、真实钱币变化、多个入口同一账户、满银行、未知读数与回退失败。

### 3.7 R 现状、可复用边界与候选分组

**R 已接受边界：** 当前 `ItemSourceHooks.GetBefore` 明确排除钱币 `71..74`；既有自动存只面向普通世界箱子，当前 `ItemVanillaOperations` 只提供出售、垃圾桶、附近世界箱子三条正式操作。不能把现有自动存/卖/扔接受结论扩展成银行自动存钱已实现或已验收。

可复用的是 R 的玩家/世界 Session、真实来源观察和完成回执原则、`HostInputState.CanStartActions` 以及游戏线程单一 `ItemOperationOwnership`。该所有者当前保护实际已定义的出售全 58 槽、丢弃来源与垃圾桶、存储涉及槽及未确认残留；没有现成银行余额事务、取出租期或钱包保留金额契约，不能挂一个新布尔开关就共享既有接受结论。

候选分组建议为“钱币存放与主动取出”，与普通物品自动处理并列，明确共同的实际槽/账户保护接口。是否保留全部保护至离开范围、是否允许玩家设置保留金额/银行顺序、首次空账户如何安全起步、多人以何种权威确认，均是产品讨论项，#83 未作决定。无需因本专题重开 #48。

## 4. 自动回血、自动回蓝、自动增益与跟随名单

| 旧数值字段 | AppSettings 仍有回血 50%、回蓝 35%，但当前这两条决策将 `ThresholdPercent=0`，实际不使用百分比字段触发。不能向玩家写成“低于 50% 自动喝红、低于 35% 自动喝蓝”。 |
| 自身冷却 | 默认回血 120 tick；回蓝默认 8 tick，配置读取将正值上限压到 8，实际可为 1..8；周期自动增益默认 1800 tick。它们是旧自动动作自身节奏，不代替原版药水冷却。 |

**完整药品集合由当前加载游戏物品定义生成，而不是硬编码药水 ID 清单。** `RecoveryPotionDefinitionCatalog` 遍历 `itemType=1..ItemID.Count-1`，逐一 `new Item(); SetDefaults(itemType)`，以真实字段分类：回血配置页收 `potion && healLife>0`；回蓝配置页收 `healMana>0`。这一定义覆盖所有满足条件的原版条目；本文不以几种常见药水冒充全集，也不把历史 `.7` 的物品输出当作 `.8` 全表。只读任务未执行 `.8 SetDefaults` 来生成逐物品的运行期名单，具体版本条目数和本地化名称不在已验证结果内。

实际使用候选的完整规则为：

| 分支 | 来源与资格 | 例外/排除 |
| --- | --- | --- |
| 回血 | `Inventory` 全部实际 IList 槽；仅当 `useVoidBag` 可调用并为真或同名布尔为真时，继续读 `VoidBag`/`bank4.item`；正类型、正数量、`potion && healLife>0`、不在回血禁用 itemType 集合。 | 不扫描其它三种银行、世界箱子、装备或其它玩家；不按收藏排除；`consumable` 被读取但不是选药门槛。使用实际数组长度，没有另设只读前 50/58 槽的限制。 |
| 回蓝 | 同样两类来源；正类型、正数量、`healMana>0`、不在回蓝禁用 itemType 集合。 | 不要求 `potion=true`，也没有选药层面的 `consumable` 或收藏排除。 |
| 增益候选 | 同样两类来源；正类型、正数量、`buffType>0 && buffTime>0 && !summon`。 | **不要求 `potion` 或 `consumable`**；收藏不排除。不能把名称“药水”解释成真实只允许消耗型药水；非召唤、带正 Buff 元数据的其它物品也符合当前静态过滤。 |
| 增益可用 | 候选 itemType 在白名单、效果当前不存在、未检测到下面四类互斥。 | 没有临近结束提前刷新阈值、持续时间最优或强度升级规则。 |

回血唯一参与数值选择的明确物品特例是诡药 `3001`：`EffectiveHealMax=max(healLife,120)`，智能触发量取该最大值；常量中另有恢复药水 `227` 名称，但已读选药算法没有赋予它额外优先级或豁免。不能因为命名常量存在就补造“优先恢复药水”的产品规则。

增益互斥集合完整为：`Main.meleeBuff` 的近战灌注组、`Main.lightPet` 的照明宠物组、`Main.vanityPet` 的普通宠物组、`BuffID.Sets.IsWellFed` 的饱食组。已有同组不同 Buff 时跳过，不比较强弱或剩余时间；已有相同 Buff 直接标 `AlreadyActive`。元数据不可读会记支持情况，但不是“所有冲突表不可读就全功能严格停止”的实现。

### 4.2 自动回血：从生命缺失到恢复与消费

1. 需要世界内有效、活着且非幽灵的本地玩家；菜单、聊天、NPC 对话会阻止药品分支，单独打开背包或箱子仍可进入。普通周期入口还等待最近 F5 控制点击 150 毫秒结束及旧全局队列空闲。
2. 满血或最大生命无效直接无动作；存在生命缺失后，先扫描与选择药品，再检查自动动作冷却、原版 `potionDelay` 和正在使用物品状态。这意味着缺血但原版药水冷却未到时，仍可能每次决策重新扫描候选。
3. **Quick：** 取有效最大治疗量最高的一件，平手取 Inventory 优于 VoidBag，同容器槽号较小者。即使只缺少少量生命，也可能选择最高治疗量药品。
4. **Smart：** 候选必须满足 `SmartHealTriggerAmount<=missingLife`，或其 `EffectiveHealMax>maxLife`（超过玩家生命上限的药仍可用）。有多个时先选择不超过玩家最大生命的候选，再取浪费量 `max(healMax-missingLife,0)` 最少者，再取治疗量较高者，最后按 Inventory/槽顺序。无合适药则等待，不退回“危急百分比随便喝”。例如缺 80、可用 50 与 100 治疗量时，普通规则选 50；如果最大生命 100 而只有 150 治疗量药，超上限例外会让它在存在缺血时可用。
5. 就绪后提交 `UseInventoryItem`，低优先级、合并重复待处理，排队期限 350 毫秒、执行期限 3 秒；记录准确容器、槽号、物品类型、预期恢复信息。开启某一模式会把旧冷却戳设为到期，方便新策略尽快评估。
6. 执行器重新确认本地玩家、世界/UI、来源容器可用、槽内同 itemType、正数量及正恢复字段。虚空袋来源在真正读槽和消费时仍重新核验 `useVoidBag`。此处身份主要是容器名+槽号+itemType，不是玩家/世界世代、物品对象引用或完整 prefix/数量签名。
7. 调用 `Player.ItemCheck_TryStartUse(item,false)`。回血若被拒绝则失败停止；接受后，若 `potion` 尝试 `ApplyPotionDelay`，再调用 `ApplyLifeAndOrMana`，按物品 Buff 元数据调用 `AddBuff`，物品 `5` 还尝试 `TryToResetHungerToNeutral`，播放使用声音，最后查询 `CanConsumeConsumableItem(item)` 决定是否调用直接减栈。
8. 该执行器读取当前选中槽用于前后观察，**没有把当前选中槽临时切成药品**；不要把快捷物品的选槽/恢复流程套在回血上。它调用原版内部恢复方法，但不是完整重放物理按键、原版 H 或整个 `ItemCheck` 消费流程。
9. 消费辅助重新读相同来源/type，减 1；最后一件优先 `TurnToAir`，失败再尝试 `stack=0`。正常路径先应用效果后决定消费，`ApplyPotionDelay` 失败不阻断后续；已经加血/加 Buff 后消费失败，没有通用效果回滚。结果 `Succeeded` 的本地条件是对应生命上升 **或**观察到减栈，不能把“只消耗成功”自动等同于“实际治疗成功”。

这组规则是事实抽取，不是对内部方法拼接方式的保留授权。R 若进入实施，真实恢复、消费、原版冷却、副作用与失败结果需要作为一个完整能力合同讨论。

### 4.3 自动回蓝：预测所持武器不足及专门 fallback

1. 仅有蓝量缺失还不够：先检查当前选中物品是否是耗蓝武器。类型/数量须有效，原始 `item.mana>0`。剔除放置方块/墙、带 pick/axe/hammer/fishingPole 的工具，以及只作弹药（`ammo>0 && useAmmo<=0`）的物品；没有伤害、射弹、用弹类型，也没有 magic/ranged/thrown/melee 标记的纯辅助物品同样排除。
2. 尝试原版 `CheckMana` 的已识别重载：`(item,-1,false,true)`、`(item,-1,false)`、`(item,-1)`；无法使用时退回 `statMana >= item.mana` 的原始耗蓝比较。后者不等于所有装备、Buff 和武器特例调整后的真实费用，结果会标 fallback。
3. 只有“当前所持武器判为不足”且玩家仍有可恢复的魔力时选药。**不要求这一刻物理开火键已按下或已经发生真实使用失败**，因此“下一次会不足”的预测不能写成“仅在一次真实攻击失败后喝药”。
4. 选可用 `healMana` 最大者；平手 Inventory 优于 VoidBag、低槽优先。魔力病只作为观察说明，不阻止；玩家正在使用物品也明确允许，以支持持续耗蓝。自身冷却默认且最多 8 tick。
5. 普通执行路径与回血共用内部恢复方法，但 `ItemCheck_TryStartUse` 被拒绝时，**AutoMana 有单独补充路径**：先调用 `CanConsumeConsumableItem` 得到允许，再 `ApplyLifeAndOrMana`、声音、直接减 1。此路径没有走普通段的 `ApplyPotionDelay`、物品附加 Buff 和物品 5 饥饿处理。
6. 同样以对应魔力上涨或减栈作为本地成功证据；多人客户端会因同步未确认降级。它没有临时切药品槽，因此持续武器选槽的影响不同于快捷物品，但仍会碰到同一来源库存、当前武器消费和原版恢复状态。

候选讨论项包括：是否保留未按攻击键即预补的行为；是否允许原版开始使用被拒绝后的内部方法 fallback；什么情况下魔力病仍允许继续喝；是否优先节约而不是总取最高蓝量。#83 不选择新答案。

### 4.4 自动增益：周期补齐、即时补齐和队列反例

**周期路径：** 总开关开启且白名单非空，经过普通队列/UI门禁与自身冷却，再刷新候选；取扫描顺序中首个 `IsWhitelisted && CanApply` 的物品，正在使用物品会阻止这一周期分支。Inventory 先于 VoidBag；不是按名单添加顺序、Buff 强度或药价排序。

**即时路径：** 开启、F5 加入白名单、白名单物品总量签名首次出现或变化，以及白名单 Buff 存在性变化后确有缺失，会请求即时 reconcile。库存签名至多每 15 tick重读，按 itemType 汇总 Inventory+可用 VoidBag 总数量并排序，不包含槽号、prefix 或对象身份；Buff 签名只记录白名单 Buff 是否存在，不记录剩余时间。无需等 1800 tick 周期冷却即可尝试补齐。

即时处理在普通“最近 F5 点击”和“队列已有工作”门禁之前运行，并逐候选 itemType 去重/预留后尝试提交；所以不能把普通分支的全局队列空闲、正在使用物品阻止或周期冷却说成即时分支也完全遵守。预留按 itemType 存在，默认 600 tick 到期；失败类型一般等待 45 tick，但 `BuffMissing` 原因允许绕过该失败节流。

**已证实的静态反例，不能把“即时补齐”直接写成一次确保全部生效：**

- `EnqueueDecision` 给所有 AutoBuff 请求的 AdmissionKey 是 `feature|actionKind|mode`，不含 itemType；周期和即时的 Mode 都为 `AutoBuff`。
- 假设空队列、A 与 B 都是白名单中可用缺失效果：A 提交后成为 pending；B 的同 key `CoalescePending` 被接受，但队列将 A 的 payload 改成 B，保留 A 的 RequestId，而不是新增第二个待执行动作。
- 服务按每条新请求自己的 RequestId 记录类型并增加 queuedCount。于是可显示“已提交 2”，实际只有 1 个 pending，最后以 A 的 RequestId 执行 B 的内容。终态回调按 RequestId 解除 A 的预留；B 的另一个新 RequestId 没有独立执行回执，仍可留在 in-flight 等到其它路径/到期处理。
- 另外，即时循环在 `EnqueueDecision` 返回 `Guid.Empty` 时仍递增 queuedCount，而准入前已预留该 itemType；因此该计数不是严格的成功入队数量，也不证明全部消费了几件。
- 以上由调用链直接得出，未运行测试或游戏。不能进一步臆断每次都漏药、一定重复消费、确定时长或 FPS；实际补齐还受后续库存/Buff 签名变化及周期分支影响。这个反例已经足以要求产品讨论区分“尝试补齐”“已接受请求”“实际增益与消费完成”。

**真实执行方式及消耗：** `BuffPotionDirectUseExecutor` 重读当前本地活玩家、来源槽及同 itemType，要求正 stack/buffType/buffTime、非 summon、预期 BuffType 未漂移；然后直接调用 `Player.AddBuff`。前后读取效果持续时间，只有新出现或确实延长才继续播放声音并直接减 1。AddBuff 已调用但效果无法确认时，不扣物品，返回未确认；效果已加上而减栈失败，同样没有把 Buff 回滚的通用机制。执行器本身未再次判断“当前仍在白名单”“现在是否与其它效果冲突/已存在”，也不检查 `potion/consumable`。因此这不是原版 B 的通用 QuickBuff，也不能把自动增益候选叫成严格安全的消耗型药水全集。

### 4.5 实际界面、跟随名单、手动入口和配置保存

- 实际增益页依次提供回血模式及药品配置、回蓝开关及药品配置、护士、家具增益、自动增益；本专题不替代护士/家具调查。药品配置按游戏定义展示条目，点选按 itemType 允许/禁用；黑名单仅改变候选资格，不改原优先级。目录展示回血按原始 healLife 递减、回蓝按 healMana 递减，平手 itemType 递增，与诡药选择时的有效最大值不能混为一谈。
- 增益名单为“可选/已选”双网格；有刷新候选、跟随添加、跟随删除、清空名单，左侧候选加入、右侧现有条目移除。加入成功请求即时补齐；清空和删除更新偏好本身。候选 UI 缓存按 1 秒刷新。名单项保存 `ItemType/BuffType/ItemName/BuffName`，身份是类型，名称是说明。
- 源码里有自动增益冷却 slider 渲染函数及 300..3600 范围，但当前 `DrawBuffPage` 没有调用该行；不能把这个孤立函数写成当前 F5 可调功能。
- **跟随添加：** 在本地 ItemCheck 使用前后观察当前所选正数量、带有效 Buff 的候选；成功读到 `summon=true` 时排除，`ItemUseBridge` 有请求时不采作手动使用。使用后 Buff 必须有效，且存在“同类型减量/类型改变”“从无到有”或“时长比之前增加超过 30 tick”之一；随后把使用前的 itemType 加入白名单，因此用掉最后一件也能记住。它是实际原版入口的前后观察加条件，不是任意背包减少即学习，也没有要求自动增益总开关开启。再次读槽/字段失败的宽松边界见下一段。
- **跟随删除：** Hook 为 `Player.DelBuff(int)` 的前置观察，要求本地玩家、目标当前是有效白名单 Buff，且 `Main.mouseLeft && mouseLeftRelease` 或对应右键组合被判为很可能手动取消，然后按 BuffType 移除所有对应白名单物品。它在原版删除完成之前更新名单；鼠标组合是手动因果的启发式，不是已经验证了某个具体 Buff 图标点击且删除成功。不能把所有消失（过期、死亡、替换）都说成会自动移除，也不能声称无误判。
- UI/跟随变更通过 `ConfigService.SaveAll` 保存到原 AppSettings。已读调用不以“成功落盘回读”作为每次玩家反馈的前置条件；“内存名单已改变”与“跨重启可恢复”是应区分的结果。旧全局 AppSettings 也不等于为每名角色分别保存名单。
- 诊断面板里的“QuickBuff 一次”是另一个受诊断开关控制的原版 B 等价入口；自动增益不会调用它。Feature Catalog 的“开启不会立即 QuickBuff”是对这条原版全体入口的区分，不代表开启已有名单后绝不立即尝试逐候选直加增益。诊断入口的保留/删除由剩余入口专题归档，不据此扩大本组功能。


### 4.6 状态、身份、取消、失败结果与多人权限

**状态归属：** `AutoRecoveryService` 持有模式/结果/冷却戳、即时请求原因、上次库存与 Buff 签名、按 itemType 的 in-flight/失败表、RequestId→itemType 表；配置归 AppSettings，候选读取归目录/兼容层，真实恢复归执行器。已读这组静态状态没有玩家/世界身份键或明确的新 Session 世代；`CanRun=false` 是提前返回，不是清空这些状态。不能凭进入菜单或换角色就宣称旧签名/预留已得到独立身份隔离。目录定义也按进程静态缓存，不能当作每个玩家独立对象。

冷却证据以实际赋值为准：`EnqueueDecision` 成功及 `RecordAdmissionDenied` 都会更新相应 LastAuto*Tick；终态回调更新结果、能力说明及 AutoBuff 预留/失败时间，**没有把回血/回蓝自身冷却改为按最终完成时刻计时**。文件头关于“terminal results drive cooldown”的注释与实际赋值不一致；调查不继承注释为事实。

候选身份与真实物品授权需区分：恢复执行层重读同一容器、同一槽、同 itemType、正数量；增益还核预期 BuffType。它们没有收藏排除、完整 prefix/实例比较、角色/世界版本或 R 式来源成员代次。虚空袋是否可用会在每次读容器时重查。停止自动功能、名单改变、库存移动、死亡和换世界时，后续 R 合同需要分别定义“禁止新意图”“取消未开始请求”“已有效果/已消耗但结果未确认如何收口”，不能统一写成清空队列后重新试。

**多人证据边界明确：** `InventoryMutationCompat.DetermineSyncResult` 对已识别为多人客户端返回 `UnsupportedNetworking`，`syncAttempted=false`、`syncSucceeded=false`；回血/回蓝若已产生恢复或消费，结果从成功降为 `AttemptedButUnverified`。直加增益与消费在客户端也降为未确认。这证明代码承认缺少受支持同步，不证明服务器会接受这些本地变化。网络模式读取自身默认 `netMode=0`，若反射没有取到字段也会落到单机解释，故未知网络身份不能被产品合同视为可靠单机证明。Feature Catalog 统一登记 `LocalAssistPendingMultiplayerVerification` 与此相符。

**另一处资格读取边界：** 跟随添加在能读到真实物品且读到 `summon=true` 时排除；若再次读槽/字段失败，其 helper 仍可能依据先前正 Buff 元数据返回 true。因此“跟随添加排除 summon”是正常成功读取下的规则，不能扩大为读失败也严格关闭。

已确认的局部失败行为包括：回血原版开始使用拒绝停止、回蓝拒绝后有专门 fallback；增益 AddBuff 无法确认则不减物品；增益已有效而消费失败记录未确认；内部恢复已发生而后续步骤失败没有通用回滚；静态预留依赖回执或到期；一次物品定义目录加载异常会缓存空数组并置 `_loaded=true`，后续访问不会自动再试，警告的 30 秒节流不是重新加载机制。

### 4.7 高频路径、稳定/变化/失败场景与观察成本

- 主调度对 `RecoveryAnyEnabled` 以 1 tick 节奏进入服务；回血/回蓝/增益/护士/家具全关时不进主要恢复服务。跟随添加/删除是独立 Hook 开关，自动增益关闭并不自动关闭名单学习。
- 普通分支优先顺序是回血 → 回蓝 → 护士 → 家具 → 药品增益；仅 NPC 对话时只尝试护士；仅箱子界面开启时跳过家具而可继续恢复药品。被某项冷却阻挡可继续评估后面一项。即时增益在这组普通优先选择之前执行，因而“救命永远优先于补 Buff”不是目前完整调用链保证。
- 满血回血较早退出，非耗蓝手持物回蓝在扫描药品前退出；但缺血时先扫描选择后检查药水病/正在用物品，自身冷却并不消除选药成本。回蓝每次先做当前物品字段与 CheckMana 兼容检查。
- 实际药品扫描对 Inventory 和可用 VoidBag 的整个数组逐槽读字段，按分支建立候选/集合；不是扫描所有 ItemID。全部 ItemID 的 `new Item/SetDefaults` 仅属于 UI 药品目录首次加载，随后静态缓存。
- 白名单开启时每 tick 构造/比较白名单 Buff 存在性签名；库存签名至多每 15 tick读取两类容器、按白名单类型累计、排序生成字符串。稳定场景不继续触发即时请求，但仍有这些观察工作。真正请求即时处理会重扫候选并检查当前 Buff 冲突。
- 普通候选冲突最多针对四组原版表并遍历当前 Buff；候选数量随两类容器中有效物品数量增长，白名单集合/签名随配置长度增长。UI 双网格每秒刷新候选；目录和 UI 缓存的存在不代表自动决策复用了同一份永不失效快照。
- 每次即时对账、尝试入队、拒绝/失败、结果与跟随学习存在诊断记录；普通阻止事件有 60 tick 节流，缺失物品、in-flight 600 tick 到期、失败 45 tick 及 `BuffMissing` 豁免是不同节奏，不能一并归为“无开销”。
- 后续 R 若授权，应覆盖关闭、全满、缺血但冷却、持续耗蓝、长期已有全部 Buff、长名单但缺药、两种同 Buff 物品、互斥增益、虚空袋开闭、名单连续修改、队列合并/拒绝、失焦/换 Session、效果已发生但消费/同步未确认等工作量与正确性场景。上述都是静态可描述路径，不是已测 CPU、GC 或 FPS，更不是已授权修复。

### 4.8 R 现有边界、产品候选与固定证据

**R 已有可复用能力：** 统一输入采样与 `HostInputState.CanStartActions`，失焦后的真实释放重新武装；玩家/世界/连接 Session；正式物品偏好持久化；按实际受影响槽保留未确认状态的 `ItemOperationOwnership`；Host 观察与原版受控操作分层。现有三个物品操作没有回血、回蓝、AddBuff、消费、药品来源或选槽恢复的正式端口。对当前 `src` 的定向符号/文本检索也未发现本专题六项旧功能生产实现。既有自动存/卖/扔只核接口及接受范围，本专题未全面复审它们。

**候选分组：** 将回血、回蓝、药品增益共同归入“恢复与增益维持”，但保留三个独立策略、各自真实原版操作及局部所有权。名单学习是该组的玩家偏好输入；护士/家具是相邻恢复来源，可共享必要观察，不能把所有业务塞回一个巨型 AutoRecoveryService。Legacy 的静态总服务、原版内部方法拼接、直接减栈及共享队列 admission key 都是历史实现证据，不是 R 架构义务。

**待产品决定的具体问题：**

1. Smart 是否保留“治疗量高于生命上限即提前可用”的例外，以及诡药按 120 最大值等待；Quick 是否明确愿意付出少量缺血即用最大药的成本。
2. 回蓝是否以手持武器预测不足为触发，还是需要真实使用意图；原版开始使用拒绝时可否存在专用补充路径。
3. 药品是否可使用收藏物品、虚空袋和数组末端槽；目前动态候选宽于“消耗型药水”，R 应明确允许类别与成本，不能承诺照搬即安全。
4. 自动增益名单是物品偏好还是效果偏好；多种同 Buff、不同强度饱食、互斥宠物/灌注如何排序、替换或保留；缺失才补还是剩余时间低时补。
5. 即时补齐能否在武器使用和其它在途操作中开始；完成反馈如何区别请求接受、实际效果、实际消耗及多人确认。
6. 跟随删除应在哪个真实输入/原版成功结果上学习，如何避免“任意鼠标点击同时 DelBuff”误判；名单按全局还是角色保存。

这些均未由 #83 决定。旧代码存在不构成保留授权；未实现的候选也不能称为产品进展。

## 5. 跨功能接口与进入产品讨论前的收口

| 与哪组相交 | 本专题已确认接口和需要保留的边界 |
| --- | --- |
| R 已接受自动存/卖/扔 | 保持收藏改变 favorite 会影响实际来源资格；快捷物品可能改类型/消耗/移槽；恢复消费减少来源数量；售卖会碰全前 58 槽及钱包。后续能力必须在实际重叠资源上合作，不能因名字都叫“背包”重新引入一个阻塞所有功能的总队列。未确认旧操作的保护不能被新功能清除。 |

| 快速开袋与自动提炼 | 产出可能含普通物品、药品、钱币；新增自动开袋/提炼来源不能靠“背包增加”取得 R 自动存卖扔资格。钱币当前被 R 普通来源 Hook 排除；Legacy 自动存钱是整体当前背包整理，其取出保护会覆盖后续产币。跨来源流程应分别证明开袋/提炼结果和后续处理。 |
| 手动取出、装备/右键变形 | 主动取钱有范围租期保护；收藏恢复只观察所覆盖主背包/当前装备；快捷物品可能将同族物品转换形态且不自动转换回去。不能把类型变形/同值对象替换当作可靠的新物品来源，也不能给装备/工具变换补造获得资格。 |
| 护士、家具、经济消费 | 普通恢复顺序将护士置于药品回血/回蓝之后；钱币存放涉及付款资源；免费家具 Buff 与药品 Buff 的相同效果及优先级应由相邻候选讨论。护士/家具的具体原版判定归对应专题，本文没有替代其调查。 |
