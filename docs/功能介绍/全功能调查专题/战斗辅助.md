## 2. F5、快捷键、配置与输入界面

### 2.1 实际战斗页

显示顺序是：辅助瞄准、自动连点、链球连击、光剑快切、完美左轮、省力魔法绳、自动转向、装备提示、自动汇报、哥布林必死。八个独立布尔能力有开／关按钮及对应功能快捷键配置入口；光剑另有间隔滑块。这里没有独立战斗物品名单编辑器、优先级拖拽、目标清单子窗或专属运行控制台。

辅助瞄准一行包含：

- 目标策略：Nearest／ClearLine；
- 范围中心：Player／Cursor；
- 假人开关；
- 标记开关；
- 鼠标范围 0–50 格滑块。

**Player 模式会禁用范围滑块，但两个模式的实际启用仍由 `CursorAimRadius>0` 决定。** 默认 Player、Cursor 半径 0 的组合，因此没有“Player 模式天然一直开”的行为。仅看这条 UI 操作链，启用时需切到 Cursor 调大半径，再按需要切回 Player；切换中心本身保留 Cursor 半径。Player 正数半径显示“屏幕范围”，Cursor 显示实际格数，0 显示关闭。

证据：Z [DrawCombatPage，49–75](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/UI/Legacy/LegacyMainWindow.Pages.cs#L49-L75)，[DrawCombatAimAssistRow、光剑行，23–219](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/UI/Legacy/LegacyMainWindow.Rows.Combat.cs#L23-L219)。

### 2.2 保存与旧配置迁移

按钮、滑块和开关处理最终写 `AppSettings` 并 `SaveAll`；范围中心切换到 Player 会取消尚未完成的辅助瞄准滑块输入。Player 模式收到范围值请求时直接忽略并清除待处理滑块状态。光剑间隔修改也清除对应滑块待处理状态。

配置归一化规则完整如下：

- 旧 `CombatAimAssistRadius`、Cursor、Player 半径均限制在 0–50。
- 首次分离半径迁移时，把旧半径复制到两种半径字段；缺省／非正释放保持值改为 8；持久鼠标辅助设为开；记录迁移完成。
- 随后 `CombatAimAssistRadius` 跟随 Cursor 半径；`PlayerAimRadius` 仍保存，但不决定当前 Player 范围。
- `ReleaseHoldTicks` 最终限制在 0–20；默认 8。
- 光剑间隔负数归默认 12，大于 30 归 30；0 保留。
- 默认中心／策略是 Player／Nearest；无效字符串的归一化回退却是 Cursor／ClearLine，不能把二者混为同一默认。
- `PersistentCursorAimEnabled` 默认开启。它是自瞄内部行为配置，不是本页单独列出的用户功能。

功能切换快捷键执行器有自动连点、链球、光剑、左轮、魔法绳、转向、装备提示、汇报、哥布林的布尔切换分支；本次核对的战斗行与执行分支没有独立 `CombatAutoAim` 总开关。不能从它有 Feature ID 推定存在同样的快捷键入口，也不能凭没有默认键值就编造按键。

### 2.3 “物理按下”并不是所有功能共用的一个事实

Legacy 有几种不同读取方式：

- 自动连点使用专门的物理左键读取。
- 左轮、魔法绳的“UseItemHeld”路径可合并 `player.controlUseItem`、`Main.mouseLeft`、原版 Trigger 或 OS 后备值，不能统称纯物理鼠标采样。
- 右键连击读取 OS 后备、`Main.mouseRight`、原版 Trigger；光剑还要求左键读取成功且未按下。
- 自动转向的手动优先读取 `controlLeft/controlRight`，不是固定 A／D，也不是玩家速度方向。
- 操作系统后备读取受到 `AllowsInputProcessing` 约束，但某个 helper 名为 `Physical…` 不代表其所有输入源都逐一经过相同焦点约束。

UI 门主要包括游戏内有效玩家、非主菜单、非聊天、非 NPC 对话、鼠标未被 UI 捕获；链球／光剑另检查箱子、旅行菜单和右键世界交互。**普通背包打开本身不等于全部战斗辅助关闭**，真正的 UI 鼠标所有权与具体功能门才是依据。

证据：Z [UseItem.PhysicalInput，17–93、155–177](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/TerrariaInputCompat.UseItem.PhysicalInput.cs#L17-L93)，[UseItem.Read，9–40](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/TerrariaInputCompat.UseItem.Read.cs#L9-L40)，[Movement.Read，7–34](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/TerrariaInputCompat.Movement.Read.cs#L7-L34)。

## 3. 共同动作入口、让路顺序与恢复

### 3.1 同一次 ItemCheck 的真实顺序

本地玩家的 `Player.ItemCheck` Prefix 首先处理旅行菜单保护、转向覆盖与手动转向，然后在已有 ItemUseBridge 与动作写入者之间仲裁。

实际优先顺序：

1. 蓝图宏伟蓝图使用；
2. 已有 ItemUseBridge 请求；
3. 自动捕捉／自动收获，有共同公平性协调；
4. 自动挖矿持续使用；
5. UseItemPulse，即魔法绳脉冲；
6. 光剑快切；
7. 无上述所有者时，战斗兜底依次尝试：**完美左轮→链球连击→自动连点→普通自瞄与链球释放辅助**。

因此不能仅按注册表的 Priority 数字排列真实效果。任何前面的所有者取得本次入口，后面的战斗兜底就让路。左轮／连点只有按下阶段附带自瞄；链球按下和释放都可附带瞄准并记录后续尾段。ItemUseBridge 只有请求明确允许 `AllowCombatAim` 时才附加战斗瞄准。蓝图放置、捕捉、收获、钓鱼等动作不能因为复用 ItemCheck 就默认继承当前敌怪目标。

证据：Z [ItemCheckWriterArbiter，110–236](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Actions/ItemCheckWriterArbiter.cs#L110-L236)，[ItemUseHookCallbacks.Prefix，75–247](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Hooks/ItemUseHookCallbacks.cs#L75-L247)。

### 3.2 写入、恢复与成功的含义

常规点击接管先记录 `controlUseItem/releaseUseItem`、必要时 `channel`、Main 左／右键状态。接管时把 `controlUseItem` 设为这一步的按下值，并制造可使用的 release 状态；点击型接管不直接改 channel，链球连击／光剑会抑制右键，通用释放型接管可改 channel。结束后由配对 Postfix 恢复。

需要明确三项例外：

1. **本组 ItemCheck、Projectile.AI 和 Projectile.Kill 安装器均为 Prefix/Postfix，没有安装本组 Harmony Finalizer。** Projectile Postfix 内部的 `try/finally` 只保证它已经开始执行后内外层恢复的顺序，不能证明原版方法抛异常时仍进入 Postfix。恢复失败有诊断，不等于异常情况下已恢复成功。
2. 光剑 Postfix 在恢复原输入后，还主动写入按下／释放状态供本轮后续原版弹射物 AI 使用；它不是“本次 ItemCheck 返回后所有输入完全还原”的实现。
3. 自动转向是对真实玩家朝向的受控修改，不做结束后的反向恢复；动作结果应当是新朝向继续保留。光剑选槽也不自动切回初始格。

“Applied”“Succeeded”在多数专用辅助中只证明输入步骤已应用、恢复或方向步骤已完成，不证明发射物生成、命中敌怪、实际暴击、服务端确认或玩家获得了预期 DPS。专门的实物结果验证应按能力单独定义。

证据：Z [UseItem.Scope，239–261](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/TerrariaInputCompat.UseItem.Scope.cs#L239-L261)，[UseItem.ItemCheckBridge，292–343](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/TerrariaInputCompat.UseItem.ItemCheckBridge.cs#L292-L343)，[ItemUseHookCallbacks.Postfix 与光剑恢复，261–415、983–994](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Hooks/ItemUseHookCallbacks.cs#L261-L415)，[ProjectileAiHookInstaller，80–105](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Hooks/ProjectileAiHookInstaller.cs#L80-L105)，[ProjectileAiHookCallbacks，50–75](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Hooks/ProjectileAiHookCallbacks.cs#L50-L75)。




## 4. 自动连点

### 4.1 完整资格与排除顺序

入口是 ItemCheck 战斗兜底中的 `CombatItemCheckAutoClickService.TryBeginTakeover`，不是后台独立调用武器的 `Shoot`。前提为：功能开启、本地有效玩家、允许游戏输入、左键持续按下、成功读取武器及原版全局自动重复使用开关。

可读持有位置是快捷栏 **0–9**，或者特殊鼠标物品槽 **58**；58 单独读取 `Main.mouseItem`。资格按下列规则判断：

1. type、stack 必须为正；
2. `channel` 一律排除；
3. `ItemID.Sets.ShootsOnUseRelease` 为真一律排除；
4. 排除所有 `fishingPole>0` 物品，并额外硬排除钓竿 ID：
   `2289、2291、2292、2293、2294、2295、2296、2421、2422、4325、4442`；
5. 排除左轮 `2269`；
6. `pick/axe/hammer` 任一为正则排除；
7. `useStyle/useAnimation/useTime` 必须为正。

**没有 damage 必须大于 0 的总条件，也没有“仅战斗武器”的总条件。** 某些可消耗、可放置物品只要通过以上规则也可进入。源码中的 LifeCrystal `29`、RainbowRod `495`、RodOfHarmony `5335` 三个 seed 常量仅供种子／测试分类，不能当成完整白名单；例如 RainbowRod 仍受 channel 排除。

原版全局自动重复使用开关读取优先 `Main.SettingsEnabled_AutoReuseAllItems`，后备 `player.autoReuseAllWeapons`。读取不可用时停止接管。若全局开关开启，并且物品有 `autoReuse`，或物品 damage>0 且符合其武器重复使用条件，则让原版处理。若全局开关关闭，单凭物品 `autoReuse=true` 不会自动使本功能让路——这是当前逻辑与“只补原版不支持的物品”UI 简写之间的具体差别。

证据：Z [TryBeginTakeover、决策与资料读取，44–181、203–321](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatItemCheckAutoClickService.cs#L44-L181)，[IsEligible、原版覆盖与开关读取，322–461](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatItemCheckAutoClickService.cs#L322-L461)。

### 4.2 真实动作、停止与结果

同时满足 `itemAnimation<=0、itemTime<=0、reuseDelay<=0、!delayUseItem` 时制造按下，否则制造释放。没有绕过原版动画、伤害、消耗、条件检查，也没有改武器 useTime。

成功取得点击 scope 后，原版 ItemCheck 继续运行；若本步按下，可叠加自瞄；Postfix 尝试恢复原输入。左键释放、换成不合格物品、UI 占用、玩家不可用或前序写入者占用本次 ItemCheck 时停止接管。它不保留一个需要继续完成的长任务，也不切换／恢复选槽。

当前 `.8` 原版 `ItemCheck_AutoReuseLogic` 先处理物品自带 `autoReuse`，再调用 `TryAllowingItemReuse`；后者另有 `autoReuseGlove`、`stressBall` 和 `autoReuseAllWeapons` 分支。**Legacy 的“原版覆盖判断”是较小的模仿集合，不等于完整原版判定。** 原版证据：O-Player **53519–53563**。这意味着迁移时应以当前原版实际能力为边界，不能复制旧简化式然后宣称完全等价。

“连点成功”诊断证明本次输入接管或恢复结果，不证明一次新的物品使用已经完成。实际弹药、魔力、可消耗物品仍可能消耗；失败后没有自动退款。O-Player `ItemCheck_Shoot` **47459–47484** 调用 `PickAmmo`，魔力检查／实际支付 **53264–53294** 仍由原版处理。

### 4.3 高频与旧问题

启用且持键时每个相关 ItemCheck 读取资料并判定；禁用时虽然尽早退出，但 Hook 仍存在，并记录其决策／跳过诊断。资料快照、锁、诊断快照和错误节流本身有成本。此处只有静态工作路径，未测 FPS。

应保留的回归点：鼠标槽 58、channel、释放发射类、全部钓竿、工具、左轮、全局开关读取失败、已有 ItemUseBridge／采集占用、按下与释放后的字段恢复。不能只以一个普通枪械用例代表这项功能。

## 5. 完美左轮

### 5.1 武器范围与行为顺序

只接受 **原版左轮 `2269`**，不泛指所有手枪或名称含左轮的物品。选槽限 **0–9**；物品正 stack、非 channel、`altFunctionUse==0`、useStyle/useAnimation/useTime 为正，本地存活非幽灵玩家，使用键保持且 UI 门允许。

实际按下计划：

- 空闲：动画不大于 0、使用时间不大于 0 或原版 `ItemTimeIsZero`、无 reuseDelay、无 delayUseItem，则按下。
- 非空闲：通常释放。
- 动画／使用时间均落入 **2 tick** 窗口且至少一项尚为正时，安排下一 tick 的按下。
- 到了所安排的**准确 tick**，仍处于 2 tick 窗口且无 delay/reuse 阻挡才按下。
- 已错过的安排被清除，不补发一串历史按下；未到窗口则继续释放。

这里的 `NormalizeFireWindow` 是把正值减去 2 后下限归 0，不是凭空要求原始计数已经归零。常量 22 是资料缺失时的额定冷却后备，不表示每把左轮被强制成固定 22 tick。

主逻辑在 ItemCheck Prefix；该类后台 `Tick` 为空。禁用 guard 与失去资格会清除安排、接管标志及旧抑制状态。

证据：Z [TryBeginTakeover，62–148；资料／资格，185–269](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatPerfectRevolverService.cs#L62-L269)，[IsReadyToFire、CreateAttackPlan、窗口归一化，272–394](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatPerfectRevolverService.cs#L272-L394)，[Reset 与诊断，430–499](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatPerfectRevolverService.cs#L430-L499)。

### 5.2 原版两端证据与消费

当前 `.8` O-Player **42999–43025**：持有 `2269`，动画进行中且 `controlUseItem=false` 时，原版额外递减动画／itemTime，并增加 `revolverCritChanceBonus`；其他条件下存在随机递减，最终按前缀参数限制额外暴击值。Legacy 只调整输入，**没有直接写暴击值，没有保证枪枪暴击**。

### 6.2 触发到执行与停止

运行检查世界、UI、玩家、资格；自身已运行则保持，已有其他 pending/running 动作或 ItemUseBridge 时不再提交。提交 `RawInput`、Normal 优先级、按来源合并 pending 请求的独占动作：

- 等候队列有效期 250 ms；
- 执行超时 15 分钟；
- 使用键必须保持；
- 记录期望选槽及物品 type；
- 脉冲间隔 2 tick；
- 明确允许附带战斗瞄准。

`RawInputActionExecutor.StartMagicStringClicker` 复核环境后启动 `UseItemPulseBridge`；真正写入发生于 ItemCheck。第一次／达到 NextPressTick 时按下，下一次按下时间设为当前 tick+2，中间 ItemCheck 释放。这个桥没有光剑桥那样的“同一 GameUpdate 仅应用一次”门，因此同一 tick 若出现额外 ItemCheck，第二次可能已走释放步骤；不能把 2 tick 参数机械解释成固定现实频率。

实际只通过脉冲入口写 `controlUseItem` 与 `releaseUseItem`，不直接改弹射物、装备或伤害。停止因素为：禁用取消自身来源、UI 不能操作、超时、玩家失效／死亡／幽灵、使用键释放、选槽／type 变化、读到魔法绳效果消失。某些 UI 跳过由执行器的运行更新完成取消，而不是只靠服务本次没提交新请求。

已经发生过按下后，以“停止使用／UI 阻挡”为由结束可返回 Succeeded；其语义是该轮持续输入任务已结束，不是逐次悠悠球命中成功。桥以选槽+type 判断仍是同一武器，没有完整物品对象／堆叠版本／会话代际凭据。

## 7. 链球连击

### 7.1 武器资格不是物品名称名单

完整资格是：持有正 stack、正 type、可造成伤害的物品；排除放置方块／墙、哨兵、召唤物放置、工具、钓竿、作为弹药本体的物品；要求 **channel、shoot>0、useAmmo==0、对应弹射物 aiStyle 15、且不是悠悠球**。公共资格保留 Coin Gun 的 damage 例外，但它不能因此跳过 aiStyle 15 等后续条件。

选槽限定快捷栏；本地玩家必须活着、非幽灵，右键按住。读到左键也按住则让路；这里左键读取失败没有像光剑那样一律拒绝，因此不能概括为所有输入事实缺失都停止。

右键让路完整范围：

- 主菜单、聊天、NPC 对话、箱子、旅行菜单或 UI 实际捕获鼠标；
- `SmartInteractShowingGenuine`，或 `SmartInteractNPC/SmartInteractProj != -1`，或 `player.tileInteractionHappened`；
- 当前已有 altFunctionUse；
- `ItemID.Sets.HasRightFire`；
- `ItemID.Sets.ItemsThatAllowRepeatedRightClick`。

物品右键 sets 读取失败会拒绝接管。世界右键 helper 在 Main 类型不存在时拒绝，但其几个字段读取失败时没有统一拒绝；不要把源码局部 fail-closed 扩大为所有环境观测都 fail-closed。单纯背包开启且没有上述占用，可以工作。

证据：Z [CombatAimFlailPolicy，28–80](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimFlailPolicy.cs#L28-L80)，[CombatFlailComboService，44–178](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatFlailComboService.cs#L44-L178)，[CombatFlailRuntime.HasVanillaRightClickSemantics，152–224](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatFlailRuntime.cs#L152-L224)，[IsWorldRightClickInteractionActive，70–101](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/TerrariaInputCompat.UseItem.UiContext.cs#L70-L101)。

### 7.2 弹射物选择、观察与动作顺序

每次需要观察时遍历 Main.projectile，候选必须 active、owner 为本地玩家、friendly、非 hostile、aiStyle 15。**先找与当前武器预期 shoot type 相同的候选；若没有，回退到数组顺序中的第一个合格本地链球。** 这是实际兜底，不应写成始终只控制当前武器对应的那一个实体。

观察结果：

- “命中”不是实际伤害事件：保存最多 **256** 项 `localNPCImmunity`，某项比上一观察值增大就视为命中变化；whoAmI／identity／type 变化会重置缓存。
- “碰撞”仅在合适飞行态与非零速度下，用当前弹射物的位置、速度、宽高调用原版 `Collision.TileCollision` 作下一步碰撞判断；方法／数据不可用时不报碰撞。
- “停滞”要求同一弹射物、ai0 接近 0、两个速度绝对值都小于 `0.001`，计数递增；否则归零。源码称 ticks，但累加发生在该观察路径被调用时，不应凭静态代码承诺严格现实帧数。

决策优先级完整如下：

1. 上一步 LaunchPress → 必须 LaunchRelease；
2. 上一步 RecallPress → 必须 RecallRelease；
3. 冷却中 → 不发新动作；
4. 没有弹射物且物品 ready → LaunchPress；
5. 有弹射物且 ai0 为服务归为返回／结束的 4、5、6 → 等待；
6. 命中变化 → RecallPress；
7. 碰撞 → RecallPress；
8. 停滞达到 18 → RecallPress；
9. 其他飞行中 → 等待。

每次释放后设置 5 tick 冷却。按下／释放都使用点击 scope，同时抑制右键并在 Postfix 恢复。该服务不直接改弹射物位置、速度、ai 或 NPC；发射、收回及其效果仍是原版输入结果。关开关、放开右键、换物品、UI／世界交互抢占会重置对应连击状态；它不保证每次 RecallPress 都真的回收，也没有“伤害已确认”的回执。

证据：Z [CreateDecision，215–291](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatFlailComboService.cs#L215-L291)，[弹射物选择与碰撞，229–382；命中／停滞，480–547](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatFlailRuntime.cs#L229-L382)。

### 7.3 与左键“自瞄链球释放辅助”分开

自瞄内部还有 `CombatAimFlailControlService`，不是右键连击开关的第二种模式：

- 物理左键仍保持时，保留原版原地旋转，不自动按下／松开以抢走蓄势。
- 观察到物理松开时提供 ReleaseToTarget，必要时对停滞链球重复释放。
- 当前实现的状态机只产生无动作或释放，不产生自动起手攻击。
- 参数是冷却 6 tick、停滞阈值 8、松开后的瞄准机会 3 tick、缓存释放瞄准最多 120 tick；右键连击还保留其按下瞄准短缓存，用于衔接释放。
- 空闲门位于读取武器、准备弹道和扫描弹射物之前。
- 不仅有 ItemCheck 内的 scoped release；运行更新的攻击抑制路径也可调用通用释放写入。因此不能一概写“自瞄从不写按键状态”。准确表述是：普通自瞄不主动起手攻击，但有链球释放与尾段控制。

当前 `.8` O-Projectile `AI_015_Flails` **44628–44650**：松开 channel 后，原版根据 `Main.MouseWorld` 计算抛出速度并设 netUpdate；**44667–44716**：飞行／返回中读取 `controlUseItem` 切换收回状态；**44725–44732**：特定状态下松开又触发下一阶段。它解释了为什么只在 ItemCheck 选准目标、不处理随后 Projectile AI 的鼠标读取，不能完整覆盖链球。

证据：Z [CombatAimFlailReleaseStateMachine，9–71](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimFlailReleaseStateMachine.cs#L9-L71)，[CombatAimFlailControlService，27–187、237–278、476–532](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimFlailControlService.cs#L27-L187)，[CombatAimFlailItemCheckTakeover，25–83](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimFlailItemCheckTakeover.cs#L25-L83)。

### 8.2 入口与状态机

运行前提：世界／本地活玩家有效；右键保持；左键必须读取成功且未按下；非聊天、NPC 对话、箱子、UI 捕获、旅行菜单；无世界右键交互；当前物品无原版右键语义；有两格候选。实际运行服务在“已有自己动作运行”提前返回之前重新做资格检查，失效时取消自己的来源。

提交 Normal、独占 RawInput 动作，pending 有效期 150 ms、单次执行超时 15 分钟，复制当时的间隔值并允许自瞄。修改 UI 间隔会影响新请求，不会偷偷改变已经开始的桥状态。

状态机：

1. **Idle**：物品 ready 才按下当前格；
2. **PressCurrent**：动画>2 继续保持；**动画恰好为 2 且 itemTime==0 才释放**；
3. 动画<=0、已经落到 1、itemTime 仍阻挡等情况归重置，不补一个迟到的“完美释放”；
4. **ReleaseCurrent**：必须等输入恢复成功后才计算／请求下一格；
5. **SwitchNext**：通过原版选槽请求更换，读到实际 selectedItem 等于期望格才算选槽确认；
6. **WaitInterval**：正间隔从确认时起等待所设 ticks，再等物品 ready；0 只取消额外间隔，仍保留释放、原版选槽确认与 ready 检查。

同一 GameUpdate 最多应用一次光剑桥输入，避免多次 ItemCheck 把按下／释放压在同一更新中。

证据：Z [运行门与请求，30–432](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatPhasebladeQuickSwitchRuntimeService.cs#L30-L432)，[Decide 与完整校验，132–259](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatPhasebladeQuickSwitchService.cs#L132-L259)，[桥的应用，192–354；恢复后选槽，529–652](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Actions/PhasebladeQuickSwitchBridge.cs#L192-L354)。

### 8.3 为什么有恢复后的合成输入

当前 `.8` 的相应原版链：

- O-Player **43856–43859**：`ShootsOnUseRelease` 且 `controlUseItem` 仍真时，阻止发射。
- O-Player **52937–52940**：这类使用还要求 itemTime==0。
- O-Player **49982–49987**：成功发射后把剩余动画转成 itemTime、清 itemAnimation，并走原版玩家同步。
- O-Player **53535–53540**：autoReuse 在某个边界可能重新使 `controlUseItem=true`。
- O-Projectile **39667–39695**：本地光剑弹射物在玩家仍持同类投射武器且 `controlUseItem=true` 时进入返回态并设置 netUpdate。

所以 Legacy 特意在 Prefix 动画为 2 时释放，并在 Postfix 恢复以后继续写 `controlUseItem=pressed、releaseUseItem=!pressed` 及 Main 左键对应值，右键保持抑制，供本轮后续 Projectile AI 读取。这个设计解决的是原版的分阶段读取，不等于输入完全局限在一个方法内。

### 8.4 停止、恢复及不能伪称的确认

右键释放、启用状态变更、上下文失效、玩家死亡、选槽／物品突变、候选不足、恢复失败、超时均可停止当前桥。已经按下时，`RequestStopOrComplete` 会先挂 StopRequested，等待下一次 ItemCheck 施加释放 scope；未处于按下则直接完成。Complete 还有清理 Postfix 残留输入的尝试。

**退出不恢复最初快捷栏格。** 已经切换就是实际选槽结果；也不取消已经由原版抛出的光剑，不撤销伤害或返还资源。输入应用／恢复次数、选槽实际读回是可记录的回执，没有逐次弹射物创建或命中回执。15 分钟是单个请求期限，不是把配置自动关闭；仍保持触发条件时后续服务有再次提交的条件。

该桥有请求 GUID、UTC 超时、选槽／type 检查，但没有 R 式玩家／世界／连接代际凭据。`TryReadFrame` 内把 Enabled、SafeContext 设真，依赖运行服务在外层复核；原版 UI／焦点边界与再次 ItemCheck 之间的时序仍需动态验证。尤其不能仅凭“停止会安排释放”证明退出世界后必定再有一个可用于释放的 ItemCheck。

## 9. 辅助瞄准：谁可用、看谁、先选谁

### 9.1 真实入口与武器资格

普通入口是本地玩家 ItemCheck 的战斗兜底，或明确 `AllowCombatAim` 的已授权使用动作。决策链是：

**配置／环境门→使用输入快照→当前物品→资格→目标观察及运动历史→范围→弹道资料→短缓存复核或重新评分→世界目标转屏幕目标→捕获原鼠标状态→临时写鼠标→原版使用→Postfix 恢复。**

自瞄本身不对普通武器自动产生起手攻击。它可以在保持使用时、允许的持续使用动画中，或合格的释放后保留窗口中提供瞄准。ItemUseBridge pending 默认阻挡，只有对应请求明确允许时例外。

武器资格：

- 当前 inventory 中选中的合法非负槽，物品正 type／stack；**这里不像左轮、转向、光剑那样只限 0–9**。
- 非 Coin Gun 必须 damage>0；Coin Gun 必须确认存在硬币弹药。
- 排除 `createTile/createWall>=0` 的放置物品。
- 排除 pick/axe/hammer/fishingPole 任一为正。
- 排除 `ammo>0 && useAmmo<=0` 的弹药本体。
- 排除 sentry 放置武器。
- 排除 `buffType>0` 且 summon 或伤害类型字符串属于 Summon／Minion／Sentry 的召唤放置武器。
- 其余须有 shoot>0、useAmmo>0、melee/ranged/magic/thrown 任一武器语义，或是 Coin Gun。

因此普通纯近战可进入，随后用保守中心；诊断武器家族可能因没有弹射物标为 Unsupported，不能反推普通自瞄资格拒绝。自瞄资格、诊断家族、弹道策略和持续鼠标资格是四个不同层次。

Coin Gun 优先按原版 ID 解析，后备 `905`；另保留名称含 Coin Gun 且 useAmmo 为硬币的后备识别。硬币存在性检查不读取银行或世界箱。资料读取和字段不支持导致的退化，不能等同当前原版确实支持每一种特殊武器。

证据：Z [CombatAimItemCheckService，49–342、587–645](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimItemCheckService.cs#L49-L342)，[CombatAimWeaponProfile，75–102、143–174](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimWeaponProfile.cs#L75-L174)。

### 9.3 NPC 完整过滤与兼容后备差异

目标来自 Main.npc。正常目标须 active，并拒绝：

- hide；
- life<=0；
- townNPC；
- friendly；
- chaseable 为假；
- lifeMax<=5；
- dontTakeDamage；
- immortal。

训练假人 type **488** 默认拒绝；打开“假人”后，**active 假人绕过上述普通敌怪过滤**。这不是把全世界友方单位都变成可瞄准对象。whoAmI 不可用时有数组索引后备；碰撞框缺失／无效时按位置与宽高构造最小有效框。资料还读取速度、AI、重力／碰撞、方向等用于预测。

强类型读取使用完整原版字段；反射后备路径要求 active、type、正常目标 life 可读，但 friendly/town/hide/dontTakeDamage/immortal 缺失记诊断并保留默认值，chaseable/lifeMax 缺失时跳过对应拒绝。这是兼容后备的宽松行为，不可表述为任何关键字段缺失都禁止攻击。

当前 `.8` O-NPC `CanBeChasedBy` **91012–91022** 的基础条件是 active、chaseable、lifeMax>5、非 friendly、非 dontTakeDamage、非 immortal（带其原版参数／调试例外）。Legacy 没有直接把该方法作为总判断，而且另加 hide／town／life 检查、另设假人例外。故 R 的 NPC 显名／稀有目标方向列表、原版追踪资格和战斗候选不能直接共享一份最终过滤结果。

### 9.4 候选数量、标记优先和最终排序

完整步骤：

1. 范围内候选按碰撞框距离升序，相同距离按 whoAmI 升序。
2. **只保留最近 32 个**，之后才作便宜评分。
3. 按便宜评分降序；平分仍按距离、whoAmI。
4. 通常取前 **4 个**作弹道、采样、视线精算。
5. **若 preferred 标记目标在这 32 个中，只取该目标一个就返回精算集合**；即使它后来所有采样点被拒绝，也不会在这一轮继续尝试其他三项。
6. 若 RequirePreferredTarget 且标记目标不在集合中，精算集合为空；未强制时才回退前 4 个。
7. 每个目标最多取当前框 6 点与预测框 6 点：中心、距各边 24% 的上／下／左／右中点、距范围中心最近的碰撞框点。
8. 预测框要求弹道已解、非保守中心、lead>0.01，预测中心相对当前中心至少移动 0.5 像素。
9. 选最终最高分采样点；近似平分时选距离较近的采样点，再选较小 whoAmI。

标记与实际开火不是两个完全独立的消费者：已有标记会约束下一轮攻击的精算候选。关闭“显示标记”也不能据此推定停止目标搜索，详见下一段生命周期。

证据：Z [Select，138–284；BuildExpensiveCandidates，350–385](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimTargetSelector.cs#L138-L284)，[CombatAimPredictedHitboxSampler，19–154](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimPredictedHitboxSampler.cs#L19-L154)。

### 9.5 两种策略的实际评分

以下完整列出改变选择顺序的项，便于后续讨论“最近”“准星方向”“优先可见”等产品语义。

记：

- `R`：范围中心到当前被评分点／框的距离；
- `Q`：玩家—鼠标射线到该点的距离；
- `P`：玩家到该点距离；
- `L`：旧锁定目标加分，符合时 90，否则 0；
- `M`：preferred 目标加分，符合时 250，否则 0；
- `T`：lifeMax>=2000 加 24，>=400 加 10，否则 0；
- “向前”是相对玩家—鼠标方向，不是简单玩家面向。

便宜评分：

| 策略／中心 | 公式 |
| --- | --- |
| Nearest | `10000-R+0.45L+M+T` |
| ClearLine／Player | 向前 +160，否则 -220；再加 `max(0,520-Q)*0.95 + max(0,900-R)*0.22 + L+M+T` |
| ClearLine／Cursor | 向前 +70，否则 -90；再加 `max(0,560-R)*0.82 + max(0,440-Q)*0.48 + L+M+T` |

采样点基础加分：中心 +180，四个内侧中点 +45，最近边界点 **-280**。

最终 Nearest 分数为 `10000-R+采样点基础加分+0.5L`。**该策略不调用视线检查**；源码虽保留“视线已清加 20”的分支，在正常 Nearest 这条路径并未取得该视线事实。它也不是严格最近 NPC：中心奖励、旧目标奖励、此前 32→4 筛选都会改变结果。

最终 ClearLine：

- 先调用 `Collision.CanHitLine`；**查询成功且 blocked 的点直接拒绝**。查询不可用不等于 blocked，仍可评分。
- 基础分为采样点基础加分+当前／预测空间奖励；
- 覆盖程度乘大型目标 58、其他 82；
- 减去离框中心比例×惩罚系数：低置信度 78；否则大型 20、其他 34；
- 确认视线通畅加 360，大型额外加 95；
- Player：向前 +190，否则 -250；再加 `max(0,520-Q)*1.05 + max(0,820-R)*0.22 + max(0,680-P)*0.12`；
- Cursor：向前 +80，否则 -110；再加 `max(0,600-R)*0.78 + max(0,420-Q)*0.52 + max(0,520-P)*0.08`；
- 加 T、L；
- 弹道有解 +50，无解 -30；保守中心 -20，其他 +20；
- 减 `min(80,重力补偿像素*0.15)` 与 `min(70,leadTicks*0.35)`。

“大型”在此评分层为碰撞框任一边>=96，或运动家族已为 LargeOrSegmented。预测空间奖励另为：当前点在低置信度时 +36；预测点 Unknown／VeryLow 为 `-220-min(90,D*0.3)`，Low 为 `-85-min(55,D*0.16)`，Medium 为 `82-min(35,D*0.06)`，更高为 `142-min(30,D*0.04)`；D 是预测目标点与最终瞄准点的距离。

由此可见 ClearLine 是“先排除已知遮挡，再综合射线、距离、碰撞框中心和预测可靠性”，不是严格“所有能看见的目标中最近”。视线只是线段查询，也不是整条弧线、真实碰撞或命中保证。

证据：Z [ScoreCheapCandidate、ScoreSample，388–599](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimTargetSelector.cs#L388-L599)，[空间／中心／采样偏置，668–756](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimTargetSelector.cs#L668-L756)。

## 10. 弹药、武器家族与运动预测

### 10.1 弹药资料的选择与速度

预测不调用 `Player.PickAmmo`；自行只读 inventory：

- 硬币弹药先看 **50–53**；
- 再看弹药格 **54–57**；
- 再看主范围 **0–53**；
- 普通弹药从 54–57 起，再 0–53；
- 范围内按槽位升序，取首个正 type、正 stack、ammo 匹配者；硬币允许其指定范围内按原版硬币 type 71–74 后备匹配。
- 不读银行、世界箱或虚空容器。

投射物 type：先武器 shoot；有 `AmmoID.Sets.SpecificLauncherAmmoProjectileMatches` 的特殊组合映射优先；火箭／溶液组合有相加路径；其他取弹药 shoot 的可用值。**预测资料里的 MoltenQuiver 转换角色是解释字段，并未在这条解析链完整重现木箭转火箭等所有原版替换。**

速度：

- 武器 shootSpeed 为基底，无效则 8；
- gunProj 只使用武器速度；其余加正弹药速度；
- 符合箭筒弹药且 MagicQuiver 时 ×1.1；
- Archery 对箭类且当前速度<20 时 ×1.2，并封顶 20；
- 结果<0.5 时回退 8；
- 每 tick 有效更新次数为 extraUpdates+1，MagicQuiver 对友方箭至少取 2；
- 有效速度是速度×有效更新次数。

缓存未命中时 Legacy 会创建临时 Projectile 并调用 `SetDefaults(type)` 读取类型资料，缓存按 type 保存，包括失败的空结果。**本调查没有执行这些调用，也没有把“临时对象”直接等同于全局无副作用函数。** 当前源码层的确定结论是预测不通过 PickAmmo 消耗真实弹药；临时 SetDefaults 的全部第三方 Hook／全局副作用不在本次已验证范围。

原版实际发射仍以 O-Player `ItemCheck_Shoot` **47459–47484** 的 PickAmmo、gunProj 特例等为准，所以“预测到一种弹药”不能替代“原版最后真的用了哪种弹药”的回执。

证据：Z [CombatAimProjectileProfile，276–381、473–615](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimProjectileProfile.cs#L276-L381)。

### 10.2 完整家族顺序与特殊集合

诊断家族的判定顺序为：悠悠球→光标生成爆发→双投射物→散射／多发→已识别回旋→天降→光标制导→追踪→光束→channel 且 aiStyle15 链球→aiStyle19 长矛→其余 aiStyle3 回旋→channel 弹射物→未归类特殊近战→直接弹射物→Unsupported。此顺序保留特例，不是产品应逐项提供开关的清单。

特殊弹道规则先于通用保守中心规则；其完整集合为：

| 集合 | 全部识别项 | 预测处理 |

### 10.3 预测窗口与完整运动类别

通用提前量上限：高速 24、普通 48、慢弹 96、重力 72、回旋去程 30、散射 18、常规退化 45、特殊通用 36 tick；重力补偿像素上限 180。固定点提前规则走自己的短提前，不等于所有武器都按同一线性截获公式。

## 11. 自瞄的标记、缓存、释放保留与弹射物阶段

### 11.1 标记是真实绘制消费者，也影响内部状态

目标更新通常按 **6 tick** 间隔重新观察／评分，设置签名变化可提前更新。关闭“瞄准标记”只隐藏绘制，**没有关闭这条搜索／评分链**。绘制先持有 `CurrentSelection`，近期 marker 缓存可覆盖它，再读目标身份。失效时调用共享 `CombatAimTargetLockService.Clear` 并把本次 selection 改为 TargetInvalid；缓存返回 clone，回退 `CurrentSelection` 才是共享选择引用，不能说每次 Draw 都修改核心 selection。证据补充：Z `CombatAutoAimService.cs:26–28`、`CombatAimDecisionCache.cs:72–82,111–122`、`CombatAimMarkerOverlay.cs:14–22,55–65,94–98`。核心失效不应依赖标记是否 Draw，后续领域更新须拥有清理，动作前复核仍保留。

标记画在 NPC 中心：优先使用原版 lock-on 光标纹理，围绕目标绘制三组旋转、轻微脉动的部件；失败时回退三个旋转十字与中心边框。中心距屏幕边界超过 96 像素不画。它不是屏外箭头，不是可点击目标清单，也没有单独的“点击锁敌”输入。

锁定来自 `MarkAttackQualified`，以 whoAmI+type 记录；同目标继续合格会刷新保留值，失去攻击资格时逐次递减，达到0清除。常量为18，但递减单位是 **MarkAttackDisqualified 调用次数**，不能写成精确18个游戏更新。它不是手动永久锁，也没有 NPC generation 校验。

证据：Z [CombatAutoAimService，36–134](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAutoAimService.cs#L36-L134)，[CombatAimMarkerOverlay，10–201](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/UI/CombatAimMarkerOverlay.cs#L10-L201)，[CombatAimTargetLockService，54–109](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimTargetLockService.cs#L54-L109)。

### 11.2 短缓存的具体有效边界

攻击选择缓存期限4 tick，marker近期选择期限6 tick。缓存键包含应用模式、物品 type／选槽／shoot／速度／弹药、channel、解析后的投射物与弹药资料、范围中心和模式、策略、两半径、标记设置、preferred 身份和运动置信度等。范围中心按16像素量化，速度按0.25，运动置信度按0.1。不是“同一种武器就一直用同一目标”。

缓存命中后仍刷新该目标的 whoAmI/type 和资格；中心每轴漂移须<=10像素，宽高差<=1。原先确认通畅且策略为 ClearLine 时再次检查视线，查询不可用或不再通畅都会拒绝这个缓存。视线帧缓存按当前 GameUpdate 清空，两个端点各按 **16像素**量化；同帧相近线段可共用结果，所以不能说是每个精确像素对都重新计算。

证据：Z [CombatAimDecisionCache](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimDecisionCache.cs)，[TryValidateCachedSelectionForUse 与 BuildSelectionCacheKey，786–944](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimItemCheckService.cs#L786-L944)，[CombatAimLineOfSight，20–99](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimLineOfSight.cs#L20-L99)。

### 11.3 释放后保留：保留瞄准，不是继续按住

释放保留默认8、最多20 tick，配置0关闭；单次记录最多应用2次。符合这条路径的武器为：

- ShootsOnUseRelease；
- channel；
- reuseDelay>0 且有 projectile／ranged／magic 语义；
- useAnimation 比 useTime 大6以上，且有相应弹射物／远程语义；
- noUseGraphic、shoot>0 且 ranged／magic／thrown。

放置物、工具／钓竿、弹药本体、哨兵和召唤放置仍排除。按住且取得目标时记录当前武器、槽位、目标 whoAmI/type、瞄准位置和设置；识别松开后，只尝试原先目标，不任意换一个新目标代替原先的释放意图。

严格重算失败时，有一个 **松开后0–2 tick、原范围再加96像素**的宽松旧瞄准回退；要求目标仍有效。宽松门只在 strictSelection 明确带有 `LineClearAvailable=true && LineClear=false` 时拒绝。严格选择若因所有点遮挡而整体得到 NoTarget，其结果未必保留该否定视线事实，因此**不能声称 ClearLine 在所有释放回退路径都绝不会保留被遮挡的旧瞄准**。

该功能不制造持续扣扳机；只是给最终松开动作提供短期瞄准。它与链球专用释放写入、光剑专用按下／释放状态机不同。

证据：Z [CombatAimItemCheckService.IsLikelyReleaseHoldWeapon，701–734](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimItemCheckService.cs#L701-L734)，[CombatAimReleaseHoldService，83–263、372–408](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAimReleaseHoldService.cs#L83-L263)。

### 11.4 持续鼠标覆盖的完整资格与时段

持续鼠标覆盖需要 `PersistentCursorAimEnabled` 且 Cursor 半径>0。完整资格按顺序：

1. 悠悠球：原版 yoyo sets 或 aiStyle99 识别，且能找到本地所有者的 active 悠悠球；没有合格活动悠悠球则不以“普通 channel”兜底；
2. 已识别链球释放类；
3. 明确允许 AI 鼠标覆盖的特殊武器，目前 Xenopopper、VortexBeater；
4. 其他合格 channel、shoot>0、useAmmo==0 的弹射武器；
5. 其余不允许这一层持续鼠标覆盖。

普通局部弹射物匹配还要求 active、本地 owner、friendly、非 hostile，type 匹配武器 shoot 或解析投射物 type。链球另要求 aiStyle15 及链球资格。特殊武器按武器辅助投射物角色识别，排除普通主弹药 projectile；Vortex 控制器 `615` 有非 friendly 的特例，但仍不允许 hostile。悠悠球的类型识别与活动对象检查是一套独立逻辑，不是魔法绳的固定21项名单。

优先安装 `Projectile.AI`；不可用时尝试悠悠球专用 AI；均失败才进入 MainUpdate 后备。后备仅对政策允许的悠悠球开放，已经有弹射物 Hook 时不再用 MainUpdate 覆盖悠悠球，普通 channel 不享有同样的主更新后备。

每个合格原版 AI／Kill scope：捕获鼠标→写入临时世界坐标→原版方法读取→配对 Postfix 恢复。没有直接改 projectile 的位置、速度、ai、owner、netUpdate；原版根据临时鼠标自行产生后续状态。Projectile scope 另有同一时刻只允许一个覆盖的门；蓝图宏伟蓝图覆盖作为内层，先恢复它，再恢复战斗鼠标。

### 11.5 两种尾段不是同一缓存

| 尾段 | 有效期与匹配 | 目标处理 |
| --- | --- | --- |
| 链球释放尾段 | 24 tick；没有有效 tick 时600 ms后备；局部 active、本地 owner、friendly、非 hostile、ai15、type 匹配 | 使用记录的旧释放坐标；这条尾段没有特殊武器尾段那套目标移动后重算／1像素回退门 |

## 12. 自动转向

### 12.1 资格、手动优先和目标回退

要求功能开启、世界／本地活玩家有效、UI 允许、快捷栏0–9持有符合战斗语义的物品，并有使用键或尚在 itemAnimation/itemTime 中。武器排除与普通自瞄一致：放置、工具／钓竿、弹药本体、哨兵、召唤放置，以及没有战斗语义者；Coin Gun 要有硬币。

自身动作仍在队列／执行、UseItem、ItemUseBridge、UseItemPulse 忙时不新增目标转向动作。

选择方向：

1. 使用键保持且 `controlLeft/controlRight` 只有一个为真时，手动左右方向优先；
2. 否则先直接采用当前有效 AutoAim selection；
3. 没有可用 selection 才重新读目标，沿用自瞄过滤／策略和可用范围；
4. 自瞄关闭时，用以玩家为中心 **36格**后备范围；
5. 原自瞄范围没有目标时，也可再试36格后备；
6. 无目标但能读到鼠标世界位置，则朝鼠标；
7. 目标水平差在±2像素内或已经朝向该侧，不改。

直接复用当前 selection 的分支没有像攻击缓存那样再读NPC身份；因此它是一份近期目标方向意图，不能表述为每次转向均已重新核实NPC存活。

### 12.2 执行、租期与回执

自动转向关开关的本服务分支只 ResetThrottle，并未 `CancelBySource`；请求中的槽位、type、目标身份作为metadata保存，`StartAutoFacing` 在实际第一次改方向前仅复核环境／本地玩家／请求方向，没有重新核对功能开关、该槽位／type或目标仍有效。槽位／type门在随后750 ms租期应用时才检查。故不能把“带这些metadata”写成首次执行前已做完整身份复核；外部队列拒绝／取消能否覆盖该窗口应按实际入口验证。证据：Z [CombatAutoFacingService，49–53、356–387](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAutoFacingService.cs#L356-L387)，[RawInputActionExecutor，30–37、115–170](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Actions/Executors/RawInputActionExecutor.cs#L115-L170)。

手动方向请求为 High，pending 有效期100 ms；目标／光标为 Low，250 ms；目标成功后设置10 tick冷却，手动分支不新增这种冷却。另外每次 ItemCheck 在其他战斗写入者前还有直接手动方向优先路径。

执行器调用 `TryChangePlayerDirection`，优先原版 `Player.ChangeDir(int)`。原方法不可用时可写 direction 字段后备；手动方向允许在原版方法没有使方向生效后再用字段后备。随后建立 **750 ms** ItemCheck 方向覆盖租期，凭请求GUID、选槽、物品type保持短时方向；槽位／type变化或到期取消。该租期的应用 helper 本身不检查当前功能开关；不能把禁用后的某次后台服务跳过，等同于所有已建立租期立即撤销。

当前 `.8` O-Player `ChangeDir` **42408–42432 起**，除改 direction，还处理吊索姿态／可能的水平位置调整、手臂旋转、itemRotation 与 itemLocation。所以准确说法是辅助不写移动按键，不应进一步声称原版 ChangeDir 完全不可能影响位置。

回执有一个具体旧缺口：`Movement.Direction.cs` **79–82** 方向读回失败时，把 afterDirection 直接赋为目标方向并返回成功；执行器再用 afterDirection==目标记 Succeeded。因此此状态并非总有真实读回证据。朝向不在结束时恢复旧值，无弹药／材料费用，没有服务端独立回执。

证据：Z [CombatAutoFacingService，42–294、390–558、595–685](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAutoFacingService.cs#L595-L685)，[RawInputActionExecutor.StartAutoFacing，115–170](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Actions/Executors/RawInputActionExecutor.cs#L115-L170)，[Movement.Direction，31–98](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/TerrariaInputCompat.Movement.Direction.cs#L31-L98)，[Movement.AutoFacing，8–149](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/TerrariaInputCompat.Movement.AutoFacing.cs#L8-L149)。

## 13. 哥布林必死：仅恢复可受击范围

### 13.1 唯一目标与真实动作

唯一条件是 HookReady、开关开启、NPC type==**107（Goblin Tinkerer）**。代码虽声明105（Bound Goblin），判定不接受它。没有寻找最近哥布林、移到NPC身边、自动攻击、瞬杀、写life、提高伤害、改friendly、改dontTakeDamage或替换AI。

实际补丁是两处窄门：

- `Player.ProcessHitAgainstNPC(Item, Rectangle, int, float, int)` 中原本因友方城镇NPC而 return 的位置，107 可继续；
- `Projectile.Damage_PVE_Inner(int, NPC, Rectangle, float, int[], ref bool)` 中友方资格布尔门，107 可通过该门。

两处补丁均定位成功才 HookReady=true；Harmony／原方法／IL锚点缺失或部分失败则不开启该功能。IL锚点依赖当前友方／城镇判断、物品或弹射物特殊常量等结构，不能因为旧测试通过就声称未来版本自动兼容。

证据：Z [CombatGoblinExecutionCompat，8–38](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/CombatGoblinExecutionCompat.cs#L8-L38)，[GoblinExecutionHookInstaller，28–147](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Hooks/GoblinExecutionHookInstaller.cs#L28-L147)，[两处 Transpiler，47–110](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Hooks/GoblinExecutionHookCallbacks.cs#L47-L110)。

### 13.2 原版剩余门与相邻关系

当前 `.8` O-Player **44611–44640** 仍保留 dontTakeDamage、可被该玩家／弹射物命中条件、碰撞框相交和视线等；O-Projectile **12572–12678** 仍保留 active、正damage、各类免疫计时、dontTakeDamage、所有者权限／ownerHitCheck与碰撞等。本开关只放宽其中友方门，不保证任何武器在任何距离都能造成伤害。

普通自瞄仍排除 friendly/townNPC，因此**打开该开关不会让自瞄主动瞄哥布林**。自动捕捉、生物显名、NPC服务对象和原版受击是不同政策消费者，不能把107的窄例外传播为“所有友方可攻击”。

predicate没有 localPlayer／netMode 限制；加载它的宿主内满足签名的命中流程都可经过这个窄门。它没有服务端协商或服务端成功回执；普通客户端是否足以在各种多人服务器上实现最终受击、服务器是否重新拒绝，需动态证据。当前结论仅是两处本地原版调用门已被明确定位，不把功能注册表的多人元数据作为通过证明。




## 14. “自动汇报”实际观察什么、发送什么

### 14.1 入口、基线、去重和失败顺序

F5 战斗页开关或功能快捷键修改 `CombatAutoBossDamageReportEnabled`。调度每 **15 tick** 调用服务，所属 lane 是 **ReadOnlyDisplay**。这个名字不代表功能无外部效果：服务会直接调用共用聊天发送器。

服务的实际流程：

1. 开启且在世界中，读取 `NPCDamageTracker.RecentAttempts()`；
2. 每个非空 tracker 用 `RuntimeHelpers.GetHashCode(对象)` 转成 int 标识；
3. 删除“已见集合”里现在已不在近期列表的标识；
4. 第一次有效观察把现有列表全部记作基线，**不发送**；第一次为空也会设置 Initialized；
5. 后续每发现新标识，先加入已见集合；
6. 本轮有一个或多个新标识，**只发送一次 `/bossdamage`**；
7. 没有新标识不发送；读取失败发布 unavailable，并保留此前状态。

标识是进程内对象哈希，不是Boss类型、战斗GUID、内容哈希、玩家／世界代际或跨存档ID。哈希碰撞可能漏认一次新对象，这是标识方式带来的推论；不把它说成已出现的实机故障。

**加入已见集合发生在发送之前。** 发送失败只记诊断并作10秒日志节流；同一批 unchanged tracker 不会在下一轮自动重试。多个新记录只记第一个 ID 作诊断，并未把它传给原版命令用于限制输出内容。

证据：Z [CombatAutoBossDamageReportService.Tick、Evaluate、读取对象ID，28–218](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Automation/Combat/CombatAutoBossDamageReportService.cs#L28-L218)，[调度定义与调用，120–126、558–562](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Runtime/RuntimeAutomationDispatcher.cs#L120-L126)。

### 14.2 “战斗结束”不是只看Boss死亡

当前 `.8` 原版完整规则：

- 普通伤害入口先把 realLife 指向的分体归到主NPC，须 active、life>0；
- 查找已有能包含该NPC的 tracker；
- 没有时，只有 NPC.boss 或自定义Boss定义才创建 BossDamageTracker；
- 记录本次伤害时限制为不超过该NPC剩余life；
- Boss tracker 依据相应 type／复合类型是否还在 `NPC.npcsFoundForCheckActive` 中决定仍活跃；
- 不再活跃就 Stop；只要有伤害信用记录便加入近期列表；
- `BossKilled` 只影响“击败／逃离”报告文字，**不是 Stop 的必要条件**。

所以造成过伤害后Boss逃离、消失也会形成近期记录，不能把触发点简写为“击杀成功”。同类型／复合类型是归组依据，不是每一个出生实体独立GUID；同类并存可能归入同一 tracker，这与NPC个体锁定身份不同。

Legacy 没有再筛“这条 tracker 必须是Boss类”。所以**名为“自动Boss汇报”的功能也会对进入近期列表的这些事件触发**。这不是本次建议扩展的新能力，是被观察列表的现有范围。

### 14.4 原版保留、输出排序与玩家身份

近期列表最多3条，加入顺序为结束顺序；超出删最早项。更新时若有多于1条，最旧项距离最后一击超过54000 tick会移除；**至少保留最后一条，不是每条15分钟后一律消失**。

报告内容来自原版，不是 Legacy 自己统计 DPS 或拼排行榜：

- 伤害归信用记录；默认 `UseExpandedSources=false`，按玩家 **name 字符串**归组；
- 有效 owner 在0–254；其他归世界伤害项；
- 开启原版扩展来源时按 name+source 分组；
- 伤害降序，平分再按命中次数降序；并没有附加字母序或玩家槽号作为最终稳定平分键；
- 百分比先向下取整，再按剩余小数分配到总和100；
- 耗时是 tracker 记录的最后命中 tick／60，不是现实墙钟精确计时；
- 对每个接收玩家生成报告时，名字相同的行高亮；
- 扩展来源模式才追加命中次数文字。

这连接到快速改名：**同名玩家可归入同一名字条目；同一玩家中途改名可分成两个名字条目。** 不能把表里的名字称为稳定账号／存档身份，也不能直接拿它与 R 的世界／会话身份拼接。此处是当前原版统计政策的事实，不是推荐给 R 的新身份模型。

原版证据：O-Damage **28–39、100–104、131–139、267–297、319–440**。

### 14.5 一次命令实际向谁输出什么

共享发送器：

- netMode0：`CreateOutgoingMessage` 后在本地 `Commands.ProcessIncomingMessage`；
- netMode1：`ChatHelper.SendChatMessageFromClient`；
- 其他 netMode：返回 unsupported；
- 返回true仅表示调用没有抛出异常，不是服务器ACK、消息被接受或所有接收者已看见。

当前 `.8` O-Command **11–23** 实际遍历 **所有 RecentAttempts**，并对所有 active 玩家0–254分别发送报告。命令并没有“只发新增的那一次战斗”的参数。

因此：近期列表已有A，新结束B触发一次命令时，输出的是 **A和B**；以后C触发，可能再次输出A、B、C。Legacy 的对象去重仅限制“何时发命令”，不限制原版命令重新展示已保留的旧报告。多个安装者若都能触发，原代码也没有跨客户端协调去重。

自动汇报与快捷宣告共用的是这段发送出口；前者没有复用快捷宣告的对象识别、目标文本或其用户触发冷却，也不经过 ItemUseBridge 或战斗动作队列。它被放在 ReadOnlyDisplay lane，世界内即使聊天／操作焦点门未通过，该 lane 仍可能调度；不能从“战斗动作因UI暂停”推出“汇报也暂停”。

证据：Z [TerrariaChatAnnouncementCompat.TrySendChat，22–51](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Compat/TerrariaChatAnnouncementCompat.cs#L22-L51)，[ShouldDispatchLane，648–678](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Runtime/RuntimeAutomationDispatcher.cs#L648-L678)；原版 O-Command **11–23**。

### 14.6 当前 `.8` 多人触发链有明确缺口

**可发送客户端聊天命令，不等于普通联机客户端会自动发现新战斗统计。**

当前 `.8` O-NPC `StrikeNPC` **82073–82078**，只有 `Main.netMode !=1` 才向 NPCDamageTracker 加普通命中伤害；持续伤害路径 **92859–92864** 也有相同多人客户端排除。南瓜月／霜月 tracker 的开始路径也位于相应非客户端条件。Legacy 自动汇报读取的却是**本进程本地 RecentAttempts**。

本次还定向搜索了当前静态 MessageBuffer、NetMessage，没有发现以 NPCDamageTracker 名义把服务器 tracker 复制到普通客户端的直接通路。该搜索不能排除所有可能的间接机制，但与上述伤害入口一起，已足以否定“调用聊天发送成功就证明普通客户端自动触发完整可用”。

精确结论：

- 单人端：本地原版建立统计→近期新增→命令本地处理，静态链闭合；
- 普通 netMode1 客户端：普通Boss伤害统计在本地的产生／复制链未闭合，不能证明自动触发；
- netMode2 服务器：即使有 tracker，共享发送器本身拒绝该 netMode；
- 玩家手动输入 `/bossdamage` 可以走原版服务器命令，这与“本地自动发现何时该发送”是两件事；
- 仍需所有者明确 R 的目标多人拓扑，再实现与验证相应观察／发送契约。

定向网络静态件：Terraria.MessageBuffer.cs（`.local/death-history-world-time/Terraria.MessageBuffer.cs`），SHA `9BB43745EAACF5E9866A4D3BE8EBAC8C9FBA1C1A24739AFB39BC750E5443AD7C`；Terraria.NetMessage.cs（`.local/研究/late-reply-origin-8a1e504/Terraria.NetMessage.cs`），SHA `B0B3E2424B3B5F7BC708BAEEA5411F7C46AE668DF572F349D3ED4D42E76B542B`。静态没有发现的通路在报告中保留为具体证据缺口，不当作动态反证。

### 14.7 生命周期还有一个入口与服务不一致

服务内 `!enabled` 和 `!inWorld` 都清 State；但生产调度先把 `enabled && laneAllowed` 送入 scheduler，再在 lane不允许时直接返回false。因此退出世界时，即使 scheduler 产生一次 DisableCleanup，也可能被 lane门挡住，服务内部 outOfWorld 清理根本未运行，而且这个关闭边沿已被调度器消费。

这形成具体静态反例：旧世界已 Initialized，经过世界外阶段未调用清理，进入新世界首次已有近期对象时，可走“新对象发送”而非“首次基线”。本次已读自动汇报生产入口未找到另一条按玩家／世界／连接代际重置这份私有状态的通路。应把它作为生命周期缺口核验，不能因为纯函数测试直接调用过 outOfWorld 分支，就说生产切世界已经验证安全。

证据：Z [RuntimeAutomationDispatcher.PerformanceMeasurement.ShouldRun，119–151](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Runtime/RuntimeAutomationDispatcher.PerformanceMeasurement.cs#L119-L151)，[RuntimeServiceScheduler.Evaluate，60–102](https://github.com/Kuroneko2020/JueMingZ/blob/6ac6356c0c564f43284590c168855e96c50e13f7/src/JueMingZ/Runtime/RuntimeServiceScheduler.cs#L60-L102)，Z 汇报服务 **123–146**。

### 15.2 与其余专题的实际连接

1. **钓鱼**：自动连点硬排钓竿；自瞄／转向／链球排fishingPole。钓鱼收杆、切杆、重抛本身依赖ItemCheck与选槽，因此必须在动作所有权层让路，不能只靠“现在通常拿的不是枪”避免冲突。
2. **捕捉、收获、挖矿、蓝图**：Z 已有真实仲裁顺序，见§3。R应保留“一次入口只有一个使用输入所有者”的能力，旧枚举顺序不是永久架构合同。蓝图宏伟蓝图还与Projectile鼠标覆盖同处一个Hook阶段，存在真实内外层恢复关系。
3. **快捷用物、回血／回蓝／增益**：用物请求可以占ItemUseBridge；恢复旧选槽、持续战斗输入、原版魔力自动补充可能同时出现。战斗模块不能把原版CheckMana／QuickMana带来的副作用归为自己直接支付或自己已验证成功。
4. **装备提示／自动配装**：提示观察已装备物；魔法绳资格读取实际magicString效果；自瞄预测读取箭筒、Archery等效果。它们不自动获得换装权。临时钓鱼配装改变这些事实时，战斗应重新读当前能力，不能靠旧快照继续使用不存在的效果。
5. **快速改名／身份／战斗记录**：原版报告按name归组，R会话按对象和连接代际；这是确实存在的两种身份，不应相互替代。快速改名的原版文件保存语义留在《钓鱼与配装》，自动汇报没有另存一份玩家身份数据库。
6. **地图／方向**：自瞄范围是战斗中心与屏幕／鼠标范围，不是地图搜索范围；标记是屏上目标环，不是世界持久地图标记或传送／导航能力。

## 16. 高频工作量、持久化与失败路径

下表是静态成本结构，不是FPS结论、实机性能收益或修复优先级结论。

| 能力／状态 | 关闭／空闲 | 活跃、变化或失败时的实际工作 |
| --- | --- | --- |
| 自动连点 | Hook仍到达，早期看开关并记录决策；不等于完全零成本 | 每次可接管ItemCheck读取选槽／物品／原版开关、决策、捕获／恢复输入及诊断快照 |
| 完美左轮 | 后台Tick为空；Prefix guard仍处理关闭／清安排 | 持有2269时按ItemCheck读取计数、计算准确下一tick、scope恢复；没有逐tick全NPC扫描 |
| 魔法绳 | 调度开关／来源忙门；无请求时不保持执行桥 | 每次桥Update和ItemCheck检查玩家、按下、slot/type及超时；脉冲计数和快照；每次请求分配执行状态 |
| 链球连击 | 未启用／未按右键在武器和projectile重工作前退出 | 需要时扫描Main.projectile；逐对象尝试读取快照再筛；最多256项免疫比较；碰撞查询；状态／诊断 |
| 光剑快切 | 未启用取消自己的来源；右键／安全门控制进入 | 外层运行服务和桥各有验证；检查固定10格；每更新至多一次ItemCheck输入；等待选槽确认时可重复请求／观察；单请求持有10格缓冲 |
| 自瞄目标更新 | 半径0在评分／视线前退出；隐藏标记不会关闭搜索 | 通常6tick刷新NPC；攻击路径可能另读NPC和弹药、准备弹道后才查选择缓存；保留32、精算通常4、每目标最多12点；不能把“缓存命中”解释为前置观察全省略 |
| 自瞄投射资料／悠悠球 | 类型缓存降低重复SetDefaults | 首遇type创建临时Projectile并SetDefaults；悠悠球活动性还扫projectile；失败资料可被缓存，若环境后续变化需明确失效策略 |
| 持续鼠标／尾段 | 无资格／关闭时早退 | 每个相关Projectile AI或Kill仍检查资格、局部所有权、缓存、鼠标捕获／恢复；特殊尾段目标移动会重算，不仅是读旧坐标 |
| 标记绘制 | 无标记开关／目标时退出 | 每次绘制刷新该目标和屏幕状态，三组动画纹理或回退图元；可清锁／改选择状态 |
| 自动转向 | 调度关闭通常只需关闭边沿清节流 | 即便10tick冷却中，前面的队列、玩家、UI、profile检查已做；无当前selection时可重新读整组目标并评分；另有每ItemCheck手动方向检查 |
| 哥布林窄门 | 补丁仍安装，helper先读HookReady／开关 | 仅命中原版对应友方门时检查107；没有独立每帧搜NPC任务 |
| 自动汇报 | 稳定关闭由scheduler跳过；关闭清理仍受lane时序限制 | 每15tick新建小ID列表、读近期对象、集合去重／修剪；新记录才发命令；原版每条近期×每个active玩家生成并发送报告，通常上限3×P份，旧记录也重建 |

Z 调度器的“关闭一次清理”是状态机行为：首次关闭只记录false；从开启到关闭产生一次cleanup；稳定关闭不再运行；从关闭到开启立即运行；之后遵守cadence或tick倒退处理。**lane或上游input门可能阻止cleanup真正到达服务**，已在§11、§14给出具体路径。

保存与I/O：

- 用户开关／参数通过AppSettings和SaveAll持久化；八项能力没有各自战斗资产文件。
- 运行中的攻击安排、选槽状态、目标历史、锁、尾段、对象哈希去重均是内存状态，不是跨存档继续执行的任务合同。
- 诊断快照、日志和错误节流仍是生产观察成本；节流不是“没有锁／字符串／分配”。本轮不恢复历史常驻测量体系，也不运行基准。
- 原版战斗、耗弹、魔力、物品消耗和聊天输出一旦发生，不因Mod后来scope失败而回滚。恢复应保护输入／选槽／所有权，不应伪造“退款”或撤回已经命中的伤害。
- 构造临时原版Projectile读默认值的冷成本与可能兼容Hook，应与真实投射物更新分开计量；不能用静态代码行数证明FPS影响。

## 18. 建议分组与少量产品决定

以下是调查后的建议，不是新功能合同或移植授权：

- **输入辅助组**：自动连点、左轮、魔法绳、链球连击、光剑快切。共享本地输入资格、单一写入者、阶段恢复／真实停止；专用武器状态机分开。
- **目标与鼠标组**：自瞄、标记、弹道资料、运动历史、释放保留、局部Projectile鼠标覆盖；自动转向作为另一个消费者，保持其独立启用与手动优先。
- **哥布林窄规则组**：独立兼容门，保留107可受击的原意，不扩成自动击杀。
- **战斗汇报组**：战斗记录观察、结束／事件政策、去重、接收范围、原版命令发送。与快捷宣告仅共享窄发送出口。
- 装备提示继续使用R已接受能力；不借本组再做一遍。

值得所有者后续集中决定的产品问题：

1. 自动连点是否保留“无damage要求、可能使用消耗品／放置品”的旧范围；UI应准确称物品使用辅助，还是收窄成战斗武器能力。
2. 自瞄是否保留旧的加权Nearest、preferred只精算一个、未知LOS可继续、释放宽松回退等可感知选择；Player默认关闭却禁用半径滑块的开启流程应怎样呈现。
3. 光剑停止后保留最后槽是否符合预期；应如何向玩家说明0间隔仍等原版ready和选槽确认。
4. 自动汇报要“Boss或含六类事件”“击败或含逃离”“只展示新战斗或调用原版全部近期”“仅自己看或广播给所有玩家”；目标多人拓扑必须一并明确。
5. 战斗快捷键是只切开关，还是将某些长按动作纳入R公共动作绑定。原有F5／Esc／焦点重新释放规则继续有效，不需要重新决定已接受的公共输入底线。

代理应自行承担的普通技术工作，不转嫁所有者：

- 使用R会话／NPC代际和现有输入门；
- 定义输入、选槽、鼠标等有限所有权与异常恢复；
- 区分请求已提交、输入已应用、原版结果已观察和服务器已确认；
- 消除“读回失败却成功”、发送前去重导致无重试等具体实现陷阱；
- 按真实消费者增加最小观察需求，限制高频扫描／缓存失效与日志成本；
- 对当前原版版本完成实际Hook入口兼容验证。

### 19.3 保留的具体缺口
