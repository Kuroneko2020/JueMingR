### 1.1 实际控制入口

玩家在 F5 蓝图页面开启“自动放置”，默认关闭；该开关有统一主开关快捷键入口。手持凝胶快捷栏控制资产／编辑动作，不是施工必需一直手持的工具。实际施工会根据目标寻找要使用的物品、工具和材料。

F5 的开关处理修改 `BlueprintAutoPlacementEnabled` 并保存配置；它不是“一次只放这一张蓝图”的命令。开启后，控制器从当前世界有效投影生成候选，涵盖可见实例中当前可处理的缺失层。隐藏、覆盖、擦除、完成记录和冲突状态共同决定哪些层进入有效工作集。

证据：Z `src/JueMingZ/UI/Legacy/LegacyMainWindow.Blueprint.cs:193–205`；`src/JueMingZ/Input/LegacyUiActionService.Blueprint.cs:274–283、1071–1095`；`src/JueMingZ/Input/FeatureToggleHotkeyService.cs:678`；`src/JueMingZ/Automation/Blueprint/BlueprintAutoPlacementService.cs:868–940、1030–1076`。

### 1.2 产品结果与实现边界

这条施工链的目标是由本地玩家通过原版物品使用完成建筑操作：

- 不移动玩家来追目标；
- 不扩大原版交互距离；
- 不把目标 Tile 属性直接写成期望值来代替物品使用；
- 不把冲突格的建筑自动拆掉以腾位置；
- 不因为投影是红色就授权挖块、挖墙或拆线；
- 工具缺失只应阻挡相应候选，不应抹掉其它合法本体或候选；
- 请求进入队列、进入 `ItemCheck`、物品动画发生、材料变化与目标完成是不同阶段。

固定 Catalog 的 `Implemented(false)` 和多人 `Unknown` 不能否定真实生产执行器，也不能代替逐能力和多人验收。现有生产队列实际注册了 `BlueprintAutoPlaceActionExecutor`。

证据：Z `src/JueMingZ/Features/Catalog/BlueprintFeatureRegistrar.cs:8–21`；`src/JueMingZ/Actions/InputActionQueue.cs:553`；`src/JueMingZ/Actions/Executors/BlueprintAutoPlaceActionExecutor.cs:22–212、953–1167`。

## 2. 从有效投影到一次施工请求

### 2.1 调度与候选来源

Runtime 的蓝图自动放置调度间隔为每个调度 tick 一次，运行条件为自动放置开关开启，或者蓝图来源仍有待处理动作。自动放置关闭时，候选解析在取得投影前返回；开启时则先解析投影和材料，再检查是否允许提交世界输入。

这一先后次序很重要：世界 UI 阻挡会阻止提交，但不等于这一轮已经省掉投影、材料及候选解析。`TickCore` 先调用 `ResolveCandidate`，随后才检查 `IsBlockedForWorldInput`。

候选只从 `Missing` 层产生；`Fulfilled`、`Completed`、`Conflict`、`Unavailable` 和其它非缺失状态分别跳过。完整对象组也有阻挡检查。材料或库存读取失败则没有正常候选，不以空数量假装成功。

证据：Z `src/JueMingZ/Runtime/RuntimeAutomationDispatcher.cs:85–86、411–420`；`src/JueMingZ/Automation/Blueprint/BlueprintAutoPlacementService.cs`，`TickCore`，547–583；`ResolveCandidate`，868–940；`BuildCandidates`，1030–1076。

### 2.2 候选顺序

排序首先按实例层级从高到低，再在同一层级内按阶段：

1. 普通 Tile；
2. 墙；
3. 对象／家具；
4. 电线；
5. 制动器；
6. 涂漆、涂层、锤击、致动等后处理。

之后依次按世界 Y、世界 X、层种类字符串、实例 ID 排序。

因此，不能把它描述成“整个世界的所有方块永远先于所有家具和后处理”：实例层级的优先级高于施工阶段。失败目标会进入与投影签名绑定的候选暂避集合，选择器优先寻找其它可执行候选；没有其它项时仍有回退和同一请求防重逻辑。

证据：Z `BlueprintAutoPlacementService.cs`，`SelectFrontierCandidate`，957–1027；`CompareCandidates`，2799–2820；`ResolvePlacementPhase`，2845–2886。

### 2.3 队列协议与资源争用

每次请求：

- 类型为 `BlueprintAutoPlace`；
- 来源为 `BlueprintMain`；
- 优先级低；
- 重复策略为 `CoalescePending`；
- 队列等待超时 750 毫秒；
- 普通执行超时 1,500 毫秒；
- 宏伟蓝图执行超时 4,000 毫秒；
- `IsExclusive = false`，但仍声明实际占用通道。

蓝图占用鼠标目标、物品使用、物品槽、快捷栏选择和 `ItemUseBridge` 通道。`IsExclusive = false` 不意味着它能与所有其它物品使用动作任意并行。旧队列本身只有一个 `_running` 动作，调度不会在这里抢占已运行动作；它同时保留通道仲裁和动作结束后的清理租约。

请求携带实例、层级、世界／相对坐标、内容、样式、材料、对象身份、工具槽、线色、后处理状态等元数据。它不是只传一个鼠标坐标，然后期待执行器猜出目标。

证据：Z `BlueprintAutoPlacementService.cs:374–388、2637–2734`；`src/JueMingZ/Actions/Channels/InputActionChannelResolver.cs:123–130`；`src/JueMingZ/Actions/InputActionQueue.Execution.cs:11–94`；`src/JueMingZ/Actions/InputActionQueue.cs:205–243`；`src/JueMingZ/Actions/InputActionQueue.CleanupLease.cs:9、76–116`。

### 2.4 防重、失败暂避与有限重试

同一个候选的 admission key 和投影签名若已经提交，控制器通常等待投影变化，不立即重复提交。失败或未验证结果会令目标让位给其它候选。

例外与上限：

- 普通墙在“已尝试但未验证”后可以有一次有界重试；
- 若失败原因是 `wallFrameRefreshFailed:`，不因此进入该墙重试；
- 后处理同一 admission key 最多接受 8 次提交；
- 锤击同一目标形状最多接受 6 次提交，锤击计数键刻意不包含当前斜坡／半砖状态，避免每次形状变化都重置预算；
- 成功会清除对应暂避和提交限制；
- 投影签名改变会清空候选暂避集合，不等于自动清空所有锤击目标计数。

admission key 包含目标和当前线色／涂层／形状／失活状态；电线还附工具库存签名、计划颜色和工具槽，后处理还附工具签名及能力。普通候选键没有直接包含玩家位置、原材料库存或最终选中的替代材料。这一差异关系到失败后能否在条件改变时重新尝试，后续成本与失败节会单列，不能笼统声称“所有环境改变都会自动重试”。

证据：Z `BlueprintAutoPlacementService.cs:452–478、586–645、655–839、1193–1234、2743–2796`。

## 3. 执行前复核、物品使用与结果确认

### 3.1 执行前重新查目标

执行器启动时重新检查世界／UI 是否阻挡，再核对候选属于受支持能力，强制刷新投影并寻找当前目标层。

非电线目标匹配包括实例 ID、层级、世界坐标、层种类、样式和内容 ID。电线匹配使用原目标线色集合，因为其“当前缺失颜色”会随每次成功变化。已经完成、已消失、被隐藏／覆盖或不再是 `Missing` 的目标不会继续当作原候选执行。

电线请求还要证明：这次请求颜色仍是当前缺失颜色的非空子集，且工具模式与颜色映射一致；不允许把已经补好的线色再次当成待加颜色。

证据：Z `src/JueMingZ/Actions/Executors/BlueprintAutoPlaceActionExecutor.cs`，`Start`，22–111；`TryResolveCurrentLayer` / `MatchesCandidate`，309–367；`IsCurrentWireRequestValid`，410–444。

### 3.2 材料、实际使用物品与工具是三个角色

材料解析前篇已经区分主背包统计 `0–57` 与虚空袋。执行器实际重新寻找的范围是主背包 `0–49`：

- 普通材料要求某个匹配槽本身具有至少所需数量；
- 计划电线有专门的聚合材料查找路径；
- 实际使用物品与材料不同，例如灵活放置魔杖，必须另在 `0–49` 找到真正要拿来使用的物品；
- 机械工具和后处理工具要验证之前计划的工具槽及能力；
- 无消耗材料的后处理必须保持材料 ID 和数量为零，不能把锤子或刮漆器算成会被吃掉的材料。

候选阶段的 `mainAvailability` 来自材料清单的 `MainInventoryStack`，因此候选资格与执行槽查找仍是不同关口。物品只在统计范围后八格、只在虚空袋、已经被玩家搬走，或原计划工具发生变化时，都不能因为上一份材料清单显示足够而绕过执行检查。

证据：Z `BlueprintAutoPlacementService.cs:1629–1662`；`BlueprintAutoPlaceActionExecutor.cs:977–1046、1319–1473`。电线聚合和工具细则在后续专节展开。

### 3.3 范围与完整对象鼠标目标

已解析完整对象的实际鼠标 Tile 目标，会用当前物品的 `tileBoost + player.blockRange` 调用原版 `IsInTileInteractionRange(..., TileReachCheckSettings.Simple, ...)` 预检。检查的是对象规划得到的放置目标，不是随便选一个可见子格。

预检不移动玩家、不扩大范围。通过这一步也不代表原版后续所有放置条件都通过；原版 `ItemCheck` 仍拥有真实物品使用、对象放置和附带的 TileEntity 创建／同步流程。

证据：Z `BlueprintAutoPlaceActionExecutor.cs:1049–1060、1164–1210`。普通块、墙及特殊对象的原版路径将在各能力节分别核对。

### 3.4 短时输入覆盖及恢复

普通施工把请求交给 `ItemUseBridge`，等待本地玩家真正进入 `Player.ItemCheck`：

- 等待物品动画、物品时间和复用延迟归零；蓝图没有开启提前使用窗口；
- 玩家必须激活、未死亡、非幽灵；
- 消费时重新读取目标槽，验证物品类型和正数量；
- 需要时先处理 `delayUseItem` 的释放等待；
- 在 `ItemCheck` 的短窗口选择使用物品、设置鼠标世界目标、压制智能交互；
- 按请求临时设置灵活魔杖 cycle offset 或机械工具模式；
- 设置物品使用输入，让原版方法执行；
- 后置处理先恢复主要输入、选槽、channel、魔杖偏移及机械模式，并通知 bridge；独立鼠标 scope 在后续代码恢复。不能把 bridge 收到通知当作所有恢复都已成功。

有两项不能夸大为完整的人为操作保护：

1. 蓝图请求设置 `SkipSelectInItemCheck = false`，实际消费时不会要求玩家仍保持开始请求时的选槽；恢复选槽 override 保存的是执行器开始时的原槽。玩家在等待窗口主动换槽是否被旧恢复覆盖，需要按此实际链处理。
2. 后置恢复返回值并没有全部升级为动作失败；异常会被记录和吞并。Hook 安装只接 Prefix／Postfix，没有在该安装器中看到额外 Finalizer。不能以“写了恢复函数”宣称原版异常等全部路径均已证明恢复成功。

证据：Z `BlueprintAutoPlaceActionExecutor.cs:1120–1158`；`src/JueMingZ/Actions/ItemUseBridge.cs:216–382`；`src/JueMingZ/Hooks/ItemUseHookCallbacks.cs:69–113、204–241、355–409`；`src/JueMingZ/Compat/TerrariaInputCompat.UseItem.ItemCheckBridge.cs:114–198、373–449`；`src/JueMingZ/Hooks/ItemUseHookInstaller.cs:81–94`。

### 3.5 “原版用了物品”与“目标完成”分别确认

bridge 的成功依据是原版物品使用相关状态发生可观察变化；这本身不证明建筑目标完成。蓝图执行器等待 bridge 终态，再强制刷新投影：

- 普通目标要成为 `Fulfilled` 或 `Completed`；
- 墙目标先确认投影，再刷新周围墙帧并再次复验；墙帧刷新失败单列为已尝试但未验证；
- 计划电线以本次 requested colors 中确已不再缺失的颜色判断进展，剩余颜色留给下一轮；其实际判据允许本次至少一种请求颜色得到满足，不要求整个模板全部线色一次完成；
- bridge 超时／失败／取消且投影未确认时分别返回对应失败；
- 其它未确认结果是 `AttemptedButUnverified`，不能当作成功保存施工承诺。

非电线完成记录由投影刷新保存，电线仍保持实时差额，详见资产篇。模型中的 `AutoPlacementProgressState` 有初始化／复制和编辑保护读取，但本轮在固定生产源码中没有找到施工流程写入它；不能把这个字段名描述为已经实现的持久化动作队列。

证据：Z `BlueprintAutoPlaceActionExecutor.cs:114–212、376–407、1239–1261`；`ItemUseBridge.cs:385–412`；`src/JueMingZ/Automation/Blueprint/BlueprintModels.cs:509、526、548`；`BlueprintPlacedInstanceTransformState.cs:598`；非电线完成保存见 `BlueprintProjectionService.cs:819–941`。


## 4. 基础施工：物块、墙与完整家具

### 4.1 普通物块与墙的真实能力

冻结 Z 的普通施工入口将 Tile 和 Wall 分开解析。Tile 允许内容编号 `0`（泥土），不能把 `0` 统一当作无内容；Wall 要求有效墙编号。候选必须是当前投影中的 `missing`，已有冲突层、不可读取层和已完成层均不提交。附带油漆、涂层、斜坡、半砖或致动状态的目标先归一到可放置的本体，已有本体后才进入后处理。对应能力分别为 `vanillaItemUse:tile`、`vanillaItemUse:wall`。

真实执行使用背包中的原版物品，临时选中该物品并给 `Player.ItemCheck` 一个目标鼠标位置。它不移动玩家、不扩大互动范围，也不通过批量改 `Main.tile` 来冒充施工。原版仍会检查放置范围、支撑、当前位置、使用时间、禁建状态等条件。

同版 `.8` 原版实际顺序为：

1. `PlaceThing` 先处理刷漆、滚漆、刮漆等分支，再在 `!noBuilding` 时处理 Tile 和 Wall。
2. 普通 Tile 检查 `IsInTileInteractionRange(... Simple, item.tileBoost + blockRange)`、智能光标目标、使用动画/时间、岩浆等条件，再经 `FigureOutWhatToPlace`、`TileObject.CanPlace` 或旧式 `WorldGen.PlaceTile` 放置。
3. 普通 Wall 还要求上下左右至少有一个实体或墙作为连接条件；成功后调用 `PlaceThing_Walls_FillEmptySpace`，原版可能顺带补相邻空洞。
4. 原版成功路径保留音效、帧刷新、物品使用时间、家具放置后 Hook、网络消息，以及原版自动刷漆/自动放致动器等附加行为。

因此，“每次提交一个候选格”不等于“原版只影响这一个格”。普通墙自动补洞、多格家具、自动建筑饰品等都是必须纳入相邻行为保护的原版效应；Legacy 并没有把这些原版效果隔离成蓝图专用事务。

**证据：**Z@`6ac6356c0c564f43284590c168855e96c50e13f7`，`src/JueMingZ/Automation/Blueprint/BlueprintAutoPlacementService.cs`，`TryResolvePlacementCapability`/低层能力解析，1940–2124；`src/JueMingZ/Actions/Executors/BlueprintAutoPlaceActionExecutor.cs`，`Start`、`TryBeginUse`，22–111、953–1167。同版 `.8` 提取 `.local/death-history-world-time/Terraria.Player.cs`，`PlaceThing` 39887–39905、`PlaceThing_Walls` 39907–39940、`PlaceThing_Walls_FillEmptySpace` 39943 起、`PlaceThing_Tiles` 40024–40061、`PlaceThing_Tiles_TryPlacing` 40073–40098、`PlaceThing_Tiles_PlaceIt` 40422–40482。

### 4.2 家具按完整对象放置，不逐个子格拼装

普通家具施工以完整对象组的代表格为入口。代表格必须是组内 `(0,0)`，组号、宽高、对象子格、位置关系、帧信息与材料身份必须能够一致解释。`LegacyPartialObject`、不完整组、组内冲突、不可读取组、非代表格、不能唯一解析物品/样式的对象均被拒绝。

动态放置目录提供“哪件原版物品能放出哪种 Tile/Style”；几何解析再用 `TileObjectData` 的宽高、原点、alternate、锚定信息解释整组。不是仅凭 Tile ID 或一个家具左上角像素猜出物品。规划器还调用原版 `TileObject.CanPlace` 进行预检，核对它返回的实际左上角、尺寸和所选 alternate；世界边缘采用 5 格安全边距。

替换家具时，原目标先通过几何与可放置检查，替换物品的执行描述再按同一目标矩形重新做原版可放置检查。即使属于允许替换的类别，也不会绕过尺寸、锚点和物品身份证明。

**重要实现限度：**规划结果有 `PlayerDirection` 和 `PlacementAlternate`，但现有 `BlueprintAutoPlacementCandidate`/请求传递保留的是 alternate、目标鼠标等字段；查得的实际 ItemCheck bridge 没有消费规划器的 `PlayerDirection`，也没有直接指定 `TileObject.CanPlace` 的 alternate。`.8` 真正放置仍使用当前玩家 `direction`。因此，“预检证明某个朝向/alternate 可放”与“实际 ItemCheck 必定使用相同朝向/alternate”之间仍有缺口。最终投影可阻止错误结果被宣布完全完成，但无法撤销一次已发生的错向放置；不能将其写成已验证的完整镜像施工保证。

**证据：**同冻结 Z，`BlueprintAutoPlacementBodyPlanner.cs`，`TryResolveGenericCapability` 118–203、`TryPlan` 223–450、`TryResolveExecutionPlacement` 619–720；`BlueprintAutoPlacementService.cs` 1370–1432、2637–2734；`BlueprintAutoPlaceActionExecutor.cs` 候选恢复 481–528、`TryBeginUse` 953–1167。`.8` `Terraria.Player.cs` 40081–40089 将当前 `direction` 传给 `TileObject.CanPlace`；40458–40461 将原版实际 `data.alternate`、`direction` 用于放置后 Hook 与网络消息。

## 5. 八类替换如何落到真实施工

### 5.1 完整集合与选择规则

替换类别完整集合仍是以下八类，没有“任意同尺寸家具通用替换”：

| 类别 | 分类 Tile 集合 | 施工含义 |
|---|---|---|
| 火把 | 4 | 可选择该类原版放置物品；原版生物群落火把转换仍可能影响实际结果 |
| 平台 | 19 | Tile 层仅这一类参与八类替换；平台后续形状仍走锤击 |
| 工作台 | 18 | 按完整家具组，用所选物品重新做几何/支撑预检 |
| 椅子 | 15 | 同上，朝向仍受原版实际放置分支影响 |
| 门 | ClosedDoor 10 | 替换默认关闭门本体；不能将开关状态当作材料类别 |
| 桌子 | 14、469 | 两种分类 Tile 纳入同一替换类别，实际尺寸与锚点仍须通过 |
| 箱子 | 21、467 | 替换的是箱体物品，不复制内容与名称 |
| 牌子 | 55 | 替换牌子本体，不复制文字 |

候选物品集合来自冻结运行环境的动态原版放置目录：要求 `IsBaseItemPlacement`、有效 Item ID，并按 `CreateTile` 分类；去重后按 Item ID 升序。灵活工具选项和稳定补充描述不能混进这八类通用材料集合。完整动态成员应按该公式和固定 `.8` 目录复原，不应将 UI 当前显示的几项样例误写成全集。

只有总替换开关和对应类别开关都开，且目标未涂色、未涂层、无斜坡、非半砖、非 inactive 时，八类替换才生效。原物品数量足够时优先原物品；否则依序选一个能独自满足本次所需数量的候选物品，不把多个不同 Item ID 拼成一件家具。材料列表规划会扣除本轮已计划使用量，避免同一批材料被重复承诺。

**证据：**八类开关、完整分类与目录集合证据见[蓝图资产与编辑](蓝图资产与编辑.md) §7–9；冻结 Z `src/JueMingZ/Automation/Blueprint/BlueprintReplacementRuleService.cs:86–118、158起、428–490、523–554`对分类、`IsBaseItemPlacement` 和选材顺序作实际约束。施工接收端为 `BlueprintAutoPlacementService.cs`，`BuildCandidates` 1250–1338，`BuildMainAvailability` 1629–1644。

### 5.2 “材料替换”不是拆掉世界里的异物

替换改变的是施工时选择哪件合格物品，以及投影判断哪些同类已放本体可以满足目标。它不授权拆除目标上的冲突物、不运行清场、不批量刷回目标原始 Tile。已有符合替换规则的本体可以被投影认定满足，即使玩家当前没有原始材料。

进入执行前，规划器记录目标描述和执行描述两套身份；执行材料 Item ID 必须与执行描述的 `MaterialItemId`（无独立耗材时为 `ItemId`）严格一致。多个不同执行描述匹配同一材料但不能唯一确定时返回 `executionDescriptorAmbiguous`；不能按“第一个看起来能放”继续。

普通家具替换要求执行描述仍属于通用原版放置类别；有状态默认本体要求同一 mechanism family；炮台要求身份等价。实际请求使用执行描述的原版物品，而不是把原目标描述的 Tile ID 直接写到世界。

**证据：**同冻结 Z，`BlueprintAutoPlacementBodyPlanner.cs`，替换分支与材料身份 386–450、`TrySelectExecutionDescriptor` 579–617、`IsCompatibleExecutionDescriptor` 787–816；`BlueprintStatefulObjectPlacementPolicy.cs`，`IsCompatibleExecutionDescriptor` 269–302；`BlueprintCannonPlacementPolicy.cs` 同名方法 206–228。

### 5.3 替换与材料显示不能掩盖执行资格差异

材料列表的“主背包”统计可包含 0–57；自动施工真正选物品/工具只查 0–49。虚空袋可参与显示与缺口说明，但不会自动调入施工槽。线材有跨主背包堆叠聚合的专用路径，其它放置材料按一个足量堆叠寻找；特殊工具还要另外找到真正使用的工具。

因此，UI 显示拥有材料或替换候选可选，不等于本轮执行一定具备资格。执行失败应说明是材料所在区域、堆叠、实际工具、世界支撑还是原版动作失败；不能用统一“缺材料”掩盖。R 候选必须给这两个口径一个明确产品解释；这属于现有 Legacy 差异，不是本轮已经决定照搬的行为。


## 6. 电线：按缺失颜色补齐，工具与材料分开

### 6.1 四色状态与数量语义

蓝图线层记录的是颜色位集合。捕获位为红 `1`、蓝 `2`、绿 `4`、黄 `8`；原版 `WiresUI.Settings.ToolMode` 却是红 `1`、绿 `2`、蓝 `4`、黄 `8`。蓝、绿必须显式换位，不能把捕获位直接塞进原版工具模式。

补线规划计算：

- `missing = target & ~current`：要补的颜色；
- `extra = current & ~target`：现场额外颜色；
- `missing == 0` 即目标满足；
- 每个缺失颜色需要一根 Item 530 电线。

额外颜色不会被剪掉，也不会阻止其它缺色继续补齐。未知颜色位、空目标、读取失败均不当成可施工目标。一个格上缺四种颜色，可在一次多色工具使用中补齐，也可受工具和材料限制分成多次。最终线层满足条件是目标颜色全部存在；历史 `CompletedLayers` 不替代实时线色复核。

**证据：**冻结 Z `BlueprintWireCompletionPlanner.cs`，缺失/额外位和数量规划，1–109；`BlueprintWireToolResolver.cs`，`MapCaptureFlagsToMechanicalToolMode` 379–436。同版 `.8` `.local/全功能调查/原版/Terraria.GameContent.UI.WiresUI.cs`，`MultiToolMode` 13–20。

### 6.2 完整工具集合与选择优先级

普通补线工具包括：

| 原版 Item ID | 能补颜色 |
|---|---|
| 509 | 红 |
| 850 | 蓝 |
| 851 | 绿 |
| 3612 | 黄 |
| 3625，多色扳手 | 四色任意非空子集 |
| 3611，The Grand Design | 由专用长生命周期适配器执行，见第 7 节 |

剪线钳、致动器工具以及其它机械物品不会因“属于机械工具”被纳入四色普通补线集合。每次请求的 ToolMode 只允许颜色位，不带 `Actuator=16`、`Cutter=32`。

选择规则：

1. 当前选中的是能覆盖至少一种缺色的普通工具时，优先使用它；“能完成”在此只要求与缺色集合有非空交集，不要求一把工具覆盖全部缺色。
2. 当前工具未优先命中时，若拥有 Grand Design 且专用适配器可用、布线冷却满足，优先用它。
3. Grand Design 不可用时仍可回退普通工具：多色扳手优先，再按红、蓝、绿、黄的业务顺序寻找可用单色工具。前一种缺色没有对应工具，不妨碍后续颜色先补。
4. 多色请求按红、蓝、绿、黄顺序截取材料数量允许的颜色。可用数量采用材料规划值与实际工具库存快照的线材数量的较小值。
5. 工具在主背包 0–49 查找；真正开工前复核计划槽位、Item ID、正堆叠和 ToolMode/请求颜色的对应关系。工具被移走后不能悄悄换用另一把同类工具。
6. 电线耗材允许将 0–49 的多个 Item 530 堆叠聚合，要求总量满足这次颜色数；记录的第一个材料槽不是唯一消费槽，更不是工具槽。

**证据：**冻结 Z `BlueprintWireToolResolver.cs`，`TryPlan` 238–317、`TryPlanPreferred` 320–369、Grand Design 计划 526–600、普通工具计划 603–711；`BlueprintAutoPlaceActionExecutor.cs`，`TryFindMainInventoryMaterialAggregate` 1476–1540、`TryValidatePlannedMechanicalTool` 1542–1623。

### 6.3 `.8` 原版实际消费与同步

单色扳手使用 `Player.ItemCheck_UseWiringTools`：按 0–57 搜索第一堆电线，原版 `PlaceWire/PlaceWire2/PlaceWire3/PlaceWire4` 成功后扣一根、设置工具时间并发送相应消息。普通扳手要通过原版互动范围、动画/使用时间以及 `CanDoWireStuffHere`。

多色扳手 Item 3625 在原版临时清掉 ToolMode 的致动器位，并以起终点相同的 `MassWireOperation` 执行一个格。单机直接执行；客户端发送消息 109。原版 `Wiring.MassWireOperation` 统计 0–57 的电线/致动器，按实际操作量消费；服务器通过消息 110 通知所属玩家消费。其单格顺序为红、绿、蓝、黄，与 Legacy 截取缺色的业务顺序不同，但请求已显式确定颜色集合。

原版 `CanDoWireStuffHere` 还拒绝世界外、墙 350，以及未击败石巨人时的指定神庙墙条件。Grand Design 的远距离特性不代表可以绕过这些区域规则。

**已证实的口径差异：**Legacy 施工资格只认可 0–49 的线材；原版真正消费可见 0–57。Legacy 没有把原版消费槽锁在资格统计的那一堆。这里材料 ID 相同，不造成错色，但会影响“哪一堆减少”的预期。未发现虚空袋自动参与此线材消费路径。

**证据：**`.8` `Terraria.Player.cs`，`ItemCheck_UseWiringTools` 47152–47320、`CanDoWireStuffHere` 47323–47345；`.8` `Terraria.Wiring.cs`，`MassWireOperation` 419–453、`MassWireOperationStep` 3343–3434；冻结 Z 执行端证据同 6.2。

### 6.4 单次成功与整层完成的差异

执行器当前线请求验收为：此次请求颜色中，**至少一个**已不再缺失，即可把这一次 action 判为成功；它不是 `requested` 全部完成的等值检查。整层投影仍以全部目标颜色存在为准，下一轮可继续补剩余颜色。

这可支持渐进施工，但诊断文本和 UI 若把 action 的 `Succeeded` 表示成“该格所有线色完成”，就会过度承诺。R 候选需要分别表达“本次有进展”和“目标已全部满足”，不能只移植一个成功布尔值。

**证据：**冻结 Z `BlueprintAutoPlaceActionExecutor.cs`，`IsCandidateProjectionVerified` 383–407；`BlueprintWireCompletionPlanner.cs` 目标满足计算。

## 7. Grand Design：必须经过按下、弹射物、释放与清理

### 7.1 为什么不能套普通单帧物品使用

Item 3611 的原版施工不是一次 ItemCheck 立即写线。它产生本地玩家的 Projectile 651，`aiStyle=125`。弹射物在保持 `Player.channel` 时根据鼠标定位，首次记录起点；释放 channel 后进入 `Kill`，仅在 `localAI[0]==1` 且 owner 为本地玩家时才提交 `MassWireOperation` 或客户端消息 109。

所以，单帧按一下后立刻恢复 channel，或在 `Kill` 前恢复了颜色模式，都可能造成未施工、错误起终点或错误工具模式。Legacy 为此设置专用适配器，并在 ItemCheck、Projectile AI、Projectile Kill 三个时段分别限定输入覆盖。

**证据：**`.8` `Terraria.Projectile.cs`，651 属性 6992–7002、AI 36337–36383、Kill 73191–73206；冻结 Z `Actions/BlueprintGrandDesignPlacementAdapter.cs`、`Actions/BlueprintGrandDesignPlacementRuntime.cs`；实际 Hook 接入 `Hooks/ItemUseHookCallbacks.cs` 650–701、`Hooks/ProjectileAiHookCallbacks.cs` 15–60、`Hooks/ProjectileKillHookCallbacks.cs` 15–51。

### 7.2 实际流程和独占范围

1. 计划阶段要求适配器空闲，能够读取本地玩家与 `wireOperationsCooldown`，冷却不大于零。工具必须是主背包 0–49 中的 Item 3611。
2. 请求记录请求 ID、原选中槽、精确工具槽/ID、目标坐标、世界与角色配对身份、请求颜色、ToolMode、期限。颜色模式只能包含四色，不能夹带剪线/致动器。
3. `WaitingForPress` → 首次 ItemCheck `Press`；之后等弹射物出现，必要时 `Hold`。每次 ItemCheck 先捕获原输入，再临时覆盖鼠标、选槽、使用输入、颜色模式。
4. ItemCheck 结束恢复鼠标、按键和颜色模式；保持阶段仅保留正确工具槽和 `channel=true`，因为弹射物在 ItemCheck 之后读取 channel。释放阶段明确设 `channel=false`，不能让捕获的旧 `true` 把 channel 复活。
5. Projectile AI 只认本地玩家所属、type 651、活动且与已绑定 `whoAmI` 一致的弹射物。首次接纳后记录槽号 whoAmI；匹配未同时验证对象引用或 generation，不能证明槽位复用时仍是原实例。AI scope 临时设置目标鼠标，结束即恢复。
6. 观察到一次对应 AI 后请求 Release。Projectile Kill scope 再临时覆盖目标鼠标及精确颜色模式，原版在这个 scope 内提交施工；结束恢复并强制释放 channel。
7. Kill 证据证明专用使用生命周期完成，执行器仍需刷新投影判定真实颜色结果。

这不是把整个游戏鼠标长期钉在蓝图目标上；只有上述 scope 覆盖鼠标/模式。但保持阶段确实暂时保留工具选槽与 channel。实际仲裁器把活跃 Grand Design 纳入 ItemCheck 写入者竞争，普通 ItemUseBridge 在它活跃时不抢先消费。挖矿、捕获、收获、战斗连点等共享同一个原版输入边界，必须保护互斥和退出恢复。

**证据：**冻结 Z `BlueprintGrandDesignPlacementAdapter.cs`，计划可用性 73–99、`TryBegin` 102–158、`TryApplyItemCheckUse` 208–285、`EndItemCheckUse` 288–358、弹射物 scope 452–627；`BlueprintGrandDesignPlacementRuntime.cs`，运行快照 44–112、应用 ItemCheck 114–193、恢复 195–232、强制释放 234–258、弹射物身份与 scope 260–365。

### 7.3 失败、关闭和清理的准确边界

适配器运行中会检查本地玩家存活/活动/非幽灵、UI 阻挡、世界身份、工具是否仍在计划槽、按下前冷却及期限。世界比较只有双方字符串非空时才判“不相同”；身份暂时读不到并不自动等价于明确换世界。

请求的普通超时在该能力下为 4000 ms；适配器自身在无请求期限时默认 2500 ms。最多应用 6 次 ItemCheck scope，之后请求清理。取消或超时会请求释放 channel、恢复原槽；不能把 action 的超时直接当作弹射物清理已经完成。

清理有两条分支：

- 从未观察到弹射物：终止请求后至少推进 2 次，并经过 300 ms grace，才可终结；
- 已观察到弹射物：等相应 Kill scope 完成；若已执行 Release、弹射物不活动但没观察到 Kill，报告 `grandDesignKillHookNotObserved`。

**静态缺口：**已观察到弹射物，但它长期未进入 Kill，或缺失必要的释放/Kill 证据时，代码没有另一条无条件总时长上限来结束该活跃所有者。请求期限触发的是“请求清理”，不能据此证明所有异常分支都在期限内释放适配器。独立复审应检查该尾部，不能将注释中的 bounded cleanup 当作已经证明的绝对界限。

Runtime Shutdown 会强制释放并清掉活跃适配器；普通 F5 自动摆放开关关闭没有直接调用此 Shutdown/Cancel。关闭开关与退出运行环境的语义不同，完整生命周期见后文。

**证据：**冻结 Z `BlueprintGrandDesignPlacementAdapter.cs` 常量 10–17、`Advance` 628–791、`RequestCleanup`/`RequestCleanupLocked` 810–890、请求验证 892–990、`Shutdown` 429–450；`Runtime/JueMingZRuntime.cs` 745 调用适配器 Shutdown。

### 7.4 原版范围与多人结论

Grand Design 的 Projectile 651 路径使用鼠标世界位置，不等同于普通单格扳手的玩家附近 TileReach 检查；区域合法性仍由 `MassWireOperationStep → CanDoWireStuffHere` 决定。Legacy 不能通过给普通工具假装一个 Grand Design ToolMode 获得同样能力。

已看到 `.8` 的客户端消息和服务器消费分支，只能证明选择了原版网络通道，不能证明 Legacy 在多人中已验证正确，更不能替代远端权限、同步延迟、断线、世界切换与重复动作的实机证据。


## 8. 灵活工具：目标变体、工具和耗材必须同时成立

### 8.1 识别方式与完整实际入口

Legacy 没有把所有灵活工具压成“拿材料当方块放”。目录初始化遍历原版 Item，调用 `GetFlexibleTileWand()`，一次性读取该 wand 的 `_options` 材料桶及桶内 `Options`；每个描述保存：

- 真正使用的工具 Item ID；
- 原版需要的材料 Item ID；
- 目标 Tile ID、Style；
- **该材料桶内部**的 `FlexibleWandCycleOffset`；
- 描述来源 `FlexibleWandOption`。

施工要求目标 Tile/Style/材料在目录中唯一命中，完整对象组可以解释；有歧义或样式无法选择时拒绝。执行时选中工具，另外验证材料；临时设置原版 `Player.FlexibleWandCycleOffset`，结束恢复其旧值。人偶装备、瓶中物品等外部载荷不由这个选项系统补造。

### 8.2 原版真正选材与 Legacy 计划的缺口

`.8` `TryGetPlacementOption` 按背包索引从前到后扫描，范围为 0–58，但跳过 50–53；第一个非空气、满足收藏品策略、类型能在 `_options` 命中的物品，决定使用哪个材料桶。然后才用 `selectCycleOffset` 选该桶内的变体。它没有接收“这次蓝图指定的材料 Item ID”。

Legacy 验证目标材料在主包 0–49 存在，也把目标桶的 cycle offset 传给原版；但未见它验证**原版按上述顺序实际选中的桶就是目标桶**，也没有移动物品或给原版传入强制材料桶。

可直接复原的反例条件：

- 玩家持有同一个多材料灵活工具；
- 蓝图目标来自材料 B 的某个选项；
- 背包更靠前有该工具也接受的材料 A；
- Legacy 因 B 存在而通过资格检查；
- `.8` 原版选择 A 的桶，对 A 的桶长度取模后使用同一个 cycle offset，可能放出另一种对象并消费 A。

最终投影会发现目标未完成，但它不是回滚机制；错误本体已经产生时，后续可能成为冲突。R 候选必须同时证明“目标选项”和“原版此刻实际选中的材料桶”，不能只检查目标材料数量。

**证据：**`.8` `Terraria.GameContent.FlexibleTileWand.cs`，`TryGetPlacementOption` 176–197；`Terraria.Player.cs`，`ModifyFlexibleWandPlacementInfo` 40101–40124；冻结 Z `BlueprintSpecialItemUsePlacementResolver.cs` 116–177、`BlueprintAutoPlaceActionExecutor.cs` 1346–1409、1135–1136。

### 8.3 消耗、免费模式与持续状态

原版区分 `ConsumesAmmoItem`：需要独立材料的 wand 在成功放置后再次选择材料并扣除；不单独消耗 ammo 的 wand 仍可能通过物品自身的 `consumable` 通道消费实际持有物品。不能把 `WithoutAmmoConsumption()` 解释成整个动作不消耗物品。

原版还维护 `FlexibleWandLastPosition` 与 `FlexibleWandRandomSeed`，目标格变化会更新它们。Legacy 的 bridge 恢复 cycle offset；不能据此声称把原版所有灵活工具全局状态都恢复到动作前。反向重力、朝向、随机/alternate 与对象支撑最终仍由原版路径处理，必须与投影目标对照。

**证据：**`.8` `Terraria.GameContent.FlexibleTileWand.cs` 104–129、176–197；`Terraria.Player.cs` 40108–40121、40486–40496、43590–43654；冻结 Z `Compat/TerrariaInputCompat.UseItem.ItemCheckBridge.cs`，应用/恢复 cycle offset 的输入 scope。

## 9. 油漆、涂层、锤击和致动：分步加工及真实限制

### 9.1 本体之后的固定决策顺序

只有 Tile、Wall、Object 层参与此后处理。必须先有经投影识别的对应本体；本体不存在时只允许先放归一的本体，不能向空气写颜色/形状来假装完成。

Wall：先颜色差异，再涂层差异。

Tile/Object：先颜色差异，再涂层差异，再斜坡/半砖差异，最后 inactive 差异。对象组允许逐子格装饰，但 `Object` 的锤击形状明确返回 `objectHammerShapeDeferred`；不能通过锤击家具来随意恢复姿势/机关状态。

同一候选只安排下一步原版动作；完成后重读投影，继续决定下一步。一次动作不同时完成全部颜色、涂层、形状和致动目标。

**证据：**冻结 Z `BlueprintAutoPlacementPostProcessPlanner.cs`，`TryResolve` 69–110、Wall 分支 112–156、Tile/Object 分支 158–247；`BlueprintAutoPlacementService.cs`，本体与后处理分派 1940–2014。

### 9.2 油漆与涂层完整映射

- paint 1–27 → Item `1072 + paintId`，即 1073–1099；
- paint 28、29、30 → Item 1966、1967、1968；
- 目标 paint 为 0 而现场有颜色 → 刮漆；
- fullbright 涂层 → Item 4668；
- invisible 涂层 → Item 5344；
- 两种涂层都缺时先 fullbright，再 invisible；
- 目标所需涂层都存在但仍有额外涂层时 → 刮涂层，再按投影决定是否补回所需涂层；
- 无法映射的颜色或未知目标涂层位不能作为可完成的正常涂层计划。

工具集合和优先级：

| 工序 | 可用工具 |
|---|---|
| 物块/对象刷漆、涂层 | Paintbrush 1071 或 SpectrePaintbrush 1543 |
| 墙刷漆、涂层 | PaintRoller 1072 或 SpectrePaintRoller 1544 |
| 刮颜色/涂层 | PaintScraper 1100 或 SpectrePaintScraper 1545 |
| 锤形状 | 任何有效原版 Item，要求 `hammer > 0`、`useTime > 0`、`useAnimation > 0`，没有硬编码锤子白名单 |
| 切换 inactive | ActuationRod 3620 |

优先当前选中的兼容工具。否则，油漆/刮刀/致动杖取主包较早的兼容槽；锤子按 `useTime` 最小、再 `useAnimation` 最小、再槽号最小选择，锤力不参与速度排序。工具选择记录槽、ID、锤力、使用时间、动画、tileBoost 与库存签名；开工前逐项复核，不能把旧计划漂移到另一种速度或范围的工具。

刷漆与涂层需要单独的耗材；刮刀、锤击、致动杖是 tool-only 候选，必须保持材料 ID/数量为 0。工具丢失只阻止对应后处理，不应把已存在本体重新当缺失来放第二件。

**证据：**冻结 Z `BlueprintAutoPlacementPostProcessPlanner.cs` 26–27、112–156、250–309、362–419；`BlueprintPostProcessToolResolver.cs` 178–190、252–359、441–465；`BlueprintAutoPlaceActionExecutor.cs`，tool-only 校验 1333–1344、精确工具复核 1625–1741。

### 9.3 同版 `.8` 证实的“有目标油漆却刷错”条件

原版刷子/滚筒没有接收蓝图指定耗材参数。`FindPaintOrCoating()` 先查 54–57，再查 0–57，拿到第一个 `PaintOrCoating` 物品。Legacy 执行器只确认所需 Item ID 的材料存在，随后选中刷子或滚筒；记录 `MaterialSlot` 不会改变原版耗材选择。

所以，目标红漆位于普通背包、前面或弹药区另有蓝漆/涂层时，原版可能先消费另一种材料，刷出其它颜色或涂层。消费成功后投影只能报告目标未完成，不能自动撤销错误加工。这也是材料列表口径与实际原版选择口径不同的具体后果。

原版在确实改变颜色/涂层后才扣该实际材料，设置相应使用时间，并通过 paint/coat 原版广播消息同步。Legacy 没有自己的第二次扣材料；也不能声称已经锁定正确消费对象。

**证据：**`.8` `Terraria.Player.cs`，刷子/滚筒 42208–42241、`FindPaintOrCoating` 42244–42261、`TryPainting` 42263–42277、`ApplyCoating` 42279–42309、`ApplyPaint` 42311–42341；冻结 Z `BlueprintAutoPlaceActionExecutor.cs` 1319–1409、`TryBeginUse` 953–1167。

### 9.4 刮刀不是“指定层、指定属性”的删除指令

`.8` 刮刀的顺序是：

1. 尝试清前景颜色；
2. 前景颜色没变化时，尝试清前景全部涂层；
3. 前景都没变化，才尝试清背景墙颜色；
4. 背景颜色没变化时，尝试清背景全部涂层。

这些分支用短路 `||`，一次通常只完成首个有变化的操作。清涂层会一起清除 fullbright 和 invisible，不提供“只删除某一位”的接口。刮刀还存在长苔藓专用原版破坏路径。

Legacy 的 `wallPaintScrape`、`wallCoatingScrape` 等能力名只是计划意图；实际同一把刮刀没有层选择参数。由此有两个可静态复原的反例：

- 想清背景墙涂层，但同格前景已有颜色/涂层：原版先清前景，可能破坏本来已经符合蓝图的前景装饰。
- 目标要求保留非零颜色，但要去掉额外涂层：原版第一次先清颜色；Legacy 下一轮按“颜色优先”重新刷回颜色；再刮时又先清颜色。若没有更强的过程状态，可能反复重刷而到不了清涂层分支。

后处理次数限制是按 admission key 计数；该 key 又包含整个主包的工具库存签名，而签名实际包含所有 0–49 物品及堆叠。补漆消耗会改变签名，因此不能把“同 key 最多 8 次”解释成整个目标最多 8 次、或上述循环一定在 8 次内停止。

**证据：**`.8` `Terraria.Player.cs`，`PlaceThing_PaintScraper` 42125–42137、长苔藓 42139–42184、`PlaceThing_PaintScraper_TryScraping` 42187–42205；`Terraria.WorldGen.cs`，`paintCoatTile` 44358–44404、`paintCoatWall` 44406–44452。冻结 Z `BlueprintAutoPlacementPostProcessPlanner.cs` 166–205、250–309；`BlueprintPostProcessToolResolver.cs` 151–168、519–549；`BlueprintAutoPlacementService.cs` 1193–1234、715–756。

### 9.5 锤击形状与工具范围

锤击一次只让原版推进一个形状状态，之后靠投影判断 slope/halfBrick 是否已达目标。原版循环受周围实体、平台连接、上下支撑及 `poundRelease` 影响，不能用一个固定“锤几下”等价公式概括所有场景。

Legacy 对同一目标的锤形状提交有 6 次限制；该目标计数不会随当前 slope 改变而重置。一般后处理另有同 admission key 8 次限制。这是防止重复尝试的上限，不证明六次一定能得到所有合法目标，也不保证无效工具不会发生相邻原版作用。

范围必须用真实工具属性理解。`.8` 锤击入口经 `IsTargetTileInItemRange(sItem)`，该方法使用 `sItem.tileBoost`；刷子、滚筒、刮刀和普通布线则使用 `tileBoost + blockRange` 的对应原版检查。不能用一种范围公式覆盖全部工具。

工具资格只证明存在锤力，不独立证明这次完整原版 mining path 只有塑形效果：原版同一入口还可能处理挖物块、锤墙、特殊 Tile 等分支。现有规划缺少针对每个目标与复合工具的完整副作用证明；R 候选应在受控操作边界中明确限定可执行目标及工具能力。

**证据：**冻结 Z `BlueprintAutoPlacementPostProcessPlanner.cs` 207–225、`BlueprintPostProcessToolResolver.cs` 318–358、441–465、`BlueprintAutoPlacementService.cs` 698–756；`.8` `Terraria.Player.cs`，mining gate 45978–46026、真实工具分支 46029–46165、`TryPoundingTile` 46355–46697、`IsTargetTileInItemRange` 46699–46702。

### 9.6 致动器放置与 inactive 切换是两件事

Actuator 层通过原版 Item 849 放致动器，本体 inactive 后处理则使用 Item 3620 致动杖。目标 inactive 与现场不同但现场没有致动器时，后处理明确 `inactiveRequiresActuator`；它不会直接写 inactive，也不会把 Grand Design 的致动器模式夹进四色补线请求。

原版致动杖要求实际 Tile 有 actuator，并通过 `Wiring.Actuate` 切换；还使用 `ActuationRodLock/Setting` 防止一次持续使用乱翻。只有前后 inactive 确实不同才设置使用时间并发消息。`Wiring.DeActive` 会限制不活动实体、特定进度条件、不可真正实体化的 Tile、上方禁止致动的物件等；有杖、有致动器不代表一定能关闭实体性。

**证据：**冻结 Z `BlueprintAutoPlacementPostProcessPlanner.cs` 228–243、`BlueprintAutoPlacementService.cs` 致动器本体分支 2015–2124；`.8` `Terraria.Player.cs` 47285–47303；`Terraria.Wiring.cs`，`Actuate` 389–405、`DeActive`/`ReActive` 3209–3247。

## 10. 特殊默认本体：保留物品身份，不恢复机关运行状态

### 10.1 完整支持家族与归一规则

冻结 Z 单列默认本体策略，支持以下有状态家族；它不是所有复杂 Tile 的通用“忽略 frame”开关。

| 家族 | 源 Tile | 保留的身份 | 施工目标 |
|---|---|---|---|
| 门 | 10、11 | 门样式与真实门物品；锁门有专门 Item 1141 提示 | 关闭的 1×3 门本体 |
| 拉杆 | 132 | 拉杆物品 | off 本体 |
| 压力板 | 135、428 | `frameY/18` 表示的具体压力板物品 | unpressed 本体 |
| 开关 | 136 | 开关物品 | off 本体 |
| 计时器 | 144 | `frameX/18` 表示 1/3/5/0.5/0.25 秒物品 | stopped 本体 |
| 逻辑灯 | 419 | `frameX/18` 的具体物品；三种灯身份不同 | 对应物品的精确本体，不能把三者混为状态 |
| 逻辑门 | 420 | `frameY/18` 的逻辑功能 | outputOff 本体 |
| 独石 | 410、455、480、509、657、658、720、721、725、733 | Tile/Style 对应的具体物品 | 默认本体；不恢复世界视觉/派对效果 |

打开的门源组是 2×3，但关闭门必须落在铰链所在列：源 `frameX mod 72 >= 36` 时默认本体左上角向右移一列。不能直接拿打开门外接矩形的左边当关闭门位置。

### 10.2 允许忽略的是已证明的状态偏移

默认本体策略要求完整组内每个子格符合相同合法帧偏移，而不是只检查代表格。允许的状态偏移为：

- 关闭门必须是默认帧；打开门只允许已证明的开门方向帧差，纵向差为 0；
- 拉杆：默认或 X 偏移 36；
- 压力板：默认或 X 偏移 18；
- 开关、计时器：默认或 Y 偏移 18；
- 逻辑灯：只承认精确默认身份帧，不把另一种灯当临时状态；
- 逻辑门：默认或 X 偏移 18；
- 普通独石：默认或一个状态步长的 Y 偏移；Tile 410 步长 56，其余 54；
- PartyMonolith 455 没有借 Tile 帧恢复全局派对的路径，仅承认精确默认帧关系。

显式材料身份具有优先权。相同 Tile 共享多个计时器、门、逻辑设施或独石物品时，不能退回目录第一项掩盖目标材料冲突。正常化失败、混合帧、半件、材料不一致、尺寸不符都保留为不可施工原因。

**证据：**冻结 Z `BlueprintStatefulObjectPlacementPolicy.cs`，材料身份 69–80、整组校验 163–266、`TryMatchSourceFrames` 502–557、`IsAllowedTransientDelta` 604–658。

### 10.3 炮台专门证明

炮台默认本体固定为 4×3，原点 `(1,2)`，底部锚点覆盖 2 格且从列 1 开始。源组必须有全部 12 格，位置、尺寸、Tile 209、样式、材料和每个子格 frame 一致；角度帧差仅允许 Y 为 0–432 的 54 倍数，X 差必须为 0。

样式 0–3 是对应物品身份，style 4 是 Portal Gun Station 的另一方向，归一为 style 3；不是一种新增材料。执行描述兼容要求物品身份等价，不能以“都是炮”替换。预检使用默认本体矩形和原版 `TileObject.CanPlace`，真正放置由原版物品使用完成。

施工不自动装弹、瞄准、发射、恢复炮口角度、打开门、启动计时器、输出逻辑信号或启动独石效果。这些运行行为属于独立用户动作与状态，不能通过复制 frame 混入默认本体施工。

**证据：**冻结 Z `BlueprintCannonPlacementPolicy.cs`，常量 18–24、整组与角度证明 106–203、身份兼容 206–252、逐格 frame 375–445、固定几何/角度/style 505–531；`BlueprintAutoPlacementBodyPlanner.cs` 335–450。同版 `.8` `Terraria.ObjectData.TileObjectData.cs`，Tile 209 几何 2647–2657；`Terraria.ID.ItemID.cs`，Cannon 928、BunnyCannon 1337、ConfettiCannon 3369、PortalGunStation 3664 的定义 3402、4220、8284、8874。

### 10.4 原版实体与副作用的交接

`.8` 的 DisplayDoll 与晶塔等对象在 `TileObjectData` 注册原版放置后 Hook；晶塔另有放置预检 Hook。Legacy 通过真正 `Player.PlaceThing_Tiles_PlaceIt` 进入这些 Hook，避免只画了 Tile 却没有原版实体。

但“默认本体不主动恢复运行状态”不意味着原版放置绝无运行副作用。例如原版普通 Tile 成功分支仍会做逻辑灯触发、自动刷漆/致动、支撑帧处理等。R 需要保留合法原版行为，同时把用户请求的目标与可能受影响的相邻状态讲清；不能直接把 Legacy 的归一标签当成全部副作用证明。

**证据：**`.8` `Terraria.ObjectData.TileObjectData.cs`，DisplayDoll 3062–3073、晶塔 3418–3424、逻辑灯与逻辑门 4241–4256、4344–4352；`Terraria.Player.cs` 40455–40477。Legacy 的归一/策略证据同 10.1–10.3。

## 11. 输入、生命周期、进度与关闭：实际语义必须分层

### 11.1 新提交、已排队、已进入原版是三个不同阶段

| 阶段 | 冻结 Z 实际检查 | 不能据此保证的事项 |
|---|---|---|
| 新提交前 | Runtime ActionSubmitting lane 要求在世界、非菜单、GameInputAvailable、聊天未打开；蓝图服务再查 `HasBlockingUi` | 不能保证排队后环境仍相同 |
| 执行器 Start | 再查世界/UI；强刷投影找到相同目标且仍 missing；复核工具/材料，部分对象再检查实际距离 | Start 的公共 UI gate 不包含 `GameInputAvailable` |
| 普通 ItemUseBridge 等待消费 | 本地玩家活动、非死亡/幽灵；目标槽物品类型与正堆叠；等待使用时间/动画可接入 | 没有完整复查蓝图世界配对、UI/focus 与所有材料选择意图 |
| Grand Design 活跃中 | 额外有玩家、UI 捕获、世界字符串、精确工具槽、冷却、deadline 与弹射物 type/owner/active/whoAmI 匹配 | UI 捕获 gate 与 Runtime gate 不是同一个集合；空身份、焦点和异常清理仍有缺口 |
| 原版动作发生后 | bridge 检查可观察使用迹象；执行器强刷投影复核，墙还有帧刷新 | 不是可撤销事务；不能从使用动画直接宣布施工完成 |

`GameInputAvailable` 来源于前台进程检查，失败再尝试 FocusHelper，两个来源都不能读取时 Legacy 返回 true。新提交会尊重这个门，但普通 action 的 Start/ItemCheck 消费没有同样的焦点复核。聊天/失焦后是否继续消费已经排队的请求，不能只看新提交门就宣布安全。

`UiStateReader.HasBlockingUi` 包含菜单、聊天、箱子/个人储物空间、NPC 对话；普通背包打开本身不在该布尔值中。Grand Design 运行时 `IsInputBlockingUiActive` 主要依赖菜单和 `mouseInterface/blockMouse` 捕获标记；它读取到的 Chat/NPC/Chest 字段并未全部直接纳入这个方法的阻挡表达式。两种检查必须分别写明。

**证据：**冻结 Z `Runtime/RuntimeAutomationDispatcher.cs` 85–86、410–423、648–679；`GameState/Ui/UiStateReader.cs` 18–33、52–58；`Compat/TerrariaMainCompat.cs` 176–208；`Actions/Executors/InputActionExecutorBase.cs` 24–27；`BlueprintAutoPlaceActionExecutor.cs` 22–111、114–201；`ItemUseBridge.cs` 216–382；`Compat/TerrariaInputCompat.UseItem.UiContext.cs` 5–68、`Compat/TerrariaUiInputContext.cs` 17–41。

### 11.2 关闭显示、关闭施工、移除实例不能混为一谈

- 关闭 F5 窗口只是 UI 可见性变化，不是关闭自动施工开关。
- 隐藏实例、取消/删除实例、区域擦除等改变投影数据；之后未开始的请求在 Start 强刷投影时可发现目标消失或状态变化而拒绝。
- 已经交给普通 bridge 的请求不会因世界实例刚被编辑就自动回滚；它的消费时点没有再次查实例存在性。
- 关闭自动施工设置只让后续 Tick 不再提交。UI 设置器和快捷键设置器均未直接调用 `CancelBySource(BlueprintMain)`。
- Dispatcher 在该功能关闭但仍有蓝图 pending/running 请求时仍允许进入服务；服务显示 disabled 后返回，ActionQueue 的独立 Update 继续推进原请求。
- Runtime Shutdown 单独强制清理 Grand Design；不能把这个生命周期动作等同于普通开关关闭。
- 队列有 `Clear()`/`CancelBySource()` 能力，不代表蓝图开关实际调用过它们。

所以当前事实是“关闭后停止新提交”，而不是已证明“关闭当下所有输入覆盖、待执行动作和弹射物都退出”。R 的关闭合同必须明确待提交、已进入原版、未确认、清理尾部各自处理方式，并且不会因强行清理而篡改原版已经发生的世界/库存结果。

**证据：**冻结 Z `Input/LegacyUiActionService.Blueprint.cs` 274–283、1071–1095；`Input/FeatureToggleHotkeyService.cs` 678；`Runtime/RuntimeAutomationDispatcher.cs` 410–423；`BlueprintAutoPlacementService.cs` 547–575、868–890；`Actions/InputActionQueue.cs` 205–243、263–324；`BlueprintAutoPlaceActionExecutor.cs` 114–201；`Runtime/JueMingZRuntime.cs` 299–310、732–751。

### 11.3 恢复输入的准确边界

普通 bridge 捕获并恢复所覆盖的鼠标位置、Tile 目标、选槽、使用按键、channel、灵活工具序号与机械 ToolMode。恢复选槽使用执行器开始时保存的 override，而不是等到真正 ItemCheck 消费时才捕获的当前用户槽；若等待期间用户主动换槽，恢复可能把用户新选择覆盖回旧槽。这个风险已在第 3 节列明，R 不能照搬“无条件恢复旧值”。

第 3 节恢复顺序补充：ItemUse Postfix 先恢复主要输入状态并通知 bridge，单独的鼠标恢复 scope 在后续代码完成；不能将整个 Postfix 简化成“所有恢复成功后才报告完成”。部分恢复调用的失败仅记录日志，且安装的是 Prefix/Postfix，没有用 Finalizer 覆盖原版方法抛出异常的情况。

队列的普通 Start/Update 异常转换成失败结果后，`CompleteLocked` 释放通道并记结果，不会统一再调用执行器 Cancel；Cancel 只在相应取消路径调用。短暂 cleanup lease 也不等同于每一种原版输入资源都已恢复。

**证据：**冻结 Z `Hooks/ItemUseHookCallbacks.cs` 355–409、对应 Hook 安装 81–94；`Compat/TerrariaInputCompat.UseItem.ItemCheckBridge.cs` 114–198、373–449；`BlueprintAutoPlaceActionExecutor.cs` 953–1167；`Actions/InputActionQueue.Execution.cs` Start/Update 异常分支 69–129、`CancelRunningLocked` 133–175、`CompleteLocked` 178–205。

### 11.4 层进度是“曾完成的承诺”，不是纯实时世界镜像

非电线层一旦投影认定 fulfilled，会写入实例 `CompletedLayers`；不要求必须由自动施工亲手建成。之后历史 completed 优先于通常的实时世界分类，因此后来手动拆掉的非电线本体可能仍维持 completed，不会自动重新补建。墙存在专门“历史完成但当前不符”的诊断计数，也不等于默认回退成 missing。

电线不同：历史 completed 不覆盖实时缺色，也不会新写电线 completed，后续缺失颜色仍可被补齐。

保存完成进度失败时，不把这次待持久化明细应用为当前快照的 completed；世界实际已放出的内容不会因此回滚。重读仍可看到 fulfilled 并继续尝试记录。`AutoPlacementProgressState` 字段在模型中存在，但本轮源码搜索没有找到生产施工将其更新为运行进度的链路，不能据此声称持久化了可恢复施工队列。

对移动/镜像限制的影响必须保留：`CompletedLayers` 可以由现场本来已有的建筑触发，并不只意味着自动施工已经开过工。区域擦除、移除投影也只是改实例，不拆真实世界，二者失效范围不同。

**证据：**冻结 Z `BlueprintProjectionService.cs`，历史完成优先 758–787、`PersistCompletedProgressIfNeeded` 819–907、落盘成功后的快照收敛 909 起；`BlueprintPlacedInstanceTransformState.cs` 的完成/自动放置进度守卫，见资产篇对应证据；本节与《蓝图资产与编辑》的持久化边界一致。

### 11.5 实际反馈与当前文案差异

F5 摘要显示自动摆放关闭、无候选及跳过原因数量，或候选数量、下一层/坐标、是否替换、最近 admission/result、成功次数与 unverified 次数。它不是每个工具/每个家具都单列的施工向导。

现有玩家可见字符串仍出现 `admission`、`result`、`ok`、`unverified` 等内部词；wire 成功字符串写“完成本次 requested bits”，但实际验收只要求至少一个请求位完成，文案比判断更强。Feature Catalog 的蓝图总入口仍标 planned/未实现，并保留某些较早 fail-closed 说明，实际源码却已有上述扩展施工分支。后续应以用户能力、实际路径与证据解释差异，不能以 Catalog 一个布尔值宣布全无或全有。

**证据：**冻结 Z `UI/Legacy/LegacyMainWindow.Blueprint.cs`，`BuildBlueprintAutoPlacementSummary` 2252–2282；`BlueprintAutoPlaceActionExecutor.cs` 164–177、383–407；`Features/Catalog/BlueprintFeatureRegistrar.cs` 20。

## 12. 稳定运行、变化失效、规模与失败成本

本节所有 Z 实现证据固定于 `6ac6356c0c564f43284590c168855e96c50e13f7`。除特别写明 R 或原版外，下列路径以 Z 仓库为根。这里列举源码可确定的工作量与反例；没有运行游戏，也不据此声称某个 FPS 数值或性能提升。

### 12.1 关闭、等待和允许调度是三种不同状态

- 蓝图自动施工调度间隔为 **1 个游戏更新 tick**，世界实例生命周期调度间隔为 **10 tick**。自动施工的启用条件是“总开关开启，或者该来源仍有排队/运行中的动作”，并继续受调度 lane 的可运行条件限制。不能把这写成任何场景都无条件逐 tick 施工。证据：`src/JueMingZ/Runtime/RuntimeAutomationDispatcher.cs:78–86、410–420`。
- `ResolveCandidate` 在总开关关闭时于读取投影前返回；这条关闭分支不会继续做材料候选扫描。但服务进入关闭分支以前仍建立本次结果与计时信息，而且总开关关闭不等于已经撤销旧队列请求或已运行的原版动作。证据：`src/JueMingZ/Automation/Blueprint/BlueprintAutoPlacementService.cs`，`ResolveCandidate:868–889`、`TickCore:552–562`；旧请求继续及输入恢复规则见第 7、11 节。
- 对一次已经获准进入服务的启用调用，服务先 `ResolveCandidate`，再检查自己的 `IsBlockedForWorldInput`。因此这层 UI 阻挡发生在候选求解之后。上层调度是否已经阻挡，必须单独判断，不能用内层次序推断所有聊天或失焦期间都执行完整扫描。证据：同文件 `TickCore:552–569`。
- 关闭自动施工也不等于关闭投影、材料窗口、实例生命周期、绘图和持久化观察等其它蓝图能力；它们在资产篇已经分开。不能把自动施工开关作为整个蓝图系统的总工作量开关。

### 12.2 稳定投影的缓存命中仍有完整实例文件读取

实际顺序不是“先检查版本号，命中后直接返回”：

1. 解析当前玩家/世界 identity；
2. `TryLoadWorld` 读取该世界实例文档；
3. 正规化、复制实例数据；
4. 建立本轮投影签名；
5. 最后才判断签名相同且距离上次解析不足 **250 ms**。

证据链：

- `src/JueMingZ/Automation/Blueprint/BlueprintProjectionService.cs`，`ResolveSnapshotLocked:593–626`，缓存间隔常量 `CacheCadenceMs:336`。
- `src/JueMingZ/Automation/Blueprint/BlueprintWorldInstanceStore.cs`，`TryLoadWorld:32–65`，尤其 `BlueprintJsonSafeFileStore.TryRead:44`、`NormalizeInstances:63`；正规化会逐实例 `Clone`，正规化擦除和完成记录，复制模板并运行对象组正规化，最后按层序排序，见 `NormalizeInstances:161–218`。
- `src/JueMingZ/Automation/Blueprint/BlueprintJsonSafeFileStore.cs`，`TryRead:15–52`：存在文件时每次 `File.Open(..., FileAccess.Read, FileShare.ReadWrite)` 并通过新建的 JSON serializer 读取对象，见 `31–34、189–192`。

因此：

- 投影缓存命中能省去本轮完整世界投影重建，**不能省去上述文件读取、反序列化、正规化、实例复制与签名建立**。
- 文件不存在时走 `File.Exists` 后的 `missing` 分支，不能把不存在文件时的成本和已有大型实例文件混为一谈。
- 擦除掩码、完成层记录进入签名前还分别创建列表并排序。证据：`BlueprintProjectionService.cs`，`AppendEraseMaskSignature:2184–2219`、`AppendCompletedLayerSignature:2221–2259`。
- `GetReadOnlySnapshotForInternalConsumer` 中的“只读”描述的是消费者不修改所借用快照的约定；它不是无 I/O、无分配或无后续存储副作用的保证。

### 12.3 自动施工稳定等待仍重建材料和候选

在投影、库存可读的成功路径上，一次 `ResolveCandidate` 会：

1. 取得投影；
2. 强制刷新施工所用材料统计；
3. 遍历投影层构建候选；
4. 对整个候选列表排序；
5. 选择 frontier 候选；
6. 到 `TickCore` 才检查“同 admission key、同投影签名已经提交过”，决定等待。

证据：

- `BlueprintAutoPlacementService.cs`，`ResolveCandidate:892–952`、`BuildCandidates:1030–1433`、`TickCore:586–603`。
- 材料强制刷新内部还会再调用一次投影获取：`src/JueMingZ/Automation/Blueprint/BlueprintMaterialService.cs`，`ForceRefreshReadOnlyForAutoPlacement:444–451`。
- `ResolveSnapshotLocked` 的缓存命中要求 `!forceRefresh`；施工调用传入 `true`，因此成功路径会再次 `BuildMaterialSnapshot`，见同文件 `579–620`。

由此能确定的是：**稳定且重复等待的候选，不会在入口直接省略材料重算、候选遍历和排序**。成功路径至少两次到达投影获取；第二次是否重建世界投影受投影自己的缓存控制，不能把“两次获取”写成“两次完整世界 Tile 扫描”。

电线与后处理工具解析也不是“缓存命中便不读库存”：

- 电线解析先读实际库存，再复制排序、构造签名，最后比较缓存；命中后仍复制缓存快照。证据：`src/JueMingZ/Automation/Blueprint/BlueprintWireToolResolver.cs`，`ResolveInventorySnapshot:197–235`。
- 后处理工具解析同样先读库存、复制排序、建立签名后判断缓存；签名含当前选槽，以及每个库存项的槽位、物品 ID、数量、锤力、使用时间、动画时间、`tileBoost`。证据：`src/JueMingZ/Automation/Blueprint/BlueprintPostProcessToolResolver.cs:199–249、519–549`。
- 本轮候选构建会按需要共用一次电线工具快照及一次后处理工具快照，不能再夸大为每个电线格都无条件重复读取全背包。
- 家具本体规划有按本次投影建立的对象组上下文；共享上下文减少重复组装，并不把完整候选扫描变成常数工作。证据：`src/JueMingZ/Automation/Blueprint/BlueprintAutoPlacementBodyPlanner.cs`，`CreateContext:72–103`。

### 12.4 签名、省略的变化与停滞反例

投影签名主要包含世界对/世界 identity、文档 revision、读取器 ready 状态、替换规则、实例身份/层序/显隐/位置/更新时间、擦除与完成记录、模板身份/更新时间/格数。**玩家位置、普通材料库存、实际世界所有 Tile 内容不在该签名中。** 证据：`BlueprintProjectionService.cs`，`BuildProjectionSignature:2124–2160`。

普通 admission key 包含实例/层/目标坐标/目标内容与样式，以及目标和当前电线、油漆、涂层、坡形、半砖、致动状态；它也不包含玩家位置和普通材料库存。电线与后处理才另外附加各自的工具库存签名等信息。证据：`BlueprintAutoPlacementService.cs`，`BuildAdmissionKey:2771–2796`、附加项 `1193–1212`。

因此有以下静态可构造反例：

> 只剩一个普通方块或家具候选；该候选已被队列接受，但执行开始时因为 `placementTargetOutOfReach` 失败。随后玩家走近，目标仍然缺失，实例与投影签名不变。新的玩家位置没有进入普通 admission key；候选仍被视为“已提交同一候选”，服务可继续返回 `waitingForProjectionChange`。

两端证据：

- 执行端实际距离检查在执行计划解析中，使用原版 `IsInTileInteractionRange`、`TileReachCheckSettings.Simple` 与物品 `tileBoost + player.blockRange`。证据：`src/JueMingZ/Actions/Executors/BlueprintAutoPlaceActionExecutor.cs:1052–1059、1170–1208`。
- 服务端接受即记录最后 key/signature；后续同 key/signature 普通候选不会因执行失败自动抹掉该记录。证据：`BlueprintAutoPlacementService.cs:589–602、619–635`；`RecordExecutorResult:452–478`。
- 该反例依赖“无其它候选改变最后提交对象、无实例或投影签名变化”等明确条件；它不是对所有场景永久停滞的泛化结论。

frontier 的“冷却”也不是严格禁止再次尝试该 key：先跳过冷却项找其它候选；若全部都冷却，会退回最后已提交项，或者第一个冷却项，最后才取列表首项。退回最后已提交项通常又被 `TickCore` 的重复提交检查挡住；退回其它冷却项则不等于禁止提交。证据：`SelectFrontierCandidate:957–998`、`IsCoolingOrPendingCandidateLocked:1002–1017`。

关闭再打开总开关不是这类停滞的明确恢复机制：关闭分支没有清除最后提交 key/signature；可见重置总状态的方法为 `ResetForTesting`。不能在用户说明中承诺“重开即恢复所有施工”。

### 12.5 完成记录会同步写整个世界实例文档

投影重建会遍历 fulfilled 层；非电线层的新完成记录会进入实例，然后调用 `SaveWorldInstances` 保存整个世界实例集合。电线故意不采用该永久完成规则，以便检测后来缺少的线色。证据：

- `BlueprintProjectionService.cs`，`ResolveSnapshotLocked:629–635`、`PersistCompletedProgressIfNeeded:819–906`。
- `BlueprintWorldInstanceStore.cs`，`SaveWorldInstances:126–158`：正规化实例集合，构造新的世界文件对象，调用 `TryWrite`；成功才增加 revision。
- `BlueprintJsonSafeFileStore.cs`，`TryWrite:55–102`：同步序列化临时文件、`WriteThrough`、`Flush(true)`，随后提交临时文件。
- 文件替换遇到 `IOException` 最多尝试四次，中间在调用线程请求 `15 / 30 / 45 ms` 三次 `Thread.Sleep`。证据：`CommitPreparedFileWithRetry:161–186`。这三次显式等待合计 90 ms；实际 I/O 和调度耗时另外计算，90 ms 不是整次保存耗时上限。

保存失败不把新完成详情作为已持久化结果供绘制/材料路径收敛；代码保留了失败结果。它也没有撤回已经成功发生的原版建造。后续投影重建仍可能再次识别到同一已完成世界状态并重试保存；日志的 30 秒节流只减少重复日志，不是保存尝试的 30 秒退避。证据：`PersistCompletedProgressIfNeeded:882–906`、`BlueprintJsonSafeFileStore.TryWrite:92–101`。

这是源码可确认的同步调用链与失败模式；不等于已经量出大型蓝图的帧卡顿。

### 12.6 规模、限额和静态状态

设参与投影的层数为 L，当前候选数为 C，擦除记录为 E，历史完成记录为 H：

- 重建材料/候选至少与参与层数相关；候选排序为比较排序量级的 `C log C`。
- 投影签名中擦除和完成集合需要分别排序；实例文档内容也随模板快照、擦除记录和完成记录增加。
- 真实世界坐标读取在一次投影构建内有共用缓存，家具规划也有本次上下文，不能把相同坐标的每层都按独立世界读取累加。
- 不能把单个动作的 750/1500/4000 ms 等超时，或者后处理“每 key 8 次”、锤形“每目标 6 次”，改写成整个蓝图总工作量上限。
- 第 9 节已指出：后处理 key 带库存数量；真实消耗导致签名变化时，可形成新 key。错色等失败场景不受“全目标终生 8 次”的保护。
- `PostProcessSubmissionCounts`、`HammerShapeSubmissionCounts` 是静态字典；成功只删除对应 key，投影签名改变只清 frontier 冷却集合。可见的全量清理在测试重置方法。对持续失败并不断产生新库存签名的情形，不能据源码承诺这些字典具有固定容量。证据：`BlueprintAutoPlacementService.cs:521–544、698–756、765–774`。

R 候选应明确自己的稳定读取、变更失效和失败退避规则，并验证大实例与长时间失败时的工作量。这里没有批准移植 Z 的每 tick 重读文件/重排候选方案，也没有批准为了替换它建立跨所有功能的万能调度队列。

### 12.7 第 11 节异常恢复证据补全

`src/JueMingZ/Hooks/ItemUseHookInstaller.cs`，`81–94`。

该段只解析 `Prefix`、`Postfix` 并调用 `PatchWithHarmony(..., prefix, postfix)`，没有在此注册 finalizer。应结合第 11 节桥接恢复和动作异常分支判断恢复保证，不能仅因存在普通 postfix 就声称原版方法异常时也必然完成恢复。

## 13. 与 R 现有基础的具体衔接，以及不能直接复用的部分

本节 R 生产基线固定为 `df8a029873176276d0f620d32b0ac02ae9ea7744`；后续调查文档提交不改变此生产身份。R 目前没有蓝图资产、投影或自动施工功能。`docs/功能介绍/Legacy蓝图.md:3、23–26` 将它明确列为 Legacy 证据，`docs/设计/配置持久化与用户数据布局.md:226–241` 的未来目录建议也不是已经实现或已获实施授权的蓝图存储。

### 13.1 可复用的是受控操作和事实回执的边界

| 蓝图施工端需要什么 | R 现有另一端 | 已有关系与本轮边界 |
|---|---|---|
| 提交时携带 session、物品身份、目标事实，并在执行前复核 | `ItemSlotObservation`、带 session 的物品操作请求、`ItemHostObservation.Matches` | 可以沿用“计划不是执行许可”的原则；尚无蓝图施工请求或世界放置操作端口 |
| 区分未适用、拒绝、执行中、完成、部分完成、取消、超时和未确认 | `ItemOperationState` | 有现成的结果语义示范；蓝图需要自己的世界层结果与消费事实，不能把出售/丢弃结果直接充作建造回执 |
| 真正调用原版，随后验证实际副作用 | `ItemVanillaOperations` | 可复用“受控原版出口＋结果复核”的设计规则；其已绑定出口是 `ItemSlot.OverrideLeftClick`，不是 `Player.ItemCheck` 建造入口 |
| 生命周期更换后旧动作不得误认为新世界动作 | session generation 与精确玩家引用 | 可复用身份边界；尚无蓝图实例 identity、目标 revision、施工 owner |
| 失焦/恢复期间限制新的自动动作，同时保留已提交回执解释 | `HostInputState`、`HostItems` | 已有现实基础；不能沿用 Z 各桥接路径不一致的 UI/焦点 gate |
| 防止施工消耗正被出售、丢弃或存放拥有的材料 | `ItemOperationOwnership`、`ItemPendingGuards` | 是现有运行时交会点，必须接入核对；不是可以忽略的未来问题 |

证据：

- `src/JueMingR.Platform/Items/ItemOperations.cs:8–41、43–64`：当前 `IItemOperationPort` 只有出售、丢弃、存放三类重载。
- `src/JueMingR.TerrariaHost/Items/ItemVanillaOperations.cs:21–26、28–63、65–105`：绑定、执行、结果复核和 `finally` 恢复范围。
- `src/JueMingR.TerrariaHost/Items/ItemHostObservation.cs:99–106`：执行前复核输入可用、Busy、候选、槽位、实际对象引用、成员 instance、type/prefix/stack/maxStack、保护状态。

`IGameOperationRequest` 是中立操作请求标记，不能因为有这个接口就称 R 已有通用蓝图执行器。也不能让 R 编译或运行时引用 Z 的 ActionQueue、规划器或桥接类。

### 13.2 R 已经会拦截与施工有关的原版消费者

“R 没有蓝图”**不等于**“R 没有 ItemCheck 相关 Hook”。

R 现有物品保护安装链已经涉及：

- `Player.ItemCheck_TryStartUse`；
- `Player.ConsumeItem`；
- `Player.FindPaintOrCoating`；
- `Player.PlaceThing_Tiles`；
- `Player.PlaceThing_Tiles_CheckWandUsability`；
- `Player.PlaceThing_Tiles_PlaceIt_AutoPaintAndActuate`；
- `Player.ItemCheck_UseWiringTools`。

证据：`src/JueMingR.TerrariaHost/Items/ItemPendingGuards.cs`，`Install:20–49`，具体上述项在 `35、39–46`。

这些 Hook 保护的是已经由 R 三类物品操作拥有的槽位，具体效果不能概括成“材料足够就能施工”：

1. **普通持有物和传统 tile wand。** 受保护的手持物会阻止起用；普通瓦片放置还会检查手持物和传统 `tileWand` 第一原版消费槽。证据：`ItemPendingGuards.cs:101–102、146–150、164–177`。
2. **灵活工具。** 使用 `.8` 原版 `TryGetPlacementOption` 找出当前实际选中的材料；如果该 wand 消耗材料且实际材料受保护，就拒绝该次放置。这与 Z 规划器“找到目标材料存在”不同，见第 8 节。证据：同文件 `151–153`。
3. **油漆/涂层。** 被保护槽在 `FindPaintOrCoating` 的选择读取中表现为不可选的空物品；真实库存没有被替换。这会改变原版第一可选颜色/涂层，施工计划必须在同一保护口径下计算实际选择，不能只按未经保护的裸库存判断。证据：同文件 `39–40、58–69`；`src/JueMingR.TerrariaHost/Items/ItemGuardTranspilers.cs`，`SelectionReads:16–27`。
4. **自动致动器。** 原版找材料调用经适配后，如果原始 `FindItem(type)` 返回的第一槽受保护，就返回 `-1`；这里没有继续搜索下一堆的承诺。证据：`ItemPendingGuards.cs:166–167`、`ItemGuardTranspilers.cs`，`ActuatorSelection:52–61`。
5. **单色电线工具。** `PendingType(530)` 对照原版从前往后找到的第一堆有效电线；后面存在受保护堆，不会无差别阻断前面可用的堆。证据：`ItemPendingGuards.cs:170–180、194`。
6. **多色扳手和宏伟蓝图。** 由于 MassWire 会统计整个库存，`item.type == 3625` 或 `item.shoot == 651` 时，前 58 槽中任何受保护电线都会阻止动作；宏伟蓝图还检查受保护致动器。不能把单色工具的第一堆规则套过来。证据：同文件 `181–194`。

上述是具体的运行时冲突面。R 蓝图候选即使在自己的预览或材料统计中判为可执行，也可能被这些既有保护合理拒绝；正确做法需要一致的事实观察与执行前复核，不是绕开保护。

### 13.3 反向关系：原版建造活动也影响 R 自动处理物品

R 已有 `ProtectActiveMaterial` 用来阻止自动物品处理夺走正在被玩家原版活动使用的材料：

- `itemAnimation / itemTime / channel` 活跃时保护实际手持物、弹药、传统 tile-wand 材料；
- `autoPaint` 活跃时保护油漆/涂层，`autoActuator` 活跃时保护致动器；
- 手持电线工具时保护电线和致动器；
- 对灵活工具，用原版 `TryGetPlacementOption` 识别实际选中的材料；
- 对相关材料，按观察 tick 共用一次当前玩家活动投射物扫描；`type == 651` 会保护电线 530 与致动器 849。

证据：`src/JueMingR.TerrariaHost/Items/ItemPendingGuards.cs:196–220`；安装入口 `src/JueMingR.TerrariaHost/Items/HostItems.cs:63`。

边界：

- 这是既有物品自动处理对原版活动的保护，不是尚未实现蓝图任务的材料预留服务。
- 保护状态与实际原版持有/使用状态有关，不能假设“刚选出候选、尚未开始使用”的未来蓝图材料已经自动受保护。
- 油漆保护的这一分支确实带 `autoPaint` 条件，不能写成任何时候背包里所有油漆均被保护。
- 对宏伟蓝图，要同时核对“施工 owner 尚持有工作、原版投射物是否仍活动、R 物品保护是否仍需要保留”三者，不能仅按关闭按钮或一个请求超时释放所有材料解释。

因此未来施工与自动出售/丢弃/存放的交会，需要同时检查两个方向：施工不得消费另一操作已拥有的材料；另一操作不得夺走施工实际消费链中的材料。

### 13.4 输入恢复必须接 R 的焦点与实际输入所有权

R `HostInputState` 把窗口激活与 session 分开：失焦限制新动作，已有原版回执仍属于原来的 session。它要求映射完成、原版输入许可成立、当前采样有焦点且不在 quarantine，才允许 `CanStartActions`。失焦和重新激活触发 rearming，直到实际输入释放后再恢复动作。证据：`src/JueMingR.TerrariaHost/Input/HostInputState.cs:11–12、27–29、35–55、59–76` 及其后续释放证明分支。

这对未来蓝图的实际要求是：

- 新建造请求使用同一现实输入许可，不另起一份“默认允许”的反射式焦点猜测。
- F5、文本、快捷键捕获、失焦和重新激活期间，不能只检查 `Main.gameMenu` 或鼠标捕获便放行。
- 暂时借用选槽、目标坐标、工具模式、cycle offset 的所有者与释放点必须明确；玩家后来真实切换的状态不能被旧快照盲目写回。
- R 源码明确 `MouseInfo` 和绝对滚轮值属于 Terraria 的观测，不是消费动作后任意恢复的自有状态，见同文件 `61–69`。不能照搬 Z 对全局鼠标/选槽字段的整体快照恢复。
- 如果原版动作执行一半失焦，正确边界是阻止新的动作并继续解释已有回执与清理，而不是把 session generation 改掉以掩盖旧动作。

这里的“接同一许可”是对既有 R 合同的复用要求，并未确定蓝图的具体 Hook 点或状态类型；这些仍需在授权实现任务中设计。

### 13.5 死亡、世界更换、异常和未确认不能合并为一个布尔值

R 现有物品链已经区分：

- `Player`：活着、允许新的业务动作的玩家；
- `SessionPlayer`：精确 session 玩家引用，死亡后仍可用来解释已提交原版回执；
- session 结束：终止旧 session 的解释，不能通过还原库存或锁来假装原版转移没有发生。

证据：

- `ItemHostObservation.cs:36–51`，注释明确死亡后的 identity 保留不给新动作许可。
- `HostItems.cs:107–125`：session 进入/退出，失去活玩家后清理未提交 acquisition，但仍运行存放回执处理；失败进入未确认，玩家文案明确不自动重试。
- `src/JueMingR.Platform/Items/ItemOperationOwnership.cs:20–32、61–70`：session 更换与结果保留规则，`Executing / Unconfirmed / TimedOut / Failed` 仍保留相应范围所有权。

蓝图需要分别表达“目标已由世界观察确认”“原版已经开始但结果未知”“材料已变化但目标尚未满足”“队列未开始即取消”“session 已结束”。不能把 Z 的 `attemptedButUnverified` 计数、过期队列和永久 CompletedLayers 合成一个绿色完成数。

已有 R 的 `ItemOperationOwnership` 明确只拥有三类实际物品操作；它不是调度器。未来若增加施工资源关系，要依实际共享资源和原版回执证明边界扩展，而不是借蓝图把全部功能迁入万能 owner。

### 13.6 需要保留的区别与不能直接继承的 Legacy 耦合

| 类型 | 必须保留或核对的两端关系 |
|---|---|
| 前置依赖 | 资产/实例/替换编辑生成目标；施工只接受该目标的当前身份和版本，不能以旧预览坐标执行 |
| 库存口径 | 显示统计的 0–57 槽与虚空袋、Z 可执行的 0–49 槽、各原版消费者自己的搜索顺序不同；R 不能让“有材料”统一遮蔽这些区别 |
| 执行一致性 | 第 8、9 节灵活工具实际材料桶、油漆第一颜色、刮除优先级与规划选择需要同口径；预览可用不能证明原版会选择同一结果 |
| 现有运行时冲突 | `ItemPendingGuards` 的材料保护和实际原版消费链；未来施工必须显式处理拒绝与重新判定 |
| UI 一致性 | 已提交、部分补线、未确认、永久本体完成与即时电线差分不能显示成同一种完成；工具缺失、只有虚空袋材料、距离不够应当给可理解的原因 |
| 生命周期 | 失焦、死亡、开关关闭、世界变更分别影响新动作许可、当前输入借用、旧回执与目标身份 |
| Legacy 偶然耦合 | 自动施工强制材料重算、投影读取顺带同步持久化、已提交 key 只随投影签名变化解锁、全局工具/输入状态借用，均不是 R 的必需实现方式 |

可复用的是以上行为证据、反例和现有 R 边界。施工端口、世界目标回执、蓝图材料 owner、工具作用域、缓存失效设计尚未实现，也不因本调查自动获准实现。

### 14.9 选项表完整不等于原版一定选中指定材料桶

原版 `TryGetPlacementOption` 的实际循环是 `i < 58 + 1`，只进入 `i < 50 || i >= 54`，因此这份 `.8` 文本实际查看的是 **0–49 与 54–58**；不是只看 Z 执行材料资格采用的 0–49。第一个非空、收藏条件允许、材料类型命中该 wand 桶的物品决定材料桶，再对该桶应用 cycle。

证据：`FlexibleTileWand.cs:176–196`，尤其 `181–191`。这也是第 8 节“目标材料存在，但原版优先命中更早的另一材料桶”反例的直接来源。材料桶的完整枚举不消除这一选择一致性问题。

### 15.3 已确认的静态反例和仍缺的证据

以下条目不能在合稿中被缩成“自动施工已完善”：

| 条目 | 静态证据能确定什么 | 尚未证明什么 |
|---|---|---|
| 家具方向 | 本体规划携带玩家方向，实际执行交接未完整应用该方向；alternate 元数据不等于强制原版采用该分支 | 各类可朝向家具在当前方向、镜像、不同锚点下的完整实际结果 |
| 灵活材料 | Legacy 目标材料存在检查与 `.8` 先命中材料桶的选择不是同一个判定 | 29 入口、全部选项的实际成功率；多材料并存时没有错误摆放/错误消耗 |
| 油漆/涂层材料 | 原版优先槽与 Legacy 目标材料选择不同，可构造先选另一种颜色/涂层的路径 | 各刷/滚/喷/刮工具在组合表面与实际库存中的完整效果 |
| 刮除顺序 | 原版前景油漆、前景涂层、墙油漆、墙涂层的优先顺序可能先改变非目标表面 | 自动后续回补能否收敛、消耗是否可接受；不能默认视为安全 |
| 部分补线 | 一次执行的成功判断可被任一请求线色满足触发，和整层目标全部满足不同 | UI 是否在所有场景正确表达部分完成、最终是否收敛 |
| 重试与停滞 | 普通 admission key 未包含玩家位置等资格变化，存在走近后仍等待投影变化的路径；后处理 8 次并非目标终生总限额 | 实际长时间失败的完整用户体验、不同外部变化下的恢复率 |
| 输入与退出 | 普通桥接、宏伟蓝图、服务入口的 UI gate 不同；关闭不会统一撤销旧请求；存在盲目旧选槽恢复和异常清理缺口 | 所有死亡/切世界/失焦/异常时点均无遗留输入或工具状态 |
| 宏伟蓝图清理 | 已观察到的投射物与 Kill 回调是 owner 生命周期的关键；某些“曾观察到但未得到预期结束”的路径没有统一绝对结束界限 | 多人延迟、投射物自然消失/异常消失、关闭中的最终清理保证 |

本轮 `.8` 已静态读到的直接证据覆盖 `Player / Main / Item / WorldGen / Wiring / Projectile / FlexibleTileWand / TileObjectData / TileObject / WiresUI / ItemID / TileID` 等与本文所述分支有关的成员。同版新增静态提取解决了宏伟蓝图、灵活选项、对象几何和工具模式的直接来源问题；本专题**没有为补齐上述完整选项表再要求执行原版或动态枚举**。

明确的 `.8` 证据边界仍有：

1. 当前静态调用链能说明客户端/本地何处调用原版、何处消耗、何处发送同步，以及本地如何观察目标；它没有完整审完每个相关包在 `Terraria.MessageBuffer` 与 `Terraria.NetMessage` 中的服务器接收、拒绝、转发与重发路径。需要进一步追网络权威时，准确类型就是这两者及具体家具的原版 TileEntity/放置 Hook；按实际操作定向补查，不把所有建造统一认成一个包。
2. 特殊家具几何和默认本体已读；每个家具 TileEntity 的完整 payload、容器内容、展示装备、文本和运行态恢复不属于本轮支持承诺，也未把所有该类实现逐一反编译成完整数据恢复调查。
3. 反编译文本与静态对象表不代替原版真实 `CanPlace`、Hook 安装、玩家输入及网络时序运行。实际 server 拒绝、延迟、断线、其它玩家同时改变目标和材料的组合未运行。
4. 没有真实单人、多玩家、专服、客户端性能或用户验收结果；“未验证”不自动等于“不支持”。

### 15.5 产品问题与普通技术修正分开

**本轮明确需要守住的边界：**

- 基础/扩展施工必须通过相应真实原版动作，不能靠万能 Tile 属性写入伪造成功。
- 工具、材料、范围、部分结果和真实确认不能被统一“施工完成”掩盖。
- 资产预览、建立实例、擦除投影、移动投影与真正建造/拆除必须分开。
- 八类替换、全部灵活工具入口及其关键材料/样式分支不能静默缩减。
- 错色、错误材料、非目标层刮除、错误方向、无界重复消耗与旧输入状态覆盖，不应作为可随意继承的 Legacy 产品行为。

**适合后续按蓝图组讨论的少量产品候选：**

| 产品问题 | 建议候选 | 代价与区别 |
|---|---|---|
| 完成记录表示历史进度，还是持续维护目标 | 将“一次施工进度”和“后来修补”明确分开；先讨论并明确一次施工语义 | 避免建筑被用户主动拆改后自动补回；若加入持续修补，需要独立开关和重试规则 |
| 关闭自动施工时如何处理已经启动的动作 | 立即停止新提交，当前原版动作按有界释放和结果解释收尾，并显示仍在收尾 | 不能承诺已发生的原版消耗或世界修改可撤销；宏伟蓝图需要明确剩余投射物生命周期 |
| 显示库存与可直接施工库存 | 明确展示“已有/可直接使用/仅其它容器可见”，首轮按选定真实消费范围执行 | 若未来支持虚空袋直接供材，必须另证实际原版出口和消费权威，不能直接搬物品或扣数量 |
| 同类替换如何选择 | 保持总开和逐类选择，显示最终替代物；原材料优先及替代候选顺序写入新合同 | 材料类别相同不保证家具尺寸、方向、外观或全部后处理一致 |
| 特殊家具复制到什么程度 | 明确默认本体的范围与不可恢复内容 | 外部 payload/运行态属于新增产品范围，不从“完整家具”四字自动扩大 |

缓存实现、目标失效条件、正确材料选择、原版恢复作用域、异常收尾以及避免同步高频 I/O，属于实现者应完成的技术工作；不应把这些普通正确性问题打包交给所有者逐条批准。

### 15.6 推荐分组与资产篇交接

建议仍以“蓝图资产与编辑”和“蓝图实际施工”保持两个职责边界，施工内部按以下证据依赖推进，顺序仍是待讨论候选：

1. **施工合同与基础出口**：当前实例/目标身份、材料与工具资格、原版输入/操作范围、普通块/墙/完整家具、结果确认、停止与既有 R 物品保护交会。
2. **完整对象和默认本体分支**：与基础家具规划共用几何和方向依据，逐个保护已列特殊家族；不另建一套猜 frame 的默认体写入器。
3. **电线与宏伟蓝图**：共用线色差分与材料事实，但普通扳手和宏伟蓝图保留不同原版动作生命周期。
4. **灵活工具**：消费桶、cycle、目标几何与实际工具选择一致，完整入口表作为核对样本。
5. **表面与形状后处理**：本体成立后再处理油漆、涂层、锤形和致动；正确选择原版材料与作用层，给出部分/失败解释。
6. **组合与规模收口**：已实现子能力共同开启时的输入、物品处理、失焦/死亡/世界变化、持久化失败、大实例和多人验证。

资产篇交给施工篇的是当前世界实例及其模板快照、投影目标、替换设置、完成/擦除语义和身份；不是许可施工随时改模板，也不是预览有图就能直接建造。施工结果回到实例进度时必须区分实际世界事实、已持久化进度和失败存储，保护模板可复用性。

## 组合成本与事前正确性

B02/B04与C04要求预览、材料面板和施工共用当前目标版本及适用事实；各自保有显示、库存口径、规划和执行职责。工具/材料桶/搜索顺序、direction/alternate必须与原版真正选择一致；事后投影发现错色、错材料或错朝向不能替代事前防止错误消费和世界修改。

§12.3/§12.4的稳定等待仍准备、走近目标但admission key未变、耗材改变重试key等原证据转成总报告成对要求：稳定等待不重复生成/提交，真实可达性与保护门变化可重新准入；耗材递减不让同一目标失败预算无限重置。保留动作前复核，不能用缓存冻结资格。

一次施工还是持续修补仍由产品决定，查询/进度提交/编辑保护不能偷偷捆绑。普通使用与宏伟蓝图的投射物生命周期不套同一种收尾节奏；关闭后停止新提交并解释实际在途结果，部分多色线、未确认和已持久进度分别反馈。
